# 3.4.1 编码质控实测 — 思考分析

## 一、招标条款原文（3 个具体场景）

> **场景 A**：出院主要诊断为肿瘤相关编码时，进行病理编码内涵校验
> **场景 B**：阑尾炎与腹膜炎诊断同时出现时，通过合并编码质控点提示是否合并编码并进行编码推荐
> **场景 C**：当开展了冠状动脉支架置入术，应补充共同使用的附加编码

## 三、招标场景 vs 现有能力映射

| 招标场景 | 对应维度 | 引擎层 | 能否命中 |
|---|---|---|---|
| **A** 肿瘤→病理编码校验 | D6 编码-临床一致性 | LLM | ⚠️ 取决于 prompt 是否引导 LLM 检查"肿瘤诊断→是否有病理诊断编码" |
| **B** 阑尾炎+腹膜炎→合并编码 | D3 编码合并 | LLM | ✅ 评测计划中已有类似用例（D3-4：急性阑尾炎+穿孔），且 prompt 明确要求检查合并编码 |
| **C** 支架术→附加编码 | D6 一致性（手术→编码完整性）| LLM | ⚠️ prompt 说的是"是否有遗漏"，但没专门提"附加编码"概念 |

## 四、关键问题

### 问题 1：LLM 能力边界

现有 `CODING_QC_SYSTEM_PROMPT` 覆盖了 4 个维度：
1. 编码合并 ✅ — 直接对应场景 B
2. 编码互斥 ✅
3. 主诊断选择 ✅
4. 编码与临床一致性 ✅ — 理论上覆盖场景 A 和 C

**但**：prompt 没有显式提到以下具体场景：
- "肿瘤编码→检查是否有病理诊断编码" — 场景 A 的核心要求
- "手术操作→检查是否补充了附加编码" — 场景 C 的核心要求

### 问题 2：是否需要修改 prompt？

**方案 1：不改 prompt，直接实测**
- 优点：零代码改动，看 LLM 自身能力
- 风险：LLM 可能不会主动检查"肿瘤→病理"和"支架→附加编码"

**方案 2：增强 prompt，增加 3 个显式检查点**
- 在 `CODING_QC_SYSTEM_PROMPT` 末尾增加：
  ```
  特别注意以下常见编码规范问题：
  - 肿瘤相关诊断时，是否有对应的病理诊断编码
  - 存在可以合并的诊断编码时（如阑尾炎+腹膜炎），是否建议使用合并码
  - 手术操作需要附加编码时（如冠状动脉支架+球囊扩张），是否提示补充
  ```
- 优点：精确命中招标 3 个场景
- 风险：过度拟合招标文字

### 问题 3：规则层 vs LLM 层

对于场景 A (肿瘤→病理)，其实可以用**规则层**实现：
```python
# 伪代码：如果主诊断是 C/D 开头（肿瘤），检查是否有 M 编码（病理）
if any(d.code.startswith(('C', 'D0', 'D1', 'D2', 'D3', 'D4')) for d in diagnoses):
    if not any(d.code.startswith('M') for d in diagnoses):
        report("缺少病理诊断编码")
```

对于场景 C (支架→附加编码)，也可以规则化：
```python
# 如果有 36.07（冠状动脉支架置入），检查是否有 36.01/36.02（球囊扩张）
if any(s.code.startswith('36.07') for s in surgeries):
    if not any(s.code.startswith(('36.01', '36.02', '00.66')) for s in surgeries):
        report("支架置入术应补充球囊扩张等附加编码")
```

## 五、建议方案

> **混合策略：规则层精确覆盖招标场景 + LLM 层兜底**

| 步骤 | 做什么 | 工作量 |
|---|---|---|
| 1 | **先实测**：构造 3 个招标场景数据，调 `/coding-qc/check`，看 LLM 原生能否命中 | 30 分钟 |
| 2 | **规则补丁**：在 `CodingQCEngine` 中新增 `check_bidding_scenarios()` 规则方法，用 3 条确定性规则精确覆盖招标场景 | 1 小时 |
| 3 | **prompt 增强**（可选）：如果 LLM 也能命中，就形成双保险 | 15 分钟 |
| 4 | **单元测试**：为 3 个场景各写 1 个测试用例 | 30 分钟 |

### 验证方案
