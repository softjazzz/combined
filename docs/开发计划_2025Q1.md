## 2. 第一阶段：系统稳定性与基础完善

**时间**: 第1-2周  
**目标**: 消除技术债务，建立稳定的开发基础

### 2.1 代码质量优化 (P0)

#### 2.1.1 清理重复代码

**问题现状**:
- 存在多个LLM服务实现：`llmService.ts`, `llmServiceNew.ts`, `enhancedLLMService.ts`
- 前后端路由重复：`main_api.py` 和 `app/routers/*` 存在重复路由
- 编译产物未清理：`.js` 和 `.ts` 文件共存

**任务清单**:
- [ ] **T1.1.1**: 统一LLM客户端接口
  - 创建 `BaseLLMClient` 抽象类
  - 实现 `OpenAIClient`, `DeepSeekClient`, `AliyunClient`
  - 删除废弃的 `llmServiceNew.ts`, `enhancedLLMService.ts`
  - 工作量: 8小时

- [ ] **T1.1.2**: 清理后端重复路由
  - 下线 `main_api.py` 中的重复路由
  - 确保所有路由只在 `app/routers/` 下定义
  - 更新文档和测试
  - 工作量: 4小时

- [ ] **T1.1.3**: 清理编译产物
  - 运行 `architecture-optimizer.ts` 清理 `.js` 文件
  - 更新 `.gitignore` 忽略编译产物
  - 配置 Vite 输出目录
  - 工作量: 2小时

#### 2.1.2 统一API响应格式

**问题现状**:
- 不同接口返回格式不一致
- 错误处理格式不统一

**任务清单**:

  interface ApiResponse<T> {

    message?: string
    traceId?: string

- [ ] **T1.2.2**: 更新所有API接口

## 附录

### A. 开发规范

**代码规范**:
- 前端: ESLint + Prettier
- 后端: Black + Flake8
- 提交规范: Conventional Commits

**分支策略**:
- `main`: 生产环境
- `develop`: 开发环境
- `feature/*`: 功能分支
- `hotfix/*`: 紧急修复

**Code Review**:
- 所有代码必须经过Review
- 至少1人Approve才能合并
- 关键功能需要2人Approve

### B. 测试策略

**测试金字塔**:
```
       /\
      /E2E\      10%
     /------\
    /集成测试\    30%
   /----------\
  /  单元测试  \  60%
 /--------------\
```

**测试覆盖率目标**:
- 单元测试: 60%+
- 集成测试: 40%+
- E2E测试: 关键流程100%

### C. 部署策略

**环境划分**:
- 开发环境 (Dev)
- 测试环境 (Test)
- 预发布环境 (Staging)
- 生产环境 (Production)

**发布流程**:
1. 功能开发完成
2. 单元测试通过
3. 部署到测试环境
4. 集成测试通过
5. 部署到预发布环境
6. 用户验收测试
7. 部署到生产环境
8. 监控和回滚准备
