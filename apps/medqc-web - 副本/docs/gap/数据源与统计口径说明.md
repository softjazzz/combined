# 数据源与统计口径说明

## 1. 文档目的

- 本文档用于统一开工前的数据来源和统计口径。
- 重点不是覆盖所有报表，而是先解决前后端最容易打架的三类问题：
  - 场景分类怎么切
  - 指标怎么定义
  - 各页面到底从哪里取数

## 2. 当前代码证据

### 2.1 工作台

- 后端 `dashboard_api.py` 已提供 `GET /api/v1/dashboard/todo-stats`。
- 返回结构包含：
  - `task_stats`
  - `defect_stats`
  - `record_stats`
  - `overview`
  - `scene_breakdown`
- 当前实现仍存在数据库失败后的 fallback 数据分支。

### 2.2 任务

- 后端 `tasks.py` 已落库 `qc_tasks`，包含：
  - `task_type`
  - `schedule_config`
  - `sampling_method`
  - `assign_method`

### 2.3 病历

- 后端 `records.py` 仍保留 `record_type` 过滤。
- CDM 模型 `cdm.py` 中多张表存在 `visit_type` 字段。
- 这说明门急诊数据在模型层有基础，但业务层还没有统一聚合口径。

### 2.4 规则

- 当前规则后端主要依赖 `scoring_rules` 表。
- 这张表适合“扣分规则管理”，不适合作为统计分析的完整维度来源。

## 3. 推荐的数据域划分

| 数据域 | 当前来源 | 开工建议 |
| --- | --- | --- |
| 账户与权限 | 内存 `users_db` | 迁移到 PG 持久化账户表 |
| 病历主索引 | `medical_records` + CDM 视图/表 | 继续以 PG 视图/表为主，建统一病历聚合视图 |
| 质控结果 | `qc_results` | 作为评分、等级、缺陷数主要来源 |
| 缺陷闭环 | `qc_defects` 或等效缺陷表 | 作为待办、整改、催办来源 |
| 整改任务 | `qc_remediation_tasks` | 作为任务倒计时、整改状态来源 |
| 抽查任务 | `qc_tasks` + `qc_task_records` | 作为任务管理和工作台任务统计来源 |
| 申诉 | `qc_appeals` | 作为缺陷争议、待审核来源 |
| 规则运营 | 现有 `scoring_rules` 之外新增规则实体 | 不直接复用单表撑全后台 |
| 调度队列 | Redis | 作为异步执行、延迟任务、worker 通信基础 |

## 3.1 基础设施口径

- `PG` 是第一阶段唯一主数据源和事实来源。
- `Redis` 不是主数据存储，不承载最终业务真相。
- 任务调度推荐采用：
  - `Celery Worker`
  - `Celery Beat`
  - `Redis Broker`
  - `PG Result Persistence / Business Persistence`

### 为什么首期不建议 RabbitMQ 或 RocketMQ

- 当前仓库已有 `celery`、`aioredis` 依赖，Redis 接入阻力最小。
- 目前任务类型以内部定时调度和异步质控任务为主，不是高吞吐事件总线场景。
- RabbitMQ/RocketMQ 更适合后续跨系统异步集成再评估，不建议在第一阶段提前引入。

## 4. 场景分类口径

### 4.1 一级场景

工作台和统计分析统一只允许四个场景：

- `all`
- `outpatient_emergency`
- `running`
- `final`

前端不要再自定义第五种命名，后端也不要同时输出多套别名。

### 4.2 推荐判定规则

#### `outpatient_emergency`

- 优先依据 CDM 或业务视图中的 `visit_type`
- 建议映射：
  - `outpatient`
  - `emergency`

#### `running`

- 住院在院病历
- 建议判定：
  - `visit_type = inpatient`
  - 且未出院或未终末归档

#### `final`

- 终末病历/已出院病历
- 建议判定：
  - `visit_type = inpatient`
  - 且已出院或已进入终末质控阶段

### 4.3 当前必须补的动作

- 建立统一病历场景聚合视图，供：
  - 工作台
  - 病历列表
  - 统计分析
  - 任务抽样
  共同使用。

如果不做统一视图，前后端会分别根据 `record_type`、`visit_type`、`status` 拼条件，最终数字一定对不上。

## 5. 工作台核心指标口径

### 5.1 任务统计 `task_stats`

#### `countdown`

- 定义：已分配且未到期完成的整改/抽查待办数量
- 推荐来源：
  - `qc_remediation_tasks` 状态为 `pending / overdue`
  - 或 `qc_tasks` 下当前用户仍待处理的任务记录

#### `in_progress`

- 定义：当前用户已领取或正在执行中的任务数量

#### `not_started`

- 定义：已分配给当前用户但尚未开始处理的任务数量

### 5.2 缺陷统计 `defect_stats`

#### `clinical_appeals`

- 定义：待处理的临床申诉数量
- 推荐来源：`qc_appeals`

#### `pending_review`

- 定义：提交整改后等待质控审核的缺陷数量

#### `urged`

- 定义：已催办但仍未完成整改的缺陷数量

### 5.3 病历统计 `record_stats`

#### `pending_review`

- 定义：待质控审核病历数量

#### `pending_recheck`

- 定义：已整改待复核病历数量

#### `total`

- 定义：当前场景内的病历总数

## 6. 概览指标口径

### `total_records`

- 定义：当前场景、当前筛选条件下的病历总数

### `avg_score`

- 定义：已完成质控病历的平均得分
- 分母不包含未完成质控病历

### `pass_rate`

- 定义：达到合格等级的病历占比
- 建议分子：
  - 等级为 `A/B`
  - 或分数大于等于合格阈值
- 必须二选一写死，不允许页面和接口各自解释

### `total_defects`

- 定义：当前场景内已识别缺陷总数

## 7. 统计分析一期建议口径

### 7.1 先做的统计模块

- 运行病历质量分析
- 终末病历质量分析
- 病案首页质量分析
- 质控员工作情况分析

### 7.2 每个统计模块最小指标集

1. 病历总量
2. 已质控量
3. 平均得分
4. 合格率
5. 缺陷总数
6. 按科室分布
7. 按等级分布
8. 明细导出

## 8. 页面到接口的推荐映射

| 页面 | 先用什么接口 | 后续再扩展什么接口 |
| --- | --- | --- |
| 工作台待办卡片 | `GET /dashboard/todo-stats?scene=` | `GET /dashboard/todo-details` |
| 工作表现 | `GET /dashboard/performance?scene=` | `GET /dashboard/performance/details` |
| 门急诊病历页 | `GET /records/outpatient-emergency` | `GET /records/outpatient-emergency/export` |
| 运行病历分析 | `GET /statistics/running/overview` | `GET /statistics/running/details` |
| 终末病历分析 | `GET /statistics/final/overview` | `GET /statistics/final/details` |
| 首页质量分析 | `GET /statistics/frontpage/overview` | `GET /statistics/frontpage/details` |
| 质控员工作情况 | `GET /statistics/staff-workload` | `GET /statistics/staff-workload/details` |

## 9. 开工前必须确认的 6 个口径点

1. `running` 和 `final` 的状态边界由哪几个字段判定。
2. `pass_rate` 以等级判定还是以分数阈值判定。
3. `pending_review` 是否包含系统质控后待人工审核病历。
4. `pending_recheck` 是否只统计已提交整改的病历。
5. 门急诊是否单独维护评分标准。
6. 统计页导出是否必须与列表筛选条件完全一致。

## 10. 一句话口径结论

开工前必须先建立 `统一场景枚举 + 统一病历聚合视图 + 统一指标定义`。只要这三件事没定，页面做得再快，工作台、列表页、统计页的数字都会互相打架。
