# 开工边界说明

## 1. 文档目的

- 本文档用于冻结 `MedQC` 对齐 V3.6 用户手册的第一阶段复刻范围。
- 目标不是一次性补齐全手册，而是先把可验收、可联调、可演示的主链路收口。
- 本文档优先解决三个问题：
  - 本轮到底做什么
  - 本轮明确不做什么
  - 哪些前置条件不满足就不要正式开工

## 2. 冻结范围

### 2.1 本轮必须覆盖的一级模块

- 登录
- 工作台
- 病历质控
- 任务管理
- 统计分析
- 质控规则管理

### 2.2 本轮必须打通的主链路

1. 用户登录后进入工作台。
2. 从工作台进入病历质控列表。
3. 支持 `门急诊 / 运行 / 终末` 三条病历质控主线。
4. 支持从列表进入病历详情审核运营台。
5. 支持缺陷处理、催办、整改、审核通过/存疑等闭环动作。
6. 支持抽查任务创建、分配、执行、进度查看。
7. 支持工作台和统计分析读取真实业务数据。
8. 支持规则后台最小可运营闭环。

## 3. 登录范围

- 登录仅支持 `用户名/密码` 和 `手机号/密码`。
- 手机号不是独立账户体系，而是同一账户的备用登录标识。
- 用户注册或建档时必须维护：
  - 用户名
  - 手机号
  - 密码
- 不做扫码登录。
- 不做短信验证码。
- 不做手机号无密码直登。

## 4. 本轮明确不做的内容

### 4.1 不纳入复刻目标的产品能力

- DRG 相关页面与流程
- 数据同步/工作站类入口
- 与 V3.6 主手册无关的 demo/test 页面
- 非主链路的实验性规则页面
- 与复刻目标无直接关系的专题大屏

### 4.2 暂不做的高级能力

- 27 项指标全量专题
- 18 项核心制度全量专题
- 复杂规则条件可视化编排器完整版
- 全量消息中心重构
- 多终端统一登录体系
- 多租户隔离改造

## 5. 当前系统必须先接受的现实约束

### 5.0 开发基座约束

- 本轮开发明确以 `workstation v4` 现有前后端为基座开展。
- 允许：
  - 新增页面
  - 新增接口
  - 新增聚合层
  - 新增配置与表结构
- 默认不允许：
  - 修改现有项目前后端脚本
  - 改动现有启动脚本、构建脚本、发布脚本、部署脚本、联调脚本
- 如果确实需要修改现有脚本，必须先人工确认后再执行。

### 5.1 认证约束

- 当前认证路由仍基于内存 `users_db`。
- 当前登录模型字段仍以 `email` 为主键语义，不符合“用户名/手机号双标识登录”的最终要求。
- 正式开工前，必须决定：
  - 是先做持久化认证，再改登录
  - 还是先兼容实现，再在第二步迁移

建议：先做持久化认证，再做双标识登录，避免返工两次。

### 5.2 数据约束

- 当前项目数据库基座为 `PostgreSQL (PG)`，第一阶段默认继续作为主数据源和事务落库基座。
- 当前统计和工作台部分接口仍存在 fallback/示例数据分支。
- 当前统计分析前端仍有明显 mock 数据区。
- 当前门急诊业务线在数据模型层有痕迹，但前后端主链路未闭环。

### 5.2A 调度基础设施约束

- 任务调度和异步执行第一阶段建议基于 `Redis` 落地。
- 推荐组合：
  - `PG`：任务、任务记录、执行状态、审计日志的最终落库
  - `Redis`：调度队列、延迟任务、worker 通信
  - `Celery + Redis`：首期任务执行器与定时调度基础
- 第一阶段不建议引入：
  - `RabbitMQ`
  - `RocketMQ`

理由：

- 当前项目已具备 `celery`、`aioredis` 依赖基础，接入成本最低。
- 本项目调度需求目前以定时抽样、任务分发、异步质控为主，不需要先上更重的消息中间件。
- RabbitMQ 和 RocketMQ 会引入额外运维复杂度，但第一阶段收益不明显。

### 5.3 规则后台约束

- 当前 `scoring_rules` 更像“扣分规则表”，不是完整规则运营后台。
- 如果不开工前先定义规则领域模型，后续页面和接口会继续碎片化。
- 规则基线先复用库里已有的 `四川省 146 条质控规则`，不在第一阶段重建全套规则内容。
- 第一阶段的目标是把这些既有规则接入到新页面、新聚合接口和新运营模型中，而不是改写规则内容本身。

## 6. 开工前必须补齐的前置产物

1. 《数据源与统计口径说明》
2. 《认证改造方案》
3. 《规则后台数据模型草图》
4. 一套可联调的样例数据
5. 一份按 V3.6 手册整理的验收清单

## 7. 开工门槛

满足以下条件后，才建议正式排期进入开发：

1. 登录口径已冻结，不再讨论扫码、验证码等新增形态。
2. `Dashboard` 场景口径已冻结为：
   - 全部
   - 门急诊
   - 运行
   - 终末
3. 门急诊、运行、终末的数据来源表或视图已确认。
4. 统计分析的核心指标分子分母已确认。
5. 认证持久化方案已确认。
6. 规则后台的最小实体模型已确认。
7. 已确认本轮默认不改现有项目脚本，如需改动走人工确认。
8. 已确认规则基线以四川省 146 条质控规则为准。

## 8. 建议的组织方式

- 前端 owner：
  - 登录与账户中心
  - 病历质控与详情台
  - 工作台与统计分析
  - 规则后台
- 后端 owner：
  - 认证与权限
  - 病历聚合与任务
  - 统计与报表
  - 规则配置与测试数据

不要让多名开发者同时改同一个聚合接口和同一套领域模型，否则前两周就会出现反复冲突。

## 9. 第一阶段验收标准

### 9.1 页面侧

- 主导航收口为手册主模块。
- 登录页支持用户名/手机号双标识登录。
- 门急诊病历页可用。
- 病历详情审核运营台可用。
- 工作台和统计页不再依赖 mock 展示核心结果。
- 规则后台至少具备最小可运营入口。

### 9.2 接口侧

- 认证不再依赖内存用户源。
- 工作台待办和工作表现返回真实数据。
- 任务支持单次任务闭环，定时任务至少具备可落库和可执行骨架。
- 统计分析至少完成运行、终末、病案首页三块真实接口。
- 规则后台至少完成标准、项目组、质控点三类核心接口。

## 10. 一句话边界结论

本轮不是“把系统所有页面都做漂亮”，而是把 `登录 + 工作台 + 病历质控 + 任务 + 统计 + 规则后台` 这条 V3.6 主产品骨架真正拉通，并且把 mock、内存认证、口径不统一这三类基础风险先清掉。
