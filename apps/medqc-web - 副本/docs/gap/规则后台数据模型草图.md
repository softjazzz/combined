# 规则后台数据模型草图

## 1. 文档目的

- 本文档用于定义规则后台的最小可运营数据模型。
- 目标不是设计一个过度复杂的规则引擎，而是先让 V3.6 手册要求的规则后台有清晰的实体边界。

## 2. 当前现状

### 2.1 已有能力

- 当前后端已有 `scoring_rules` CRUD。
- 仓库内已存在 `app/data/sichuan_rules_146.json`，可作为第一阶段规则基线。
- 当前模型主要围绕以下字段：
  - `category`
  - `name`
  - `description`
  - `deduction`
  - `max_deduction`
  - `veto`
  - `severity`
  - `enabled`
  - `sort_order`

### 2.2 当前问题

这张表可以支持“扣分项列表”，但撑不起以下能力：

- 评分标准管理
- 评分详情管理
- 评分项目组管理
- 默认评分标准配置
- 生效范围
- 质控点上线/下线生命周期
- 文书管理
- 测试病历管理

### 2.3 第一阶段规则来源约束

- 第一阶段规则内容不重新发明，先以库里已有的 `四川省 146 条质控规则` 为规则种子。
- 新规则后台的重点是：
  - 规则标准化入库
  - 规则分组展示
  - 规则与质控点、文书、测试病历的映射
  - 规则启用范围和默认标准配置
- 第一阶段不建议做：
  - 大规模重写规则文本
  - 大规模替换规则编码
  - 在规则内容尚未完成映射前就新增第二套规则集

## 3. 推荐的最小领域模型

### 3.1 核心实体

1. `rule_standard`
   - 评分标准
   - 例如：住院终末评分标准、运行病历评分标准、门急诊评分标准

2. `rule_item_group`
   - 评分项目组
   - 例如：病历首页、病程记录、知情同意、医嘱单

3. `rule_item`
   - 评分详情/评分项
   - 表示某个具体扣分项

4. `qc_point`
   - 质控点
   - 表示某个可执行、可上线、可绑定文书的检查点

5. `qc_point_scope`
   - 质控点生效范围
   - 表示适用场景、科室、病历类型、评分标准

6. `document_type`
   - 文书类型目录
   - 例如：入院记录、首次病程、出院记录、门诊病历

7. `test_record`
   - 测试病历
   - 用于规则验证和回归

## 4. 推荐关系

### 4.1 标准与项目组

- 一个 `rule_standard` 可以包含多个 `rule_item_group`
- 一个 `rule_item_group` 归属于一个 `rule_standard`

### 4.2 项目组与评分项

- 一个 `rule_item_group` 可以包含多个 `rule_item`
- 一个 `rule_item` 归属于一个 `rule_item_group`

### 4.3 评分项与质控点

- 一个 `rule_item` 可绑定一个或多个 `qc_point`
- 一个 `qc_point` 也可以被多个 `rule_item` 复用

因此推荐增加关系表：

- `rule_item_qc_point_rel`

### 4.4 质控点与适用范围

- 一个 `qc_point` 可以有多个 `qc_point_scope`
- 每个 scope 描述：
  - 适用场景
  - 适用科室
  - 适用病历类型
  - 适用评分标准

## 6. 推荐关系图

```text
rule_standard
  └─ rule_item_group
       └─ rule_item
            └─ rule_item_qc_point_rel
                 └─ qc_point
                      ├─ qc_point_scope
                      └─ qc_point_document_rel
                           └─ document_type

qc_point
  └─ qc_point_test_rel
       └─ test_record
```

## 7. 为什么不建议继续扩写 `scoring_rules`

如果继续只在 `scoring_rules` 上加字段，最终会把以下概念混在一起：

- 评分标准
- 扣分项
- 质控点
- 生效范围
- 文书绑定
- 测试样例

这样做的结果是：

1. 前端页面很难拆分。
2. 后端接口语义会越来越模糊。
3. 统计分析无法稳定按标准、项目组、质控点做聚合。

## 8. MVP 范围建议

第一期不要把所有规则平台能力一次做满，建议只做：

1. `rule_standard`
2. `rule_item_group`
3. `rule_item`
4. `qc_point`
5. `qc_point_scope`
6. `document_type`

`test_record` 可以作为第一期后半段或第二期补齐。

同时增加一条落地约束：

- `四川省 146 条质控规则` 先作为 `rule_item` 或等效规则明细的初始化数据源。
- 后台页面先实现“可查看、可分组、可绑定、可启停”，再讨论规则内容扩编。

## 9. 接口设计建议

### 第一批接口

- `GET/POST/PUT/DELETE /rule-standards`
- `GET/POST/PUT/DELETE /rule-item-groups`
- `GET/POST/PUT/DELETE /rule-items`
- `GET/POST/PUT/DELETE /qc-points`
- `GET/POST/PUT/DELETE /qc-point-scopes`
- `GET/POST/PUT/DELETE /document-types`

### 第二批接口

- `POST /qc-points/{id}/online`
- `POST /qc-points/{id}/offline`
- `GET/POST/PUT/DELETE /test-records`
- `POST /qc-points/{id}/test`

## 10. 开工前必须确认的点

1. 门急诊和住院是否共用项目组。
2. 不同场景是否允许挂不同默认评分标准。
3. 一个质控点是否允许跨多个评分标准复用。
4. 规则表达式是先存 JSON，还是直接接已有规则引擎。
5. 文书目录是否复用 CDM 文书类型编码。
6. 四川省 146 条规则落入 `rule_item`、`qc_point`，还是通过中间映射表接入。

## 11. 一句话模型结论

规则后台要先把“评分标准、评分项、质控点、生效范围、文书、测试病历”拆成独立实体，再谈页面和接口；继续依赖单张 `scoring_rules` 表扩写，只会把后面的规则平台越做越乱。
