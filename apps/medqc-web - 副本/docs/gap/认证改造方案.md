# 认证改造方案

## 1. 改造目标

- 将当前演示态认证改造成可用于正式内网部署的认证体系。
- 支持同一账户通过两种标识登录：
  - 用户名 + 密码
  - 手机号 + 密码
- 手机号用于“忘记用户名时仍可登录”，不是独立账户体系。

## 2. 当前现状

### 2.1 代码现状

- `auth.py` 当前从内存 `users_db` 读取用户。
- 登录接口 `POST /api/v1/auth/login` 当前只接受 `LoginRequest.email + password`。
- `UserCreate`、`UserResponse`、`UserUpdate` 中虽有 `phone` 字段，但登录主标识仍是 `email`。
- `storage/memory.py` 内置了 demo 用户，说明当前实现偏向开发/演示。

### 2.2 当前问题

1. 认证不持久化，服务重启和环境切换风险高。
2. `email` 字段承载了“用户名”语义，模型命名不准确。
3. 手机号存在但不能直接用于登录。
4. 默认 demo 用户仍在用户源中，不适合正式环境。

## 3. 推荐实现原则

1. 不做两套登录体系，只做一套账户体系。
2. 不做“手机号验证码登录”，只做“手机号密码登录”。
3. 前端不一定要做两张登录页，建议一个登录入口统一支持双标识。
4. 后端统一使用“登录标识”解析，而不是保留 `email` 这个旧命名继续扩大歧义。
5. 先把用户源持久化，再做双标识登录，避免重复迁移。

## 4. 推荐目标模型

### 4.1 账户实体

建议新增或改造账户表 `auth_users`：

| 字段 | 说明 |
| --- | --- |
| `id` | 用户主键 |
| `username` | 用户名，唯一，登录标识之一 |
| `phone` | 手机号，唯一，登录标识之一 |
| `display_name` | 展示名 |
| `department` | 科室 |
| `roles` | 角色集合 |
| `password_hash` | 密码哈希 |
| `status` | 启用/停用 |
| `avatar` | 头像 |
| `bio` | 简介 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |
| `last_login_at` | 最近登录时间 |

### 4.2 唯一约束

- `username` 唯一
- `phone` 唯一

如果历史数据里手机号为空，可允许空值，但正式上线前建议补齐。

## 5. 推荐接口改造

### 5.1 登录接口

建议将原接口改为：

`POST /api/v1/auth/login`

请求体：

```json
{
  "account": "zhangsan 或 13800138000",
  "password": "******"
}
```

说明：

- `account` 可以是用户名，也可以是手机号。
- 后端根据格式或索引表查询账户。

不建议继续使用 `email` 字段名，否则前后端都要持续做语义翻译。

### 5.2 注册/建档接口

建议注册或管理员建档时必须同时写入：

```json
{
  "username": "zhangsan",
  "phone": "13800138000",
  "display_name": "张三",
  "department": "内科",
  "password": "******",
  "role": "doctor"
}
```

### 5.3 资料更新接口

资料修改需要支持：

- 更新手机号
- 校验手机号唯一
- 禁止与其他账户冲突

## 6. 前端交互建议

### 6.1 推荐方案

建议登录页使用单输入框方案：

- 输入框标签：`用户名/手机号`
- 密码输入框：`密码`
- 登录按钮：`登录`

理由：

- 用户认知最简单
- 不需要维护两套表单校验
- 忘记用户名时直接填手机号即可

### 6.2 不推荐方案

- 不建议做“用户名登录 Tab”和“手机号登录 Tab”两套页面。
- 这会让同一套账户体系在界面上看起来像两套登录系统，没有必要。

## 7. 后端实现步骤

### Phase A：持久化账户表

1. 新增账户表或认证用户表。
2. 把内存 `users_db` 中现有用户迁移到持久化存储。
3. 保留生产环境守卫，阻止 demo 用户继续作为正式账户源。

### Phase B：双标识登录

1. 登录请求模型改为 `account + password`。
2. 后端按以下顺序解析：
   - 先匹配用户名
   - 未命中再匹配手机号
3. 命中后校验密码哈希。
4. 更新 `last_login_at`。

### Phase C：资料与唯一性治理

1. 增加用户名唯一校验。
2. 增加手机号唯一校验。
3. 增加手机号格式校验。
4. 管理端补录缺失手机号。

## 8. 兼容迁移建议

### 8.1 旧字段兼容

如果当前前端、网关、测试脚本大量依赖 `email` 字段，可分两步迁移：

1. 第一步：
   - 后端内部先支持 `account`
   - 同时兼容 `email`
2. 第二步：
   - 前端和测试脚本全部切到 `account`
   - 删除 `email` 语义

### 8.2 旧用户迁移

- 如果现有内存用户本质上是测试账号，可直接导入为：
  - `username = admin / qc_manager / doctor`
  - `phone = 138...`
- 如果已有真实内网用户清单，应优先从主数据源导入。

## 9. 风险与控制

### 风险 1：手机号重复

- 控制措施：加唯一索引，上线前执行重复数据清理。

### 风险 2：用户名与旧 `email` 混用

- 控制措施：新接口统一用 `account`，旧字段只做过渡兼容。

### 风险 3：demo 用户进入生产

- 控制措施：保留生产启动守卫；上线前移除默认账户。

## 10. 开工验收标准

1. 认证用户源已持久化。
2. 登录接口已支持用户名/手机号双标识。
3. 前端登录页只保留一个统一登录入口。
4. 手机号唯一性校验生效。
5. 默认 demo 用户不再作为正式账户源。

## 11. 一句话方案结论

认证改造不要继续围绕 `email` 打补丁，应该直接收口为 `统一账户表 + account 登录标识 + 用户名/手机号双唯一约束`。这样才能一次性把“手机号备用登录”和“认证持久化”两个问题一起解决掉。
