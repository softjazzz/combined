# 正式单病历质控并发优化交付说明

日期：2026-05-08

## 交付结论

- 正式终末 `fast_screen_full` 已从 pack 串行执行改为 pack 级并发执行，默认 `pack_concurrency=3`。
- 优化不改变候选规则、pack 划分、prompt、上下文、`context_token_budget`、`quality_profile`、`batch_output_mode`。
- 同一病历实测：串行基线约 `307.70s`，并发 3 约 `59.73s`；两者均为 `18 packs / 18 次 LLM`。
- 本轮不修改 Sheet2 客户样本验证页 acceptance package，不影响 exact/blocked/skip 结论。

## 正式入口

- 正式运行入口：`apps/medqc-web/backend/app/routers/qc_sichuan.py` 的 workstation/final batch 任务。
- 触发条件：`bundle_scene=final`、`execution_strategy=fast_screen`、非 `validation_mode=customer`、非客户泸县规则集。
- 调用方法：`run_final_fast_screen(...)`，正式入口不显式传 `pack_concurrency`，因此使用服务默认值 `3`。
- 客户样本验证页走 `qc_sample_pools` 和 acceptance package/样本验证链路，不走本次 fixed pack 并发执行入口。

## 为什么不会降低准确性

- 每个 pack 内仍调用原 `evaluate_batch_compact`，没有改 LLM prompt 或输出 schema。
- 并发只改变不同 pack 的调度顺序，最终结果按 `pack_definitions` 原顺序合并。
- 单个 pack 异常只将该 pack 内规则降级为 `uncertain`，不会中断整份病历，也不会把异常包装成 `compliant`。
- 如果 LLM 批量响应缺少某条规则结果，该规则会保留并降级为 `uncertain`，不会静默丢失规则。

## 默认并发为什么是 3

- 3 并发能明显缩短墙钟时间，同时比 6 或更高并发更保守，降低客户现场 provider 429、timeout 或排队风险。
- 实测并发 3 时 `observed_max_concurrency=3`，`provider_error_count=0`，`timeout_count=0`，`rate_limit_count=0`。
- 当前参数内部默认下限为 1；正式 API 暂未暴露并发参数，避免前端误配置。

## 客户现场观察项

- 在结果 `pack_metrics` 中观察：`configured_concurrency`、`observed_max_concurrency`、`wall_clock_time`、`sum_pack_api_time`、`concurrency_efficiency`。
- 限流/异常观察：`provider_error_count`、`retry_count`、`timeout_count`、`rate_limit_count`。
- 如果 `rate_limit_count` 或 `timeout_count` 持续大于 0，说明瓶颈在 provider 或网络，不应通过裁剪证据解决。

## 降级方案

- 如客户现场 provider 限流，可在正式入口显式传 `pack_concurrency=1` 临时恢复串行行为。
- `pack_concurrency=1` 已由单测覆盖，输出顺序和串行语义保持一致。
- 不建议通过关闭规则、裁剪上下文或降低质量 profile 来处理限流；优先降并发、加 provider 队列或优化重试策略。

## 验证覆盖

- `test_fast_screen_qc.py` 覆盖并发 1 等价串行、并发 3 输出顺序稳定、单 pack 异常隔离、缺失单规则结果不丢规则。
- `test_qc_sichuan_batch_throughput.py` 覆盖正式 final fast_screen 路由仍进入 fixed pack 路径，并使用服务默认并发。
- Sheet2 回归脚本用于确认客户样本验收链路未被本次正式运行优化影响。
