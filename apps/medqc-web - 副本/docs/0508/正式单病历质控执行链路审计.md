# 正式单病历质控执行链路审计

审计日期：2026-05-08

审计范围：仅审计正式单病历质控入口、规则执行策略和 dry-run/只读 run 指标；未修改 dashboard 全量质控入口，未写入 `qc_results` / `qc_defects`。

## 结论

- 正式终末质控在 `fast_screen_full` 规则集下不是 146 个质控点逐条调用 LLM，而是 `final bundle -> fixed fast_screen packs -> evaluate_batch_compact`。
- 本次样本 `visit_id=1915580` dry-run 预计：84 个候选规则、30 个固定 pack、预计 30 次 LLM 调用。
- 本次只读实跑结果：实际执行 18 个 pack、18 次 LLM 调用；未出现单规则 fallback。
- dry-run 与实跑 pack 数不同，是因为实跑会按 bundle 文书命中情况跳过缺主文书的 pack，并对缺文书规则返回 `not_applicable/uncertain` 类结果。
- 正式工作区批量入口和客户样本验证页是隔离的；客户样本验证仍是人工问题复现/规则定向链路，不代表正式全量质控成本。

## 执行策略事实

- `QCRuleOrchestrator` 路径：先执行 `executor_type=program` 且 `ProgrammaticRuleExecutor.can_execute()` 支持的规则，再按 `execution_domain/doc_scope[/rule_family]` 分 bucket，调用 `evaluate_batch_compact` 批量 LLM。
- orchestrator 默认 pack 候选为 `3/5/8/10/12/15`，最大 pack size 为 15；执行缓存 `QCExecutionCache` 可启用，默认 TTL 1800 秒。
- selective refine 存在，但只对 `allow_selective_refine=true` 且低置信/高风险候选按预算触发单规则精修；这不是默认全量逐规则。
- `run_final_fast_screen` 路径使用 `FAST_SCREEN_FULL_PACK_DEFINITIONS` 固定包，`prompt_strategy=fast_screen_fixed_v1`、`bucket_strategy=fixed_packs`、`batch_output_mode=minimal`。
- 当前 final fast_screen 固定包路径会统计规则元数据里的 `program`，但不进入 `QCRuleOrchestrator` 的程序化执行阶段；若要进一步降本，应优先把 fast_screen fixed pack 与 program executor 合流。

## 样本测试

样本：`visit_id=1915580`，从 release `mr.csv` 推断到 `patient_id=0000243422`、`institute_id=泸县人民医院`。

dry-run 计划：

- 候选规则：84
- 程序化规则元数据：2（`SC-118`、`SC-119`）
- LLM 规则：82
- 预计 pack：30
- 预计 LLM 调用：30
- 实际 LLM 调用：0（dry-run 不调用 LLM）

只读实跑：

- 候选规则：84
- 实际进入 LLM 的规则：59
- 实际执行 pack：18
- 实际 LLM 调用：18
- 单规则 fallback：0
- token：71623，总 API 时间：202.01 秒，首个结果延迟：3.00 秒
- 结果：`non_compliant=11`、`uncertain=8`、`compliant=26`、`not_applicable=39`

断言：`actual_llm_call_count=18 <= pack_count + fallback_count=18`，且不等于候选规则数 84，也不等于 146。

## 旧入口风险

- 静态扫描共发现 20 个风险点：`rule_for_visit_loop=7`、`document_fallback=5`、`single_rule_engine_call=4`、`multi_document_loop=4`。
- 用户可触发但用途明确的单规则入口：`/api/v1/qc/sichuan/evaluate-rule-for-visit`，用于规则定向验证，不应作为正式全量质控默认入口。
- 工作区批量任务中存在 `_evaluate_rule_level_visit_bundle()` 逐规则回退，但触发条件是人工样本池 `manual_problem_sample_pool` 且单规则偏好，不是 formal final fast_screen 主路径。
- `/api/v1/qc/sichuan/evaluate` 仍可作为旧单文书入口触发 `evaluate_document()`，适用于调试/旧页面；正式页面应继续走 workspace batch + bundle。
- 包解析失败时 orchestrator 会拆包或单规则 retry，这是容错和 selective refine，不是默认逐规则执行。

## 十个验收问题回答

1. 正式终末 `fast_screen_full` 默认候选规则为 84 条，不是 146 条全量。
2. dry-run 预计 LLM 调用 30 次。
3. 本机只读实跑实际 LLM 调用 18 次。
4. 本次 fast_screen 规则集中带程序化元数据的是 `SC-118`、`SC-119`；但 fixed fast_screen 当前未真正先跑 program executor。
5. LLM pack 见 `single_visit_qc_execution_plan_audit.csv`，按入院、首程、病程、围手术、出院、检查检验等固定包划分。
6. 存在用户可触发的单规则入口 `/evaluate-rule-for-visit` 和旧 `/evaluate`，但不是正式终末 fast_screen 默认入口。
7. 正式 workspace final fast_screen 在 `execution_strategy=fast_screen` 且非客户样本规则集时使用 `run_final_fast_screen()`。
8. 客户样本验证页与正式质控入口已清晰隔离：前者服务验收包/人工问题复现，后者服务 workspace/bundle/fast_screen。
9. 当前架构可支撑“不是逐规则 LLM”的成本预期，但 18 次 LLM / 202 秒仍有优化空间。
10. 下一步优先优化 fast_screen fixed pack 与 program executor 合流，其次优化 pack 划分和 selective refine 策略。
