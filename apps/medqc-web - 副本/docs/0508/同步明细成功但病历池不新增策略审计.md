# 同步明细成功但病历池不新增策略审计

生成日期：2026-05-27

## 1. 审计结论

根因判断：代码策略问题为主，客户机数据问题为辅，配置问题需要现场复核。

开发机代码存在一条明确的 detail-only visit 静默 success 路径：

1. `/api/v1/sync/trigger` 会把 `date_window`、`target_departments`、`table_groups` 传给 `etl_sync.run_sync`。
2. `run_sync` 在表直连模式下调用 `collect_visit_keys_by_policy` 生成 `eligible_visits`。
3. `collect_visit_keys_by_policy` 固定从远端 `public.discharge_record` 按 `discharge_date/discharge_time/discharge_datetime + dept_name` 生成 `(patient_id, visit_id)` 集合。
4. 后续所有表，包括 `mr`，都只按这批 visit_keys 调用 `fetch_remote_rows_by_visit_keys` 拉取。
5. 如果 `discharge_record/admission_record/orders/course/diagnosis` 等明细表能按 visit_id 拉到数据，但远端或本地 `mr` 对这些 visit_id 没有行，当前代码不会把它视为失败或 warning。
6. `run_sync` 的最终 `success` 只看有没有异常；`mr record_count=0`、detail rows>0、病历池不可见不会影响 `success=true`。
7. 工作站病历池主要从 `cdm.mr` 读取基础列表，所以 `cdm.mr=0` 会导致页面病历池不新增。

这与客户机现象一致：`eligible_visits=8`、`total_records=1383`、明细表有数据，但 `cdm.mr=0`、`public.visit_index=0`、页面病历池数量不变。

## 2. 入口链路图

```text
前端 DataSyncConfig / useDataSync
  -> syncApi.triggerSync('/api/v1/sync/trigger')
  -> backend app.routers.sync.trigger_sync
  -> _resolve_selected_tables(tables, table_groups)
  -> etl_sync.run_sync(... scene/date_window/target_departments/table_groups ...)
  -> validate_pg_sync_plan
  -> collect_visit_keys_by_policy 生成 eligible visit_keys
  -> for each target table:
       fetch_remote_rows_by_visit_keys(source_table, visit_keys)
       upsert_to_local(table_name, rows)
       if table in {mr, admission_record, discharge_record}:
          ingest_sync_rows -> public.visit_index
          refresh_scene_bundles_for_rows
  -> 返回 success/status/total_records/eligible_visits/tables
```

旧接口 `/api/system/sync/trigger` 已在 `system_config.py` 中调用 `_reject_legacy_write_endpoint`，返回 410，不应是当前客户机一键同步的主路径。正式路径是 `/api/v1/sync/trigger`。

## 3. eligible_visits 来源

代码位置：`apps/medqc-web/backend/app/services/etl_sync.py`

关键函数：`collect_visit_keys_by_policy`

当前策略：

- 固定使用远端 `discharge_record` 作为病例集合锚点。
- 必须存在 `patient_id`、`visit_id`、`dept_name`。
- 日期字段从 `discharge_date`、`discharge_time`、`discharge_datetime` 中选择。
- 科室过滤使用 `LOWER(TRIM(dept_name)) IN (...)`。
- 输出唯一 `(patient_id, visit_id)` 集合。

影响：

- eligible visit 可以由 `discharge_record` 生成，不依赖 `mr`。
- 如果 `discharge_record` 命中 8 个 visit，但 `mr` 没有对应行，eligible 仍为 8。
- 当前没有“eligible 生成后强制验证 `mr` 覆盖”的逻辑。

## 4. mr 同步条件

代码位置：`apps/medqc-web/backend/app/services/etl_sync.py`

当前 `mr` 同步方式：

- `sample_full_domain` 和 `core_8` 均包含 `mr`。
- `run_sync` 不按 `mr` 自己的日期字段筛选 `mr`。
- `mr` 与其他表一样，使用 `fetch_remote_rows_by_visit_keys(remote_schema, source_table='mr', visit_keys=scoped_visit_keys)`。
- 如果远端 `mr` 对这些 visit_keys 返回 0 行，`upsert_to_local('mr', records=[])` 返回 0，不报错。
- table log 中 `record_count=0`、`status=success`。

缺陷点：

- `mr` 是病历池主锚点，但在同步 summary 中没有作为必达表校验。
- `mr_rows_upserted=0` 且 detail rows>0 时没有 warning/failure。
- 没有输出 `missing_mr_visit_ids`、`detail_only_visit_count`。
- 没有对 eligible visit_ids 做 `mr` by visit_id backfill 后的完整性断言。

## 5. detail tables 同步条件

当前 detail tables 同步方式：

- `fetch_remote_rows_by_visit_keys` 只要求源表存在 `patient_id`、`visit_id`。
- 对每张表使用 `(patient_id::text, visit_id::text) IN (...)` 拉取。
- 明细表只要能按 visit_id 命中，就会 upsert 到本地 CDM 表。
- 明细表成功不要求 `mr` 成功。

因此会出现：

```text
discharge_record/admission_record/diagnosis/orders/course rows > 0
mr rows = 0
run_sync success = true
total_records > 0
病历池不新增
```

这就是 detail-only visit 静默 success。

## 6. visit_index 刷新条件

代码位置：`apps/medqc-web/backend/app/services/visit_index_service.py` 与 `etl_sync.py`

当前策略：

- `etl_sync._VISIT_INDEX_ANCHOR_TABLES = {'admission_record', 'discharge_record', 'mr'}`。
- `run_sync` 对这些表同步到的 rows 调用 `ingest_sync_rows`。
- `visit_index` 表无 schema 限定，默认写入当前 search_path 下的 `visit_index`，通常是 `public.visit_index`。
- `ingest_sync_rows` 只要求 row 有 `institute_id/patient_id/visit_id`，不要求 `mr` 存在。

审计判断：

- 通用 `run_sync` 理论上会在 admission/discharge 有 rows 时写 `visit_index`。
- 客户机 `public.visit_index=0` 说明有以下可能：
  - 本次同步未实际拉到 admission/discharge anchor rows，只是其他 detail rows 先前已有；
  - `institute_id` 缺失导致 `ingest_sync_rows` 跳过；
  - `visit_index` 写入失败但被 warning 吞掉；
  - 客户机走的不是这条 `run_sync` 路径；
  - search_path/schema 与检查口径不一致。
- 但即使 `visit_index` 有行，当前工作站病历池仍主要基于 `mr` 查询，不能替代 `mr` 主记录。

## 7. 病历池查询策略

代码位置：`apps/medqc-web/backend/app/services/workstation/worklist_service.py`

`_load_base_rows` 使用：

```text
mr = _table('mr', 'cdm', 'public')
select mr.institute_id, mr.patient_id, mr.visit_id, mr.name, ...
from mr
```

影响：

- 病历池基础列表由 `cdm.mr` 优先提供。
- `admission_record/discharge_record/diagnosis/orders/course` 的 detail-only 数据不会进入病历池基础列表。
- `visit_index` 当前不是工作站病历池的 lightweight fallback。

因此客户机 `cdm.mr=0` 足以解释“页面病历池数量没有变化”。

## 8. schema 策略

代码位置：`apps/medqc-web/backend/app/services/etl_sync.py` 与 `database/connection.py`

当前策略：

- `DB_SCHEMA_MODE=split` 且表名在 `_CDM_SYNC_TABLE_NAMES` 中时，本地写入优先选择 `cdm`。
- `_CDM_SYNC_TABLE_NAMES` 来自全部 `SYNC_TABLES`，包括 `mr` 和明细表。
- 若同名表同时存在 `public` 和 `cdm`，split 模式会优先写 `cdm`。
- `visit_index` 不在 CDM 同步表集合中，由 `visit_index_service` 创建无 schema 限定表，通常落在 `public`。

需要客户机检查：

- `DB_SCHEMA_MODE` 是否为 `split`。
- `PG_LOCAL_TARGET_SCHEMAS` 是否包含 `public,cdm`，且优先级符合预期。
- `cdm.mr` 与 `public.mr` 是否存在分叉。
- `public.visit_index` 是否为实际 search_path 命中的表。

但从开发机代码看，schema 分叉不是主要缺陷；主要缺陷仍是 `mr` 缺失未被当成同步质量问题。

## 9. idempotent_reused 风险

代码位置：`apps/medqc-web/backend/app/routers/sync.py` 与 `services/sync_idempotency.py`

当前幂等 key：

```text
source:tier:sync_date:operator
```

未包含：

- `date_window`
- `target_departments`
- `table_groups`
- `scene`
- `policy_version`

风险：

- 同一操作员、同一 `sync_date` 下，改变科室、日期窗口或表分组后，可能返回旧 run 的 `idempotent_reused=true`。
- 前端 `executeSync` 只判断 `result.success`，没有显式提示“本次为复用旧结果，不是新同步”。
- 这可能让现场误以为已按新的 `target_departments=['普通外科']` 执行同步。

这不是本次 detail-only 的唯一根因，但属于同步验收口径缺陷。

## 10. 测试覆盖审计

已看到的相关测试：

- `test_sync_consistency.py` 覆盖 split schema 优先级、run_sync 基本成功、upsert 主键策略。
- `test_custom_qc_sample_pool_service.py` 覆盖 `sample_full_domain` 包含 `mr`，以及样本池同步聚合 rows、可刷新 running/final bundle。
- `test_sync_router.py` 覆盖 preflight 基本行为。

缺失测试：

- 没有覆盖“eligible visit 来自 `discharge_record`，但 `mr` 返回 0，detail rows>0”的场景。
- 没有覆盖“同步 success 但病历池不可见”的场景。
- 没有覆盖“`mr_rows_upserted=0`、`detail_rows>0` 时必须 warning/failure”的验收口径。
- 没有覆盖 `idempotent_reused` 在 date_window / target_departments / table_groups 变化时不得复用旧结果。
- 没有覆盖 `visit_index` 写入失败被吞掉后同步仍 success 的可观测 warning。

## 11. 是否会导致客户机现象

会。

客户机现象：

- 一键同步返回 success。
- `target_departments=['普通外科']`，`date_window=2026-05-25`。
- `eligible_visits=8`，`total_records=1383`。
- 4 个 visit_id 在 admission/discharge/diagnosis/orders/course 等明细表有数据。
- `cdm.mr=0`，`public.visit_index=0`。
- 页面病历池数量没有变化。

开发机代码可解释该现象：

- eligible 可由 `discharge_record` 生成，不要求 `mr`。
- detail 表可成功同步，不要求 `mr`。
- `mr` 缺失不触发 warning/failure。
- 病历池基础列表依赖 `cdm.mr`。
- 同步 history 只记录 `total_records`，不突出 `mr` 与 `visit_index` 覆盖。

  - `discharge_record.record_count`

- 远端 `public.mr` 是否存在 2404019、2404311、2406109、2412559。

- 本地 `cdm.admission_record`、`cdm.discharge_record`、`cdm.diagnosis` 等是否为本次 run 新写入。
- `public.visit_index` 是否存在；如存在，检查是否 search_path 问题或写入 warning。
