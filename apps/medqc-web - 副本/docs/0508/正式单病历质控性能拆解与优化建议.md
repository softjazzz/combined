## 可程序化候选

- 已在本轮实跑包中命中的明确程序化候选：`SC-118`、`SC-119`、`SC-122`，主要是出院记录字段/医嘱存在性。
- 按规则名启发式扫描，更多候选集中在文书存在性、时效、签名、字段缺失、手术/会诊/输血/医嘱/检查检验存在性。
- 候选清单见 `single_visit_qc_pack_performance_breakdown.json.analysis.program_candidate_rules`。

## 上下文裁剪候选

- 入院记录包 `admission_content_core`/`admission_consistency_core`：单文书字符不大，但 pack 大，适合按结构字段分发而非全文重复。
- 日常病程包 `daily_course_*`：source 字符少但 API time 异常高，优先查 LLM 服务延迟和 prompt 复杂度，而不是只看文本长度。
- 手术/术前讨论/出院相关包：有明确文书域，适合构建手术摘要、出院摘要、讨论结论摘要。
- 检验检查类包后续在大样本上应只输入异常项、最新项、与诊断/病程相关项，避免全量列表。

## 优化建议

### A. 低风险，建议优先做

- 增强 pack 级 cache：按 `visit_id + pack_id + bundle hash + rule version + prompt version` 缓存，避免同一病历重复跑固定包。
- 对无相关文书的 pack 在 bundle 层直接 `not_applicable`，当前已跳过部分 pack，但建议把跳过原因显式写入 pack 明细。
- 将存在性、时效、签名/字段缺失规则接入 fast_screen 的 program executor，而不是只在 orchestrator 路径使用。
- 对检验检查/医嘱上下文做摘要和异常项优先裁剪。
- 对 `high-cost low-yield` 包增加 cheap trigger，例如无手术/无输血/无会诊时不进 LLM。

### B. 中风险，需回归验证

- 重新划分高 token 或高耗时 pack，例如把 `admission_content_core` 中字段完整性与语义一致性拆开。
- 增加两阶段执行：首轮 cheap trigger，二轮只对命中的 pack 做 LLM 精审。
- 对 `SC-036/SC-070/SC-146` 建结构化 evidence summary，减少跨域原文。

### C. 高风险，暂不建议直接做

- 改 LLM 输出 schema。
- 改主规则口径。
- 合并不同文书域的大 pack。
- 默认关闭某些规则。

## 收益估算

- 将本轮已识别程序化候选移出 LLM，按规则均摊估计可减少约 `5977` token；由于仍有同包其他规则，短期不一定减少 LLM 调用。
- Top 5 token pack 合计 `25619` token；若上下文裁剪 30%，预计减少约 `7686` token。
- high-cost low-yield pack `6` 个，合计 `25457` token；若 cheap trigger 能跳过其中一半，可减少约 `3` 次 LLM 和 `12728` token。
- 建议目标：单份终末病历 LLM 调用降到 `10-12` 次，token 降到 `4-5万`，耗时降到 `90-150s`。

## 数据限制

- 底层 `run_final_fast_screen` 当前只汇总 pack_metrics，未直接暴露每包 parse error / missing rule ids；本轮通过规则结果 metadata 反推。
- 由于外层命令超时边界，本轮实际 run 的逐包明细保留 16 个有 `pack_id` 的执行包；总 token 与包 token 汇总差异 12，可用于性能排序。
- 不写库，不修改正式业务逻辑。
