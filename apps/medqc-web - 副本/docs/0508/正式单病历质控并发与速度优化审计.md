# 正式单病历质控并发与速度优化审计

审计日期：2026-05-08

范围：正式 `final fast_screen_full` 主路径；本轮聚焦墙钟时间、并发、超时、限流和准确性保护，不裁剪上下文、不关闭规则、不改 prompt schema、不改 Sheet2 验收结论。

## 结论

- 原 `run_final_fast_screen` 在 `for pack in pack_definitions` 中逐包 `await evaluate_batch_compact`，18 个实际 LLM pack 是串行等待。
- `QCRuleOrchestrator` 支持 `llm_concurrency=6`，但 final fixed fast_screen 绕开 orchestrator，因此该并发度此前不生效。
- LLM client 未见全局锁；网络调用通过 `safe_post_json` async 发起，具备并发调用条件。
- 本轮已给 final fast_screen 增加低风险 pack 并发，默认 `pack_concurrency=3`，不改规则、上下文、prompt、quality profile 或 batch output mode。
- 同一 `visit_id=1915580` 实测：`pack_concurrency=3` 墙钟约 `59.73s`，串行基线约 `307.70s`，LLM 调用数均为 `18`。

## 实现说明

- 修改点：`apps/medqc-web/backend/app/services/fast_screen_qc.py`
- 新增参数：`pack_concurrency: int = 3`
- 并发粒度：pack 级并发，每个 pack 内仍使用原 `evaluate_batch_compact`
- 异常隔离：单个 pack 异常只将该 pack 规则置为 `uncertain`
- 顺序稳定：并发结果按 `pack_definitions` 原顺序合并
- 诊断字段：`execution_mode`、`configured_concurrency`、`observed_max_concurrency`、`sum_pack_api_time`、`wall_clock_time`、`concurrency_efficiency`、provider/retry/timeout/rate limit 计数、`pack_diagnostics`

## 并发观测

- 当前 18 个 pack 原先是串行；202s/307s 主要来自 pack 串行等待叠加，而不是单包必须依赖前一包。
- 并发后 `observed_max_concurrency=3`，`concurrency_efficiency=2.6765`，说明 provider 未明显限流。
- 最慢 pack 仍为 `admission_content_core`，并发实跑 `slowest_pack_api_time=49.08s`。
- `provider_error_count=0`、`timeout_count=0`、`rate_limit_count=0`，默认 3 并发当前可接受。

## 准确性保护

- 候选规则数不变：84。
- 实际 LLM pack 数不变：18。
- LLM 调用数不变：18。
- 不降低 `context_token_budget`。
- 不改变 `batch_output_mode=minimal`。
- 不改变 `quality_profile=throughput_v1`。
- 不改变 LLM prompt 内容和输出 schema。
- 不把 `uncertain` 改成 `compliant`。
- 不改 Sheet2 验收 exact/blocked/skip。

## 后续建议

- 保持默认 `pack_concurrency=3`，在客户环境观察 rate limit/timeout 后再考虑 4 或 5。
- 增加 pack 级 cache 是下一优先级，可进一步降低重复运行等待时间，且不影响召回。
- 若 provider 出现 429/timeout，应增加自适应并发或 provider 侧队列，而不是裁剪上下文。
- 不建议为了速度关闭规则或删证据；速度优化优先从并发、缓存、重试策略和 provider 吞吐入手。
