# 正式质控小模型结构化证据 POC 阶段总结

生成日期：2026-05-15

## 结论先行

本轮 POC 证明了“小模型先抽结构化证据，大模型再裁决”的技术可行性，但没有证明它在全量 84 条正式质控场景下优于现有正式链路。

更准确的结论是：

- 作为全 84 条正式质控主链路替代方案：暂不成立。
- 作为少数证据结构清晰规则族的旁路验证方案：有继续验证价值。
- 作为 evidence package / 证据组织器，辅助现有正式链路减少误判：有产品化探索价值。

因此，当前不建议把结构化证据 POC 直接接入页面、落库或替换 `final fast_screen_full` 主链路。

## 原始假设

本轮 POC 的原始假设是：

1. 使用小参数模型 `qwen3.5-35b-a3b` 先快速抽取结构化证据。
2. 使用较强模型 `qwen3.6-35b-a3b` 只基于结构化证据做二审裁决。
3. 通过减少大模型读取长文书的次数和长度，降低 token、缩短耗时，并提升证据可审计性。

目标不是新增一套正式质控结果，而是在只读 POC 中验证该架构是否值得后续产品化。

## 测试范围

- 规则范围：正式 `sc_content_full_v1` / `final fast_screen_full` 84 条内涵质控规则。
- 样本范围：沿用既有 10 份正式质控抽检病历。
- 运行方式：只读 POC，不写正式业务表，不接页面，不替换主链路。
- 模型：
  - extractor：阿里云百炼 `qwen3.5-35b-a3b`
  - adjudicator：阿里云百炼 `qwen3.6-35b-a3b`
- 对照基线：现有正式 84 条链路的 10 病历阿里云抽检结果。
- Sheet2 验收门禁始终保持：

```text
exact_confirmed=156 / blocked_with_reason=102 / skip=25 / needs_exact_review=0
```

## 关键阶段

### 1. 五条规则 POC

早期 POC 只覆盖 `SC-036 / SC-070 / SC-099 / SC-100 / SC-101` 五条规则。

这轮结果显示：

- JSON 输出稳定。
- 证据结构可读。
- token 大幅低于完整正式链路。

但这不是等价比较，因为只覆盖 5 条规则，不能代表 84 条全量质控。

### 2. all84 初版

首次扩展到 84 条后，脚本按 9 个 evidence package 抽取证据，再做大量裁决。

结果：

- 10 病历 840 条裁决跑通。
- 调用数和耗时明显高于正式链路。
- token 也高于正式链路。

主要问题是执行结构不合理：

- 每份病历固定 9 次 extractor。
- adjudicator batch 拆得过碎。
- 大模型仍读取了过多证据内容。
- 程序化可短路的规则仍进入二审。

### 3. v4 执行结构优化

v4 将证据域从 9 个合并为 5 个，并增加程序化短路。

关键指标：

| 指标 | all84 初版 | v4 |
|---|---:|---:|
| LLM 调用 | 252 | 97 |
| token | 962,527 | 432,912 |
| wall time | 2037.5s | 1043.2s |
| 平均每病历 | 203.8s | 104.3s |

v4 证明了结构化证据链路可以通过证据域合并和短路显著压缩调用数与 token。

但 v4 存在严重质量口径问题：大量送入二审的规则没有返回裁决，被保守映射为 `rejected_by_system`。这会造成潜在真实缺陷被误驳回，因此 v4 不能验收。

### 4. v5 并发优化

v5 增加单病历内部并发：

- `extractor_concurrency=3`
- `adjudicator_concurrency=3`
- 10 病历仍顺序执行，避免 provider 压力扩大。

关键指标：

| 指标 | v4 | v5 |
|---|---:|---:|
| token | 432,912 | 475,190 |
| wall time | 1043.2s | 499.0s |
| 平均每病历 | 104.3s | 49.9s |
| LLM 调用 | 97 | 112 |

v5 达到了耗时目标，但发现更严重的完整性问题：

```text
rules_sent_to_adjudicator_count=728
adjudicator_output_rule_count=316
missing_adjudicator_output_count=412
```

也就是说，大量规则进入二审但模型没有返回裁决。将这类缺失输出映射为 `rejected_by_system` 是错误的，因为“模型未返回”不等于“规则不成立”。

### 5. v6 二审完整性修复

v6 要求每个 `expected_rule_id` 必须有唯一裁决；缺失时补裁，仍缺失则进入 `technical_error_internal`，不得伪装成系统驳回。

关键指标：

| 指标 | v6 |
|---|---:|
| total_rule_decision_count | 840 |
| rules_sent_to_adjudicator_count | 728 |
| adjudicator_output_rule_count | 728 |
| missing_adjudicator_output_count | 0 |
| technical_error_internal_count | 0 |
| provider / timeout / parse_error | 0 |
| total_tokens | 551,980 |
| wall_clock_time | 619.786s |
| 平均每病历耗时 | 61.979s |
| LLM calls | 112 |

v6 修复了完整性问题，是当前最可信的 POC 版本。

## 与正式链路对比

| 指标 | 正式 baseline | POC v6 |
|---|---:|---:|
| token | 608,247 | 551,980 |
| token 变化 | - | 下降约 9.25% |
| wall time | 320.585s | 619.786s |
| 耗时变化 | - | 约 1.93 倍 |
| 平均每病历 | 约 32.1s | 约 62.0s |
| 规则裁决数 | 正式只输出命中/问题项 | 840 全网格裁决 |

v6 的 token 略低于正式链路，但耗时接近正式链路的 2 倍。考虑到系统复杂度显著上升，当前收益不足以支撑替换主链路。

## 被验证成立的点

1. 小模型可以稳定抽取结构化 evidence package。
2. 大模型可以基于结构化 evidence package 完成 84 条规则裁决。
3. 通过 evidence family 合并、程序化短路、并发，可以把 all84 POC 从不可用状态压到接近可评估状态。
4. 结构化输出比纯长文书 prompt 更易审计：
   - trigger
   - required evidence
   - supporting evidence
   - contradicting evidence
   - missing evidence
   - coverage flags
5. 对规则适用性强的场景，例如植入物、病理、会诊、异常结果处理，结构化证据有明显解释力。

## 未验证成功的点

1. 没有证明全 84 条结构化证据链路更快。
2. 没有证明全 84 条结构化证据链路显著省 token。
3. 没有证明全 84 条结构化证据链路准确性优于正式链路。
4. `confirmed_defect` 数量明显高于 baseline，需要质量复核：

```text
baseline confirmed_defect=14
v6 confirmed_defect=44
```

这可能是结构化证据更敏感，也可能是误报增加。未复核前不能作为质量提升结论。

## 当前主要风险

### 1. 复杂度上升

结构化证据链路引入了：

- extractor prompt
- evidence schema
- adjudicator prompt
- expected rule id 完整性校验
- missing rule retry
- gate / guardrail
- 程序化短路
- 多版本报告与对比口径

这套复杂度只有在明显提升速度或准确性时才值得产品化。目前尚未达到。

### 2. 质量未复核

v6 的技术门禁通过，但质量门禁尚未完成。尤其是：

- 44 条 confirmed_defect 是否真实成立？
- 559 条 rejected_by_system 是否存在误驳回？
- 237 条 data_quality_gap 是真实数据缺口，还是 evidence schema 抽取不足？

### 3. 规则不一定都适合结构化证据

84 条规则中，部分规则天然依赖跨文书语义判断、病情上下文或医学合理性判断，不一定适合先结构化再裁决。

## 阶段结论

本轮 POC 不支持“全 84 条都先用小模型跑一遍可以提速”的假设。

更合理的定位是：

1. 结构化证据链路可作为少数规则族的旁路验证方案。
2. 结构化 evidence package 可作为正式链路的证据组织增强层。
3. 不应直接替换当前 `final fast_screen_full` 主链路。

## 建议下一步

### 优先级 1：完成 v6 质量复核

需要对 v6 产物做只读质量复核：

- 44 条 confirmed_defect 全量复核。
- 抽样 50 条 rejected_by_system。
- 抽样 50 条 data_quality_gap。
- 输出规则级推荐：
  - ready_for_feature_flag
  - needs_schema_fix_before_feature_flag
  - needs_prompt_fix
  - source_data_blocked
  - not_suitable_for_structured_evidence_now

### 优先级 2：挑选少数规则族做 feature flag 旁路

不要直接 all84 接入。可以优先挑选：

- 会诊意见落实
- 检查检验异常处理
- 植入物 / 高值耗材 / 病理取材
- 出院记录字段完整性

这些规则族证据结构相对清晰，更适合结构化证据方案。

### 优先级 3：沉淀 evidence package 能力

即使不替换正式主链路，也可以将 POC 中可靠的 evidence package 设计沉淀为：

- 规则证据组织器
- 页面证据解释层
- 误报排查工具
- 数据缺口诊断工具

这比强行替换正式链路更稳妥。

## 暂不建议做的事

- 暂不接入页面。
- 暂不替换正式质控主链路。
- 暂不扩大到 20/50 病历。
- 暂不把 v6 的 confirmed_defect 当作正式质量结论。
- 暂不为了追求速度降低二审完整性门禁。
