# 内涵质控点批量上线与测试计划

> 日期：2026-04-18  
> 范围：`workstation-v4` 终末病历/运行病历批量质控  
> 当前优先级：先打通“内涵质控第一批规则集”的稳定批量上线，再扩展到更多规则

## 1. 背景与问题

当前质控规则可以粗分为两类：

1. 形式质控
   - 例如：文书是否存在、是否超时完成、是否有签名、是否有审批单、是否有知情同意书。
   - 这类规则更适合程序化判断、SQL 查询、结构化字段、正则或时间计算。
   - 如果全部交给 LLM，会浪费 token，且结论反而可能不稳定。

2. 内涵质控
   - 例如：主诉是否能导出第一诊断、现病史与主诉是否一致、诊断依据是否充分、诊疗计划是否具体、诊疗经过是否完整、出院诊断是否漏填或顺序错误、医嘱与病程是否一致。
   - 这类规则需要理解医学语义、上下文逻辑和跨文书一致性，更适合由 LLM 参与判断。

目前真实测试已经暴露出核心矛盾：

- 单条质控效果较好，但耗时长、token 成本高。
- 全量批量质控速度更可控，但如果规则和证据混包不合理，内涵问题容易漏报或变成泛化结论。
- 因此不应直接把全部 170+ 规则一次性上线为 LLM 批量质控，而应先筛出“LLM 真正有价值”的内涵质控点，分批上线和验证。

## 2. 为什么要单独上线内涵质控点

### 2.1 提升 LLM 使用价值

LLM 最适合解决的是“读懂病历内容后判断是否合理”的问题，而不是简单查有没有签名、有没有某张表。

例如：

- `SC-023` 首次病程记录无病例特点。
- `SC-026` 首次病程记录诊断依据或鉴别诊断不充分、不全面。
- `SC-121` 诊疗经过不全面、不详细。
- `SC-125` 出院诊断或死亡诊断错填、漏填、顺序错误。

这些规则需要 LLM 理解诊断、病情、检查、治疗和文书之间的关系。

### 2.2 降低误报和噪声

如果形式质控和内涵质控混在一起跑，结果里会大量出现：

- 缺文书。
- 缺签名。
- 超时。
- 缺表单。

这些问题会淹没真正需要医生阅读的内涵问题，导致用户感觉“质控结果都是形式问题，没有真正指出医学逻辑问题”。

### 2.3 控制 token 和耗时

内涵质控规则应该走：

```text
文书域/规则族分桶 -> 效果优先批量筛查 -> 低置信/高风险规则单条精审
```

形式质控规则应该走：

```text
结构化字段/文书命中/时间字段/签名字段 -> 程序化判断
```

这样才能避免所有规则都用 LLM 重复读取整份病历。

### 2.4 便于上线验收

内涵质控第一批上线应以“医生是否认可问题结论”为核心，而不是仅看命中数量。

如果第一批规则太多，很难判断问题来自：

- 规则本身不适合 LLM。
- 文书域路由不准。
- bundle 证据缺失。
- prompt 不稳定。
- 分包策略不合理。

所以必须分批测试。

## 3. 当前规则数量与分布

### 3.1 规则总数口径说明

当前项目中存在多个规则口径：

| 口径                | 说明                                                                         |
| ------------------- | ---------------------------------------------------------------------------- |
| SC146               | 当前四川规则 POC 和 `rule_family` 映射的主验证集，规则编号 `SC-001 ~ SC-146` |
| 约 170/179 活动规则 | 历史页面或治理表中的活动规则口径，可能包含 SC 扩展、LX/LXE 或其他规则        |
| LX/LXE              | 另外一批首页质控、医保结算清单等规则，不纳入本轮内涵质控上线结论             |

本计划先以 `SC146` 为可核验基线。后续若产品页面展示为 170/179 条，需要先统一规则真源，再把本计划中的分类方法扩展到全量活动规则。

### 3.2 SC146 按规则族分布

当前已按 `rule_family` 对 SC146 做二次路由分类：

| 规则族                    | 数量 | 类型判断                  | 说明                                             |
| ------------------------- | ---: | ------------------------- | ------------------------------------------------ |
| `content_completeness`    |   42 | 内涵为主                  | 文书内容是否完整、是否描述清楚、诊疗计划是否具体 |
| `consistency_cross_doc`   |   11 | 内涵为主                  | 主诉/现病史/诊断/检查/医嘱/病程之间是否一致      |
| `procedure_order_linkage` |   31 | 内涵为主                  | 手术、麻醉、医嘱、检查、治疗和病程之间是否闭环   |
| `presence_required`       |   21 | 形式为主                  | 是否缺文书、缺记录、缺表单                       |
| `timeliness`              |   19 | 形式为主                  | 是否在规定时间内完成                             |
| `signature_authority`     |   22 | 形式为主，部分需 LLM 辅助 | 签名、审核、授权主体、知情同意主体               |

按宽口径，潜在内涵规则为：

```text
content_completeness 42
+ consistency_cross_doc 11
+ procedure_order_linkage 31
= 84 条
```

但其中仍有部分规则偏“缺项/描述不清”，并不都适合作为第一批 LLM 上线规则。按严格口径，当前更适合 LLM 第一阶段上线的内涵质控点约为：

```text
40 ~ 60 条
```

第一批建议只选 `12 条`，不是因为内涵规则只有 12 条，而是为了先建立可验证、可解释、可上线的闭环。

## 4. 第一批上线规则集

### 4.1 第一批规则选择原则

第一批规则必须满足：

- 明显属于内涵质控，而不是纯形式质控。
- 能从 bundle 文书中获取足够证据。
- 质控结论能被医生理解和复核。
- 适合终末病历场景，能在 `/workstation-v4/records/final` 中闭环展示。
- 不强依赖尚未稳定结构化的数据，如完整医嘱明细、输血前九项、抗菌药物分级、授权委托关系等。

## 5. 批量质控执行策略

### 5.1 第一批上线策略

第一批内涵质控规则建议使用：

```text
quality_profile = effect_priority_v1
bucket_strategy = domain_family
enable_selective_refine = true
refine_confidence_threshold = 0.75
use_execution_cache = 按环境决定，测试时关闭，生产时开启
```

执行流程：

1. 根据规则文书域和规则族分桶。
2. 对同一文书域/规则族的规则进行批量筛查。
3. 对以下结果触发单条精审：
   - `status=uncertain`
   - `confidence < 0.75`
   - 严重缺陷且初筛命中
   - 规则族为 `timeliness` 或 `signature_authority` 且命中问题
   - 结论、证据、建议存在逻辑矛盾
   - 不合规但证据为空
4. 精审结果覆盖批量筛查结果。
5. 前端只默认展示 `non_compliant` 和 `uncertain`，合规结果折叠。

### 5.2 为什么不是全量 84 条一次上线

不建议直接上线 84 条内涵候选，原因：

- 每条规则的证据需求不同，容易导致分包上下文不稳定。
- 一次性上线过多，医生反馈难以定位问题来源。
- 部分规则需要结构化数据支撑，当前 bundle 未必足够。
- 规则族还需要根据真实病历效果继续修正。
- 过多低质量结果会降低用户对系统的信任。

## 6. 分批测试计划

### 6.1 P0：第一批 12 条闭环测试

目标：验证终末病历批量质控能稳定产出可读、可复核的内涵问题。

范围：

- 规则数：12 条。
- 场景：终末病历 `final`。
- 样本：优先选择已有 bundle 的真实病历。
- 页面：`/workstation-v4/records/final` 任务详情抽屉和内涵质控结果面板。

测试要求：

- 每份病历规则覆盖率 `100%`。
- `missing_rule_ids=0`。
- `parse_error=0`。
- 每条命中结果必须包含：
  - 规则编码。
  - 规则名称。
  - 文书域。
  - 结论。
  - 证据。
  - 建议。
  - 置信度。
  - 是否精审。
- 抽样人工复核不少于 30 条命中/待复核结果。

验收标准：

- 结果能被医生或质控人员读懂。
- 明显误报率可控。
- 不出现大量“缺文书”掩盖内涵问题。
- 平均耗时明显低于全量单条规则执行。

### 6.2 P1：扩展到 25~30 条

目标：加入入院记录、病史逻辑、诊断一致性。

新增候选：

```text

SC-010
SC-011
SC-012
SC-018
SC-019
SC-020

SC-038
SC-039
```

测试重点：

- 主诉、现病史、诊断之间的一致性。
- 检查结果是否在病程中分析。
- 医嘱和病程是否一致。
- 会诊意见是否执行并记录。

验收标准：

- 与 P0 相比，问题覆盖面扩大，但误报率不能明显上升。
- 跨文书一致性规则必须能展示证据来源。
- 前端按文书域/规则族分组展示，避免结果混乱。

### 6.3 P2：手术病历专用内涵规则

目标：仅对手术病历启用手术相关内涵质控。

新增候选：

```text

SC-084
SC-085
SC-097
SC-099
SC-101
SC-105
SC-114

```

前置条件：

- bundle 能稳定识别手术病历。
- 手术记录、麻醉记录、术前小结、术前讨论、术后首次病程记录能稳定进入证据上下文。
- 非手术病历必须判定为不适用，不能误报。

验收标准：

- 非手术病历不触发手术规则。
- 手术相关问题可以定位到对应文书。
- 对植入物、取材、病理、术后病程等问题能给出具体证据。

### 6.4 P3：特殊高风险规则

目标：逐步加入抗菌药物、输血、知情同意主体等复杂规则。

不建议在 P0/P1 直接上线，原因：

- 需要更多结构化证据。
- 需要规则库或临床知识库支持。
- 单纯 LLM 判断容易产生看似合理但不可审计的结论。

应先补齐：

- 抗菌药物分级和适应证数据。
- 输血前检查、评估、记录、反应记录。
- 患者签名身份、授权委托、法定代理人信息。
- 高值耗材、自费项目、特殊治疗清单。

## 7. 测试样本要求

### 7.1 最小 smoke

用于开发验证：

- 样本数：1~5 份。
- 目标：接口不报错，规则覆盖率 100%，前端能展示。
- 不能作为上线依据。

### 7.2 小规模回归

用于 P0 上线前验证：

- 样本数：20~40 份。
- 覆盖：
  - 普通终末病历。
  - 手术终末病历。
  - 多诊断病历。
  - 有明显出院记录缺陷的病历。
  - 无明显缺陷的阴性样本。

### 7.3 正式验收

用于上线决策：

- 样本数：不少于 100 份。
- 人工复核：
  - 每类规则至少抽 10 条结果。
  - 所有 `uncertain` 必须复核。
  - 所有严重缺陷命中必须复核。

| 指标       | P0 要求                                        |

| 指标         | P0 要求                                       |
| ------------ | --------------------------------------------- |
| 结果默认视图 | 只展示问题项和待复核项                        |

| 任务详情     | 能查看命中明细、失败明细、精审情况            |

## 9. 已知风险

### 9.1 规则适用性风险

死亡病例、手术病例、儿童病例、新生儿病例等必须先判断适用性。

真实测试中已经发现：

- 死亡病例专属规则如果不做适用性过滤，会误报到普通出院病历。

处理策略：

- 死亡规则必须有死亡记录或死亡事件证据才执行。
- 手术规则必须有手术相关文书或手术标志才执行。
- 儿童/新生儿规则必须有年龄或新生儿文书证据才执行。

### 9.2 bundle 证据不完整风险

如果 bundle 只是长文本拼接，而不是结构化文书集合，LLM 容易出现：

- 找不到目标文书。
- 把入院记录内容当成出院记录内容。
- 把家族史中的“配偶已故”误认为患者死亡。
- 出院诊断、入院诊断、辅助检查之间边界混乱。

处理策略：

- 继续强化文书域 routing。
- 证据上下文必须标注文书来源。
- 前端结果必须显示证据来自哪个文书。

### 9.3 LLM 非结构化输出风险

真实测试中已经出现单条精审返回非结构化 JSON 的情况。

处理策略：

- 单条精审 prompt 必须加强 JSON 输出约束。
- parse 失败后自动重试一次。
- 重试失败时标记 `uncertain`，不得直接作为不合规结论。

## 10. 后续开发落点

## 11. 当前建议结论

本阶段不建议把 170+ 规则全部作为 LLM 批量质控上线。

建议先上线：

```text
内涵质控首批规则集 v1：12 条
```

然后按以下路径推进：

```text
P0：12 条终末/病程核心内涵规则
P1：扩展到 25~30 条，加入入院和跨文书一致性
P2：手术病历专用内涵规则
P3：抗菌药物、输血、知情同意等高风险复杂规则
```

这样做的目标不是减少规则数量，而是先把最适合 LLM 的规则跑稳，建立用户信任，再逐步扩展覆盖面。
