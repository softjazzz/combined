## 3.7 样本病历必须完成的质控点

这部分不是按 rule id 管理，而是按客户现场接受度和 `sheet2` 问题事实管理。  
结合：

- `docs/sheet2_unique_issues.txt`
- `docs/sheet2_unimplemented_unique.txt`
- `apps/medqc-web/docs/0418/QC/客户样本验证与批量质控测试结果汇总.md`

可以把“样本病历必须完成”的质控点理解为一组硬门槛。  
它们很多属于程序性、时效性、缺文书、签名、闭环执行类问题。

### 3.7.1 病程与查房时效

这类问题在客户样本里出现非常高频，应视为现场联调硬门槛：

- 入院 `8` 小时内首次病程记录
- 入院 `48` 小时内主治医师查房
- 入院 `72` 小时内副主任/高级职称医师查房
- 非危重患者连续 `3` 天未完成一次病程
- 病危患者每日病程/查房记录
- 出院当天或前一天必须有上级医师查房记录
- 长住院（如超 `30` 天）讨论记录、阶段小结及时完成

### 3.7.2 手术围术期文书闭环

客户样本里，围术期文书缺失或超时是第二高频硬门槛：

- 术前小结
- 术前讨论
- 术前主刀医师查房
- 手术记录 `24` 小时内完成
- 术后首次病程及时完成
- 术后连续 `3` 天查房
- 主刀/术者签名完整
- 手术同意书签字主体合法
- 手术名称、时间、主刀、麻醉方式在多文书间一致

对当前 `0426` 样本验证来说，这一类问题不能简单等同于“operation_record 已进 bundle”。  
还必须看文书是否存在、是否有内容、是否在规定时限内完成。

### 3.7.3 会诊闭环

客户样本里会诊问题不只是“有没有会诊记录”，还包括：

- 会诊申请后是否有会诊记录
- 会诊记录后是否有请会诊执行记录
- 执行记录是否写清“已执行什么”
- 是否出现“照抄会诊意见但实际未执行”
- 是否有延迟执行、执行不完整、无复查等问题

这类问题当前和 `SC-070` 相关，但实际客户验收时往往更看重“闭环是否成立”。

### 3.7.4 转科、出院、输血、有创操作等程序性质控点

这类问题同样高频，且多数目前不在首批 LLM 内涵里：

- 转入记录 `24` 小时内完成
- 转出记录/转入记录内容完整
- 出院记录在规定时间内完成
- 提前书写出院记录
- 输血前评估、输血记录、输血后评价完整
- 输血时间与输血后评价时间一致
- 有创操作记录按模板完整书写
- 危急值记录具备报告时间、处置时间、具体处置

这些点在客户现场属于“样本病历必须过”的基础线，不应误认为是后续再做的低优先级优化。

## 3.8 质控点与 bundle 的关系

这部分是下个 Agent 快速上手样本验证的关键。

### 3.8.1 样本池里的 `bundle_status` 不是文书质量分

在 `custom_qc_sample_pool_service.py` 里，样本项有：

- `sync_status`
- `bundle_status`
- `candidate_rule_ids`
- `document_scope_labels`

其中 `bundle_status` 当前主要表示：

- `ready`
- `pending`
- `missing`

它本质上是在回答：

- 这条病历的运行态 bundle 是否已经生成，可供样本验证页和联审页消费

它不在回答：

- 文书内容是否完整
- 结构化字段是否足够
- 这条病历是否已经“通过质控”

### 3.8.2 候选规则会从 bundle 文书来源动态补充

当前服务会从：

- `public.running_record_bundle`
- `public.final_record_bundle`

解析 `source_table`，然后按 `_BUNDLE_SOURCE_TABLE_CATEGORY_MAP` 动态补候选规则。

对于当前样本验证特别重要的映射包括：

- `admission_record` -> `admission_consistency`
- `first_course_record` -> `first_course_reasoning`
- `daily_course_record` -> `daily_course_analysis`
- `consultation_record` -> `consultation_execution`
- `senior_course_record` -> `senior_round_content`
- `presurg_summary` / `presurg_discussion` / `surgery_record` / `anesthesia_record` / `surgery_safecheck_record` / `postsurg_firstcourse_record` -> `operation_record`

这意味着：

1. bundle 里的 `source_table` 会影响候选规则集合
2. 文书导入不完整，会直接影响样本池对可质控范围的判断

### 3.8.3 文书范围标签同样来自 bundle

样本验证页上显示的文书范围标签，也是从 bundle 的 `source_table` 推导出来的。

2. `bundle ready` 不等于“客户样本质控点已经可完整验证”
3. 如果底层 `cdm` 表本身是瘦表，bundle 仍可能只能产出 `empty_document`

### 3.8.6 下个 Agent 的使用建议

接手客户样本验证时，先按这个顺序理解数据：

1. 病历是否已经 `matched`
2. 样本项 `sync_status` 是否完成
3. 样本项 `bundle_status` 是否为 `ready`
4. bundle 中是否真的有对应 `source_table`
5. 对应文书是 `assembled`、`partial` 还是 `empty_document`
6. 最后再判断是规则没覆盖、装配没取对字段，还是底层同步表本身缺字段

## 3.10 联审右侧“质控问题区”前端渲染方式

代码位置：

- `apps/medqc-web/src/components/qc/QCReviewDrawer.vue`

### 3.10.1 当前不是二级分组渲染，而是扁平卡片列表

这是一个很重要的事实。  
当前联审右侧“质控问题区”并没有像左侧文书目录那样再按 `group` 做树形/折叠分组。

但在理解“右侧问题区”之前，还要先记住一个前端数据来源顺序：

1. 打开抽屉时，前端会先调用：
   - `getDefectList({ record_id })`
   - `getRecordDetail(record_id)`
2. `defectList` 的初始来源是缺陷列表接口，不是 `qc-detail`
3. `loadRecordDetail()` 成功后，如果 `detail.defects` 是数组，会再用 `detail.defects` 覆盖当前 `defectList`
4. `reviewItemList` 只来自 `detail.review_items`

这意味着：

- 右侧正式缺陷卡片并不只依赖一个接口
- 如果你看到 `defectList` 有数据，不能立刻断言它一定来自 `qc-detail`
- 如果 `qc-detail` 没有 `review_items`，右侧也不会自动从别处补一份规则级卡片

它的逻辑是：

1. 如果 `defectList.length > 0`
   - 渲染 `defectList`
   - 每条问题一张卡片

2. 否则
   - 渲染 `reviewItemList`
   - 每条问题一张卡片

也就是说：

- 右侧问题区当前是“扁平列表”
- 不是“按规则族/文书类型/严重级别分区块”

### 3.10.2 `defectList` 分支怎么渲染

当联审接口返回 `defects` 时，右侧每张卡片主要显示：

- `rule_name`
- `status`
- `description`
- `category`
- `location`

视觉上：

- 严重程度通过 `severity` 映射彩色圆点
- 状态通过 `status` 映射 badge
- 当前选中项展开 `QCReviewActionBar`

因此对旧缺陷表数据来说，右侧问题区更像：

- 缺陷清单视图

而不是：

- 结构化规则命中视图

### 3.10.3 `reviewItemList` 分支怎么渲染

当联审接口没有 `defects`，而是回退到 `review_items` 时，每张卡片主要显示：

- 标题：
  - `rule_code`
  - `rule_name`

- 状态 pill：
  - `status`

- 辅助 pill：
  - `document_type`
  - `rule_family`
  - `defect_level`

- 主体内容：
  - `findings`
  - `evidence`
  - `suggestion`
  - `confidence`

这比 `defects` 分支更接近真正的规则级判定结果。

### 3.10.4 点击问题后的联动定位

无论是 `defectList` 还是 `reviewItemList`，点击卡片后都会尝试：

1. 根据 `document_type` 优先过滤左侧文书
2. 从 `evidence / findings / rule_name` 里抽取检索文本
3. 在当前文书或全部文书分块里找高亮片段
4. 联动左侧正文滚动定位

对于 `reviewItemList`，定位质量主要受这些字段影响：

- `document_type`
- `evidence`
- `findings`

如果这些字段空或过泛，右侧点击后只能选中文书，无法准确高亮。

### 3.10.5 当前前端“分组”的真实含义

如果一定要说“分组”，当前右侧只存在两层非常弱的分组语义：

1. 数据源分组
   - `defects`
   - `review_items`

2. 卡片内部通过 pill 暗示的维度
   - `document_type`
   - `rule_family`
   - `defect_level`

但它没有真正的：

- 规则族折叠分组
- 文书类型分组
- 严重级别分组

这意味着下个 Agent 如果要优化右侧问题区，第一反应不该是“修 bug”，而应明确：

- 当前设计本来就是扁平卡片列表

### 3.11.7 读图方式

下个 Agent 如果只想快速判断链路卡在哪，按下面这套问法即可：

1. 客户原始问题有没有进样本表
   - 查 `manual_problem_sample_pool_items.manual_issue_text`

2. 这条样本有没有被分类、有没有候选规则
   - 查 `coverage_type / issue_category / candidate_rule_ids_json`

3. 这条病历有没有匹配并同步成功
   - 查 `matched_visit_id / sync_status / bundle_status`

4. 样本批量任务有没有真实跑出规则结果
   - 查 `custom_qc_batch_jobs.items_json`

5. 结果有没有被进一步物化成正式缺陷
   - 查 `qc.qc_defects`

6. 联审右侧现在到底展示的是哪一层
   - 有 `defects` 就是正式缺陷层
   - 没有 `defects`、只有 `review_items` 就是批量任务回退层

### 3.11.8 当前链路最容易误判的地方

这条链路里最容易误判的，不是接口报错，而是“把不同层的数据当成同一回事”：

1. 把 `manual_issue_text` 当成最终规则命中结果
2. 把 `candidate_rule_ids` 当成已经执行并命中的规则
3. 把 `bundle_status = ready` 当成文书内容已经完整
4. 把 `review_items` 当成已经固化进 `qc_defects`
5. 把联审右侧空问题区当成“样本没有问题”，而不是“缺陷未持久化 / 任务未回填”

所以排查顺序必须守住：

- 样本表
- 批量任务结果
- 缺陷表
- 联审接口
- 前端渲染
