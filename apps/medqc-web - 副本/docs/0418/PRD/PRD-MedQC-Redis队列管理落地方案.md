## 1. 背景与结论

### 1.1 当前背景

MedQC 已经把部分上传与批量处理改为后台执行，但当前实现仍以进程内内存为主。
这意味着：

1. 服务重启后，排队中和执行中的任务状态可能丢失。
2. 多实例部署时，任务无法在实例之间共享。
3. 大模型处理能力有限时，多个业务入口会同时争抢同一套算力。
4. 用户可以看到“已提交”，但系统缺少可恢复、可追踪、可限流的统一调度层。

### 1.2 本文档结论

在 MedQC 当前阶段，**优先采用 Redis 作为统一任务队列，PostgreSQL 作为任务状态与历史台账，是最务实且足够支撑小流量上线的方案**。

核心判断如下：

1. 当前问题的本质是“任务调度与恢复能力不足”，不是“必须上重型消息系统”。
2. Redis 足以承接当前多类质控任务的排队、优先级和并发控制。
3. PostgreSQL 可以同时承接病历业务数据和任务台账，只要任务状态写入保持克制且有边界。
4. 本期不需要直接引入 RabbitMQ / RocketMQ，避免过早增加运维复杂度。

### 1.3 为什么现在不直接上 RabbitMQ

1. 当前目标是“稳住上线”，不是建设大规模分布式调度平台。
2. 现阶段任务类型虽多，但规则仍可控，优先级和并发治理可以先在 Redis 层完成。
3. 先把任务状态、失败重试、告警和恢复闭环做扎实，比更换更重的组件更重要。

## 2. 产品目标

### 2.1 目标

建设 MedQC 统一队列管理能力，支撑以下任务在同一调度体系下运行：

1. 运行病历质控
2. 终末病历质控
3. AI 生成病案首页
4. AI 生成结算清单
5. DRG 预入组与批量处理
6. 智能上传后的后台解析任务

系统应满足：

1. 提交即返回，不再让用户长时间等待。
2. 所有任务可查询、可取消、可追踪、可恢复。
3. 当大模型算力有限时，系统能自动排队，不发生任务互相挤爆。
4. 多类任务可按优先级、公平性和并发上限受控执行。
5. 服务重启后，任务状态不丢失，系统能识别哪些任务需要恢复或重试。

### 2.2 非目标

1. 本期不做跨机房多活。
2. 本期不做复杂工作流编排平台。
3. 本期不把所有运行日志写入 PostgreSQL。
4. 本期不引入 Kafka、RabbitMQ、RocketMQ 等更重方案作为首发形态。

## 3. 适用范围

### 3.1 纳入统一队列的任务

| 任务类型         | 来源入口                  | 是否占用大模型能力 | 是否必须排队 |
| ---------------- | ------------------------- | ------------------ | ------------ |
| 运行病历质控     | 工作台病历详情            | 是                 | 是           |
| 终末病历质控     | 工作台病历详情 / 批量触发 | 是                 | 是           |
| AI 生成病案首页  | 工作台详情页              | 是                 | 是           |
| AI 生成结算清单  | 工作台详情页              | 是                 | 是           |
| DRG 批量上传处理 | DRG 模块                  | 否 / 部分占用      | 是           |
| 智能上传后台解析 | 上传入口                  | 否 / 部分占用      | 是           |

### 3.2 暂不纳入统一队列的内容

1. 普通只读查询接口
2. 不依赖大模型、且执行时间极短的本地计算
3. 单纯的页面刷新与状态查询请求

## 4. 核心设计原则

### 4.1 先分工，再扩展

本方案采用“三层分工”：

1. Redis：负责排队、抢占、并发闸门和优先级控制。
2. PostgreSQL：负责任务状态、历史记录、失败原因和查询台账。
3. 文件存储 / 对象存储：负责保存大文件或大结果，不把大内容堆进数据库。

### 4.2 Redis 与 PostgreSQL 的职责边界

#### Redis 负责什么

1. 待执行任务队列
2. 不同优先级的任务分发
3. 并发计数与全局闸门
4. 某一类任务的执行配额
5. 短期去重锁、运行锁、取消信号

#### PostgreSQL 负责什么

1. 任务基本信息
2. 当前状态
3. 状态变更时间
4. 发起人、业务对象、任务结果摘要
5. 失败原因、重试次数、取消原因
6. 审计记录与历史查询

#### 明确不建议放进 PostgreSQL 的内容

1. 频繁变化的临时队列顺序
2. 每秒级心跳明细
3. 详细的大模型原始响应全文
4. 大文件本体

### 4.3 为什么 PostgreSQL 扛得住

1. 病历是业务主数据，任务台账只是少量附加写入。
2. 每个任务只在关键节点写状态，如“已接收、处理中、成功、失败”，不是持续高频刷写。
3. 只要任务记录独立成表、查询有限制、历史有归档，当前阶段 PostgreSQL 足以支撑。

## 5. 总体方案

### 5.1 高层架构

```text
用户操作
  -> API 接口
    -> 任务受理层
      -> PostgreSQL 创建任务台账
      -> Redis 入队
        -> Worker 拉取任务
          -> 执行质控 / 生成 / 解析 / 批处理
            -> PostgreSQL 更新状态与结果摘要
              -> 前端查询任务进度与结果
```

### 5.2 设计目标

系统需要同时解决三类问题：

1. 谁先执行：通过优先级和配额控制。
2. 一次能执行多少：通过全局并发和分类并发限制。
3. 出问题如何恢复：通过 PostgreSQL 状态台账和重试规则完成。

### 5.3 默认处理原则

1. API 提交成功后，只返回任务编号和当前状态。
2. 前端轮询或订阅任务状态，不等待长任务同步完成。
3. Worker 只从 Redis 拿任务，不自行绕过队列直连模型服务。
4. 任务状态以 PostgreSQL 为准，Redis 仅作为调度媒介。

## 6. 任务模型设计

### 6.1 统一任务类型

建议统一任务类型字段：

1. `running_record_qc`：运行病历质控
2. `final_record_qc`：终末病历质控
3. `frontpage_generate`：病案首页生成
4. `settlement_generate`：结算清单生成
5. `drg_batch_process`：DRG 批量处理
6. `smart_upload_parse`：智能上传解析

### 6.2 优先级建议

按业务价值和紧急程度，默认优先级如下：

| 优先级 | 任务类型     | 说明                           |
| ------ | ------------ | ------------------------------ |
| P1     | 运行病历质控 | 直接影响在院问题发现，优先保障 |
| P1     | 终末病历质控 | 影响出院归档质量，优先保障     |
| P2     | 病案首页生成 | 面向已出院病历，可排队处理     |
| P2     | 结算清单生成 | 面向已出院病历，可排队处理     |
| P3     | DRG 批量处理 | 允许批量排队，避免挤占实时任务 |
| P3     | 智能上传解析 | 可后台慢慢消化                 |

### 6.3 公平性规则

1. 不允许某一类批量任务长期占满全部处理能力。
2. 高优先级任务保留固定执行名额。
3. 低优先级任务在高峰期允许延后执行。
4. 同一用户或同一科室的批量任务需要设置数量上限，避免霸占资源。

## 7. 状态管理设计

### 7.1 任务状态

统一使用以下状态：

1. `accepted`：已受理
2. `queued`：排队中
3. `running`：处理中
4. `succeeded`：已完成
5. `failed`：已失败
6. `retry_waiting`：等待重试
7. `cancelled`：已取消
8. `partial_succeeded`：部分完成

### 7.2 状态存储原则

1. PostgreSQL 是唯一状态真相来源。
2. Redis 中可以保存短期运行标记，但不能作为最终结果依据。
3. 前端展示、管理台查询、告警判断全部以 PostgreSQL 状态为准。

### 7.3 服务重启后的恢复规则

1. `queued` 状态任务：重新入队。
2. `running` 状态任务：按超时阈值判定是否回收并重试。
3. `retry_waiting` 状态任务：到期后重新进入 Redis。
4. `succeeded / failed / cancelled`：不再恢复执行。

## 8. 调度规则

### 8.1 全局闸门

为大模型能力设置总闸门，限制同一时刻最大处理数。

示例原则：

1. 总执行位固定，如 3 到 5 个。
2. 任一任务进入执行前，都必须先拿到执行位。
3. 没拿到执行位的任务继续留在队列中等待。

### 8.2 分类配额

在总闸门下，再给不同任务类型设置配额。

建议首版：

1. 运行病历质控：保底配额最高
2. 终末病历质控：与运行病历同级或略低
3. 首页生成 / 结算生成：中优先级
4. DRG 批量 / 智能上传：低优先级，仅占用剩余能力

### 8.3 峰值保护

当排队积压明显时，系统应自动采取以下策略：

1. 暂停低优先级新任务进入执行位
2. 降低批量任务并发
3. 对新提交任务直接提示“已进入排队”
4. 必要时限制同一用户的批量提交数量

## 9. 失败处理与重试

### 9.1 失败分类

#### 可重试失败

1. 大模型超时
2. 短暂网络异常
3. 服务限流
4. 临时资源不足

#### 不可重试失败

1. 参数错误
2. 权限错误
3. 文件格式错误
4. 业务前置条件不满足

### 9.2 重试策略

1. 自动重试次数有限，例如 2 到 3 次。
2. 每次重试之间要拉开间隔，避免失败风暴。
3. 超过上限后，任务进入失败终态，并保留失败原因。

### 9.3 取消策略

1. 排队中的任务允许直接取消。
2. 运行中的任务可标记取消，执行单元在安全点中止。
3. 已完成任务不可取消，只能重新提交新任务。

## 10. 数据留存设计

### 10.1 PostgreSQL 中至少保存的内容

建议建立统一任务台账表，至少包含：

1. 任务编号
2. 任务类型
3. 业务对象编号
4. 发起人
5. 当前状态
6. 优先级
7. 提交时间
8. 开始时间
9. 完成时间
10. 重试次数
11. 失败原因
12. 结果摘要
13. 取消原因
14. 最后更新时间

### 10.2 建议建立的附属记录

1. 任务事件表：记录关键状态变化
2. 任务结果摘要表：存简化结果，避免主表过大
3. 任务归档策略：对老任务按月清理或归档

### 10.3 大结果处理原则

1. 大文本、大文件不要直接塞进任务主表。
2. 结果摘要保留在 PostgreSQL。
3. 全量文件或大对象保留在文件系统或对象存储，并在 PostgreSQL 中留引用地址。

## 11. 接口与交互要求

### 11.1 用户可见行为

队列管理上线后，用户侧要有明确预期：

1. 点击后立即得到“已提交”反馈
2. 可以查看排队中、处理中、已完成、失败
3. 可看到失败原因的简要说明
4. 可对排队中任务发起取消
5. 对重复提交要给出明确提示，而不是生成大量重复任务

### 11.2 统一接口能力

本期至少需要统一以下能力：

1. 创建任务
2. 查询任务详情
3. 查询任务列表
4. 查询任务结果摘要
5. 取消任务
6. 对失败任务重新发起

### 11.3 前端要求

1. 所有长任务统一走“提交任务 + 查状态”模式。
2. 不允许继续保留“接口一直等到处理完成”的页面体验。
3. 任务列表需要支持按状态、类型、时间和发起人筛选。

## 12. 运维与告警要求

### 12.1 必须观察的指标

1. 当前排队任务数
2. 各任务类型等待时长
3. 当前执行中任务数
4. 失败率
5. 重试率
6. 被取消任务数
7. 大模型调用超时率
8. PostgreSQL 任务表写入延迟

### 12.2 告警建议

1. 高优先级任务等待时间持续过长
2. 失败率连续升高
3. 重试率异常升高
4. Redis 不可用
5. PostgreSQL 任务台账写入失败
6. 队列积压超过阈值

### 12.3 故障策略

1. Redis 故障时，系统停止受理新的长任务，避免进入不可控状态。
2. PostgreSQL 故障时，任务提交直接失败，不允许只写 Redis 不留台账。
3. 恢复后按 PostgreSQL 状态重建必要队列。

## 13. 容量判断与适用边界

### 13.1 当前阶段判断

对 MedQC 当前目标而言，Redis + PostgreSQL 方案可以支撑：

1. 内网或受控生产环境
2. 小流量到中低流量任务规模
3. 多种质控任务共享同一套大模型能力
4. 单系统内部的统一任务调度

### 13.2 何时需要升级到更重方案

当出现以下情况时，再评估 RabbitMQ / RocketMQ：

1. 任务量持续大幅上涨
2. 多个系统需要共享同一消息平台
3. 任务流转规则明显复杂化
4. 对极强的消息可靠投递能力有更高要求
5. 需要更细粒度的跨系统解耦

### 13.3 当前不升级的理由

1. 现在最重要的是把“能恢复、能排队、能追踪”补齐。
2. 过早引入更重队列，会提高部署、维护和排障成本。
3. 当前阶段更适合先把业务规则和容量边界跑清楚。

## 14. 分阶段实施计划

### 14.1 第一阶段

先完成统一台账和 Redis 入队：

1. 为现有长任务建立统一任务表
2. 提交任务时先写 PostgreSQL，再写 Redis
3. 前端统一改为任务状态查询模式
4. 停止继续扩散进程内内存队列

### 14.2 第二阶段

补齐调度治理：

1. 增加优先级队列
2. 增加分类并发配额
3. 增加失败重试
4. 增加取消与恢复逻辑
5. 增加队列与任务告警

### 14.3 第三阶段

补齐生产化能力：

1. 增加归档策略
2. 增加管理视图
3. 增加容量报表
4. 明确升级到更重消息系统的触发条件

## 15. 验收标准

### 15.1 功能验收

1. 所有长任务提交后均返回任务编号。
2. 服务重启后，未完成任务状态不丢失。
3. 前端可查询任务当前状态与结果摘要。
4. 同一时刻不会超过设定的大模型并发上限。
5. 低优先级任务不会长期挤占高优先级任务执行位。

### 15.2 稳定性验收

1. Redis 短时故障不会导致任务台账丢失。
2. PostgreSQL 恢复后可重建队列。
3. 高峰期系统能返回“排队中”，而不是整体卡死。
4. 重复提交不会无限生成重复任务。

### 15.3 运维验收

1. 可以看到当前排队量和执行量。
2. 可以定位失败原因。
3. 可以统计不同任务类型的等待时间和失败率。
4. 可以手动处理失败任务。

---

## 16. 一句话决策

**MedQC 当前阶段采用“Redis 管排队，PostgreSQL 管状态”的队列方案，可以满足小规模上线需求；真正需要优先解决的不是更换更重组件，而是先把任务状态持久化、统一调度和恢复机制做好。**
