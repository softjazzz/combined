# PRD 文档落盘方案：病案质控管理员端

## Summary

在 `docs/` 下新增正式 PRD，文件名建议为 `docs/PRD-病案质控管理员端.md`。这份文档只聚焦**病案首页质控管理员端**，不再包含医保结算清单质控，也不包含 DRG/金额影响相关能力。

PRD 的定位固定为：

- 现有 `病案工作台` 保留，继续服务医生和单病例演示
- 新增 `病案质控管理台`，服务病案质控员/病案科管理员
- 管理员端只解决“首页质控批量审核、问题管理、整改闭环”三件事

## PRD 内容结构

### 1. 背景与问题定义

文档开头明确写清：

- 当前入口是 `病案工作台 -> 打开单病历 -> 运行首页质控`
- 该设计最初目的是功能演示，证明系统具备首页质控能力
- 该路径偏临床医生视角，适合单病例查看和操作
- 对病案质控管理员不适用，主要问题是：
  - 逐病历进入，批量效率低
  - 无法先看风险队列再集中处理
  - 问题没有统一列表化管理
  - 整改、复检、审核闭环弱

这里引用竞品图的结论：

- 竞品的核心不是“先进病历再点质控”
- 而是“运行病历列表 + 缺陷筛选 + 列表审核 + 详情联审”
- 说明管理员需要的是流程化后台，而不是病例详情页增强版

### 2. 产品目标与设计原则

PRD 固定定义以下目标：

- 支持病案质控员按时间、科室、病区批量运行首页质控
- 支持管理员优先处理严重缺陷和高风险病历
- 支持首页质控问题统一管理、审核、整改、复检
- 支持从问题列表快速进入单病历联审

设计原则固定为：

- `任务优先`，不是 `病例优先`
- `问题池优先`，不是 `详情页优先`
- `管理员独立入口`，不是继续堆叠在医生工作台中
- `保留现有工作台`，不破坏原有演示和医生侧流程

### 3. 目标用户与使用场景

用户角色固定分两类：

- 病案质控员/病案科管理员：主用户，使用新管理台
- 临床医生/个案处理人员：继续使用现有病案工作台

核心场景写为：

- 每日批量质控出院病历首页
- 按科室集中审核首页问题
- 按缺陷等级、状态、责任科室优先处理
- 派发整改给责任科室并跟踪复检结果

### 4. 产品方案

产品架构写成双入口：

- 入口一：现有 `病案工作台`
  - 用于单病历查看、个案处理、演示流程
- 入口二：新增 `病案质控管理台`
  - 用于批量运行、列表审核、问题管理、整改闭环

管理员端页面布局固定为三层：

- 顶部：筛选区 + 批量操作区
- 中部：`运行病历列表 / 首页问题池 / 整改闭环` 三个主视图
- 右侧或下方：单病历联审详情区

管理员端主视图固定定义如下：

- `运行病历列表`
  - 面向病历任务
  - 看每份病历的首页问题数、风险等级、状态
- `首页问题池`
  - 面向问题处理
  - 首页质控问题按统一结构展示
- `整改闭环`
  - 面向状态流转
  - 跟踪待整改、待复检、已关闭问题

### 5. 页面与交互要求

PRD 中明确页面字段，不留给实现者二次决策。

顶部筛选区：

- 时间范围
- 科室
- 病区
- 出院状态
- 质控状态
- 问题状态
- 关键词搜索：住院号 / 病案号 / 患者姓名

批量操作：

- `批量质控`
- `重新质控`
- `导出问题`
- `批量分派`
- `批量通过`

运行病历列表字段：

- 住院号
- 病案号
- 患者姓名
- 科室
- 出院日期
- 首页问题数
- 缺陷等级汇总
- 风险等级
- 当前状态

首页问题池字段：

- 问题ID
- 病历标识
- 规则名称
- 问题类型
- 缺陷等级
- 风险等级
- 责任科室
- 责任人
- 整改状态
- 审核状态

联审详情区布局：

- 左侧：文书导航、病案首页导航
- 中间：原始病历正文或结构化首页
- 右侧：问题卡片列表，支持证据高亮、定位、审核动作

问题操作固定为：

- `确认问题`
- `误报`
- `派发整改`
- `退回复核`
- `审核通过`

### 6. 病案首页质控范围

PRD 里只保留首页质控，不再写结算清单质控。

首页质控覆盖范围固定为：

- 字段完整性
- 字段一致性
- 编码规范性
- 基础逻辑校验
- 首页与病历正文证据一致性

问题池仅处理首页质控问题，不再出现以下内容：

- 医保结算清单问题
- DRG 影响标记
- 金额影响标记
- 首页/结算来源切换

### 7. 数据与接口要求

PRD 中新增“管理员端数据接口”章节，只包含首页质控所需接口：

- 病历任务列表接口
- 批量首页质控任务创建接口
- 首页问题池查询接口
- 单病历联审详情接口
- 问题动作接口
- 管理员统计接口

统一问题模型字段固定为：

- `case_id`
- `rule_code`
- `severity`
- `risk_level`
- `status`
- `review_status`
- `assignee`
- `evidence_anchor`

不再写以下字段：

- `source_module`
- `drg_impact`
- `amount_impact`

### 8. MVP 范围

第一阶段只做：

- 管理员独立入口
- 批量首页质控任务
- 运行病历列表
- 首页问题池
- 联审详情
- 整改闭环基础动作

明确不纳入第一阶段：

- 医保结算清单质控
- DRG 相关联动
- 金额影响分析
- 高级调度编排
- 大屏和复杂统计

### 9. 验收标准

PRD 必须写可验收条目：

- 能按筛选条件批量运行首页质控
- 能在首页问题池中查看和筛选问题
- 能从问题跳转到联审详情并定位证据
- 能对问题执行确认、误报、整改、复检、通过
- 能区分管理员端与医生端入口，不影响现有病案工作台

## 补充章节（细化）

### 补充 A：问题状态机

问题（缺陷）的完整生命周期状态流转如下：

```
                  ┌──────────────┐
                  │   pending    │  ← 质控引擎生成
                  └──────┬───────┘
                         │
               ┌─────────┼─────────┐
               ▼                   ▼
      ┌────────────┐      ┌───────────────┐
      │  confirmed │      │  false_alarm   │  ← 管理员标记误报
      └─────┬──────┘      └───────────────┘
            │                     （终态）
            ▼
   ┌─────────────────┐
   │ remediation_sent │  ← 派发整改
   └────────┬────────┘
            │
            ▼
   ┌─────────────────┐
   │   submitted     │  ← 责任科室提交整改
   └────────┬────────┘
            │
      ┌─────┼─────┐
      ▼           ▼
┌──────────┐ ┌──────────┐
│ approved │ │ rejected │  ← 管理员审核
└──────────┘ └─────┬────┘
  （终态）         │
                   ▼
          ┌─────────────────┐
          │ remediation_sent│  ← 退回后重新整改
          └─────────────────┘
```

状态枚举值对应 `qc_defects.status` 字段：

| 状态       | 枚举值             | 说明                     |
| ---------- | ------------------ | ------------------------ |
| 待处理     | `pending`          | 引擎生成初始状态         |
| 已确认     | `confirmed`        | 管理员确认问题存在       |
| 误报       | `false_alarm`      | 管理员标记为误报（终态） |
| 已派发整改 | `remediation_sent` | 已分派给责任科室         |
| 已提交整改 | `submitted`        | 责任人提交整改材料       |
| 审核通过   | `approved`         | 管理员审核通过（终态）   |
| 审核驳回   | `rejected`         | 管理员驳回，退回重新整改 |

操作权限：

- **管理员**可执行：确认、误报、派发整改、审核通过、审核驳回
- **临床科室**可执行：提交整改
- 误报撤销：一期 **不支持**，需新建问题重新处理

### 补充 B：批量质控执行语义

**引擎调用**：

- 批量质控调用现有 `四川146条` 规则引擎（首页相关子集），不另建引擎
- 引擎调用入口与"病案工作台 → 运行首页质控"共享同一后端 service

**执行模式**：

- **异步任务**：管理员点击"批量质控"后，后端创建 `qc_tasks` 任务记录，通过后台队列逐条运行
- 前端显示任务进度条（轮询 `qc_tasks.progress` 字段）
- 单次批量上限建议 **500 条**，超出提示分批执行

**结果写入策略**：

- 每条病历生成一条 `qc_results` 记录 + N 条 `qc_defects` 记录
- **重新质控**：先软删除该病历的旧 `qc_results` 和关联 `qc_defects`（保留历史快照），再写入新结果
- 不影响已有的 `qc_appeals` 和 `qc_remediation_tasks`（独立生命周期）

**超时与错误处理**：

- 单条病历质控超过 30 秒视为超时，标记 `qc_task_records.status = 'failed'`
- 失败不阻塞其余病历，任务完成后在报告中汇总失败列表

### 补充 C：PRD 概念与现有数据模型映射

PRD 中的概念直接复用已有 ORM 表，**不另建新表**：

| PRD 概念     | 对应表                 | 对应模型类          | 说明                         |
| ------------ | ---------------------- | ------------------- | ---------------------------- |
| 运行病历列表 | `qc_task_records`      | `QCTaskRecord`      | 每条记录 = 一份病历的分配    |
| 批量质控任务 | `qc_tasks`             | `QCTask`            | 每次批量操作 = 一条任务      |
| 首页问题池   | `qc_defects`           | `QCDefect`          | 所有缺陷的统一池             |
| 质控结果     | `qc_results`           | `QCResultBiz`       | 每份病历的评分汇总           |
| 整改闭环     | `qc_remediation_tasks` | `QCRemediationTask` | 派发整改 → 提交 → 审核       |
| 问题操作历史 | `qc_defect_history`    | `QCDefectHistory`   | 每次状态变更留痕             |
| 申诉         | `qc_appeals`           | `QCAppeal`          | 一期不在管理台处理，保留入口 |

PRD 中的 **统一问题模型** 字段到 `qc_defects` 列的映射：

| PRD 字段          | DB 列                                   | 说明                             |
| ----------------- | --------------------------------------- | -------------------------------- |
| `case_id`         | `record_id`                             | 病历标识                         |
| `rule_code`       | `rule_code`                             | 规则编码                         |
| `severity`        | `severity`                              | warning/error/info               |
| `risk_level`      | 由 `severity` 派生                      | 前端计算，不另存                 |
| `status`          | `status`                                | 见补充 A 状态机                  |
| `review_status`   | 由 `status` 派生                        | `approved`/`rejected` 即审核状态 |
| `assignee`        | 关联 `qc_remediation_tasks.assignee_id` | 通过整改任务关联                 |
| `evidence_anchor` | `location` + `evidence`                 | 证据定位                         |

### 补充 D：权限与数据范围

**一期权限方案**：路由级分离 + 角色过滤，不引入 RBAC 框架。

| 角色           | 入口           | 数据范围     | 操作权限        |
| -------------- | -------------- | ------------ | --------------- |
| 病案质控管理员 | 病案质控管理台 | 全院所有科室 | 全操作          |
| 科室质控员     | 病案质控管理台 | 仅本科室     | 查看 + 整改提交 |
| 临床医生       | 病案工作台     | 仅个人病历   | 查看 + 提交整改 |

实现方式：

- 前端：菜单路由通过 `meta.roles` 控制可见性
- 后端：API 通过 `current_user.role` + `current_user.department` 过滤查询范围
- 一期无需引入 Casbin，用现有 `sys_users.role` 字段即可
