# CDM建模缺陷复盘与整改建议

更新时间：2026-04-27  
适用项目：`D:\LLM\LX888` / `apps/medqc-web`

## 1. 结论摘要

本次 `0426` 样本联审问题，表面上看是：

- 病历联审页面部分手术相关单据为空
- 客户机本地 PG 与本机联审展示不一致
- 多轮排查需要逐层确认源库、客户机本地 PG、导出 CSV、本机 PG、bundle、前端

但最终根因不是前端渲染问题，也不是一次性的同步异常，而是：

**项目在 `cdm` 建模阶段，把多张结构化文书表错误地“瘦身”为只保留元数据和 `record_content` 的简化表。**

这是一类建模缺陷，不是单点 bug。

本次已经确认的典型受影响表包括：

1. `anesthesia_record`
2. `presurg_summary`
3. `surgery_safecheck_record`

这些表在源库具有大量结构化字段，但在本地 `cdm` 模型和客户机本地 PG 表结构中被主动裁剪，最终导致：

1. 同步链路无法完整落库
2. 导出快照天然丢字段
3. 联审装配缺少可用内容
4. 页面只能看到空壳文书
5. 排查时会误导为“前端问题”“bundle 问题”“导出问题”

## 2. 问题定性

## 2.1 不是“少同步几个字段”

如果只是同步配置偶发漏字段，通常表现为：

- 源库有列
- 本地表也有列
- 但某次同步没写进去

这类问题可以通过补同步 SQL 或重跑任务修复。

本次不是这种情况。

本次确认的是：

1. 源库字段存在
2. 客户机本地 PG 同名 `cdm` 表没有这些列
3. 仓库中的 ORM 模型定义也没有这些列

因此这是：

**建模先天不完整，导致同步能力上限被直接锁死。**

## 2.2 不是“展示层暂时没做完”

如果展示层没做完，通常表现为：

- 数据库里已有字段
- bundle 可取到内容
- 页面只是没渲染

而本次问题不是这样。

对多张手术相关文书而言：

- 客户机本地 PG 的 `cdm` 表就没有字段
- 本机导入后也不可能恢复
- 页面空只是数据真实情况的反映

所以：

**不能把这个问题归咎为前端欠缺或联审装配欠缺。**

## 2.3 是“错误的数据承载决策”

本项目以 `cdm` 作为标准化病历承载层。  
按正常数据建模原则：

1. `cdm` 层应尽量完整承接源侧标准字段
2. 展示层可以按需裁剪
3. 规则引擎、联审、导出、对账都应以 `cdm` 为可信底座

但当前实际做法是：

- 在 `cdm` 建表时，预先把大量“暂时看起来用不上”的结构化字段砍掉

这相当于：

**在存储层做了展示层式的裁剪。**

这是设计边界错误。

## 3. 典型案例

## 3.1 `anesthesia_record`

### 源库特征

源库 `public.anesthesia_record` 包含大量结构化字段，例如：

- 麻醉方式
- 麻醉前血压 / 体温 / 心率 / 呼吸 / 血氧
- ASA 分级
- 手术开始 / 结束时间
- 麻醉开始 / 结束时间
- 麻醉管理措施
- 呼吸管理
- 麻醉总结
- 麻醉医生签名

### 本地 `cdm` 特征

客户机本地 PG 和当前项目模型中，该表只保留了：

- 基础身份字段
- 文书元数据
- `record_content`

### 直接后果

HIS 页面可以展示：

- 麻醉前生命体征
- 麻醉方式
- 麻醉开始/结束时间

但联审页面只能看到：

- 标题
- 更新时间
- 空正文

这不是展示问题，而是承载层被阉割。

## 3.2 `presurg_summary`

### 源库特征

源库 `public.presurg_summary` 包含：

- 科室 / 病房 / 床号
- 术前指征
- 计划手术名称 / 时间
- 计划麻醉方式
- 手术要点
- 术前准备
- 术后处理
- 可能并发症
- 签名信息
- 备注 / note

### 本地 `cdm` 特征

客户机本地 PG 和项目模型中，大量字段被砍掉，只剩：

- 元数据
- `record_content`

### 直接后果

例如 `document_id = 4536585||18` 的术前小结：

- `record_content` 是空
- 但源库实际在其他结构化字段里有完整内容

结果就是：

- 源库看起来有内容
- 联审页看起来像空文书

这类问题极具误导性。

## 3.3 `surgery_safecheck_record`

### 源库特征

源库中该表包含：

- 手术方式
- 主刀医生
- 麻醉方式
- 麻醉医生
- 手术护士
- 三方核查声明
- 手术开始时间

### 本地 `cdm` 特征

客户机本地 PG 和项目模型中，以上字段都不存在，仅剩：

- 标题壳
- 空 `record_content`

### 直接后果

联审页中的“手术安全核查记录”无法展示真正核查内容。

## 4. 为什么这是严重问题

## 4.1 它会系统性误导排查

当 `cdm` 层建残后，任何上层问题都会表现成多个假象：

1. 页面好像没渲染
2. bundle 好像没装配
3. CSV 好像没导全
4. 本机导入好像有问题
5. 客户机本地 PG 好像丢数据

最终要花大量时间逐层排除，才能追到：

- 原来是最底层表结构先天不完整

这就是本次排查耗时的真正来源。

## 4.2 它破坏了 `cdm` 作为可信底座的意义

如果 `cdm` 不是完整承载层，而只是“只保留少量字段的临时视图”，那下列能力都会持续不稳定：

1. 联审展示
2. 规则引擎判断
3. 数据导出
4. 快照复现
5. 线上问题回放
6. 样本验收

也就是说，影响不只是一页 UI，而是整个病历质控链路的可信度。

## 4.3 它使后续功能开发建立在错误地基上

如果继续在这种瘦表基础上叠功能，会发生：

1. 前端反复做空态兼容
2. bundle 逻辑不断特判
3. 规则开发不断误判“文书不存在”
4. 研发误以为数据就是没有

这会持续制造技术债。

## 5. 根本性问题在哪里

## 5.1 建模阶段把“暂时不用”误当成“永远不用”

这次暴露的问题，本质上是一个常见但严重的建模误区：

> 为了简化开发或减少表字段，在建表阶段就把暂时没有直接展示需求的结构化字段删掉。

这个决策在短期看似能省事，长期会带来更高成本，因为：

1. 数据一旦没落库，后面所有层都拿不到
2. 补字段会牵涉同步、迁移、展示、测试全链路返工
3. 排查成本远高于一开始多建几个字段

## 5.2 存储层和展示层职责混淆

正确职责边界应当是：

- 存储层：完整承载标准数据
- 装配层：决定如何拼装
- 展示层：决定如何呈现

当前做法实际上变成了：

- 存储层：提前按展示需要裁剪

这会让任何未来新增展示/规则能力都被底层反向卡住。

## 5.3 缺少“字段裁剪影响评估”

如果确实要裁剪字段，至少应该在设计阶段明确：

1. 哪些字段被删
2. 为什么删
3. 会影响哪些业务场景
4. 是否仍能支持联审 / 规则 / 导出 / 回放

本次现象表明，当初并没有做足这类评估，或者评估结论没有被严格执行。

## 6. 整改建议

整改必须按层做，不能只补前端。

## 6.1 P0：恢复 `cdm` 表完整承载能力

优先表：

1. `anesthesia_record`
2. `presurg_summary`
3. `surgery_safecheck_record`

要求：

1. 补齐源库关键结构化字段到本地 `cdm` 表
2. 更新 ORM 模型定义
3. 更新迁移或初始化逻辑

如果不做这一步，后续任何展示修补都只是临时方案。

## 6.2 P0：修正同步映射

需要检查和修复：

- `web.anesthesia_record`
- `web.presurg_summary`
- `web.surgery_safecheck_record`

以及项目内 ETL / sync 配置，确保：

- 源库字段 -> 本地 `cdm` 字段

能真实同步，而不是只保留 `record_content`。

## 6.3 P1：补联审装配

在字段真正进入 `cdm` 表后，再补：

- `assembler.py`
- 对应 bundle 装配
- 结构化字段中文标签

建议按表专项实现，不要继续依赖 `record_content` 兜底。

## 6.4 P1：补自动化校验

为了避免将来再发生“源库有字段，本地表没列”的问题，建议加入自动检查：

1. 源库字段清单快照
2. `cdm` 模型字段清单
3. 同步后本地表字段清单
4. 三者做差异校验

至少对核心文书表启用此校验。

## 6.5 P2：明确 CDM 建模原则

建议形成一条明确规范：

> 对于进入 `cdm` 的标准化病历表，默认应完整承接源侧标准字段；如需裁剪，必须有设计文档、字段清单和影响评估，不允许口头或隐式裁剪。

否则相同问题会在其他表上反复出现。

## 7. 建议的任务拆分

可以按以下 4 个任务拆给开发：

### 任务 1：补表结构

- 修改 `cdm` ORM 模型
- 修改建表/迁移逻辑
- 补三张表缺失列

### 任务 2：补同步链路

- 检查 `web.*` 取数字段
- 检查 ETL 落库映射
- 重新同步客户机本地 PG

### 任务 3：补联审装配

- 结构化拼接 `anesthesia_record`
- 结构化拼接 `presurg_summary`
- 结构化拼接 `surgery_safecheck_record`

### 任务 4：补回归校验

- 样本病历对比源库/本地 PG/联审展示
- 字段差集检查
- 页面联审人工验收

## 8. 对负责人可直接复述的结论

> 这次问题不是普通同步 bug，而是 `cdm` 建模阶段把多张结构化文书表错误瘦身，导致本地表结构无法承载源库已有字段。前端显示为空只是结果，不是根因。真正要修的是：恢复本地 `cdm` 表结构完整性，补同步映射，再补联审装配。否则后续在手术、麻醉、讨论类文书上还会持续出现“源库有内容、本地看起来没内容”的误判和排查成本。

## 9. 本次复盘的核心教训

一句话总结：

**不要在存储层替展示层做裁剪。**

`cdm` 的价值是作为可信、可复用、可回放的数据底座。  
一旦在建模阶段自作主张砍掉结构化字段，后面所有上层能力都会被连带拖垮。
