# AGENTS Rules For Codex

## 范围与基本偏好

- 默认范围是本仓库，前端重点为 `apps/medqc-web`。
- 使用中文沟通、注释和 commit message；文本统一 UTF-8 无 BOM、LF。

## 协作、证据与验收

- 主协调 Agent 对需求、架构和最终验收负责。委派前必须亲自核对业务目标、真实调用链、数据/测试证据，并写明：待验证根因、最小改动范围、失败语义、验收指标和剩余风险。
- 实现 Agent 只按明确的文件范围和验收标准执行，不得扩大范围或改变架构；测试/审查 Agent 负责独立证伪。多 Agent 只并发处理边界清晰且相互独立的工作。
- 子代理的因果结论、基线质疑和完成声明，主协调 Agent 必须用代码路径、保存产物或复现实验独立验证后才能引用；假设被推翻时须留痕更正。
- 主协调 Agent 必须亲自审查关键 diff、模型输入、状态映射、调用量、性能和真实病例结果。测试数量或 `READY_FOR_REVIEW` 不能代替业务验收。
- 默认采用小闭环：1–2 个业务点 → 真实问题 → 最小修复 → 聚焦测试 → 真实输入复核 → 性能/准确性对比。达到验收标准后提交并停止扩展；新范围需另立任务。

## 架构与防止过度工程化

- 先证明真实问题再设计抽象。没有至少两个已发生的独立问题、替代方案和增量指标，不新增通用基类、注册表、依赖注入、全局 Store、配置开关或学习型/LLM 层。
- 每个业务事实只能有一个权威所有者和一条主资料链。规则执行器判定；Renderer 组织文案；Finalizer 校验补缺；Aggregator 装配排序；Envelope、数据库、API 与前端原样搬运，不得在后续层重新解释状态、原因码或事实。
- 普通新规则应由“规则执行器 + 对应测试”完成。若必须同时修改任务入口、公共编排、聚合器、保存、API 和前端，应先证明缺失合同或重复所有者，再单独评审公共边界。
- 兼容逻辑隔离在旧入口；新主链不得依赖旧 payload、旧聚合或旧执行器。测试优先比较同一输入下的状态、原因码、关键事实、证据定位、LLM 调用/Token 与耗时。
- Vue 文件达到 1200 行、Python 文件达到 2000 行，或计划向单文件新增 200 行以上生产代码时，任务方案必须说明为何不能使用现有模块或新的完整职责模块。
- 拆分必须迁出完整、可独立测试的职责，原则上不少于 250 行；不得创建转发壳或逐函数碎片。结构拆分不得同时改变业务行为，需报告代码量变化、接口变化和行为等价证据。
- Digest/SHA 仅用于发布完整性、漂移、缓存或精确回放；优先复用已有 digest，不给普通 DTO、Prompt、trace 或 POC 重复加哈希，也不在客户界面展示 SHA。

## LX0609 质控硬约束

- 先按规则号确定权威来源：`docs/0602/luxian_0609_formal_rule_catalog.csv` 覆盖 001–049 且定义允许状态；`docs/0602/泸县0609质控点-业务标准基线-v1.md` 覆盖 001–075；《LX0609-我方口径标准汇编》选择性覆盖；077 等扩展规则只使用对应扩展证明。禁止跨区间套用口径。
- 结果状态必须属于该规则的允许集合；运行时词表不等于单规则合同。050–077 未定义允许集合时须先补合同。`uncertain`、`technical_error` 不得进入交付结果。
- “零回退”任务必须列出保护集合（已验收记录及台账中 `compliant`/`non_compliant` 的记录），并标明每个基线对应的代码/产物时点；不得只依赖可能为空的 `closure_status`，也不得使用早于前序改动的基线。
- 同一事实的客户可见范围必须唯一。发现不同读取路径口径不一致时，按接口边界收敛，禁止单侧扩大可见范围。
- `needs_review`/“未关闭”只表示尚未复核，不代表标准缺失。声称“判据缺失、待院方确认或待落地”前，必须查实现并附文件:行号；证据不足时写“未找到实现”。来源优先级：客户确认规则原文 ＞ 国家/行业标准下限 ＞ 我方实现口径。
- 结构化字段、时间、存在性和可验证规则优先由 Python 判定。只有语义或跨文书关联无法稳定确定时，才使用“最小上下文 + 单次受控 LLM 原子事实提取 + Python 校验与状态映射”，并明确输出枚举、失败语义、调用/Token 上限和真实病例验收集。

## 患者数据与排查产物

- 排查脚本和过程产物放 `.tmp/0910-full-audit/`；含患者原文的文件必须以 `-private` 结尾且严禁提交。
- `docs/` 只保存可长期引用的结论；一次性过程文件留在 `.tmp/`。凭据只从 `backend/.env` 读取，不得写入脚本或报告。

## 工具与项目边界

- `.codegraph/` 存在时，理解代码位置和调用链应先用 CodeGraph：`codegraph explore "问题或符号"`，影响分析用 `codegraph impact <symbol>`。修改后若继续依赖索引则运行 `codegraph sync .`；索引异常才重建。CodeGraph 不能替代真实 trace、测试、浏览器验证和性能数据。
- `workstation-v4` UI 遵循 `docs/gap/WorkstationV4-医疗浅色-DESIGN.md`：浅色医疗中后台、清晰层级、总览/筛选/明细/结果分区，复用现有 token 与组件；纯展示需求不得修改后端合同。
- TypeScript 修改优先修复 API DTO、Store、props/emits 等类型边界；新模块启用严格类型。禁止用宽泛 `any` 或 `@ts-ignore` 绕过错误；必要时使用带原因的 `@ts-expect-error`。不得新增 `.vue.ts` 镜像文件。
- 禁止提交 `dist/`、coverage、临时日志等生成物；禁止通过关闭 CI 门禁强行通过。

## 验证与提交

- 小改动先跑聚焦测试；完成一个功能闭环、修改共享类型/API 边界或准备提交时再跑完整检查。
- 提交前默认运行：`npm run check:encoding`、`npm run lint`、`npm run type-check`、`npm run test:unit`。本地资源不足时至少运行前两项，并在提交说明中记录未跑项目；Python 改动还须运行相关 pytest/静态检查。
- 提交前执行 `git diff --cached --name-only`。暂存区含他人改动时必须按路径提交，避免 Husky/lint-staged 改写无关文件；如必须 `--no-verify`，须手动完成适用检查并在提交说明中写明原因。
- 文件读取、状态检查、测试和本地服务启动可直接执行；删除、强制推送、全局安装和数据库写操作须获得明确授权。普通 `git push` 在用户已授权本次交付时无需重复询问。
- 每个功能或修复完成验证后主动提交，commit message 使用中文。
