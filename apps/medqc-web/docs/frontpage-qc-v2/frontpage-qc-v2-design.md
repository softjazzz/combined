# 首页质控 V2：从零设计方案

- 日期：2026-10-13
- 状态：草案，待确认
- 依据：
  - 《住院病案首页数据质量管理与控制指标（2016 版）》，见 `apps/medqc-web/docs/住院病案首页必填项与质控标准.md`：76 项必填、100 分评分、10 项质控指标
  - `docs/0418/PRD/PRD-病案质控管理员端.md`：批量质控、问题池、问题状态机、500 份 ≤ 5 分钟
  - 阶段 0 误报审计（同目录 `phase0-false-positive-list.md`）
- 已定口径（2026-10-13 确认）：
  - 首页上的质控医师、质控护士、质控日期三项停用
  - 本院不采集的字段，对应规则停用
  - 编码校验放宽为格式校验，兼容国临版扩展码，不查字典
  - 规则运行出错判“资料不足”，不再默认通过

## 一、为什么推翻重做

旧实现（`FrontpageFormalQC` + `/formal-qc/validate` + 前端逐份循环调用）有 4 个根本问题，修补成本高于重写：

1. **规则和数据脱节**：规则读的是一套虚构的平铺字段名，和库里的首页结构对不上，82 条里 42 条对全部首页误报。
2. **结论只有“通过/不通过”两态**：分不出“医生漏填”和“数据没同步过来”，出错时还默认判通过。
3. **没有后端任务**：批量质控在浏览器里逐份串行调接口，关页面就断，没有任务记录。
4. **没有结果模型**：结果写进一个结构已漂移的旧 `qc_results` 表，前端无法做列表、问题池和统计。

## 二、设计原则

1. **以 2016 版标准为唯一规则来源**：规则清单按标准的 76 项必填和评分表逐条落地，每条规则写明出处（标准条目号和评分类别）。
2. **先归一，再判定**：引擎不直接读数据库行。先由适配层把首页转成统一的 `FrontpageDoc`（字段名、类型、代码字典统一），规则只读 `FrontpageDoc`。字段映射集中在一处，可审计、可测试。
3. **四态结论**：每条规则对每份首页给出
   - 合规
   - 不合规
   - 资料不足：数据缺失或异常，无法判断
   - 不适用：条件不满足，例如无手术时不查手术字段

   只有“不合规”扣分、进问题池；“资料不足”单独计数，不扣分。
4. **确定性规则不调用模型**：V2 一期全部是确定性规则，不调用模型，单份毫秒级。正文证据一致性放到后续阶段。
5. **交互对齐运行和终末质控**：页面结构、任务状态条、结果预览、导出、结果分析的交互与“运行病历质控 / 终末病历质控”一致，用户不需要学第二套操作。

## 三、总体架构

```
CDM 正式首页（MedicalRecordFrontpage + 诊断 + 手术 + 费用）
        │  get_frontpage_sheet（已有，只读）
        ▼
① 适配层 frontpage_qc_v2/adapter.py
   - 字段映射（集中一张表）
   - 类型归一：年龄解析“45岁/3月/10天”，代码字符串转数字
   - 代码字典：入院途径、离院方式、性别、过敏、血型等，中文和代码互转
   - 主诊断按诊断类型取，不按顺序取
   - 数据异常识别：列错位、整块缺失 → 标记为资料不足来源
        ▼  FrontpageDoc（强类型 dataclass）
② 规则引擎 frontpage_qc_v2/engine.py + rules/*.py
   - 声明式规则：id、名称、标准出处、评分类别、扣分、适用条件、判定函数
   - 四态结论 + 证据（字段路径、展示值、期望值）
   - 规则异常 → 资料不足，并记录异常类型（不含病历原文）
   - 评分：按 2016 版 100 分制分 A/B/C/D 类扣分，含单项封顶
        ▼  FrontpageQcOutcome
③ 持久化 frontpage_qc_v2/store.py（新表，见第五节）
④ 批量任务 frontpage_qc_v2/jobs.py（后端异步执行，进度可轮询）
⑤ 接口 routers/frontpage_qc_v2.py
⑥ 前端页面：首页质控（替换病历池 stage=frontpage_qc）
```

## 四、规则体系

### 4.1 规则分组

| 分组 | 内容 | 预计条数 |
|---|---|---|
| 完整性 | 2016 版 76 项必填，按适用条件判定（条件必填见 4.2） | 约 55（扣除停用项） |
| 规范性 | 代码取值合法：性别、入院途径、离院方式、入院病情、血型、过敏、切口愈合等级、手术级别、麻醉方式；ICD-10 和 ICD-9-CM-3 格式兼容国临版扩展码 | 约 14 |
| 逻辑与一致性 | 时间先后、住院天数与出入院时间相符、年龄与出生日期相符、性别与诊断/手术编码相符、年龄与诊断相符、死亡离院与尸检、新生儿体重、颅脑损伤与昏迷时间、Z 码主诊断、分娩结局码、损伤中毒须有外因码、病理诊断须有病理号、费用分项之和等于总费用 | 约 18 |

具体条数以规则清单评审稿为准。规则清单作为第一个交付物单独给你逐条过。

### 4.2 条件必填（默认口径，可调整）

| 字段 | 适用条件 |
|---|---|
| 手术日期、术者、Ⅰ助、麻醉方式、切口愈合等级、手术级别 | 有手术或操作 |
| 麻醉医师 | 有手术且麻醉方式不是“无/局麻” |
| 病理诊断、病理号 | 有病理检查 |
| 尸检标志 | 离院方式为死亡 |
| 过敏药物名称 | 过敏标志为“有” |
| 损伤中毒外部原因及编码 | 主诊断为 S/T 章 |
| 新生儿出生体重、入院体重 | 年龄小于 1 周岁（库里无天龄字段，用出生日期和入院日期推算） |
| 颅脑损伤昏迷时间 | 诊断含颅脑损伤编码 |
| 重症监护室名称和进出时间 | 有 ICU 记录 |

### 4.3 停用清单（按已定口径）

- 质控医师、质控护士、质控日期
- 本院不采集：治疗类别（中医）、出生地、工作单位地址及电话邮编、健康卡号、户口地址及邮编、现住址电话邮编、日常生活能力评分
- 具体以字段盘点结果为准：库里完全没有对应列的必填项列入停用候选，由你最终确认

停用规则保留在清单里并标“停用”，统计时不计入分母。以后医院补采后可以直接启用。

### 4.4 “资料不足”的判定

> 修订（2026-10-13）：字段盘点发现，“整块缺失”“列错位”只出现在测试和合成病例里，真实同步首页没有。所以改为下面的显式配置，不再靠“整组为空”去猜。

| 情形 | 判定 |
|---|---|
| 字段在“同步缺口配置”里（目前是入院时间、出院时间，以及待确认的编码员、自付金额），且为空 | 资料不足，原因写“首页同步未带入” |
| 依赖资料不足字段的逻辑规则（如住院天数核对、手术日期范围） | 资料不足 |
| 整块数据不存在：无出院诊断、无费用记录 | 对应规则判资料不足 |
| 规则运行出错 | 资料不足，异常类型写入结果 |
| 其他字段为空（“-”算已填） | **不合规** |

资料不足在页面上独立展示（“资料不足 N 项”），并能按原因汇总，供数据同步排查。

### 4.5 评分与等级

- 按 2016 版评分表计分：患者信息 18、住院过程 26、诊疗信息 50、费用 6，共 100 分。A/B/C/D 类扣分，含单项封顶。
- 停用项和资料不足项不扣分。结果里同时给出“可评分项占比”，避免资料不足多的首页显得分数虚高。
- 等级：≥ 90 分为优秀，75–90 分为合格，< 75 分为不合格（2026-10-13 已确认），阈值放在配置里。

## 五、数据模型（新表，`qc` schema，alembic 迁移）

不复用结构已漂移的 `qc_results` / `qc_defects`，新建 3 张表：

**frontpage_qc_runs**：一次批量任务

- 基本信息：id、状态（queued / running / completed / failed / cancelled）、筛选条件 JSON、规则集版本
- 进度：总数、已处理、合规份数、不合规份数、资料不足份数
- 审计：创建人、创建时间、开始时间、结束时间、错误摘要

**frontpage_qc_results**：每份首页每次质控一行

- 关联：id、run_id、patient_id、visit_id、科室、出院日期
- 结论：得分、等级、不合规数、资料不足数、可评分项占比
- 追溯：规则集版本、输入指纹（首页内容 hash，用于判断“结果是否过期”）、is_latest

**frontpage_qc_findings**：每条非合规结论一行

- 定位：id、result_id、rule_id、规则名称、分组、评分类别、扣分
- 结论：verdict（fail / data_gap）、字段路径、展示值、期望说明、资料不足原因
- 复核：复核状态（pending / confirmed / false_alarm）、复核人、复核时间、复核意见

迁移要求（按开发约束）：

- alembic 迁移同时支持 split schema 和单 schema
- 旧库升级时不改动、不删除旧表
- 测试初始化（SQLite fixture）同步建表
- 下线旧接口时只停止写入，不删除旧数据

## 六、接口（`/api/v1/frontpage-qc`）

| 接口 | 用途 |
|---|---|
| `GET /rules` | 规则清单：分组、出处、扣分、启用状态 |
| `POST /runs` | 创建批量任务：按所选病历或当前筛选，单次上限 500 份 |
| `GET /runs/{id}` | 任务进度，前端轮询 |
| `POST /runs/{id}/cancel` | 取消任务 |
| `GET /records` | 首页质控结果列表：科室、出院日期、关键词、等级、是否有问题、是否资料不足、结果是否过期；分页 |
| `GET /records/{patient_id}/{visit_id}` | 单份结果：分数、分组问题、资料不足项、首页字段视图 |
| `POST /findings/{id}/review` | 复核：确认 / 误报 + 意见 |
| `GET /analytics` | 统计：10 项指标中可自动计算的部分、规则 Top N、科室排名、资料不足原因分布 |
| `POST /records/export` | 导出 Excel：所选或当前筛选 |

## 七、前端

`首页与结算清单 → 首页质控` 入口改为新页面 `FrontpageQcView`，结构对齐运行和终末质控页：

- **页头**：标题“首页质控”、视图切换（病历结果 / 结果分析）、“质控所选”和“质控当前筛选”按钮
- **指标卡**：已质控份数、平均分、优秀率、不合规问题数、资料不足份数
- **任务状态条**：任务进度；失败、取消、部分完成都有明确提示
- **筛选栏**：科室、出院日期、关键词、等级、问题类型（不合规 / 资料不足）、结果过期
- **列表 + 右侧预览**
  - 列表列：患者、住院号、科室、出院日期、得分、等级、问题数、资料不足数、质控时间
  - 预览：按“患者信息 / 住院信息 / 诊疗信息 / 费用信息”分组的问题卡片，每张卡写字段、当前值、要求和扣分，带“确认 / 误报”按钮；资料不足单独折叠
- **结果分析**：规则 Top 10（可下钻到命中病历）、科室排名、资料不足原因分布，以及 2016 版可自动计算的指标（填报完整率、主要诊断编码正确率（格式层面）、手术编码正确率（格式层面）、数据质量优秀率）
- **单病历入口**：病历详情里的“首页质控”页签只读展示最新结果和“重新质控”按钮；进入页面时不自动运行

## 十、已确认（2026-10-13）

1. 等级阈值：≥ 90 优秀、75–90 合格、< 75 不合格。
2. 资料不足按 4.4 判定。
3. 条件必填按 4.2。
4. 入口：先在“首页与结算清单”下并行放新入口“首页质控（新）”，验收通过后替换旧入口。
5. 质控对象：HIS 同步的正式首页；AI 生成首页草稿不在一期范围。
