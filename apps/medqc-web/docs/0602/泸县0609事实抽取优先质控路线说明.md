# 泸县0609事实抽取优先质控路线说明

## 1. 一句话结论

“先抽取结构化事实，再基于事实执行质控”的路线可行，且是后续提升 LX0609 准确性、速度和证据可解释性的主要方向。

但它不能一次性替换现有质控链路。更合理的落地方式是：先在高误报、高不稳定的质控族上试点，形成事实缓存和证据 trace，再逐步扩展到全部 49 个客户质控点。

## 2. 为什么要做这条路线

当前 LX0609 质控链路里，一些质控点容易受到整份病历长上下文影响，出现以下问题：

- 远距离关键词误触发。例如病历里出现“病理”“肿瘤”“化疗”“抗生素”，但不一定代表本次住院、本次手术或本次治疗适用对应质控点。
- 证据不够清楚。结果里有时只能看到一句很短的片段，客户难以理解为什么判为不合规、数据不足或不适用。
- LLM 直接看大段病历时容易把历史、既往史、当前手术、医嘱、报告混在一起。
- 全病历上下文过长，导致速度慢、成本高，也增加模型误判概率。

事实抽取优先路线的目标是把“质控判断”拆成两步：

1. 先从病历文书中抽取可追溯事实。
2. 再让规则或模型基于这些事实判断质控点是否适用、是否缺数据、是否存在问题。

## 3. 目标形态

正式链路建议如下：

```mermaid
flowchart LR
  A["病历文书/结构化表"] --> B["事实抽取层"]
  B --> C["事实缓存"]
  C --> D["适用性门控"]
  D --> E["程序化规则/LLM质控"]
  E --> F["客户质控点聚合"]
  F --> G["客户可读证据展示"]
  C --> H["开发 trace"]
  D --> H
  E --> H
```

事实层输出不直接判定合规，只回答：

- 发现了什么事实。
- 来自哪份文书或结构化表。
- 原文片段是什么。
- 记录时间是什么。
- 置信度是多少。
- 是规则抽取还是 LLM 抽取。

## 4. 事实对象建议

建议后续统一 facts schema：

| 字段                   | 说明                                       |
| ---------------------- | ------------------------------------------ |
| `fact_id`              | 事实唯一 ID                                |
| `visit_id`             | 病历/就诊 ID                               |
| `family`               | 质控族，例如手术麻醉、肿瘤病理             |
| `fact_type`            | 事实类型，例如手术事实、病理报告、化疗事实 |
| `source_table`         | 来源表                                     |
| `source_document_id`   | 来源文书 ID                                |
| `source_document_type` | 来源文书类型                               |
| `record_time`          | 文书或事实记录时间                         |
| `quote`                | 原文短片段                                 |
| `normalized_value`     | 可选，结构化后的时间、数值、枚举           |
| `confidence`           | 置信度                                     |
| `extractor`            | `deterministic` / `llm` / `hybrid`         |
| `extractor_version`    | 抽取器版本                                 |
| `created_at`           | 抽取时间                                   |

## 5. 哪些事实适合规则抽取

规则抽取适合低歧义、字段明确、可重复计算的事实：

- 入院时间、出院时间、文书记录时间、提交时间。
- 手术开始/结束时间。
- 首次病程记录时间。
- 病理报告时间。
- 医嘱开始/停止时间。
- 是否存在明确的输血医嘱、输血记录、输血申请。
- 是否存在明确的抗菌药物医嘱。
- 是否存在明确的病危/病重医嘱。

这些事实优先用 Python 规则、结构化表字段、正则和字段映射抽取，速度快、可解释、便于单测。

## 6. 哪些事实适合 LLM 抽取

LLM 适合高语义、高上下文判断的事实抽取，但不建议直接让 LLM 给最终质控结论。

优先适合 LLM 的事实：

- 本次手术是否属于恶性肿瘤相关手术。
- 病理送检/取材描述是否已经在手术记录或病程中出现。
- 会诊目的是否明确。
- 会诊意见是否可执行。
- 手术讨论是否覆盖关键风险和方案。
- 术前讨论中术者是否实际参与。
- 主诉与第一诊断是否存在明显逻辑断裂。

LLM 在这里的职责是“抽事实和给建议”，不是直接替代规则判定。

## 7. 优先试点范围

不建议一开始覆盖全部 49 条。建议先做两个高风险族：

### 7.1 手术麻醉

当前容易出问题的点：

- `LX0609-024` 恶性肿瘤手术适用性。
- `LX0609-025` 植入物/条码适用性。
- `LX0609-028` I/II 类切口 + 抗菌药物医嘱时限。
- `LX0609-039/040` 术前讨论、四级手术、MDT 适用性。

适合 facts 层的原因：

- 需要区分“本次手术事实”和“既往史/诊断关键词”。
- 需要区分“有手术”与“手术等级、切口类型、植入物、抗菌药物医嘱”。
- 门控准确性直接决定是否误报。

### 7.2 肿瘤病理

当前容易出问题的点：

- `LX0609-013` 病理结果是否需要回看。
- `LX0609-019` 取材情况是否已在手术记录/病程记录中体现。
- `LX0609-026` 化疗医嘱和病程记录一致性。
- `LX0609-027` 出院记录中恶性肿瘤相关治疗计划。

适合 facts 层的原因：

- “病理报告”“送病检”“取材”“化疗”容易被远距离关键词误触发。
- 客户需要看到明确来源证据，否则很难接受不合规判断。

## 8. POC 观察结果

当前已做临时 POC：

- 确定性事实抽取：10 份手术相关病历 × 7 个质控族。
- LLM 事实抽取：2 份问题病历 × 手术麻醉/肿瘤病理 2 个质控族。

观察到：

- 手术麻醉族中，LLM 事实层与全量上下文门控可以保持一致，说明事实层替代全量上下文有可行性。
- 肿瘤病理族中，事实层会把部分全量上下文触发的规则压成不适用，说明全量上下文存在宽触发风险。
- LLM 事实抽取耗时仍高，不能同步串行进入主链路。必须做异步缓存或预抽取。

结论：

- 路线可行。
- 不能直接全量上线。
- 需要做事实缓存、trace 和分阶段灰度。

## 9. 关键设计原则

### 9.1 facts 不直接判合规

事实层只回答“有没有事实、事实来自哪里”，不要回答“是否违规”。

错误做法：

> 病理取材未记录，不合规。

正确做法：

> 发现事实：手术记录中有“阑尾向患者家属展示后送病检”。来源：手术记录。记录时间：xxxx。

后续规则再判断这个事实是否满足 `LX0609-019`。

### 9.2 优先复用结构化字段

能从表字段拿到的时间、医嘱、报告时间，不应再让 LLM 猜。

### 9.3 LLM 用于语义事实，不用于硬规则计算

例如：

- LLM 可以判断“这是不是本次恶性肿瘤手术”。
- 但“术后 24 小时内是否完成手术记录”应由程序计算。

### 9.4 客户侧展示 facts，开发侧保留 trace

客户看到：

- 来源文书。
- 原文片段。
- 关键时间。
- 缺失字段。
- 判定依据。

开发 trace 保留：

- source_rule_id
- source_status
- source_conclusion
- source_evidence
- trigger_decision
- aggregation_reason
- postprocess_reason
- fact_extractor_version
- llm_prompt_version

## 10. 建议实施阶段

### 阶段 1：事实层服务化

目标：

- 建立 `luxian_0609_fact_extraction.py` 服务。
- 支持确定性 facts 抽取。
- 支持注入式 LLM facts 抽取。
- 输出统一 facts schema。
- 不接入正式主链路，只用于 POC 和单测。

验收：

- 能抽出手术、植入物、抗菌药物、病理报告、送检、化疗等事实。
- 能基于 facts 重新跑 gate。
- 能对比 full_context gate 与 fact_context gate 差异。

### 阶段 2：手术麻醉 + 肿瘤病理灰度接入

目标：

- 只接入两个质控族。
- facts 优先，原全量上下文作为 fallback。
- trace 中保存 facts 与 gate 决策。

验收：

- 抽 20-30 份 0426 病历复跑。
- 对比误报、漏报、data_gap、not_applicable 变化。
- 重点验证 `LX0609-019/024/025/026/028/039/040`。

### 阶段 3：事实缓存

目标：

- facts 按 visit_id 缓存。
- 同一病历多次质控不重复抽取。
- LLM facts 异步执行，不阻塞主页面。

验收：

- 质控速度明显下降。
- 任务 trace 可查看 facts 来源。
- 客户侧结果证据更结构化。

### 阶段 4：扩展到会诊、输血、查房病程

目标：

- 会诊：抽会诊申请、会诊意见、执行记录。
- 输血：抽输血医嘱、申请、记录、收费血制品。
- 查房病程：抽病危/病重医嘱、查房/病程时间轴。

验收：

- 没有强触发事实时直接 not_applicable。
- 有事实但缺字段时 data_gap。
- 有足够事实时才进入不合规判断。

## 11. 风险和限制

### 11.1 LLM facts 仍可能漏抽

事实层不是银弹。如果 LLM 漏抽事实，会导致规则不触发。

缓解：

- 关键事实规则抽取兜底。
- facts trace 可回看。
- 高风险规则保留 full_context fallback。

### 11.2 性能问题

LLM facts 抽取不能同步串行执行。

缓解：

- 按质控族裁剪文书。
- facts 异步缓存。
- 只对高语义规则调用 LLM。
- 对同一病历复用 facts。

### 11.3 数据同步缺表会影响 facts

如果客户库没有同步同意书、医嘱、病理、输血等表，事实层也会缺证据。

缓解：

- facts 输出同时标记缺失来源。
- 客户侧展示为“数据不足”，不要误判为确定缺陷。

## 12. 最终建议

继续走这条路线。

短期不要全量替换现有质控链路，而是先做：

1. 手术麻醉 facts。
2. 肿瘤病理 facts。
3. facts trace。
4. 20-30 份真实结构病历回归。

如果这两族的误报率明显下降，再把同样模式推广到会诊、输血、查房病程。

这条路线的核心价值不是“让 LLM 多跑一轮”，而是把病历先变成可复核、可追踪、可缓存的事实层，让后续质控判断更稳定、更快、更能说服客户。
