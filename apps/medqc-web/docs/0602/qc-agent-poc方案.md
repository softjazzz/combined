# 质控 Agent POC 方案

日期：2026-06-02

## 背景

当前系统已经具备病历池、病历 bundle、正式质控、内涵性质控、病案首页生成、医保结算清单质控等独立能力。用户现在希望通过自然语言直接触发质控，例如：

- 查某个患者这次住院有没有质控问题。
- 查某个医生最近一批病历的高风险缺陷。
- 对某个科室某个时间段的出院病历执行正式质控。
- 针对病案首页、医保结算清单或内涵性规则做专项检查。

这个需求可行，但不建议做成“LLM 自由访问数据库并自由判断”的开放式 agent。推荐做成受控质控 Agent：自然语言只负责理解意图和编排工具，数据查询、病历打包、质控执行、证据返回全部走现有后端服务。

## POC 目标

实现一个可演示的“质控助手”入口，用户在对话框输入一句自然语言，系统能解析质控目标，匹配病历范围，调用现有质控链路，并返回结构化质控结果。

POC 不追求一次性覆盖所有复杂追问，优先证明以下闭环：

1. 自然语言查询病历范围。
2. 明确命中患者、医生、科室、时间、出院状态等筛选条件。
3. 对单病历或小批量病历执行受控质控。
4. 返回规则编号、缺陷描述、证据文书、证据原文、建议处理。
5. 支持用户继续追问汇总和展开。

## 设计原则

1. LLM 不直接拼 SQL，不直接访问数据库。
2. LLM 不直接修改质控结果。
3. 所有查询、执行、写入、导出都走白名单工具。
4. 批量任务、写库任务、导出敏感信息必须二次确认。
5. 所有结论必须带规则编号和证据，不能只返回“模型认为”。
6. 权限边界沿用现有登录用户权限，不允许越权查科室或患者。
7. 每次 agent 调用保留 trace：用户、自然语言输入、解析意图、调用工具、命中病历、质控结果。

## 用户场景

### 单病历质控

示例输入：

```text
帮我看张三这次住院有没有主要诊断选择问题
```

Agent 行为：

1. 解析患者姓名“张三”和任务“主要诊断选择问题”。
2. 调用病历搜索工具，匹配张三的住院记录。
3. 如果命中多份，返回候选病历让用户选择。
4. 调用病历 bundle 工具获取全病历。
5. 调用正式质控或内涵性质控规则。
6. 返回缺陷、证据、规则编号和建议。

### 科室批量质控

示例输入：

```text
查一下中医科 5 月出院病历，重点看病案首页和内涵质控
```

Agent 行为：

1. 解析科室为“中医科”，时间为 2026-05-01 至 2026-05-31，日期口径为出院日期。
2. 调用病历池查询工具，统计命中病历数。
3. 如果数量较大，先询问用户是抽样还是全量后台执行。
4. 创建批量质控任务。
5. 返回进度、结果汇总和高风险缺陷列表。

### 医生维度质控

示例输入：

```text
统计李医生最近 20 份出院病历的高风险缺陷
```

Agent 行为：

1. 解析医生姓名“李医生”、数量“最近 20 份”、范围“出院病历”。
2. 调用病历搜索工具，按医生和出院时间排序取样。
3. 执行正式质控或高风险规则集。
4. 返回医生维度缺陷分布、重复问题、需优先处理病历。

### 同步后病历质控

示例输入：

```text
普通外科昨天同步的新病历跑一遍正式质控
```

Agent 行为：

1. 解析科室、同步时间、任务类型。
2. 查询最近同步记录和病历池新增记录。
3. 匹配可质控病历。
4. 创建正式质控任务。
5. 返回批量结果。

## 架构方案

POC 推荐增加一个独立后端域：`qc_agent`。

建议新增接口：

```text
POST /api/v1/qc-agent/chat
GET  /api/v1/qc-agent/sessions/{session_id}
GET  /api/v1/qc-agent/jobs/{job_id}
POST /api/v1/qc-agent/confirm
```

核心流程：

```text
用户输入
  -> 意图解析
  -> 参数规范化
  -> 工具计划生成
  -> 权限检查
  -> 命中病历确认
  -> 调用质控工具
  -> 汇总结果
  -> 返回结构化答案
```

## 工具白名单

Agent 只能调用后端注册过的工具。

| 工具                                      | 用途                                   | 是否允许写库 |
| ----------------------------------------- | -------------------------------------- | ------------ |
| `search_records(filters)`                 | 按患者、医生、科室、日期、关键词查病历 | 否           |
| `get_record_bundle(record_id)`            | 获取单份病历全量文书 bundle            | 否           |
| `run_formal_qc(record_ids, rule_scope)`   | 执行正式质控                           | 可选         |
| `run_semantic_qc(record_ids, rule_scope)` | 执行内涵性质控                         | 可选         |
| `run_frontpage_qc(record_id)`             | 执行病案首页质控                       | 可选         |
| `run_settlement_qc(record_id)`            | 执行医保结算清单质控                   | 可选         |
| `get_qc_results(job_id)`                  | 获取质控任务结果                       | 否           |
| `summarize_qc_results(results)`           | 汇总质控结果                           | 否           |
| `explain_qc_issue(issue_id)`              | 展开单条缺陷证据                       | 否           |

POC 第一阶段可以只实现前 5 个工具。

## 意图结构

自然语言应解析成稳定 DTO，而不是直接拼接接口参数。

```json
{
  "intent": "run_qc",
  "target": {
    "patient_name": null,
    "doctor_name": "李医生",
    "department": "中医科",
    "date_range": {
      "start": "2026-05-01",
      "end": "2026-05-31",
      "field": "discharge"
    },
    "limit": 20
  },
  "qc_scope": {
    "formal": true,
    "semantic": true,
    "frontpage": false,
    "settlement": false,
    "rule_ids": []
  },
  "output": {
    "format": "summary",
    "include_evidence": true
  }
}
```

## 分阶段实现

### M1：单病历自然语言质控

目标：打通最小可用闭环。

能力：

- 输入患者姓名、病案号、住院号、visit_id。
- 匹配单份病历。
- 支持正式质控、病案首页质控、医保结算清单质控。
- 返回结构化缺陷和证据。

推荐验收语句：

```text
帮我看张三这次住院有没有问题
跑一下 visit_id=2404019 的病案首页质控
这份病历做医保结算清单质控
```

### M2：小批量科室/医生质控

目标：支持科室、医生、时间范围的批量任务。

能力：

- 支持科室 + 日期范围。
- 支持医生 + 最近 N 份。
- 支持出院日期、入院日期、同步时间口径。
- 命中超过阈值时要求用户确认。
- 结果按医生、科室、规则、严重程度汇总。

推荐验收语句：

```text
中医科 5 月出院病历抽 10 份跑正式质控
李医生最近 20 份病历看高风险问题
普通外科昨天同步的新病历跑一遍首页质控
```

### M3：追问式分析

目标：让用户围绕结果继续追问。

能力：

- 展开某条规则。
- 展开某份病历。
- 汇总重复缺陷。
- 输出客户汇报摘要。
- 导出报告前二次确认。

推荐验收语句：

```text
哪些问题最严重？
SC-083 相关问题展开看证据
按医生汇总重复问题
给我一份客户汇报摘要
```

## 前端入口

推荐在 `workstation-v4` 中新增右侧或底部“质控助手”入口。

界面要求：

1. 医疗浅色中后台风格。
2. 输入框支持自然语言。
3. 返回结果分为“范围、执行、结果、证据”四块。
4. 命中多份病历时展示候选列表。
5. 批量执行前展示确认卡片。
6. 质控结果可跳转到病历详情或质控详情。

POC 不需要复杂聊天历史，但需要保留当前 session 的上下文，支持 3 到 5 轮追问。

## 后端实现建议

建议新增模块：

```text
backend/app/routers/qc_agent.py
backend/app/services/qc_agent/
  intent_parser.py
  tool_registry.py
  orchestrator.py
  schemas.py
  result_summarizer.py
```

实现重点：

- `intent_parser.py`：将自然语言解析为 DTO。
- `tool_registry.py`：注册可调用工具。
- `orchestrator.py`：按 DTO 编排工具调用。
- `result_summarizer.py`：把质控结果转成用户可读摘要。
- `schemas.py`：定义请求、响应、工具参数、确认状态。

## 权限与安全

1. 所有接口必须登录。
2. 使用现有角色权限：医生、病案科、质控员、管理员。
3. Agent 工具调用必须带当前用户上下文。
4. 查询结果按用户权限过滤。
5. 批量执行、持久化结果、导出报告必须确认。
6. 日志中不要记录完整病历全文，只记录摘要、ID 和 trace。
7. 输出证据片段要限制长度，避免泄露过多无关隐私信息。

## 风险

| 风险                   | 处理方式                                 |
| ---------------------- | ---------------------------------------- |
| 自然语言解析错范围     | 批量任务前确认范围                       |
| 命中多份同名患者       | 必须让用户选择                           |
| LLM 直接给出无证据结论 | 强制使用工具结果和证据                   |
| 批量任务超时           | 后台 job + 进度查询                      |
| 权限越界               | 工具层统一校验当前用户权限               |
| 结果解释不稳定         | 缺陷结论以规则引擎结果为准，LLM 只做摘要 |

## POC 验收标准

M1 通过标准：

1. 能用自然语言查到单份病历。
2. 能执行至少一种现有质控链路。
3. 返回规则编号、缺陷描述、证据文书、证据原文。
4. 命中多份病历时不会直接乱跑。
5. 无权限或无病历时返回明确错误。

M2 通过标准：

1. 能按科室、医生、日期范围匹配病历。
2. 超过阈值时要求确认。
3. 能异步执行批量质控。
4. 能按严重程度、规则、医生或科室汇总。

M3 通过标准：

1. 能追问展开单条缺陷。
2. 能围绕上一轮结果继续汇总。
3. 能生成客户汇报摘要，但导出前必须确认。

## 推荐下一轮 CLI 任务

```text
/goal 实现质控 Agent M1 POC：新增受控自然语言质控助手接口，支持单病历查询、确认、调用现有质控链路并返回结构化缺陷证据。不要让 LLM 直接拼 SQL，不改现有质控规则，不写生产库。完成后补后端单元测试和 workstation-v4 最小入口。
```

## 结论

质控 Agent 方案可行，且很适合当前系统。它的价值不是替代现有规则引擎，而是把病历池、bundle、正式质控、内涵质控、首页质控、结算清单质控这些能力组合成一句话可调用的工作入口。

POC 应从单病历和小批量受控执行开始，先保证范围准确、结果有证据、权限可控，再逐步扩展到批量分析和追问式汇总。
