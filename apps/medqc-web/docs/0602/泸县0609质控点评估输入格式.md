# 泸县0609质控点评估输入格式

## 目的

`scripts/qc/evaluate_luxian_0609_rules.py` 用于把客户样本验证任务结果和 golden cases 做对比，输出每条泸县0609质控点的精确率、召回率和上线建议。

评估脚本支持两类输入：

1. 标准 predictions JSON。
2. 后端 workspace batch job JSON，其中结果在 `items` 或 `summary.items` 中。

## 标准 predictions JSON

```json
{
  "rule_set_key": "luxian_0609_qc_v1",
  "model": "qwen3.5-35b-a3b",
  "results": [
    {
      "qc_point_id": "LX0609-001",
      "case_id": "visit-001-positive",
      "visit_id": "2324802",
      "actual_hit": true,
      "status": "已命中",
      "document_type": "admission_record",
      "document_name": "入院记录",
      "hit_field": "记录时间",
      "matched_text": "入院时间 2026-04-01 10:00，入院记录时间 2026-04-02 12:30",
      "evidence_summary": "入院记录完成时间超过入院后24小时。",
      "suggestion": "请按规范在患者入院后24小时内完成入院记录。",
      "confidence": 0.95
    }
  ]
}
```

## 必填字段

| 字段                             | 说明                                                                               |
| -------------------------------- | ---------------------------------------------------------------------------------- |
| `qc_point_id`                    | 泸县0609 规则编号，例如 `LX0609-001`。                                             |
| `case_id`                        | golden case 的唯一编号。若没有 case_id，脚本会尝试使用 `sample_id` 或 `visit_id`。 |
| `actual_hit`                     | 规则是否实际命中。也可用 `hit`、`is_hit`、`triggered`、`matched`。                 |
| `status`                         | 可读状态，例如 `已命中`、`未命中`、`数据不足`、`规则不适用`、`需人工复核`。        |
| `evidence_summary` 或 `evidence` | 命中时必须有证据。                                                                 |

## 可选证据字段

| 字段            | 说明                                                  |
| --------------- | ----------------------------------------------------- |
| `document_type` | 文书类型，例如 `admission_record`、`surgery_record`。 |
| `document_name` | 展示名称，例如 `入院记录`。                           |
| `hit_field`     | 命中字段，例如 `记录时间`、`主诉`、`会诊意见`。       |
| `matched_text`  | 原文片段或字段值。                                    |
| `suggestion`    | 处理建议。                                            |
| `confidence`    | 置信度。                                              |

## workspace batch job JSON

如果输入是后端批量任务 JSON，脚本会读取：

- `items[]`
- `summary.items[]`
- `results[]`
- `summary.rule_results[].items[]`

每条 item 至少需要：

| 字段                                      | 映射                                                  |
| ----------------------------------------- | ----------------------------------------------------- |
| `rule_code` 或 `rule_id`                  | 映射到正式目录中的 `rule_ids`，再反查 `qc_point_id`。 |
| `record_id`                               | 作为 case_id 或 visit_id 匹配 golden case。           |
| `status` / `is_compliant`                 | 判断是否命中。                                        |
| `evidence` / `findings` / `document_type` | 作为证据字段。                                        |

注意：如果一个 `rule_code` 同时对应多个 `LX0609` 质控点，脚本不会猜测映射，需要在预测结果里显式提供 `qc_point_id`。

工作台批量任务完成后，可以把 `/api/v1/qc/sichuan/workspace/batch-jobs/{job_id}` 返回的数据保存为 JSON，然后直接评估：

```bash
python scripts/qc/evaluate_luxian_0609_rules.py --predictions path/to/workspace-batch-job.json --write --fail-on-not-ready
```

脚本会把 `summary.rule_results[].items[]` 展开为预测结果，并按目录中的 `rule_ids` 反查 `LX0609-xxx`。状态映射口径：

| 批量任务状态                                          | 评估含义 |
| ----------------------------------------------------- | -------- |
| `non_compliant` / `confirmed_defect`                  | 命中     |
| `compliant` / `not_applicable` / `rejected_by_system` | 未命中   |
| `uncertain` / `data_quality_gap` / 无法识别状态       | 不可判定 |

## 运行方式

```bash
python scripts/qc/evaluate_luxian_0609_rules.py --predictions path/to/predictions.json --write --fail-on-not-ready
```

输出：

- `docs/0602/luxian_0609_qc_eval.json`
- `docs/0602/luxian_0609_qc_eval.csv`
- `docs/0602/泸县0609质控点评估报告.md`

## 从客户样本池导出候选 golden cases

在正式填写 `docs/0602/泸县0609质控点-golden-cases.json` 前，先用客户样本池导出的 items JSON 生成候选样本报告：

```bash
python scripts/qc/export_luxian_0609_golden_candidates.py --sample-items path/to/sample-items.json --write
```

如果当前环境已连接本地数据库，也可以直接读取样本池：

```bash
python scripts/qc/export_luxian_0609_golden_candidates.py --pool-id 0426 --match-status matched --write
```

输入 JSON 支持以下结构：

- 数组：`[{...}, {...}]`
- 对象：`{"items": [{...}]}`
- 对象：`{"data": {"items": [{...}]}}`

每条 item 会读取：

| 字段                                             | 用途                              |
| ------------------------------------------------ | --------------------------------- |
| `candidate_rule_ids` / `candidate_rule_ids_json` | 映射到正式目录里的 `LX0609-xxx`。 |
| `matched_visit_id` / `visit_id`                  | 作为候选样本病历号。              |
| `manual_issue_text`                              | 作为人工标注的问题描述。          |
| `patient_name` / `department`                    | 作为复核辅助信息。                |

输出：

- `docs/0602/luxian_0609_golden_candidates.json`
- `docs/0602/泸县0609质控点-golden-cases候选报告.md`

注意：候选报告只作为人工复核输入，不会自动写入正式 golden cases。`ambiguous` 表示一个规则 ID 对应多个泸县0609质控点，必须人工选择；`unmapped` 表示当前样本规则 ID 还没有进入正式目录。

## 生成 golden cases 人工复核队列

候选报告生成后，先把已映射到 `LX0609-xxx` 的候选阳性样本整理为人工复核队列：

```bash
python scripts/qc/build_luxian_0609_golden_review_queue.py --write
```

输出：

- `docs/0602/luxian_0609_golden_review_queue.json`
- `docs/0602/luxian_0609_golden_review_queue.csv`
- `docs/0602/泸县0609质控点-golden-cases复核队列.md`

复核规则：

1. 只有 `review_status=accepted` 且 `accepted_case_type=positive` 的样本，才能写入正式 golden cases。
2. 证据不足、映射错误、样本不适用时，必须填写 `review_status=rejected` 和 `reject_reason`。
3. 复核队列只解决阳性样本来源；每条规则仍需另行补充 `negative` 和 `boundary`。

## 生成 golden cases 复核证据包

复核队列生成后，先导出只读证据包，辅助判断候选样本是否真的命中对应 `LX0609` 质控点：

```bash
python scripts/qc/build_luxian_0609_review_evidence_pack.py --write
```

也可以只导出部分样本：

```bash
python scripts/qc/build_luxian_0609_review_evidence_pack.py --qc-point-id LX0609-018 --max-rows 10 --write
python scripts/qc/build_luxian_0609_review_evidence_pack.py --review-id LX0609-029-REVIEW-P-001 --write
```

输出：

- `docs/0602/luxian_0609_review_evidence_pack.json`
- `docs/0602/泸县0609质控点-golden-cases复核证据包.md`

证据包只包含病历上下文、推荐文书清单和短证据片段，不输出完整病历全文。复核时应优先处理 `data_status=ready` 的样本；如果片段与客户质控点不匹配，应在复核队列中标记 `review_status=rejected`，不能直接导入正式 golden cases。

## 发现 formal_ready 规则的自动候选样本

对已经具备执行基础但缺少 golden cases 的 `formal_ready` 质控点，可以从客户样本池自动筛选候选样本：

```bash
python scripts/qc/discover_luxian_0609_formal_ready_cases.py --pool-id a627718c-bde9-4cd3-af9d-7856c072525e --max-per-type 12 --write
```

输出：

- `docs/0602/luxian_0609_formal_ready_sample_candidates.json`
- `docs/0602/泸县0609质控点-formal-ready样本候选.md`

该脚本只生成候选，不写正式 golden cases。当前 `formal_ready` 重点覆盖：

- `LX0609-017` 多次病程记录复制
- `LX0609-021` 会诊申请目的不明确
- `LX0609-032` 有手术记录但无手术安全核查表

`LX0609-001`、`LX0609-002`、`LX0609-016` 当前已降级为数据缺口：样本池缺入院时间或首次病程正文，不能硬判为可执行规则。

## 自动候选转人工复核队列

自动候选需要转成复核队列并人工确认后，才能导入 golden cases：

```bash
python scripts/qc/build_luxian_0609_auto_candidate_review_queue.py --write --merge
```

输出：

- `docs/0602/luxian_0609_auto_candidate_review_queue.json`
- `docs/0602/luxian_0609_auto_candidate_review_queue.csv`
- `docs/0602/luxian_0609_golden_review_queue_merged.csv`
- `docs/0602/泸县0609质控点-自动候选复核队列.md`

## formal-ready 最小复核包

为了先打通第一批 golden cases，可以只处理当前 3 条 `formal_ready` 规则，每条规则各取 1 个阳性、1 个阴性、1 个边界候选：

```bash
python scripts/qc/build_luxian_0609_formal_ready_min_review_sheet.py --write
python scripts/qc/check_luxian_0609_formal_ready_min_review_sheet.py --write
```

输出：

- `docs/0602/luxian_0609_formal_ready_min_review_sheet.csv`
- `docs/0602/luxian_0609_formal_ready_min_review_sheet.json`
- `docs/0602/泸县0609质控点-formal-ready最小复核包.md`
- `docs/0602/luxian_0609_formal_ready_min_review_sheet_quality.json`

质量检查必须满足：`formal_ready_rule_count=3`、`row_count=9`、`complete_rule_count=3`、`error_count=0`。

人工复核后，可以先把最小复核包 dry-run 回写到合并复核队列：

```bash
python scripts/qc/apply_luxian_0609_p0_review_sheet.py --sheet docs/0602/luxian_0609_formal_ready_min_review_sheet.csv --write-report
```

确认 `error_count=0` 后，才允许加 `--write`：

```bash
python scripts/qc/apply_luxian_0609_p0_review_sheet.py --sheet docs/0602/luxian_0609_formal_ready_min_review_sheet.csv --write --write-report
python scripts/qc/check_luxian_0609_review_queue.py --write
```

如果只想验证最小复核包本身的 accepted 行能否导入，也可以直接 dry-run：

```bash
python scripts/qc/import_luxian_0609_reviewed_cases.py --review-csv docs/0602/luxian_0609_formal_ready_min_review_sheet.csv --write-report
```

注意：最小复核包默认 `review_status` 为空，导入器会跳过，不会误写入正式 golden cases。只有人工填写 `review_status=accepted`、`accepted_case_type` 和 `reviewer_note` 后，才允许进入导入流程。

## formal-ready 最小预测质量门禁

在人工复核前，可以先用最小复核包 dry-run 当前 formal-ready 规则的预测输出，验证执行器、预测格式和评估脚本是否能闭环。该步骤不等于准确率评估，也不能替代人工 accepted golden cases。

```bash
python scripts/qc/predict_luxian_0609_formal_ready_cases.py --review-csv docs/0602/luxian_0609_formal_ready_min_review_sheet.csv --output docs/0602/luxian_0609_formal_ready_min_predictions.json --write
python scripts/qc/check_luxian_0609_formal_ready_predictions.py --write
python scripts/qc/evaluate_luxian_0609_rules.py --predictions docs/0602/luxian_0609_formal_ready_min_predictions.json --write
```

输出：

- `docs/0602/luxian_0609_formal_ready_min_predictions.json`
- `docs/0602/luxian_0609_formal_ready_min_predictions_quality.json`
- `docs/0602/泸县0609质控点-formal-ready最小预测质量报告.md`

预测质量检查必须满足：`formal_ready_rule_count=3`、`prediction_count=9`、`complete_rule_count=3`、`error_count=0`。如果该门禁失败，说明预测结果缺少 `qc_point_id`、`visit_id`、命中状态或证据字段，不能进入准确率评估。

## 生成候选样本覆盖矩阵

正式上线前，需要确认每条 `LX0609` 质控点是否已经具备阳性、阴性、边界三类候选样本。候选样本不等于正式 golden cases，必须人工复核为 `accepted` 后才能导入。

```bash
python scripts/qc/build_luxian_0609_candidate_coverage.py --write
```

输入：

- `docs/0602/luxian_0609_formal_rule_catalog.json`
- `docs/0602/luxian_0609_golden_review_queue_merged.csv`
- `docs/0602/泸县0609质控点-golden-cases.json`
- `docs/0602/luxian_0609_merged_review_evidence_pack.json`

输出：

- `docs/0602/luxian_0609_candidate_coverage.json`
- `docs/0602/luxian_0609_candidate_coverage.csv`
- `docs/0602/泸县0609质控点-候选样本覆盖矩阵.md`

覆盖状态口径：

| 状态                     | 含义                                                    |
| ------------------------ | ------------------------------------------------------- |
| `formal_cases_ready`     | 正式 golden cases 已有阳性、阴性、边界三类样本。        |
| `ready_for_review`       | 候选样本已覆盖三类，但尚未人工复核为正式 golden cases。 |
| `partial_candidates`     | 已有部分候选，但缺少至少一种 case type。                |
| `data_insufficient_only` | 只有数据不足候选，需要补数据源或确认口径。              |
| `no_candidates`          | 当前还没有可复核候选。                                  |

推荐推进顺序：

1. 先处理 `ready_for_review`，把三类候选齐全的规则人工复核并导入 golden cases。
2. 再处理 `partial_candidates`，按缺失 case type 补样本。
3. 对 `no_candidates` 先补执行器或扩大样本发现范围。
4. 对 `data_insufficient_only` 明确数据源缺口，不能标记为正式上线。

## 生成 golden cases 复核任务包

候选覆盖矩阵确认后，可按质控点和样本类型拆成复核任务包，方便人工从 P0 开始逐包确认：

```bash
python scripts/qc/build_luxian_0609_review_work_packages.py --write
```

输出：

- `docs/0602/luxian_0609_review_work_packages.json`
- `docs/0602/luxian_0609_review_work_packages.csv`
- `docs/0602/泸县0609质控点-golden-cases复核任务包.md`

优先级口径：

| 优先级 | 含义                                                                      |
| ------ | ------------------------------------------------------------------------- |
| `P0`   | 该质控点三类候选已齐，优先人工复核，accepted 后可进入 golden cases 导入。 |
| `P1`   | 已有部分候选，先复核现有候选，同时继续补齐缺失样本类型。                  |
| `P2`   | 当前无待复核候选。                                                        |

复核任务包只组织候选样本，不会自动修改 `review_status`，也不会自动写入正式 golden cases。

## 导出 P0 候选人工复核表

P0 复核包表示某些质控点已具备阳性、阴性、边界三类候选，适合优先人工确认。可以导出一个只包含 P0 候选的复核表：

```bash
python scripts/qc/export_luxian_0609_p0_review_sheet.py --write
```

输出：

- `docs/0602/luxian_0609_p0_review_sheet.json`
- `docs/0602/luxian_0609_p0_review_sheet.csv`
- `docs/0602/泸县0609质控点-P0候选人工复核表.md`

填写说明：

1. 接受样本：填写 `review_status=accepted`，确认或调整 `accepted_case_type`，填写 `reviewer_note`。
2. 拒绝样本：填写 `review_status=rejected`，清空 `accepted_case_type`，填写 `reject_reason`。
3. 不确定样本：保持空白或 pending，不导入正式 golden cases。
4. P0 复核表是人工处理表，复核结论仍需回写到 `luxian_0609_golden_review_queue_merged.csv` 后再执行队列质量校验和导入。

生成 P0 表后，可以先构建首轮复核优先级，只挑每条 P0 规则的阳性、阴性、边界各 1 条优先确认：

```bash
python scripts/qc/build_luxian_0609_p0_review_priority.py --write
```

输出：

- `docs/0602/luxian_0609_p0_review_priority.json`
- `docs/0602/luxian_0609_p0_review_priority.csv`
- `docs/0602/泸县0609质控点-P0复核优先级.md`

注意：优先级脚本只给人工复核顺序，不会自动写入 `accepted`，也不会写入正式 golden cases。

## 回写 P0 复核表到复核队列

人工在 `luxian_0609_p0_review_sheet.csv` 中填写 `review_status` 后，先 dry-run 检查将要回写的变更：

```bash
python scripts/qc/apply_luxian_0609_p0_review_sheet.py --write-report
```

确认变更无误后再写回 merged review queue：

```bash
python scripts/qc/apply_luxian_0609_p0_review_sheet.py --write --write-report
python scripts/qc/check_luxian_0609_review_queue.py --write
```

输出：

- `docs/0602/luxian_0609_p0_review_apply_report.json`
- `docs/0602/泸县0609质控点-P0复核表回写报告.md`

回写脚本只处理 `review_status` 非空的行。未填写结论的 P0 候选会被跳过，不会污染原始复核队列。

## 校验复核队列质量

人工复核前后都应先校验复核队列格式，避免 accepted/rejected 行字段不完整：

```bash
python scripts/qc/check_luxian_0609_review_queue.py --write
```

输出：

- `docs/0602/luxian_0609_review_queue_quality.json`
- `docs/0602/泸县0609质控点-golden-cases复核队列质量报告.md`

校验规则：

1. `accepted` 必须填写 `accepted_case_type`、`reviewer_note`、`evidence_expectation`。
2. `rejected` 必须填写 `reject_reason`，且不能填写 `accepted_case_type`。
3. `pending` 不能填写 `accepted_case_type` 或 `reject_reason`。
4. `positive accepted` 的 `expected_hit` 不能为 false；`negative accepted` 的 `expected_hit` 不能为 true。

## 导入 accepted 样本到正式 golden cases

人工复核完成后，在 `luxian_0609_golden_review_queue_merged.csv` 中把确认可用的候选标记为：

- `review_status=accepted`
- `accepted_case_type=positive/negative/boundary`
- `reviewer_note` 填写复核说明

先执行 dry-run 并生成导入报告：

```bash
python scripts/qc/import_luxian_0609_reviewed_cases.py --write-report
```

确认导入数量、重复样本和缺失样本类型无误后，再写入正式 golden cases：

```bash
python scripts/qc/check_luxian_0609_review_queue.py
python scripts/qc/import_luxian_0609_reviewed_cases.py --write --write-report
python scripts/qc/check_luxian_0609_golden_cases.py
```

输出：

- `docs/0602/luxian_0609_golden_import_report.json`
- `docs/0602/泸县0609质控点-golden-cases导入报告.md`

注意：导入脚本默认优先读取 `luxian_0609_golden_review_queue_merged.csv`。未标记为 `accepted` 的候选会被跳过，避免把未经人工复核的样本写入正式 golden cases。

默认所有自动候选均为 `review_status=pending`，导入器会跳过，不会进入正式 golden cases。人工复核通过后，需要填写：

- `review_status=accepted`
- `accepted_case_type=positive / negative / boundary`

建议先执行 dry-run：

```bash
python scripts/qc/import_luxian_0609_reviewed_cases.py --review-csv docs/0602/luxian_0609_golden_review_queue_merged.csv
```

确认导入数量符合预期后，才允许加 `--write`。

## 为合并复核队列生成证据包

自动候选与原始人工候选合并后，需要重新生成证据包，确保合并复核队列中的候选都能看到病历定位、文书清单和短证据片段：


- `docs/0602/泸县0609质控点-合并复核证据包.md`

## 正式版发布闸门

规则、样本、复核和评估都准备完成后，必须运行发布闸门。发布闸门会同时检查：

- 49 条规则目录是否完整。
- 规则实现状态是否都达到 `formal_ready`。
- 每条规则是否都有阳性、阴性、边界 golden cases。
- 人工复核队列是否无结构错误且已完成复核。
- 候选样本覆盖是否完整。
- 准确性评估是否全部达到发布候选标准。
- 客户样本验证页面是否已有闭环验收证据。

当前阶段建议先生成报告但不让命令失败：

```bash
python scripts/qc/run_luxian_0609_release_gate.py --write --no-fail
```

输出：

- `docs/0602/luxian_0609_release_gate.json`
- `docs/0602/泸县0609质控点-正式版发布闸门报告.md`

进入正式发布前，去掉 `--no-fail`，让脚本作为 CI 或交付前检查项：

```bash
python scripts/qc/run_luxian_0609_release_gate.py --write
```

如果仍有任何 `fail` 或 `unverified` 检查项，规则集不得标记为正式上线版本。

## golden cases 建设建议

`docs/0602/泸县0609质控点-golden-cases.json` 不应手工随意填写。建议来源顺序：

1. 客户样本池 item：
   - `manual_issue_text` 作为人工问题描述。
   - `candidate_rule_ids` 作为规则候选。
   - `matched_visit_id` 作为病历定位。
2. 客户样本验证任务结果：
   - `record_id` 对齐 `matched_visit_id`。
   - `rule_code` 对齐 `candidate_rule_ids` 或正式目录的 `rule_ids`。
   - `evidence`、`findings`、`document_type` 用于证据确认。
3. 人工复核结论：
   - 确认为阳性后，填入 `positive`。
   - 明确不应触发的正常病历，填入 `negative`。
   - 数据不足、排除条件成立、相似但不应触发的病例，填入 `boundary`。

每个 case 建议结构：

```json
{
  "case_id": "LX0609-001-P-001",
  "visit_id": "2324802",
  "sample_item_id": "optional-sample-item-id",
  "expected_status": "已命中",
  "expected_hit": true,
  "evidence_expectation": "入院记录完成时间超过入院后24小时，需能展示入院时间和记录时间。",
  "reviewer_note": "客户样本池人工标注确认。"
}
```
