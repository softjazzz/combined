# 泸县0609质控点正式上线长程任务

生成时间：2026-06-10

## 目标

把“泸县0609质控点验证 v1”从演示规则包升级为可正式用于客户样本验证的专项质控集。上线口径不是“页面能发起任务”，而是 49 条客户质控点都能在样本验证病历上给出稳定、可解释、可复核的质控结果。

最终交付应满足：

- `/workstation-v4/customer-sample-validation` 可选择并运行“泸县0609质控点正式版”。
- 49 条质控点逐条具备明确的执行定义、数据依赖、触发条件、排除条件和证据链。
- 每条规则能在样本病历中输出结构化结果：是否命中、命中原因、文书/字段证据、整改建议、置信度。
- 规则结果不依赖“看起来像”，而是通过黄金样本集和自动化评测脚本验证准确性。
- 不伪装能力：未接入医嘱、费用、检查、检验等数据前，相关规则不能标记为正式可用。

## 工作边界

### 本任务包含

- 泸县0609 49 条客户质控点的正式规则目录。
- 文书类、跨文书类、跨表联查类规则的执行链路补齐。
- 样本验证页面规则集选择和任务执行闭环。
- 规则级证据链展示和结果可复核。
- 黄金样本与准确率评估脚本。
- 阿里云百炼 `qwen3.5-35b-a3b` 作为语义判断模型的默认验证模型。

### 本任务不包含

- 修改正式业务写入表。
- 把疑似问题直接写入正式质控结果。
- 为了演示把待补规则做成空壳。
- 暴露 raw_response、prompt、medical_text、documents、embedding、内部 bundle。

## 上线判定标准

每条质控点必须达到以下最小标准，才允许进入“正式版”规则集：

| 标准     | 要求                                                                        |
| -------- | --------------------------------------------------------------------------- |
| 规则定义 | 有唯一规则 ID、客户原文、规范依据、判定口径。                               |
| 触发条件 | 明确什么情况下适用，例如有手术记录、有输血记录、恶性肿瘤诊断、病危医嘱等。  |
| 排除条件 | 明确不适用场景，例如局麻除外、急诊抢救手术除外、无相关检查/医嘱时不触发。   |
| 数据依赖 | 明确需要哪些文书、结构化表、时间字段或费用项目。                            |
| 执行器   | 明确程序规则、LLM 语义规则、跨文书规则或跨表联查规则。                      |
| 证据链   | 输出必须能引用具体文书、时间、字段或原文片段。                              |
| 整改建议 | 建议必须对应当前问题，不能是模板话术。                                      |
| 黄金样本 | 至少有 1 个阳性样本和 1 个阴性样本，或说明该规则在当前样本池缺少阳性/阴性。 |
| 准确性   | 在可验证样本上达到既定阈值。                                                |
| 安全边界 | 不暴露敏感内部字段，不写正式业务表。                                        |

## 准确性指标

第一阶段不追求“理论 100 分”，但正式上线要有量化门槛：

- 文书存在性/时限类：Precision >= 0.95，Recall >= 0.95。
- 跨文书一致性类：Precision >= 0.90，Recall >= 0.90。
- LLM 语义判断类：Precision >= 0.85，Recall >= 0.85，且必须有人审抽样复核。
- 跨表联查类：结构化数据覆盖率 >= 0.90 后再进入正式版；覆盖率不足时只允许进入灰度版。
- 严重缺陷规则：不得出现明确证据不足仍高置信命中的情况。

## 规则分层

### A 类：可优先正式化

适合先完成并进入正式版：

- 入院记录、首次病程、手术记录、抢救记录的完成时限。
- 48 小时主治查房、72 小时高级职称查房。
- 病程记录复制粘贴。
- 主诉不能导出第一诊断。
- 术前小结、手术记录、手术安全核查、知情同意书等文书缺失。
- 术前讨论、四级手术 MDT。
- 输血知情同意、输血前评估、输血记录、输血后评价等文书存在性与完整性。

这类规则的重点是把现有“近似规则”改成客户口径，并补齐证据链。

### B 类：需要跨文书补强

适合第二批完成：

- 病情稳定患者 3 天无查房病程记录。
- 会诊记录单与请会诊执行记录闭环。
- 请会诊执行记录照抄会诊意见。
- 恶性肿瘤手术记录未写淋巴结清扫情况。
- 恶性肿瘤出院后治疗计划缺失。
- 手术植入物信息不完整。
- 手术记录非手术者签字。
- 麻醉访视缺失或填写不规范。
- 麻醉记录单缺失。
- 术中输血多文书记录不一致。

这类规则必须先建立按 `visit_id` 聚合文书 bundle 的能力，不能把全病历粗暴塞给模型。

### C 类：需要跨表联查

适合第三批完成：

- 病重患者 2 天无查房病程记录。
- 病危患者每日查房或病情变化记录缺失。
- CT/MRI 检查前病程记录或原因缺失。
- CT/MRI 报告后 24 小时未记录或阳性结果未分析。
- 细菌培养报告后 24 小时未记录或阳性菌未分析。
- 化疗记录与医嘱不一致。
- I/II 类切口预防抗菌药物使用超时。
- 输血前常规检查不完整。
- 输血医嘱与收费不一致。

这类规则必须接入医嘱、检查、检验、费用、输血等结构化数据，数据覆盖率不达标时不能上线正式版。

## 长程任务拆解

### M1：建立正式规则目录和上线门禁

目标：先让 49 条规则有机器可读的正式目录。

交付物：

- `docs/0602/luxian_0609_formal_rule_catalog.json`
- `docs/0602/泸县0609质控点-正式上线规则清单.md`
- `scripts/qc/check_luxian_0609_catalog.py`

验收：

- Excel 49 条全部在正式目录中有唯一条目。
- 每条都有状态：`formal_ready`、`needs_evidence_hardening`、`needs_cross_document`、`needs_data_linkage`、`blocked_missing_source`。
- `formal_ready` 规则必须能映射到真实存在的规则 ID 或程序执行器。
- 检查脚本失败时能明确指出缺哪条、缺什么字段、引用了不存在的规则 ID。

### M2：补齐 A 类规则并建立黄金样本

目标：把低风险、高确定性的文书类规则先做成真正可用。

交付物：

- A 类规则的客户口径实现。
- 每条 A 类规则至少 2 个黄金样本。
- `scripts/qc/evaluate_luxian_0609_rules.py`

验收：

- A 类规则在样本池中可批量执行。
- 输出包含文书名、记录时间、命中字段或原文证据。
- 文书存在性/时限类 Precision 和 Recall 均不低于 0.95。

### M3：补齐 B 类跨文书规则

目标：构建规则级文书 bundle，让跨文书比对稳定可复核。

交付物：

- `qc_context_bundle` 或等价的规则级上下文聚合服务。
- 会诊、手术、麻醉、输血相关跨文书规则执行器。
- B 类规则黄金样本。

验收：

- 每条 B 类规则只读取必要文书，不读取无关全病历。
- 结果能显示参与比对的文书和关键字段。
- 跨文书类规则 Precision/Recall 不低于 0.90。

### M4：补齐 C 类跨表联查规则

目标：接入结构化数据，使医嘱、检查、检验、费用类规则可以真实判断。

交付物：

- 医嘱分类器：病危、病重、手术、化疗、抗菌药物、输血。
- 检查检验分类器：CT、MRI、病理、细菌培养、阳性/异常结果。
- 费用项目映射：至少覆盖输血相关费用。
- C 类规则灰度执行报告。

验收：

- 结构化数据覆盖率报告可生成。
- 数据覆盖率不足的规则自动标记为 `insufficient_data`，不输出假阳性。
- 跨表联查规则达到灰度阈值后才进入正式版。

### M5：样本验证页面正式闭环

目标：让客户样本验证页面可以清楚地区分正式版、灰度版和待补规则。

交付物：

- 规则集选择：SC 全量、泸县0609正式版、泸县0609灰度版。
- 任务结果中显示规则覆盖状态、数据覆盖状态、命中证据。
- 对未上线规则展示“待补/待联查”，不混入正式统计。

验收：

- 发起泸县0609正式版时，只运行达标规则。
- 发起泸县0609灰度版时，可选择包含待验证规则，并明确标识。
- 页面可导出样本验证报告。

### M6：上线前回归与报告

目标：形成可给客户/院方看的正式上线报告。

交付物：

- `docs/0602/泸县0609质控点正式上线验收报告.md`
- 规则准确率报告。
- 样本验证截图或导出结果。
- 未达标规则清单和原因。

验收：

- 所有 `formal_ready` 规则通过自动化评测。
- 没有空壳规则进入正式版。
- 没有敏感内部字段泄露。
- 代码检查通过。

## 推荐执行顺序

1. 先做 M1，不改业务逻辑，建立规则目录和自动门禁。
2. 再做 M2，拿 A 类规则快速形成可信演示闭环。
3. 然后做 M3，解决客户最容易人工核查的跨文书问题。
4. 最后做 M4，处理依赖结构化数据的规则。
5. UI 优化放在 M5，但不能用 UI 掩盖规则未完成。
