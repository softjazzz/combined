## 49 条质控点不是直接执行 49 次

泸县 0609 在规则管理页展示的是 49 条客户质控点，编号形如 `LX0609-001`。

执行时并不是把这 49 条包装规则直接提交给 LLM，而是：

1. 前端选择 `luxian_0609_qc_v1`。
2. 后端通过 `resolve_sample_validation_rule_set_by_key()` 解析规则集。
3. 规则集在 `backend/app/services/qc_rule_sets.py` 中定义。
4. 49 条客户质控点映射为 59 条底层可执行规则。
5. 底层规则 ID 包括 `SC-*`、`LX-*`、`LXE-*`、`CL-*`。
6. 批量任务执行的是这 59 条底层规则。

因此，页面上应明确区分：

- 客户质控点数：`49`
- 底层执行规则数：`59`
- 实际命中问题数：按任务结果统计

## 分桶机制

底层执行规则进入 `QCRuleOrchestrator.evaluate_rules()` 后，规则会先分为：

- 程序化规则：本地程序直接判断。
- LLM 规则：进入 LLM 分桶执行。

LLM 规则按规则元数据构造 bucket key：

- `execution_domain`
- `doc_scope`
- `rule_family`，仅 `domain_family` 策略时参与；`fixed_packs` 下主要按 `execution_domain + doc_scope` 分组。

随后每个 bucket 内再按固定 pack 大小尝试批量调用 LLM。批量返回必须满足：

- JSON 可解析。
- 返回包含全部期望规则。
- 没有缺失规则 ID。
- 没有低置信度规则 ID。

任一条件失败，就会触发 pack fallback，把当前包拆小或退回单规则执行。

## 当前风险

### P0：多病历选择范围问题

现象：在一次选择 8 份病历的任务中，实际只跑了 1 份。

原因：样本池为 `running` 场景，但选中的多数病历在终末病历范围；原逻辑只按样本池 scene 统计和执行。

处理：已补充 `effective_scope=all` fallback。后续再跑多病历时需要先确认任务详情里的 `total_records` 等于实际选中去重病历数。

### P1：固定分包 fallback 过高

现象：单病历 9 个 pack 中 8 个 fallback。

可能原因：

- 批量 LLM 返回缺失某些 rule_id。
- 批量 JSON 解析失败。
- 部分规则低置信度触发拆包。
- pack 内规则异质性太强。

影响：

- 耗时变长。
- token 消耗升高。
- “分桶执行”的吞吐优势没有充分发挥。

### P1：缓存没有命中

本次 `cache_hit=0`、`cache_miss=59`。如果同一病历、同一规则集重复验证仍无缓存命中，需要进一步检查缓存 key 是否包含不稳定字段，或样本验证链路是否没有复用缓存。

### P1：前端缺少机制可见性

页面目前更像展示任务结果，没有把以下机制指标清楚展示出来：

- 客户质控点数 49
- 底层执行规则数 59
- LLM 调用数
- 程序化规则数
- pack 数
- fallback pack 数
- cache hit/miss
- 运行范围 `running/final/all`

这些指标不展示，现场很难解释为什么任务耗时、为什么 49 条规则执行出了 59 条规则结果。

## 下一步建议

### 第一步：只跑 1 份，先看机制

下一轮不要直接跑 8 份。建议在页面选择 1 份病历，确认：

- 页面显示选中 1 份。
- 任务详情 `total_records=1`。
- 规则集为 `luxian_0609_qc_v1`。
- `rule_count=59`。
- 任务完成后能看到 pack/fallback 指标。

### 第二步：补任务详情的机制字段

建议在客户样本验证任务详情中增加只读诊断区：

- 规则包：泸县0609质控点验证 v1
- 客户质控点：49
- 执行规则：59
- 执行策略：快速筛查
- 分桶策略：固定分包
- 实际包数：来自 `summary.pack_metrics.total_packs`
- fallback 包数：来自 `summary.pack_metrics.fallback_packs`
- LLM / 程序化：来自 `summary.executor_breakdown`
- 缓存命中：来自 `summary.cache_breakdown`

### 第三步：先降低 fallback，再扩大样本

如果单病历仍出现大比例 fallback，优先检查批量 LLM 输出协议和 pack 规则组合，而不是继续扩大到 8 份。目标是：

- 单病历 `fallback_packs / total_packs` 明显下降。
- 任务耗时稳定。
- 每条问题都有可复核证据。

### 第四步：再跑 3 份，最后跑 8 份

建议节奏：

1. 1 份机制验证。
2. 3 份小批量稳定性验证。
3. 8 份 POC 验证。

只有前一阶段机制稳定，才进入下一阶段。
