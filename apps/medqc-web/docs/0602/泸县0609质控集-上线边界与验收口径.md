# 泸县0609质控集-上线边界与验收口径

更新时间：2026-06-16

## 1. 文档目的

本文用于统一“泸县0609质控点验证 v1”的客户沟通、演示说明、POC 验收和后续上线边界。核心目标是避免把“可演示、可验证、可辅助复核”的能力误解为“可直接正式上线、可自动裁决、可进入绩效扣分”的能力。

本文适用于：

- 给医院院长说明系统价值和当前边界。
- 给质控科说明哪些结果可复核、哪些仍需人工确认。
- 给信息科说明数据依赖、接口缺口和上线风险。
- 给研发团队约束后续规则、证据链、任务架构和页面展示。

## 2. 当前能力定位

当前 `luxian_0609_qc_v1 / 泸县0609质控点验证 v1` 定位为：

| 能力状态                     | 是否允许 | 说明                                                                 |
| ---------------------------- | -------- | -------------------------------------------------------------------- |
| 演示                         | 允许     | 可用于展示客户第一批质控点的规则管理、样本验证、批量任务和结果证据。 |
| 受控 POC                     | 允许     | 可在限定样本池、只读任务、人工复核前提下验证规则效果。               |
| 影子运行                     | 允许     | 可并行跑在真实业务之外，结果只用于观察、调优和人工复核。             |
| 自动进入正式缺陷考核         | 不允许   | 当前缺少足够真实 golden answer 和持续准确率证明。                    |
| 自动写正式质控结论           | 不允许   | 不写正式缺陷结果表，不作为正式病历质控裁决。                         |
| 影响归档、医保结算、绩效扣分 | 不允许   | 不进入病案归档、医保结算、绩效扣分或责任追踪闭环。                   |

## 3. 必须保留的安全边界

1. **只读运行**：泸县0609质控任务默认只读分析，不改病历、不改首页、不改结算清单、不改正式质控结果。
2. **人工复核**：所有 `non_compliant`、`data_gap`、`uncertain`、`technical_error` 结果必须保留人工复核入口。
3. **数据缺口显式展示**：缺少医嘱、费用、检查、检验、输血、麻醉、术前讨论等数据时，只能显示数据不足，不能显示合格。
4. **合成样本隔离**：`LX0609_SYN_*` 或客户自建测试病历不得混入真实生产统计、归档、医保结算和正式质控。
5. **敏感信息过滤**：前端和报告不得暴露 `raw_response`、`prompt`、`embedding`、完整病历全文、内部链路数据。
6. **版本留痕**：规则集版本、规则版本、模型版本、样本池版本和人工复核记录必须可追溯。

## 4. 验收状态定义

泸县0609结果只允许使用以下状态，前端、报告和统计口径必须保持一致：

| 状态              | 含义                               | 是否计入缺陷 | 是否计入合格 | 处理方式                             |
| ----------------- | ---------------------------------- | ------------ | ------------ | ------------------------------------ |
| `non_compliant`   | 确有缺陷或高度可信风险             | 是           | 否           | 必须展示证据和建议，进入人工复核。   |
| `compliant`       | 满足规则要求                       | 否           | 是           | 必须说明关键满足点。                 |
| `not_applicable`  | 触发事件不存在，例如无手术、无输血 | 否           | 否           | 单独统计为不适用，不进入分母。       |
| `data_gap`        | 数据不足，无法判断                 | 否           | 否           | 单独统计为数据不足，列明缺失数据。   |
| `uncertain`       | 模型或规则无法稳定判断             | 否           | 否           | 进入人工复核，不得自动判缺陷或合格。 |
| `not_executed`    | 规则未执行、工具未接入或被门控跳过 | 否           | 否           | 展示未执行原因。                     |
| `technical_error` | 模型、网络、解析、数据库或任务异常 | 否           | 否           | 展示技术错误并允许重试。             |

## 5. 当前验收边界

### 5.1 可以作为演示或受控 POC 的内容

- 规则集选择和批量任务创建。
- 客户样本池、客户自建测试病历和合成样本验证。
- 49 条客户质控点的规则目录、规则分型和依赖说明。
- 已接入主干的 Trigger Gate、客户点聚合、程序化规则结果和部分 PG/CDM 证据补全。
- 合成样本和少量真实样本的机制验证。
- 结果按 `non_compliant / compliant / not_applicable / data_gap / uncertain` 分流展示。

### 5.2 可以做受限验收的内容

- 已具备数据、证据链和 golden answer 的单条或小批量规则。
- 程序化时限、存在性、字段完整性规则。
- 已验证的跨文书规则，例如固定比较对象明确、证据能定位到文书和时间。
- 只读批量任务的创建、执行、查看、导出。

### 5.3 必须标注待接入或人工复核的内容

- 全量 49 条规则正式上线。
- 依赖医嘱、费用、检查检验、输血、麻醉、手术执行验证的数据联查规则。
- LLM-only 的严重缺陷自动裁决。
- 真实生产准确率、召回率、误报率承诺。
- 进入正式质控考核、归档、结算或绩效闭环。

## 6. 上线闸门

泸县0609规则从 POC 进入试点前，至少需要满足：

1. 49 条规则均完成规则分型和数据依赖标注。
2. 每条可验收规则均有证据链 schema 输出。
3. 每条可验收规则至少有阳性、阴性、边界或数据缺口样本之一，且经过人工复核。
4. 高风险规则人工复核一致率达到约定阈值。
5. `data_gap`、`not_applicable`、`uncertain` 不被计入合格率。
6. 前端能清晰展示证据、数据缺口、人工复核状态和规则版本。
7. 后台任务具备失败重试、运行日志和审计留痕；正式上线前需迁移到队列化任务架构。

## 7. 对外表达建议

对院长：

> 当前系统可以帮助医院快速发现病案质控风险、形成问题概览和复核线索；现阶段定位为只读辅助和受控 POC，不直接替代质控员正式裁决。

对质控科：

> 每条命中结果必须能看到触发事实、来源文书、关键片段、判断理由和处理建议；数据不足时系统会明确提示，不会把缺数据当作合格。

对信息科：

> 规则准确性依赖 PG/CDM 数据覆盖，尤其是医嘱、检查检验、输血、费用、手术麻醉文书。缺少数据源的规则会显示 `data_gap`，不进入正式判断。
