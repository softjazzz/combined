# 泸县0609质控分桶策略优化方案

## 1. 背景

泸县0609质控点验证 v1 包含 49 条客户质控点，映射为 58/59 条底层可执行规则。当前质控执行依赖 LLM 批量评估，多条规则会被打包成 pack 一次调用模型。

前期旁路 POC 显示：

- `baseline_current` 在三份样本上速度和 token 成本最好。
- `domain_family_max5` 虽然拆得更细，但耗时更长，token 约为 baseline 的 1.9 到 2.0 倍。
- 两种策略都能返回完整 JSON，但逐规则结论差异很大，约 24 到 27 条规则发生判断变化。

这说明当前核心问题不是“模型能否返回 JSON”，而是“同一规则在不同 pack 上下文里是否会改变判断”。因此，分桶策略不能只按 fallback、耗时、token 选择，必须同时考虑医学质控准确性、适用性判断稳定性、证据可复核性。

## 2. 当前 baseline_current 的真实行为

规则集配置中写的是：

```text
bucket_strategy = fixed_packs
```

但后端 orchestrator 当前只支持：

```text
domain_only
domain_family
```

因此 `fixed_packs` 会被归一化为 `domain_only`。

`domain_only` 的实际 bucket key 是：

```text
execution_domain + doc_scope
```

以泸县0609样本为例，实际分为 4 个桶：

| bucket                      | 规则数 | selected pack size | 正式执行 pack 数 |
| --------------------------- | -----: | -----------------: | ---------------: |
| admission::primary          |      4 |                  3 |                2 |
| consult_discussion::primary |      3 |                  3 |                1 |
| course::primary             |     26 |                 15 |                2 |
| surgery::primary            |     25 |                 15 |                2 |

当前 baseline 的优点是吞吐好、调用次数少、token 成本低；问题是 `course` 和 `surgery` 两个大桶内部混合了时限、存在性、签名、跨文书一致性、检验检查分析等不同逻辑，容易引发适用性判断和证据判断不稳定。

## 3. 优化原则

### 3.1 不直接迁移 domain_family_max5

`domain_family_max5` 只能证明“更细分会改变判断”，不能证明“更准”。在没有人工金标准前，不应把它迁入主干。

### 3.2 保留 baseline_current 作为吞吐基线

当前主干继续保留 `baseline_current`，用于生产对照和吞吐兜底。

### 3.3 新增 hybrid_medqc_v1 作为旁路策略

新增旁路策略 `hybrid_medqc_v1`，只在 POC 脚本中运行，不改 `QCRuleOrchestrator`、不改正式任务表、不写正式质控结果。

分桶维度从单纯：

```text
execution_domain + doc_scope
```

扩展为：

```text
execution_domain
+ doc_scope
+ evidence_group
+ trigger_group
+ logic_type
+ risk_tier
```

目标是让同一个 pack 内的规则尽量共享同一批证据、同一类触发条件和相近的判断逻辑。

## 4. hybrid_medqc_v1 分桶设计

### 4.1 evidence_group

证据源分组，用于决定模型主要看哪类材料。

| evidence_group               | 含义                                       |
| ---------------------------- | ------------------------------------------ |
| admission_record             | 入院记录、主诉、现病史、入院诊断           |
| course_records               | 病程记录、查房记录、病情变化记录           |
| lab_reports_course_notes     | 检验报告 + 病程分析处理                    |
| imaging_reports_course_notes | CT/MRI/影像报告 + 病程分析处理             |
| surgery_docs                 | 手术记录、术前讨论、术后病程、手术安全核查 |
| anesthesia_docs              | 麻醉记录、麻醉同意书、麻醉相关签名         |
| transfusion_docs             | 输血医嘱、输血记录、输血知情同意           |
| consult_discussion_docs      | 会诊申请、会诊记录、讨论记录               |

### 4.2 trigger_group

触发条件分组，用于降低“不适用”和“不合规”之间的翻转。

| trigger_group     | 含义                         |
| ----------------- | ---------------------------- |
| admission_event   | 入院事件、首次病程、入院时限 |
| critical_status   | 病危、病重、抢救             |
| surgery_event     | 手术、术前、术后、麻醉       |
| transfusion_event | 输血、血浆、输血前检查       |
| consult_event     | 会诊、讨论、MDT              |
| abnormal_lab      | 异常检验、细菌培养、危急值   |
| abnormal_imaging  | 阳性影像结果                 |
| general_trigger   | 一般触发条件                 |

### 4.3 logic_type

判断逻辑类型，用于控制 prompt 难度和 pack size。

| logic_type            | 含义                           |
| --------------------- | ------------------------------ |
| timeliness            | 时限类                         |
| existence             | 文书或字段存在性               |
| signature_consent     | 签名、授权、知情同意           |
| lab_followup          | 检验异常分析处理               |
| imaging_followup      | 影像阳性结果分析               |
| cross_doc_consistency | 跨文书、医嘱、费用、执行一致性 |
| semantic_content      | 内容完整性和语义充分性         |
| general_semantic      | 一般语义判断                   |

### 4.4 risk_tier

风险层级用于限制 pack size。

| risk_tier   | 含义                                       |
| ----------- | ------------------------------------------ |
| normal      | 常规质控                                   |
| normal_high | 普通偏高风险，需证据充分                   |
| high        | 高风险，如抢救、病危、麻醉、输血、四级手术 |

## 5. pack size 策略

`hybrid_medqc_v1` 不使用全局固定包大小，而是按逻辑类型和风险层级动态限制：

| 场景                      | 推荐上限 |
| ------------------------- | -------: |
| 高风险 + 跨文书/检验/影像 |        3 |
| 高风险 + 签名/知情/存在性 |        5 |
| 跨文书一致性              |        3 |
| 检验异常分析              |        5 |
| 影像阳性结果分析          |        5 |
| 签名/知情同意             |        5 |
| 时限/存在性               |        8 |
| 一般语义判断              |        8 |

旁路 POC 中，`hybrid_medqc_v1` 使用候选包大小：

```text
3 / 5 / 8
```

并启用：

```text
partial_accept = true
network_retry_first = true
```

## 6. 旁路 POC 实现范围

脚本：

```text
scripts/qc/poc_luxian_0609_pack_strategy_lab.py
```

新增策略：

```text
hybrid_medqc_v1
```

输出目录：

```text
.runtime-logs/qc-pack-poc/
```

输出文件：

```text
luxian_0609_pack_strategy_<timestamp>.json
luxian_0609_pack_strategy_<timestamp>.md
```

旁路 POC 明确不做：

- 不改正式 `QCRuleOrchestrator`。
- 不改正式规则集配置。
- 不创建正式批量任务。
- 不写正式质控结果表。
- 不替换客户样本验证页面的生产执行策略。

先用三份已测样本做对比：


## 8. 验收口径

### 8.1 工程指标

- `final_result_count / llm_rule_count >= 0.98`
- `fallback_rate` 不高于 baseline 明显水平
- `provider_error_count` 不超过 baseline + 1
- token 不超过 baseline 的 1.5 倍，若超过需说明收益
- 耗时不超过 baseline 的 1.3 倍，若超过需说明收益

### 8.2 质控效果指标

仅凭自动结果不能判定更准。必须对以下差异做人工复核：

- `not_applicable -> non_compliant`
- `compliant -> non_compliant`
- `non_compliant -> compliant`
- `uncertain -> non_compliant`
- 高风险规则状态变化

人工复核结论以源文书证据为准，不以模型置信度为准。

### 8.3 是否迁入主干

只有满足以下条件，才考虑把 `hybrid_medqc_v1` 迁入主干灰度：

- 在小型 golden set 上准确率优于 baseline。
- 高风险规则漏报不增加。
- 不适用判断错误率下降。
- 证据引用质量不下降。
- token 和耗时在可接受范围内。

## 9. 下一步建议

1. 跑三份样本的 `baseline_current` vs `hybrid_medqc_v1` 旁路对比。
2. 生成规则级差异清单。
3. 抽取 20 到 30 条差异规则做人工复核。
4. 根据人工复核结果调整 `logic_type / trigger_group / evidence_group / risk_tier` 规则元数据。
5. 将稳定策略固化为正式可观测配置，再考虑灰度进入主干。

## 10. 当前结论

当前不建议直接替换 `baseline_current`。推荐路线是：

```text
baseline_current 继续作为生产吞吐基线
hybrid_medqc_v1 作为旁路策略验证准确性和稳定性
人工 golden set 决定是否迁移
```

核心原则：

> 质控 pack 不是越大越省，也不是越小越准；关键是同一 pack 内规则是否共享证据、触发条件和判断逻辑。高风险规则小包强证据，低风险规则大包摊薄成本。
