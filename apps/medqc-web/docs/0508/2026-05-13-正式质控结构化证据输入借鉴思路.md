# 正式质控结构化证据输入借鉴思路

> 目的：记录对 `nexorin9` 公开仓库中病历质控相关原型的可借鉴方向，作为下一轮正式质控证据组织升级的任务入口。本文只做方案备忘，不代表已引入代码。

## 背景

当前正式终末 `fast_screen_full / sc_content_full_v1` 已能稳定运行 84 条内涵质控规则，并通过阿里云百炼完成 10 病历只读抽检。现阶段主要瓶颈不再是调用链路，而是结果质量稳定性：

- LLM 首审有时抓到短片段、文书标题、记录时间等弱证据。
- 二审裁决虽然能拦截一批误判，但仍依赖输入证据质量。
- `data_quality_gap` 中大量问题并非源库缺失，而是缺结构化跨文书对照、反证和 coverage flags。
- `confirmed_defect` 的可交付性取决于证据是否完整、可读、可追溯。

因此下一步不宜继续单纯调 prompt 或放宽 confirmed 准入，而应升级“规则证据输入层”。

## 可借鉴仓库方向

### 1. `emr-narrative-coherence-tracker`

仓库方向：病历叙事一致性、时间线冲突、实体一致性、医嘱与病程记录一致性检测。

可借鉴点：

- 将跨文书一致性拆成 detector，而不是让 LLM 泛读所有文书。
- 重点关注：
  - 时间线矛盾：入院、手术、会诊、出院时间不一致。
  - 实体矛盾：诊断、手术名称、部位、转归在不同文书中不一致。
  - 医嘱-病程一致性：有医嘱但病程无记录，或病程描述与医嘱不符。

对应本项目：

- 建议新增“跨文书一致性 evidence pack”。
- 优先服务 SC-019、SC-083、SC-100、SC-125、SC-146 等需要跨文书对照的规则。

### 2. `emr-compliance-evidence-generator`

仓库方向：将合规条款转换成证据要素，生成可审计的 evidence list。

这是最值得借鉴的方向。

可借鉴点：

- 每条规则先定义 evidence schema：
  - 必需证据：没有这些证据不能确认缺陷。
  - 支持证据：增强判断的片段或字段。
  - 反证：说明规则不适用或问题不存在的证据。
  - 缺口：当前 bundle/CDM 中缺失的证据。
- LLM 只基于结构化证据包裁决，减少无关上下文干扰。

对应本项目：

当前方式：

```text
规则 pack + bundle 文书上下文 -> LLM 首审 -> 后处理/二审裁决
```

建议升级为：

```text
规则 -> evidence schema -> 结构化证据包
     -> 程序化 precheck / coverage flags
     -> LLM 首审
     -> LLM 二审裁决
     -> 四层准入分流
```

### 3. `medical-record-evidence-chain`

仓库方向：病历矛盾证据链追因，聚合医嘱、计费、护理、文书时间线，生成调查清单。

可借鉴点：

- 不只输出“有问题”，还输出证据链断点。
- 断点类型可分为：
  - 源库缺表或缺行。
  - 本地 CDM 未同步。
  - bundle 未覆盖。
  - 文书已覆盖但结构化字段不足。
  - 规则证据不足。

对应本项目：

- 可以统一 `data_quality_gap`、Sheet2 blocked backlog、source/local/bundle audit 的缺口表达。
- 页面上可以把“数据缺口”展示成“证据链断点”，而不是像质控缺陷。

### 4. `qc-evidence-validator`

仓库方向：验证质控动作与电子病历记录是否匹配，输出质控盲区台账。

可借鉴点：

- 对每个规则结果做 evidence validation：
  - 缺陷结论是否有直接原文。
  - 原文是否来自正确文书。
  - 是否存在反证。
  - 是否只是记录时间、标题、模板词。

对应本项目：

- 可以作为二审前的确定性 guardrail。
- 对 confirmed_defect 增加硬门槛：必须有直接 quote、字段来源、文书类型、触发条件和反证检查结果。

### 5. 医嘱、计费、护理、输血、病理专项仓库

相关方向包括：

- `order-billing-nursing-timeline-auditor`
- `order-billing-lineage-tracker`
- `lab-medication-loop-detector`
- `pathology-report-kg-validator`
- `blood-transfusion-chain-verifier`
- `blood-transfusion-sequence-verifier`
- `blood-transfusion-safety-checker`
- `image-report-keyword-detector`

可借鉴点：

- 这类规则不适合完全靠 LLM 泛读，应该先用程序化 evidence flags。
- 典型证据链：
  - 检验异常 -> 病程处理意见 -> 医嘱调整/复查。
  - 手术记录 -> 病理送检/病理报告 -> 出院记录。
  - 输血申请 -> 配血 -> 输血记录 -> 病程观察。
  - 医嘱 -> 执行/费用/护理记录 -> 病程记录。

对应本项目：

- 先做 coverage flags，再交给 LLM 裁决。
- 不要让 LLM 在没有触发证据时判断“不完整”。

## 与当前质控方式的对比

### 当前方式优势

- 已跑通 84 条规则。
- pack 并发后速度稳定，阿里云百炼 10 病历抽检约 30-45 秒/份。
- 能快速覆盖多类语义规则。
- 不需要为每条规则先建完整证据模型。

### 当前方式短板

- 证据输入相对散，LLM 容易抓弱证据。
- 反证不足，导致不适用场景被误判。
- `data_quality_gap` 与真实数据缺失、bundle 缺口、规则证据不足混在一起。
- confirmed 质量高度依赖二审和 guardrail。

### 结构化证据输入优势

- 准确性更高：规则先限定“该看什么证据”。
- 可解释性更强：每条结论能回到必需证据、支持证据、反证、缺口。
- 更适合准生产：方便医生/质控科看懂，也方便定位是规则问题还是数据问题。
- 可减少无效 LLM 判断：不适用或证据缺口可程序化分流。

### 结构化证据输入代价

- 开发成本更高，需要为规则族定义 evidence schema。
- 短期不一定减少 token，因为需要补证据拼装和二审输入。
- 需要对 CDM/bundle/source coverage 更严格。

结论：不推翻当前 `fast_screen_full`，而是在它前面补“结构化证据输入层”。

## 建议落地顺序

### P0：先做高误判/高价值规则族

优先规则：

- SC-099：术中取材与病理结果记录。
- SC-100 / SC-101：植入物条形码、植入物种类数量。
- SC-036：异常检验检查结果未分析处理。
- SC-070：会诊意见未落实。
- SC-083：病程记录与治疗/检查/医嘱闭环。
- SC-019：入院/首次病程/出院诊断或病情依据一致性。

原因：

- 这些规则最近抽检中误判或 data gap 较集中。
- 都需要触发条件、跨文书对照和反证。
- 单纯调 prompt 收益有限。

### P1：定义统一 evidence schema

建议结构：

```json
{
  "rule_code": "SC-100",
  "trigger": {
    "status": "present | absent | unknown",
    "evidence": []
  },
  "required_evidence": [],
  "supporting_evidence": [],
  "contradicting_evidence": [],
  "missing_evidence": [],
  "coverage_flags": [],
  "data_quality_flags": []
}
```

关键要求：

- `trigger=absent` 时不得进入 confirmed_defect。
- `required_evidence` 不足时优先进入 data_quality_gap。
- 有明确反证时进入 rejected_by_system。
- LLM 二审必须解释引用哪条 evidence，而不是重新自由发挥。

### P2：接入正式质控链路

建议链路：

```text
bundle/CDM -> evidence builder -> evidence package
evidence package -> first-pass pack prompt
first-pass result + evidence package -> adjudicator
adjudicated result -> confirmed/data_gap/rejected/technical
```

注意事项：

- 保留现有 pack 并发和 provider 稳定性诊断。
- 不要一次性改 84 条。
- 每轮只选 3-5 个规则族，配套 10 病历只读回放和质量复核。

## 验收指标

每轮改造至少验证：

- Sheet2 回归不变：`exact_confirmed=156 / blocked_with_reason=102 / skip=25 / needs_exact_review=0`。
- 正式质控 provider 稳定：provider/upstream/parse/timeout/rate/technical 全为 0。
- `confirmed_defect` 复核保留率提升。
- `data_quality_gap` 分类更准确，能区分：
  - source_missing
  - local_missing
  - bundle_missing
  - evidence_schema_missing
  - true_data_gap
- `rejected_by_system` 抽样复核不能误驳回明显真实缺陷。
- 页面展示中 confirmed/data gap/rejected 的原因可读。

## 不建议做的事

- 不直接复制 `nexorin9` 仓库代码。先吸收结构设计，再按本项目 CDM/bundle/fast_screen 架构实现。
- 不扩大到 84 条全量 evidence schema 一次性改造。
- 不放宽 confirmed 准入来制造“更多缺陷”。
- 不把 data_quality_gap 当成医生病历缺陷展示。
- 不使用病历生成类仓库作为正式质控能力来源，避免系统边界混淆。
