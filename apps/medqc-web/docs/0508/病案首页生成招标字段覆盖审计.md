# 病案首页生成招标字段覆盖审计

## 审计范围

本审计基于现有代码只读梳理，未做业务逻辑修改。覆盖对象：

- 后端 schema：`apps/medqc-web/backend/app/schemas/frontpage.py`
- 后端抽取服务：`apps/medqc-web/backend/app/services/frontpage_extraction_service.py`
- 首页 API：`apps/medqc-web/backend/app/routers/frontpage.py`
- 医保结算清单组装：`apps/medqc-web/backend/app/services/settlement_assembly_service.py`
- 医保结算清单 API：`apps/medqc-web/backend/app/routers/settlement.py`
- 前端正式工作台展示：`apps/medqc-web/src/views/workstation-v4`

状态定义：

- 已支持：schema、prompt/抽取、后处理/编码、结算映射或 UI 中已有可用闭环。
- 部分支持：已有字段或 prompt，但结构、精度、逐项能力、证据或结算映射不足。
- 缺 schema：FrontPageDraft 缺明确结构化字段。
- 缺 prompt：抽取 prompt 未明确要求或要求不足。
- 缺编码：未输出 code/candidates/confidence 或未接入本地/语义/LLM 编码链路。
- 缺 UI：正式 workstation-v4 未展示或未按新结构展示。
- 缺测试：缺招标字段级回归测试。

## 总体结论

现有 frontpage 链路已经不是空白系统：基本信息、住院信息、诊断、手术、其他医疗信息、人员、费用七个模块都有 schema 和分模块 prompt；诊断/手术已有本地 ICD 后处理；结算清单已有 `FrontPageDraft -> settlement` 组装服务；正式工作台已有病案首页生成与粘贴病历入口。

但距离招标参数的“全病历阅读理解后自动生成病案首页 + 医保结算待遇清单，支持多上报场景”仍有关键缺口：

- 诊断结构仍以字符串数组为主，缺逐条诊断对象，无法稳定承载每条诊断的编码、候选、置信度、入院病情、证据。
- 当前 `FrontPageDiagnoses.admission_condition` 是全局字段；`settlement_assembly_service` 会把同一个入院病情套到所有其他诊断，不能满足逐诊断推理要求。
- 手术结构主手术字段较完整，但其他手术多为 `Dict[str, str]`，缺统一对象 schema、候选编码、术者代码、I/II 助代码、麻醉医师代码等逐条结构。
- 字段级 `evidence/confidence/source_document/source_text` 没有通用模型，只存在顶层 `evidence`/`confidence` 和部分诊断证据。
- `auto-generate-draft` 向后兼容可用，但没有 scene/report_scene，也没有统一返回 `frontpage + settlement + coverage + warnings`。
- `visit_id` 非流式路径失败时仍可能回退 demo，且注释仍写“当前为 demo/占位”，不符合“不允许静默 demo 空壳”的验收要求。
- 结算清单组装已存在，但映射不完整，费用分类、人员代码、其他医疗信息、逐诊断/逐手术结构损失较多。
- 正式工作台可展示主要字段，但缺场景切换、coverage/warnings、字段级 evidence/confidence 摘要和结算草稿联动展示。

## FrontPageDraft schema 现状与缺口

已存在分组：

- `basic_info`
- `hospitalization`
- `diagnoses`
- `procedures`
- `other_medical_info`
- `staff`
- `costs`
- 顶层 `evidence`
- 顶层 `confidence`

主要 schema 缺口：

- 缺统一字段元数据模型，例如 `FieldEvidence(value, confidence, source_document, source_text, normalized, warnings)`。
- `diagnoses` 缺逐条诊断对象。建议保留现有字段兼容，同时新增：
  - `ed_diagnoses: List[DiagnosisItem]`
  - `discharge_main_diagnosis: DiagnosisItem | None`
  - `discharge_other_diagnoses: List[DiagnosisItem]`
  - `tcm_diagnoses: List[DiagnosisItem]`
- `DiagnosisItem` 至少包含：`name/code/type/candidates/confidence/admission_condition/admission_condition_reason/source_document/source_text/evidence/outcome`。
- `procedures` 缺逐条手术对象。建议保留现有主手术字段，同时新增：
  - `main_procedure: ProcedureItem | None`
  - `other_procedures_structured: List[ProcedureItem]`
- `ProcedureItem` 至少包含：`name/code/candidates/confidence/date/level/operator/operator_code/assistant1/assistant1_code/assistant2/assistant2_code/incision_grade/incision_healing_grade/anesthesia_method/anesthetist/anesthetist_code/source/evidence`。
- `other_medical_info` 对损伤中毒、病理、ICU、昏迷仍是扁平字段，建议新增结构化子对象并保留旧字段。
- `costs.categories` 是 dict，缺明确医保费用分类 schema 和字段级 evidence。

## Prompt 覆盖现状与缺口

现有 prompt 已按模块拆分：

- `BASIC_INFO_PROMPT`
- `HOSPITALIZATION_PROMPT`
- `DIAGNOSES_PROMPT`
- `PROCEDURES_PROMPT`
- `OTHER_MEDICAL_INFO_PROMPT`
- `STAFF_PROMPT`
- `COSTS_PROMPT`
- `ADMISSION_CONDITION_PROMPT`

主要缺口：

- `DIAGNOSES_PROMPT` 对中医诊断没有明确字段；对“入院记录诊断/诊断类型: 初步诊断/其他诊断:”这类真实客户格式覆盖不足。
- `ADMISSION_CONDITION_PROMPT` 有逐诊断输出设计，但 schema/后处理没有稳定落到每条诊断对象。
- `PROCEDURES_PROMPT` 有人员字段，但其他手术结构不完整，不能保证每条其他手术都有术者/麻醉/切口/编码候选。
- `OTHER_MEDICAL_INFO_PROMPT` 覆盖招标字段，但缺 candidates/confidence/source。
- `COSTS_PROMPT` 有分类项，但结算清单费用字段没有完整展开映射。

## 编码链路现状与缺口

已存在：

- `local_icd_service.py`
- `icd_coding_service.py`
- `icd_code_mapper.py`
- `external_coding_service.py`
- `resolve_diagnosis_codes`
- `resolve_procedure_codes`

主要缺口：

- 诊断和手术候选编码字段不统一。已有 `discharge_main_icd_suggestions` 等部分字段，但没有逐条 `candidates/confidence`。
- 损伤中毒外部原因、病理诊断缺独立编码输出和候选。
- 现有编码后处理偏“填最终 code”，不够支撑招标要求的可解释、可审核编码。

## 医保结算清单映射缺口

`SettlementAssemblyService` 已能把 `FrontPageDraft` 和 CDM SQL 组装为结算草稿，但存在：

- 诊断列表映射使用旧数组字段，其他诊断共用全局 `admission_condition`。
- 手术列表只映射主手术和 `other_procedures` dict 的部分字段，人员代码/麻醉医师代码/助手代码不完整。
- 费用字段只默认 `total_cost`，没有把 `costs.categories` 展开到医保清单明细。
- 其他医疗信息中 Rh、过敏药物、损伤中毒外因、病理编码、ICU 转移、昏迷等映射不完整。
- `_generate_draft` 只尝试读取 `ai_generation_results`，与当前 `save_ai_frontpage_draft` 的存储表/字段不完全一致，实际可能回退到 MR 伪草稿。
- API 返回是裸 settlement dict，没有 scene/frontpage/coverage/warnings。

## visit_id 文书聚合现状

现有 `frontpage_extraction_service.py` 已有两条路径：

- `_get_medical_text(visit_id)`：拼接 MR、入院记录、出院记录、诊断表、病程、手术、检验、检查等。
- `_get_llm_context_text(visit_id)`：精简拼接入院、出院、首次病程、日常病程、手术、检验检查等。

风险：

- `generate_draft_from_visit` 注释仍称“当前为 demo”，且 LLM 失败会回退 demo。
- `extract_from_text` 空文本也会回退 demo。
- 招标验收要求“不允许 success 但实际返回 demo 空壳”，需要改为明确错误或 partial/warnings。

## 前端展示现状与缺口

已存在：

- 正式 `workstation-v4` 病案首页生成与粘贴入口。
- `StructuredDataView` 可展示核心基本信息、住院信息、诊断、手术、其他医疗、人员、费用。
- `SettlementWorkspace` 可展示结算清单草稿并运行结算形式质控。

缺口：

- 病案首页/医保结算/联合草稿没有统一场景切换。
- coverage/warnings/confidence/evidence 未作为统一生成结果展示。
- 新增逐条诊断、逐条手术对象尚无正式 UI。
- 其他医疗信息展示不足：损伤中毒、ICU 进出、昏迷、病理编码、过敏药物等未完整展示。

## M1 建议边界

考虑完整招标改造跨度较大，M1 应先做可运行闭环：

- 新增或扩展请求参数 `scene/report_scene`，默认兼容旧 `auto-generate-draft`。
- 新增统一生成服务：输入 `medical_text/documents/visit_id`，输出 `scene/frontpage/settlement/coverage/warnings`。
- 保持旧字段兼容，同时新增逐条结构字段。
- `combined` 场景返回首页草稿和结算清单草稿；不写业务表。
- coverage 先以招标字段矩阵计算：present/missing/partial/warnings。
- visit_id 无文书时返回明确错误或 `partial + warnings`，不静默 demo。
- 前端先展示场景切换和覆盖摘要，详细字段复用现有 `StructuredDataView` / `SettlementWorkspace`。
