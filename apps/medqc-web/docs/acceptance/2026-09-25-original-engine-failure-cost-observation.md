# 原始 LX0609：异常失败时的成本观测边界

## 问题与最小修复

正式 Worker 的外层异常由 `fail_batch_job` 写入任务失败状态。若前一个进度摘要已写入 `luxian_0609_usage_observation_complete=true`，异常可能发生在后续模型调用期间；原失败事务原样保留该标记，公开任务 DTO 会把无法确认的调用成本展示为完整观测。

只在**正在运行的 LX0609 任务**由该失败事务收尾时，把观测完整性置为 `false`。此前已记录的 Token 数和未知执行器键保留；不将其清零，不推断实际新增用量。排队阶段的接纳失败没有进入模型执行，其他规则集不更改此字段。任务的临床结果、失败状态、自动重试与 Canonical 写入协议未修改。

随后核对运行中任务续约过期的另一条失败事务，复现了相同误报：已保存的完整观测标记在失去执行 owner 后仍为 `true`。该事务原本只处理带续约标记的 LX0609 任务，现也将完整性置为 `false`，保留已经观测到的 Token。旧代次的迟到写入仍由既有代次条件拒绝。

## 复现与验证

- 隔离 SQLite 任务表中，领取后的任务先保存 `usage_observation_complete=true` 和 12 个已观测 Token，再调用正式失败事务。修复前断言得到 `true` 而失败；修复后数据库及客户安全 DTO 均为 `false`，已观测的 12 个 Token 保留。
- 排队阶段失败不凭空产生用量观测标记；非 LX0609 运行任务的既有摘要不变。
- 带续约标记的运行中任务先保存完整观测标记与 12 个 Token，再模拟续约过期。修复前失败任务仍显示 `true`；修复后数据库显示 `false`，12 个已观测 Token 不变，旧代次完成仍被拒绝。
- `test_luxian_0609_attempt_boundary_audit.py` 整份 33/33 通过；该文件连同失败族归因和正式扩展持久化两组共 36/36 通过。Ruff 与 `git diff --check` 通过。

测试只覆盖进程内服务对隔离 SQLite 的真实事务。客户 PostgreSQL 多进程竞争、模型实际中断时的费用和安装包恢复没有被此测试证明；它们仍是长程 goal 的外部退出证据。
