# LX0609 Golden 签核最小流程

日期：2026-07-21

## 目的与当前边界

当前 `shadow45` 是固定 20 例、45 条规则的安全候选运行，不是已验收
Golden。900 条记录均为 `candidate`，全局客户主链接入仍为 **0/49**。

本流程的目标不是一次人工复核 900 条，而是先取得一个规则范围明确、可追溯、
可回滚的“小批接入候选”。任何未被签收的规则继续保持 Shadow 或暂缓。

## 账本完整性门

accepted ledger 必须同时归档：

1. 人工复核所依据的 candidate ledger；
2. 三份同范围、同 selector 的无持久化运行产物；
3. 接受账本及审批记录。

质量门校验 accepted ledger 的 candidate digest，并逐行将 candidate 与第一份
基准运行的状态、受控原因码、证据摘要哈希对齐。第二、三份运行不会被当作
“配置错误”掩盖，而是继续参与确定性精确匹配或语义稳定性/PPV/召回门。

账本与导出物只允许包含 `case_label`、规则 ID、状态、受控原因码、摘要哈希及
审批元数据；不得携带病历正文、坐标、真实日期时间、提示词、原始模型输出、
截图或 SQL。case label 到真实就诊的映射仅保留院内受控环境。

## 第一批推荐范围

优先 `LX0609-029` 与 `LX0609-030`：两条均为确定性规则，当前固定20例候选
同时覆盖 `compliant`、`non_compliant`、`not_applicable`，且没有 `data_gap`。

为避免 promotion 工具要求“候选每一行都有显式签收”而出现漏审，第一批应重新
运行 **固定20例 × {029, 030} = 40 条** 窄范围候选，并复核全部 40 条，而不是
在 900 条候选中事后抽取或删行。其余规则仍不随该批升级。

## 人工签核步骤

1. 在院内只读临床界面复核每一条 029/030：
   - `non_compliant`：确认触发条件及缺失事实；
   - `compliant`：确认目标文书/结构化事实确实满足；
   - `not_applicable`：确认触发事实不存在且来源完整。
2. 填写 review 模板的预期状态、受控原因码、审核人代号、时间、版本和接受状态；
   系统 observed 状态不得直接抄写为人工真值。
3. 通过 promotion 工具生成独立 accepted ledger；禁止手写或拼接 JSON。
4. 对同一 selector/rule set 连续运行三次：
   - 029/030 必须状态、原因码和证据摘要 100% 精确一致；
   - 技术错误为 0；隐私扫描为 0；开关关闭回滚保持旧链不变。
5. Golden gate 通过后，仍需业务批准人确认“仅 029/030”范围的接入和回滚编号，
   才能把这两条从 Shadow 提升为客户接入候选。

## 后续规则的分层原则

- 语义规则：除上述要求外，每条至少补足 3 个临床确认的 `non_compliant` 与
  3 个临床确认的非缺陷边界例，三次运行稳定，PPV ≥95%、召回 ≥90%。
- `data_gap`：不把它当作“无问题”。按“规则 × 原因码”分层抽核缺失原因是否真实；
  一旦发现系统性错误降级，冻结该规则。
- `not_applicable`：每个拟接入规则至少复核两个触发缺失样本。
- `LX0609-025`：已出现真实语义漂移，不进入任何候选接入批次，详见
  [025 稳定性审计](2026-07-21-lx0609-rule025-stability-audit.md)。

这是一套接入证据流程，不是用模型或脚本替代临床签核。
