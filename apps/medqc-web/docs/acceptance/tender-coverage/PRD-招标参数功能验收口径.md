# PRD - 招标参数功能验收口径

更新时间：2026-06-16

## 1. 文档目标

本 PRD 用于统一招标参数对应的产品功能边界、验收口径和演示口径。当前阶段采用“最低基本要求”作为验收边界：每个条款需要有可演示入口、真实接口或本地数据源、结构化结果展示和只读/草稿安全边界；不要求达到医学专家金标准、全字段 100% 覆盖、医保正式一致率或多源证据闭环。

验收对象是系统是否按招标参数字面形成可演示功能闭环。不以静态页面占位替代功能，但允许能力以草稿、模拟、候选建议、待人工复核方式完成。

2026-06-16 专家评审补充口径：

- 当前系统适合用于演示、受控 POC、影子运行和人工复核辅助，不适合直接进入医院正式缺陷考核、病案归档、医保结算或绩效扣分闭环。
- 合成样本验证通过只能证明程序路径、状态流和证据格式可运行，不能等同于真实病历质控准确率。真实验收必须补充分层真实样本和经质控专家确认的 golden answer。
- 本 PRD 的“可演示闭环”不等于“可正式上线”。所有会影响正式首页、医保结算、DRG/DIP 正式结果、正式缺陷认定或绩效扣分的结论，必须保留人工复核和上线闸门。

## 2. 通用安全边界

- 自动生成结果只能进入草稿、预览、模拟或待人工复核状态。
- 不自动写正式病案首页。
- 不自动写正式医保结算清单。
- 不自动写正式 DRG/DIP 入组结果。
- 不自动写正式质控缺陷结果，不自动进入病案归档、医保结算或绩效扣分闭环。
- 不向前端或报告暴露 `raw_response`、`medical_text`、`documents`、`record_content`、`internal_data`、`prompt`、`embedding`、`vector`。
- 病案智能助手、SQLBot、统计问数和批量任务默认只读；必须使用工具白名单、RBAC、二次确认和审计日志控制高风险动作。
- 客户自建测试病历必须与真实生产病历隔离。POC 阶段允许使用 `CUSTOMER_TEST`、专用 visit_id 前缀或独立样本池；正式环境建议使用独立 schema、测试库或 `is_test=true`，并从正式统计、导出和考核中排除。

## 2.1 结果状态和统计口径

质控、首页生成、编码建议、DRG/DIP 模拟、付费监测等智能结果必须区分业务结论和技术状态。

允许的业务状态：

- `non_compliant`：确有缺陷或风险，必须有证据和建议。
- `compliant`：符合规则，必须说明关键满足点。
- `not_applicable`：触发事件不存在，例如无手术、无输血、无病危病重医嘱。
- `data_gap`：当前数据不足，不能判定，例如缺医嘱、费用、检查报告、麻醉记录或输血数据。
- `uncertain`：模型或规则无法稳定判断，需要人工复核。

正式上线前应补充的技术状态：

- `not_executed`：规则或能力未真正执行，例如被门控跳过、依赖工具未接入或规则未实现。
- `technical_error`：模型、解析、网络、数据库或任务执行异常。

统计要求：

- `not_applicable` 不计入缺陷率或合格率分母，应单独展示为“不适用”。
- `data_gap` 和 `technical_error` 不能算作合格，应单独展示为“无法判断/数据不足/技术异常”。
- LLM-only 的严重缺陷、低置信度、状态反转、证据缺槽、跨表冲突、影响医保/结算/绩效的结论必须进入人工复核。

## 2.2 证据链最低要求

所有面向客户展示的质控、编码、首页生成、入组和付费监测结果，应尽量提供可复核证据。最低证据字段包括：

| 类型     | 必要字段                                                        |
| -------- | --------------------------------------------------------------- |
| 规则信息 | `rule_id`、规则名称、规则版本、规则集版本、执行器类型           |
| 触发证据 | 是否适用、触发事实、触发来源、不适用原因                        |
| 数据依赖 | 需要的表/文书/字段、已接入数据、缺失数据                        |
| 来源定位 | 来源表、文书类型、文书 ID、记录时间、字段路径、原文片段或结构值 |
| 判断过程 | 阈值、比较值、实际值、差值、结论                                |
| 复核信息 | 置信度、人工复核状态、复核人、复核意见                          |

时限类规则必须额外展示：触发时间、截止时间、实际完成时间、计算间隔、来源表/文书、时间字段名。

跨文书规则不能只输出“内容不一致”或“记录不完整”，应输出证据矩阵，例如术前小结、术前讨论、手术记录、麻醉记录之间的冲突字段、文书来源和记录时间。

## 2.3 任务架构和上线边界

当前进程内 detached 线程池可用于演示和小规模 POC，目标是避免前端请求等待长时间 LLM 任务。但正式上线前，批量质控、首页生成、DRG/DIP 分析和付费监测应迁移到队列化任务架构，至少具备：

- 任务持久化。
- 幂等键。
- 重试和死信队列。
- 任务取消和恢复。
- 并发隔离和限流。
- 审计日志。
- 可观测性和运行状态查询。

在队列化任务完成前，所有长耗时任务只能作为演示或受控 POC 能力，不应承诺生产级高并发稳定性。

## 3.1 能力分级口径

### 3.1.1 可先作为演示能力

以下能力可以作为院长演示、售前演示或受控 POC 展示，但不得直接承诺生产闭环：

- 首页自动生成草稿。
- 医保结算清单草稿。
- 智能编码查询和候选推荐。
- DRG/DIP 预入组和模拟结果。
- 病案问题概览。
- 病案智能助手问答。
- SQLBot 问数入口。
- 合成样本验证。
- 报表导出。

### 3.1.2 可做受限验收

以下能力可以在明确安全边界、数据范围和人工复核前提下做受限验收：

- 规则集选择和客户样本池验证。
- 后台批量任务创建、进度和结果查看。
- 已确定性实现且证据完整的时限、存在性、字段完整性规则。
- 部分首页和结算清单字段完整性、规范性审核。
- 只读编码候选查询。

### 3.1.3 必须标注待接入、数据不足或人工复核

以下能力不能包装成已正式完成：

- 泸县0609或其他客户质控点全量正式上线。
- 跨医嘱、费用、检查检验、输血、麻醉、手术执行验证的规则，若对应数据源尚未完整接入。
- LLM-only 的严重缺陷自动裁决。
- 医保付费监测正式结论。
- 正式 DRG/DIP 分组结果。
- SQLBot 自由问数直接访问生产病历明细。
- 自动写正式病案首页、医保结算清单或正式质控结果。

## 3.2 当前阶段不纳入阻塞验收的增强项

以下内容属于后续增强，不作为当前最低基本要求的阻塞项：

- 首页和结算清单所有字段 100% 自动提取准确。
- 使用脱敏金标准样本证明医学准确率、字段召回率或医保一致率。
- 通过手术记录、麻醉记录、医嘱、费用和手术相关单据等多源证据严格证明手术是否真实执行。
- 自动写入正式病案首页、医保结算清单、正式 DRG/DIP 入组结果或正式质控结果。
- 对全部地区、全部医院付费方案完成生产级本地化适配。
- 对所有 DRG/DIP 指标、报告和导出格式完成生产级经营分析闭环。

## 3.3 条款级补充说明

### 3.3.1 首页自动生成

首页自动生成当前按“草稿生成 + 来源展示 + 人工确认”验收。系统可以演示患者基本信息、住院信息、诊断及手术操作、其他住院医疗信息、人员信息和费用信息的抽取或缺失状态，但不得直接写正式首页。正式上线前需要补齐字段级证据、字段来源、置信度、人工采纳/驳回记录和版本审计。

### 3.3.2 ICD 编码和编码内涵质控

智能编码查询可以作为最低验收能力。编码内涵质控必须逐步补齐 ICD 字典版本、医保版/国临版映射来源、编码推荐依据、编码变更记录、病理编码和费用字段关联证据。不能把“编码是否存在”误称为完整编码内涵质控。

### 3.3.3 DRG/DIP 预入组和本地化适配

DRG/DIP 当前结果应标注为“模拟入组/预入组”。本地化适配不能只用配置表对账证明一致率，正式验收需要地区规则版本、医保分组结果回归样本、入组差异原因和人工复核记录。一致率 95% 属于后续金标准样本验收，不作为当前最低演示口径。

### 3.3.4 医保付费监测

付费监测可以展示费用风险、盈亏、支付率和控费建议的模拟结果。若医嘱、费用、医保清单、结算标准或地方付费标准不完整，结果必须标注数据不足或模拟分析，不能作为正式控费结论。

### 3.3.5 病案智能助手和问数能力

病案智能助手当前建议保持自研轻量 Agent Router，先保证工具白名单、只读边界、结果结构化和审计留痕。LibreChat 可作为对话壳或多模型管理候选，SQLBot 只能连接只读视图或分析库，不得连接生产病历全文表，不得允许自由 SQL 访问原始病历。

### 3.3.6 真实样本和 golden answer

上线前必须建立真实样本 golden set。合成病历用于验证机制、边界条件和状态流转；真实病历用于验证数据接入、真实书写差异、误报漏报；golden answer 必须由质控专家确认。POC 报告应包含样本范围、规则覆盖、数据接入覆盖、混淆矩阵、典型命中证据、误报漏报案例、待接入清单和上线边界。

## 4. 3.4.1 ICD 编码规范内涵质控专项定义

### 4.1 正向范围

3.4.1 只验收编码侧内涵，不验收普通病历书写质量。当前阶段最低要求是能在结构化样例或真实候选数据中识别或提示以下至少一类编码问题：

- 肿瘤主诊断编码与病理诊断编码、形态学 M 码之间的不一致或缺失。
- 病理编码存在时，病理诊断名称、病理诊断费和首页字段之间的不一致。
- 阑尾炎与腹膜炎同时出现时，是否需要按 ICD 规则合并编码。
- 冠状动脉支架置入术存在时，是否需要补充共同使用的附加编码。
- 诊断编码与手术操作编码不匹配。
- 医保版编码与国家临床版编码映射不一致。
- 编码问题对病案首页、医保结算清单、DRG/DIP 预入组结果的影响。

### 4.2 排除范围

以下内容不作为 3.4.1 的验收对象：

- 病程记录是否写得详细。
- 查房记录是否书写充分。
- 主诉、现病史、体格检查文字质量评价。
- 医生书写水平评价。
- 文书缺失、文书时限和文书格式问题。

这些问题分别归入：

- `3.3.1`：字段完整性、规范性、采集标准规则。
- `3.4.3`：疾病诊断画像、手术操作画像、诊断发生发展时间轴、手术操作执行与否验证，以及首页书写辅助对照。

### 4.3 结果卡要求

3.4.1 的演示结果应尽量展示：

- 当前诊断编码或手术操作编码。
- 触发的 ICD 编码规则。
- 编码依据和医学/规则解释。
- 推荐编码、合并编码或附加编码。
- 对首页、结算清单或 DRG/DIP 入组的影响。
- 只读提示：不写正式首页、不写正式结算清单、不写正式 DRG/DIP 结果。

## 5. 3.4.3 诊断及手术操作完整性校验专项定义

### 5.1 当前阶段最低要求

系统需要形成一个可演示闭环：

- 使用现有 `AIProfileDashboard.vue` 作为画像展示入口之一。
- 使用 `/api/v1/frontpage/profile/analyze` 或 `/api/v1/clinical-completeness/{visit_id}` 作为画像、时间轴或执行验证的数据来源。
- 页面明确展示四块内容：`疾病诊断画像`、`手术操作画像`、`诊断发生发展时间轴`、`手术操作执行与否验证`。
- 在病案首页页签旁提供 `画像辅助` 入口或提示区。
- 结果只作为病案首页书写或生成时的辅助对照，不写正式首页、结算清单或正式质控结果。

### 5.2 当前阶段不要求

- 不要求整合手术记录、麻醉记录、医嘱、费用、手术相关单据等全部证据源。
- 不要求证明每个手术“真实执行”的医学法证级闭环。
- 不要求自动判定全部首页诊断/手术漏填、错填或无依据。
- 不要求与正式病案首页字段做逐字段强联动写回。

## 6. 验收脚本

推荐总入口：

```powershell
python scripts\acceptance\run_tender_acceptance.py
```

前端截图证据可单独运行：

```powershell
npm run test:e2e:tender
```

验收通过只表示已经满足当前最低基本要求的可演示闭环。医学准确性、医保入组一致率、字段提取准确率和多源证据完整性仍需使用脱敏金标准样本集做专项评测。
