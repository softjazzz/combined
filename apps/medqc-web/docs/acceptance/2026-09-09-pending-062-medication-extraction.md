# 062 出院带药自由文本提取闭环

## 证据与边界

原病例只有一份出院记录，出院医嘱 213 字、有用药信号，无结构化带药列表，未命中四个固定字段标签。既有执行器返回 data_gap，模型调用为 0。完整自由文本反例（药名、剂量、途径、频次及疗程明确）同样返回 data_gap，已复现。

本轮不重新制定临床标准：沿用现有药名、剂量、途径、用药时间四组字段；现有用药时间组包含疗程/用药时间/频次，不将频次改为必须提供疗程。修复的是可读取的医嘱无法解析，不以减少待处理数量替代准确性。

## 实施方案

仅当结构化带药未提供、固定标签解析失败且只有一份非空出院医嘱时，调用一次独立受控提取。多份出院记录不猜选；已提供但非法的结构化字段不被模型覆盖；既有确定性分支保持 0 次调用。原执行器只增加该入口、调用计数，不堆入新的语义解析职责。

输入限该文书的 discharge_order，经已有隐私脱敏；最多 8000 字符，不静默截断。输出最多 20 项、4096 Token，一次 generate 且禁用长度重试；无模型客户端、超时、非法 JSON、额外字段、伪造原文引用为技术失败。逐药四字段明确 present/missing/uncertain，present 必须引用输入原文，missing 返回空值，任一语义不确定保留待判断，不猜剂量或途径。模型只抽取，Python 按既有规则计算完整性。

使用现有 executor resource 中的 llm_client；在新旧执行入口分别透传既有依赖，不新增公共接口、数据库字段、配置、缓存、Resolver 或注册层。NativeExtendedDocumentExecutionResult 既有 usage 字段承载实际调用及 Token；异常尝试也计数。

## 验收与风险

完整自由文本应可合规；明确缺字段仍应不合规；不确定与技术失败不可误报为医生漏写。严格测试边界、脱敏及引用、单次调用、既有结构化零调用，并经过 Binding 与最终客户结果验证。真实原病例只裁剪出院医嘱做受控复核，不自动更新任务或发布包。

尚未覆盖多份出院记录的选择合同，也未改公共出院截止时间来源优先级；不得宣称所有待处理结果已修完。源库资料缺失及暂停规则需分别处理。

## 验证结果

- 新抽取单测 24 项、真实执行与最终聚合集成测试 8 项；连同已有 extended、出院事实映射、renderer、registry 共 747 项通过（3.88 秒）。主协调补充超时原因码与传输错误区分后，32 项再次通过（0.38 秒）。
- 两个实际执行入口均透传既有 llm_client，模型用量沿原有 envelope 字段返回；结构化、超长和不在单份范围的测试保持 0 次调用。
- 人工构造的非患者两药文本使用项目配置 qwen3.7-flash / dashscope.aliyuncs.com 真实验证：ready，2 项均有四字段原文引用，1 次网络请求，294 输入 + 269 输出 = 563 Token，约 2.764 秒。未写业务库或观测数据库。
- 原病例在用户补充授权后完成真实验证：仅发送脱敏后的 213 字出院医嘱至项目配置的阿里云百炼，qwen3.7-flash 返回 1 项带药，四字段均为可在原文定位的引用。主协调亲自核对药名、1贴、外用、bid\*7天，无补写。实际 native → Binding → 最终结果为 compliant / requirement_satisfied，missing_fields 为空；1 次网络请求，371 输入 + 155 输出 = 526 Token，约 2.210 秒。此前受限环境传输失败及自动审批拒绝均未算作成功验证，用户补充授权后才重新执行。未写业务库或观测数据库。
- 前端没有修改；无自动修复 ESLint 通过。现有 check:encoding 扫描 0 文件，另对本轮文件独立严格检查 UTF-8 无 BOM/LF。

## 对客户问题的回答

本轮主要是技术解析缺口，而非要求医生补写已经存在的信息。现有“用药时间”允许频次/疗程的历史口径保持不变，若医院要求两者都具备，应另行确认标准。出院截止来源优先级是另一项未定合同，不能凭本轮代码修复替代确认。源码完成不等于客户机部署完成，原任务与正式发布包尚未更新。

独立审查未发现阻塞问题；另修正非法 API 耗时时仍保留已验证 Token 统计，新增反例后抽取模块 25 项再次通过（0.23 秒）。原任务保存结果和客户机发布包未更新。
