# 原始 LX0609 阶段 B：客户样本规则族子任务配置读取只读审计

## 审计范围

固定代码基线 `9d5fc3e68281bd8356e34bc005bc8cf6e6447f1d`。本轮不改生产代码，只用合成病历验证：客户样本一次提交生成父任务和两个不同规则族子任务；第一子任务完成后改变医学设置，再启动第二子任务。真正执行了样本路由的范围解析和子任务生成、正式四川批量 Worker、`SichuanQCService.evaluate_running_final_bundle_input` 与原始 LX0609 `prepare_luxian_0609_execution`。外部病历源、数据库配置读取、模型、证据表读取被隔离替换。

## 已确认事实

- 样本路由把 `rule_set_version`、`task_frozen_date`、`record_evaluation_snapshot`、`record_scene_snapshot` 原样写入同一父任务及两个子任务。测试固定一份三坐标齐全的合成在院病历，选择 `LX0609-01-01-01` 与 `LX0609-07-01-01`，实际产生两个不同规则族子任务。
- 两个子任务先后启动时，正式 Worker 分别调用 `get_settings()`；每个 Worker 将本次读取的 Settings 传给 bundle 服务与规则准备阶段。`get_settings()` 本身每次重新构造 Settings，没有全局缓存。同一父任务的固定日期和规则集版本**不冻结医学设置**。
- 第一子任务使用关闭通用触发门禁的设置，第二子任务使用开启该门禁的设置，两者均完成；`prepare` 实际收到不同 Settings。合成空来源下结果分别为 001 `data_gap/authoritative_time_missing`、输血 07-01-01 `not_applicable/trigger_absent_complete`。这证明同一任务可以混用运行时医学设置，**不证明这两条合成结果已经发生临床结论漂移**。
- 第二次再关闭输血 Native 执行开关，第二子任务在正式计划门禁处失败，未进入 `prepare`，第一子任务仍已完成。这是安全拒绝，不是静默回退；父任务是否应整体失败及客户展示另属任务汇总验收范围。
- Worker 读取 `rule_set_version` 后用于进度、观测及结果摘要；在本轮所追执行路径未看到它与当前目录/代码版本做一致性校验。测试没有在运行中替换 Python 代码，因此不能据此断言跨版本部署必然混合执行。

## 证据与局限

专属测试 `backend/tests/unit/test_luxian_0609_family_children_settings_readonly.py` 包含两组固定输入与期望，两个场景均经过真实路由和正式 Worker 参数链。测试不调用真实模型、不写客户库，不把运行时预算/并发变化当成医学缺陷，也不声称两次设置变化导致该合成病历的最终状态不同。医学开关的切换由受控 Settings 提供者模拟；生产中须配置文件/环境被重新读取或后续子 Worker 在新进程启动，才会出现相同条件。
任务创建时间在测试内固定为 2026-09-24；规则、三坐标、病历场景、来源空集及两个子任务的结果状态均由测试明确断言。

本轮先固定可复现事实，未提出或实现新的配置冻结框架。后续若决定修复，应先确定哪些开关构成必须同代次的医学判定合同，再用真实病例或受控固定模型响应证明结果影响；运行预算可保持每 Worker 独立变化。
