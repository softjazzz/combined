# LX0609 原始 Worker 执行尝试边界修复

## 问题与基线

审计基线提交 `1e5496c1c` 证实：取消后以同一任务 ID 重试，旧 Worker 的迟到结果可以覆盖新一轮执行；`running` 可被重复领取；正式重试路由可重复提交同一任务 ID。取消保持终态时，原有 `complete_batch_job` 已用条件更新阻止迟到 Canonical 写入，因此本次保留这条有效保护。

## 修复边界

只对 `rule_set_key=luxian_0609_qc_v1` 的正式任务建立执行尝试身份。`queued→running` 由单条条件更新原子领取，同时把随机代次写入现有 `filters_json` 内部字段。领取方法返回数据库实际保存的完整 JSON 文本快照；Worker 在第一次 `await` 前持有它。进度、取消轮询、完成、失败、自动重试都核对此快照。重试仅接纳终态任务，并通过原状态和原始文本做条件更新；重新入队也更新代次，避免授权检查尚未返回的旧 Worker 将新一轮 `queued` 写成失败。手工重复请求返回 409，且不会二次提交后台任务。未增加数据库列、锁或全局状态机。

`started_at` 不作为身份：数据库时间精度和冻结时钟都可能让前后两次执行取到同值。内部字段只用于事务条件，不进入模型/规则配置，也不通过客户安全投影展示。0916 与通用任务未改为此机制。

完成和失败保留任务行更新与 Canonical/父任务刷新在同一归属判断之后；旧代次条件更新未命中时直接回滚，不能写结果或刷新父任务。已有取消判定继续生效。

## 隔离验证

`test_luxian_0609_attempt_boundary_audit.py` 中 16 项隔离 SQLite 测试通过：取消后旧完成不能覆盖新 `running`；重复领取只成功一次；重复手工重试仅提交一次；固定相同 `started_at` 时旧进度、失败、轮询和自动重试被拒；真实 Worker 在受控 provider `await`、通用 QC 评估分支和正式 0609 bundle 评估分支的受控 `await` 发生取消、同 ID 重试与新领取后，旧 Worker 不能发布。父任务重试对两项不同规则族、不同 rule_ids 和科室筛选的子任务各自轮换不同代次，保留各自原业务筛选；某子任务仍在 running 时，父重试整笔回滚，无部分子任务被重置。旧子 Worker 的授权失败不能污染新排队任务。当前尝试可以正常写进度、完成并只自动重试一次。真实 CanonicalResultStore 在同一 SQLite 事务中验证旧尝试零行、新尝试写入一行且可按病例三坐标读取有效 Envelope。无代次调用不能写入已领取的正式任务；授权失败只可写入同一 `queued` 快照，旧快照不得写入重新入队的新任务；内部 UUID 不出现在读取 DTO 的 `filters`。原 detached runner 无去重的事实测试保留，说明互斥由存储领取和路由接纳负责。

测试使用合成 `JWT_SECRET`、指向本机不可达端口的合成 `DATABASE_URL` 完成模块导入，实际事务替换为隔离 SQLite；没有访问客户库或模型。正式分支测试保留 Worker 的原生规则包选择和 `evaluate_running_final_bundle_input` 调用边界，用合成 bundle、证据输入和返回桩控制 await；证明迟到写入被挡，不代替真实医学判定回放。Canonical 测试使用生产 CanonicalResultStore 与真实结果表定义的 SQLite 副本，不再替换最终保存方法；它验证保存和读取门禁，但不代替 PostgreSQL 并发集成验收。需要主协调 Agent 在集成树上再做固定输入回放与真实任务链验收。

扩展运行既有 throughput 文件时，前 35 项通过，第 36 项是原测试预期非法旧编号返回 422，当前规则目录预检返回 503；此处发生在任务创建，尚未进入本修复的领取/重试路径。其余失败尚未逐项归因，不能据此宣称全套回归通过。既有 result-persistence 合同文件在进程内仅把模块初始化 engine 指向隔离 SQLite、跳过生产 schema 同步后，13 项全部通过；事务替身与被测实现未替换。`ruff check`、语法编译和暂存文件编码检查通过。

## 局限

主协调集成验收：`172c1eb1f/ca3a308b9` 集成后，测试fixture显式将 `_draft_schema` 置为无schema，避免集成环境的生产 `qc` 配置污染隔离SQLite。15项执行代次与2项三入口测试共17项通过；既有持久化合同在进程内只隔离初始化engine/schema同步后13项通过，npm lint通过。仍需补不同子任务筛选保留、父任务重试整体回滚及实际Canonical Store保存测试，不能用探针代替真实保存证明。

本次生产修改保留在现有任务事务所有者和Worker内：领取、重试、进度与完成必须共享现有SQL事务条件；新建转发模块不能减少这些调用点，反而会增加身份传递边界。因此未在本次修复中拆分已有大文件，也未同时修改医学规则。

此修复不取消模型请求本身。旧 Worker 在下一个取消检查前可能已产生外部调用费用，但迟到结果不能交付。若进程在任务 `running` 期间崩溃，任务恢复策略仍由既有调度管理，本次没有新增租约或超时恢复。多进程 PostgreSQL 事务互斥还需要在集成环境验证；SQLite 测试证明条件更新逻辑与可达调用路径。
