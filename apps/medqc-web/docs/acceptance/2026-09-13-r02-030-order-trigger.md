# LX0609-030 手术医嘱触发修复验收

## 问题证据

LX0609-030 的正式目录、业务基线、Planner 和确定性门禁均要求：存在明确手术医嘱或已实施手术事实时，必须核对手术记录。正式 typed 运行时 Provider 原先只生成已实施手术事实，没有生成手术医嘱事实，导致“有手术医嘱但无手术记录”被错误判为不适用。

0910 样本原始 CDM 核对显示：C17 有一条结构化 `order_type=手术`、`order_status=新开` 的有效医嘱，且手术记录为 0，旧结果却为 `not_applicable/trigger_absent_complete`。C19 的有效医嘱均为已知非手术类型；C29、C30 各有两条 `order_type=麻醉` 的有效医嘱，现有权威分类器无法证明其属于手术医嘱或非手术医嘱。

只补触发事实仍不完整：typed 030 原先只允许绑定手术记录引用，而缺手术记录场景没有该引用；来源注册表也没有允许 030 使用 `inpat_nondrug_order` 作为决策支持来源。这会使正确命中的 C17 被升级为技术异常。

## 最小修复

- 正式 typed Evidence Session 路径复用已有手术医嘱分类器。完整来源中的明确有效手术医嘱生成 `current_visit_surgery_order_confirmed/ordered` 事实。
- 完整来源中的已知非手术医嘱保持完整否定，允许判不适用；分类不确定、来源截断或完整性未证实时停止确定性否定，安全返回数据不足。
- 030 缺手术记录时只绑定同一快照中分类器确认的阳性医嘱行；不使用 signal hash 或来源级引用替代阳性证据。
- 仅为 030 增加 `inpat_nondrug_order` 决策支持来源；029、032 的来源和判定合同不变。
- 修复 typed 数据不足结果的原因码映射，避免合法 `data_gap` 被转换为 `technical_error/decision_contract_violation`。

## 剩余风险

`order_type=麻醉` 是否应长期归入明确非手术类型，需要结合客户源系统字典形成单独口径。当前实现保留数据不足，避免用医嘱名称猜测手术。无 snapshot 的旧 runtime 兼容入口仍不读取完整医嘱类型字段；正式 typed Bundle/Evidence 主链不受影响。
