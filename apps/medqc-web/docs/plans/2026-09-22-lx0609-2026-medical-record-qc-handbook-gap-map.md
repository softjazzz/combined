# LX0609 与《病案管理质量控制指标检查要点指导手册（2026版）》差距映射

> 日期：2026-09-22
> 文档来源：用户提供的四川省病案质量控制中心《病案管理质量控制指标检查要点指导手册（2026版）》全文
> 对照基线：`docs/0602/luxian_0609_formal_rule_catalog.csv`、`backend/app/data/luxian_0609_rule_master_v1.json` 及当前 LX0609 正式执行器
> 本文只做规则差距和实施顺序分析，不代表新增规则已经进入生产。

## 1. 结论

这份手册适合作为 LX0609 的新增权威来源。现有 001–079 已覆盖病历时效、CT/MRI 结果记录与分析、病理取材与结果记录、培养结果记录与分析、围术期文书、输血、查房和部分知情同意，但对手册强调的“医嘱—执行—报告—病程”闭环仍有明显缺口。

优先扩展方向应是：

1. CT/MRI 医嘱与病程一致性、检查次数与报告数量一致性；
2. 病理报告完整性；
3. 微生物培养医嘱与病程一致性、报告完整性，并把细菌、真菌和病毒培养纳入统一事件范围；
4. 抗菌药物、化疗、手术和输血的医嘱—记录一致性；
5. 手术记录、手术安全核查表和抢救记录的内容完整性；
6. 不合理复制的两个现有空白场景。

新增规则继续使用 `LX0609-*` 独立编号。旧 `SC-*` 只能作为规则来源或历史证据编号，不复用旧执行器，不形成嵌套规则链。

### 2.5 规则编号、目录顺序与共享事实

2026-09-22方案更新：按照用户希望长期只有一套编号的要求，先独立完成四段式规则身份迁移，再扩展规则。此前长期保留三位 `rule_id`、另外展示四段 `rule_code` 的方案不再作为实施目标。

采用以下统一身份约束：

1. 目录直接保存四段式 `rule_id`，执行器、模型响应、保存、查询、前端及导出共用该身份。旧001–079通过一次性迁移处理，不留常驻转换层。
2. 四段式采用 `规则集-大类-子类-质控点`，例如 `LX0609-06-01-01`。编号发布后稳定，显示分组或排序改变不重新编号。
3. `06` 表示“检查检验”，其下 `01=CT/MRI`、`02=病理`、`03=微生物培养`；最后两位是在该子类内连续增长的质控点序号。以后新增 CT 规则只增加 `06-01-06`，不会被病理或培养规则隔开。
4. 旧新对应表只供迁移与等价验收使用，不进入生产读取链。任务选择、历史结果与反馈关联一并迁移；旧冻结验收产物保留归档，不覆盖原始证据。具体范围见身份迁移设计与盘点文档。
5. 现有 `family_key`、`executor_key` 继续负责执行归属和事实复用，不从业务编码推导执行逻辑。比如 CT/MRI 和培养可以同属 `exam_lab` 执行族，但分别拥有独立的影像事件和培养事件事实合同。

CT/MRI 组建议按业务流程连续展示：

| 业务编码 | 旧技术编号 | 规则 |
| --- | --- | --- |
| LX0609-06-01-01 | 无；新规则直接使用四段式身份 | CT/MRI 医嘱—病程一致性 |
| LX0609-06-01-02 | LX0609-010 | 检查前病程是否说明检查原因 |
| LX0609-06-01-03 | 无；新规则直接使用四段式身份 | CT/MRI 报告单完整性 |
| LX0609-06-01-04 | LX0609-011 | 影像报告结果是否记录 |
| LX0609-06-01-05 | LX0609-012 | 阳性影像结果是否分析 |

共享事实由 `exam_lab` 规则族一次形成“影像检查事件台账”，各规则只读取所需字段：

```text
影像检查事件
├─ 结构化事实：医嘱、执行状态、检查主记录、报告、检查时间、报告时间、事件关联状态
└─ 语义事实：病程是否提及检查、是否说明原因、是否记录结果、是否分析阳性结果、证据坐标

Python 逐事件判定
├─ CT/MRI-01 读取医嘱、执行和病程提及事实
├─ CT/MRI-02 读取检查前原因事实
├─ CT/MRI-03 读取检查次数、报告及关联状态
├─ CT/MRI-04 读取结果记录事实
└─ CT/MRI-05 读取报告阳性状态和分析事实
```

医嘱、执行、检查主记录、报告存在性、数量和关联由 Python 一次计算，不调用模型。确需语义识别时，以同一检查事件的最小病程窗口一次抽取受控原子事实，010–012及新增规则共享该结果；不允许按规则重复提交相同病历文本。某个语义字段失败只影响依赖它的规则，报告完整性等纯结构化规则仍须正常完成。

## 3. 推荐实施批次

### 第一批：现有数据链可直接支撑，优先做

## 4. 执行合同

### 4.1 多事件病例

手册规定同次住院多次检查或诊疗时，任意一次不符合即判该指标不符合。执行器必须逐事件判定，再归并：

```text
任一事件已确认不合规 → 规则不合规
没有已确认不合规，但存在无法关联/来源不完整事件 → 资料不足
全部相关事件合规 → 合规
来源完整且没有相关事件 → 不适用
```

未到检查时点、资料不足或技术失败的事件不得覆盖另一事件已经确认的不合规结果。

### 4.2 问题选项优先级

手册要求同一指标同时命中多个问题描述时优先选择前面的选项。患者质控页面仍应保留每个独立问题，便于医生一次修完；只有生成官方《检查记录表》的指标级摘要时，才按手册顺序选择首个问题类型。这个优先级应由对应指标执行器输出，不能由前端或通用聚合器重新解释。

### 4.3 LLM 边界

- 医嘱、检查主记录、报告数量、时间、签名和结构化必填字段由 Python 判定。
- 病程是否明确记录某次检查/治疗、阳性结果是否有分析、内容是否表达具体措施等语义事实，使用最小事件窗口做一次受控提取。
- 同一规则族共享事件事实，不为每个新增质控点重复调用模型。
- 模型只返回事件 ID、文书坐标和受控枚举，证据原文由 Python 按坐标回填。

## 5. 验收要求

1. 先冻结 001–079 在同一真实病例集上的状态、原因码、事实、证据定位、LLM调用数和耗时；新增规则不得改变保护集合。
2. 每条新规则至少覆盖：合规、不合规、不适用、资料不足；多事件规则另加“一次失败、其余成功”和“已确认失败+另一事件资料不足”。
3. CT/MRI 第一批必须覆盖：病程无医嘱、医嘱无病程、内容不一致、检查无报告、单次住院多次检查中一项失败。
4. 在客户样本验证中用同一批30份病例回放；如果某条规则没有自然阳性样本，补脱敏冻结样本，不能降低判据凑覆盖。
5. 新增规则继续使用全局40个HTTP槽位，但无适用事件时必须在规则族内部前置结束，不进入模型调用。
6. 新规则默认关闭，完成真实病例验收和客户结果文案复核后再进入默认规则集。

## 6. 当前最合适的下一步

先冻结第一批六条规则的正式名称、允许状态、来源表、事件业务键和失败语义。随后只开发 CT/MRI 两条规则作为首个小闭环，并同步清理 010 中错误归属的 `exam_report_missing` 判定。CT 小闭环通过后，再按同一模式扩展病理和培养，避免一次新增十余条规则而失去逐条复核能力。
