# V5 医生到质控端代码闭环模拟

## 范围与边界

- 运行、终末各一轮自动缺陷整改；沿用合法保存结果合同，不调用真实模型。
- 专属临时 PostgreSQL 集群、合成病例和持久账号，经正常登录及 JWT 进入正式路由；没有认证依赖替换。
- 使用 FastAPI TestClient 的进程内 HTTP，不是对运行中的 8011 发请求，不替代浏览器/部署环境验收。
- 文书修改由测试夹具模拟外部电子病历系统保存：只更新临时集群合成文书的正文与主诉，不宣称已实现产品文书编辑 API。
- 不改生产代码、迁移、规则版本选择、默认读取或前端；V7.1、本地产品成果、原保存结果均保留。
- 不推送、不合并、不写业务库；核心制度继续阻塞，80项代码台账61/80不增计。本轮不扩大为人工缺陷、申诉、病历审核等全业务验收。

## 模拟步骤

| 步骤 | 整改状态/版本 | 医生待整改 | 质控待验收 | 医生消息累计 |
| --- | --- | --- | --- | --- |
| 质控派发 | pending / 1 | 1 | 0 | 1 |
| 医生读取提醒 | pending / 1 | 1 | 0 | 1 |
| 质控催办 | pending / 2 | 1 | 0 | 2 |
| 医生首次提交 | submitted / 3 | 0 | 1 | 2 |
| 注入通知失败，驳回回滚 | submitted / 3 | 0 | 1 | 2 |
| 质控驳回 | rejected / 4 | 1 | 0 | 3 |
| 医生修改后重提 | submitted / 5 | 0 | 1 | 3 |
| 质控验收 | approved / 6 | 0 | 0 | 4 |
| 医生读取验收结果 | approved / 6 | 0 | 0 | 4（未读0） |

每步核对正式列表待办、精确对象消息和整改分析下钻。医生已提交在报表中按原合同显示为 `pending_acceptance`，不提前计作已整改。首次催办已被首次提交回应；重提之前没有新的有效催办，因此最终标签为 `self_rectified`，不是 `urged_rectified`。

额外断言：越权对象访问/提交/读消息被拒绝，医生不能自行验收，重复派发及旧版本提交返回409；通知失败时状态、事件和消息一同回滚；两次提交的文书对照各自保留；历史动作顺序准确；最终CSV与下钻一致。数据库前后结构相同，除合成整改、事件、消息和模拟文书外，其余表行完全不变，包括原质控结果。

质控端接收医生提交通过正式待验收列表验证，本轮不宣称新增了“医生提交后给质控员发统一消息”的能力。

## 复现

从应用的 `backend` 目录运行，选择空闲55000段端口：

```powershell
py -3.10 scripts/run_pr8_disposable_pg_tests.py --pg-bin 'D:/Program Files/PostgreSQL/18/bin' --port 55442 tests/unit/test_v5_doctor_qc_cycle_pg.py -s -o junit_family=legacy --junitxml=C:/medqc-pr8-adapt/apps/medqc-web/.tmp/0910-full-audit/v5-doctor-qc-cycle-private.xml
```

运行器禁读dotenv、限制连接到本次新建集群和合成库、禁止模型网络。每次新建合成数据库；结束自动停止自身PG集群，不操作5432或现有验收服务。私有日志/数据保留在应用忽略目录 `.tmp/0910-full-audit/pr8-pg-*-private/`，不提交。每轮步骤JSON打印为 `V5_DOCTOR_QC_CYCLE=`，也存入JUnit的 `v5_doctor_qc_cycle` property。
