# 客户机两条医嘱时间定向补数

## 授权和范围

用户确认客户机先备份，再补四列和 C17/C22 两条医嘱的空时间，不影响其他数据。
源端核查已证明三类时间有值、取消时间空；C17 的源通用名与本地 generic_name
口径不同，但编码相同且源商品名与本地 generic_name 完全一致，按预览 v2 校验。

仅修改客户机 medqc 库 cdm.inpat_drug_order，不对非药品医嘱、public 表、签名、
检验表或 Alembic 版本做变更。四列采用现有 000049 迁移的相同类型，后续正常迁移
会跳过这些已存在列；本脚本不声称完成整个 000049。

## 执行命令

将执行包放在 D:\medqc，解压至 D:\medqc\order-time-fill 后执行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass `
    -File 'D:\medqc\order-time-fill\fill-medqc-order-times.ps1' `
    -BackendPath 'D:\medqc\medqc-web-customer-R26.4\backend' `
    -BackupDir 'D:\medqc\backups' `
    -Apply
```

## 事务、备份和验证

源库强制只读事务，读取四坐标匹配的两行。目标 SERIALIZABLE 事务内锁定药品医嘱表，
锁等待上限 5 秒，SQL 超时 30 秒；若有自定义启用触发器，先拒绝继续以免连带修改。
事务写入之前保存原表列定义、原始两行和待补时间到本机 private JSON，fsync 并读回核对。
只给缺失字段加可空列，不改既有列类型、不设默认、不删表。
只更新原来为 NULL 且源端有值的字段；源空保留本地，非空冲突拒绝，重复执行已相同值不再更新。
提交前核对全部原有非目标字段和四个时间；任何失败回滚整笔 DDL/DML。
如果提交时连接中断，报告 data_committed=null，须核查后再操作，不声称一定回滚。

备份是这次修改的定向备份，不是全库备份；含原始两行，留在客户机，不需上传。
报告仅包含别名、目标列、结果、备份路径和受控错误码，不输出凭据或病历原文。

## 边界

不改订单状态、药名、开立/计划开始时间，不启用全局 homology 开关，不刷新 Bundle，
不改历史质控结果，也不调用模型。计划结束不等于已核实的实际停嘱。
客户机旧 R26.4 的规则读取补丁还未部署，数据库补数成功不代表旧规则立即读取了新列。

18 项补数脚本测试 + 16 项预览测试，合计 34 项通过；Ruff、编码及 PowerShell AST 检查通过。
覆盖真实 main 控制流中的备份失败不写入、校验失败回滚、成功只提交一次、提交断连报告未知，
以及四坐标更新、NULL 守卫、类型冲突、重复执行、时间时区和非目标字段保持不变。
连接均为测试替身，没有对真实本机或客户机执行补数，也未调用模型。
前端未修改、隔离树无 node_modules，本任务不运行前端全量检查。
