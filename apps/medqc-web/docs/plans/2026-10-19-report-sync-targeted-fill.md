# 病理诊断与死亡正文定向补全

客户只读验证确认C23/C25共5份病理报告本地诊断全空，C02/C03/C04/C06/C09共5份死亡记录本地正文全空；新口径生成的10条内容均完整，客户旧死亡章节映射尚未更新。

`backend/scripts/apply_report_sync.py` 是一次性运维入口，复用只读工具及生产homology适配，需显式传入 `--apply`。源库始终只读；本地只UPDATE这10条已有记录的诊断/正文字段，不按病例删除或整行替换。逐条核对完整主键和病理号、时间、状态，已有相同内容跳过，已有不同非空内容则停止。

本地行锁定后，先将原始10行保存到客户机独立私有备份文件并刷盘，再在同一个事务中UPDATE并回读值。事务阶段任意失败全部回滚。提交后调用现有统一刷新入口重建这7份病例的当前running/final及domain bundles，再检查exam_results/terminal中对应原字段与补全值完全一致。源库、历史质控结论、运行配置和后端文件不修改，不调用模型。

基础表提交和bundle刷新是两个阶段；若后阶段失败，日志明确 `data_committed=true` 和失败阶段，不声称基础数据已回滚。相同内容幂等跳过，可核查后重试刷新。日志仅包含计数、受控错误类型和本地备份路径；私有备份含原始内容，不提交或回传。

新增12项加现有同源相关回归共71项通过，Ruff通过。覆盖实际SQLite UPDATE事务及中途失败回滚、备份、内容冲突、幂等、记录范围变化、bundle字段一致性和日志不输出合成敏感内容。用合成数据验证入口的提交前备份失败、提交后刷新失败两个边界；尚未对客户机执行写入，不能宣称补全已完成。无真实模型或业务库写入。本轮不改前端，资源约束下不重复前端全量，提交前执行编码和不自动修改源文件的Lint检查。

这是一次性补全，不会永久升级客户机的同步程序；旧同步逻辑再次运行仍可能覆盖补回内容。后续仍须部署已完成的病理来源及死亡章节组装正式修复。重跑质控应新建任务使用新资料，旧任务的冻结输入及结论不改写。
