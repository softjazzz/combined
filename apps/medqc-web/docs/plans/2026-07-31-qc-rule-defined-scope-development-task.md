## 1. 任务背景

客户提供的质控点清单共 75 条。当前 LX0609 目录只正式纳入前 49 条，且部分规则仍依赖未定义的业务字典、项目清单、关联口径或语义标准。

本阶段不以“规则数量全部上线”为目标，也不允许用宽泛关键词、模糊 LLM 判断或固定返回“数据不足”的方式制造覆盖率。

本阶段只处理以下两类规则：

1. 业务条件、适用范围、时限、输入字段和结果状态已经能够明确约束的规则。
2. 一条复合规则中能够独立拆出的明确子判定。

以下规则统一进入 Pending：

- 依赖医院版本化字典或项目清单，但当前尚未建立。
- “完整、规范、明确、合理、阳性、重点、特殊”等概念没有受控定义。
- 缺少事件关联、权威时间或角色关系定义。
- 客户口径存在冲突。
- 只能依靠无边界的 LLM 自由判断。

## 3. 已确认的业务口径

### 3.1 主诉长度

- **主诉长度小于或等于 20 个字符时合规。**
- **主诉长度超过 20 个字符时不合规。**
- 主诉原文去除首尾空白后按 Unicode 字符计数；标点和内部空白计入字符数。
- 结果事实必须同时返回原始主诉、计数字符串和实际字符数。
- “只写症状不写诊断”“不能导出第一诊断”等语义不得混入长度判定，单独进入 Pending。

### 3.2 病危、病重状态

- 以结构化非药品医嘱为权威来源。
- 生效中的“病危”“病重”医嘱分别代表病危、病重状态。
- “解除、取消、停止、停病危、停病重”等医嘱结束对应状态。
- 每日覆盖按患者处于对应状态的自然日计算。

### 3.3 病情变化

“病情变化时未记录病程”暂不开发。

当前没有受控事件清单，尚不能确定以下事件是否全部属于病情变化：

- 转为病危或病重。
- 抢救事件。
- 重要检验检查异常。
- 危急值。
- 生命体征明显恶化。
- 重大治疗方案调整。
- 转 ICU、转科或急诊手术。

该部分作为 LX0609-009-B Pending，待客户确认事件类型、事件权威来源、记录时限和允许关联的病程文书后再开发。

### 4.3 明确规则的补充实现口径

1. “完成时间”必须使用文书权威记录时间或提交时间，不允许使用同步时间代替。
2. 时间不足、权威时间缺失、文书正文被截断时返回 `data_insufficient`，不得判为不合规。
3. 不满足适用条件时返回 `not_applicable`，不得返回合规。
4. LX0609-016 的“完全相同”只做确定性比较：
   - 去除首尾空白。
   - 统一全角、半角空格。
   - 统一换行。
   - 不删除医学内容。
   - 标准化后正文相同才判定问题。
5. LX0609-040 的多学科讨论定义为：
   - 文书明确标识 MDT/多学科讨论；或
   - 同一次讨论中存在两个及以上不同临床科室的有效参与人。
6. 医生签名、术者、上级医师、会诊医师必须保留人员标识、姓名、职称、科室、角色和签署时间；仅从正文猜测姓名不能作为唯一判定依据。

## 6. 数据和 Bundle 任务

本阶段规则开发前必须完成以下输入保障：

1. 检验结果按“同一申请/标本/报告”聚合，报告下保留多条检验项目，不再一项生成一份文书。
2. 每份文书保留：
   - `document_id`
   - `document_type`
   - `record_time`
   - `submit_time`
   - `author_id`
   - `author_name`
   - `author_title`
   - `author_department`
   - `signatures[]`
3. `signatures[]` 至少包含：
   - 人员标识和姓名
   - 签名角色
   - 职称
   - 科室
   - 签名时间
4. 手术相关事件保留：
   - 手术医嘱
   - 实际手术
   - 术式
   - 手术级别
   - 紧急/择期标识
   - 术者及助手
   - 麻醉方式
5. 文书正文被截断时必须设置明确的截断标记，规则不得把截断后的缺失内容判为不合规。

## 9. 验收标准

### 9.1 规则级验收

每条本阶段目标规则至少准备：

1. 一份确定问题病例。
2. 一份合规病例。
3. 一份不适用病例。
4. 一份关键输入缺失病例。
5. 必要时增加边界时间病例，例如恰好 8 小时、24 小时、48 小时。

每条规则必须验证：

- 适用性门控正确。
- 权威起止时间正确。
- 判定事实可读。
- 证据可定位。
- 数据不足不误判为问题。
- 技术异常不被包装成数据不足。

### 9.2 业务验收

- 主诉 20 个字符：合规。
- 主诉 21 个字符：确定问题。
- 未下病危、病重医嘱的患者不会进入病危/病重规则。
- 病危状态每日覆盖规则不调用“病情变化”语义判断。
- 无手术事实的病历，手术专属规则返回不适用。
- 有手术事实时，手术者和签名医生可从 Bundle 中独立核对。
- 新增 14 条规则结果经过 Canonical Envelope 原样保存和读取。

### 9.3 性能和调用约束

- 确定性时限、存在性、角色匹配优先使用 Python。
- 同一病历、同一事实抽取只执行一次并复用。
- 需要 LLM 的规则必须使用裁剪后的最小必要上下文。
- LLM 输出必须限定为受控枚举，并由 Python 校验。
- 单条规则不得因 LLM 失败改判合规或不合规。

## 10. 完成定义

本阶段只有同时满足以下条件才算完成：

1. 45 条完整规则和 2 个明确子判定均进入 Native 执行链。
2. Pending 规则未被计入已覆盖数量。
3. Bundle 保留文书签名和权威时间。
4. 结果通过 Canonical Envelope 原样保存、读取和展示。
5. 聚焦自动化测试通过。
6. 使用真实脱敏病例完成正例、反例、不适用和数据不足复核。
7. 每条已完成规则的 `golden_gate_state` 不再是 `pending`。

## 11. 剩余风险

- 客户源库可能没有提供部分文书签名、手术参与人或权威时间。
- 不同医院对抗菌药等级、危急值和输血前检查项目存在版本差异，不能使用全局硬编码。
- 旧 Sichuan/custom 规则的标题相似，但执行语义和当前客户口径不一定一致，迁移时必须重新验收。
- 规则数量增加后可能带来重复事实抽取和 LLM 调用，需要按病历级缓存事实，而不是按规则重复生成。
