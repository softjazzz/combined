# 2026-10-03 业务助手 M2 单病例复检与专项任务（D05/M04）

## 结论

已实现“预览 → 用户确认 → 正式任务 → 回读进度 → 前后保存结果并列”的代码闭环，并以合成数据和内存 SQLite 测试覆盖。真实闭环尚未验证：需要共享库迁移 46（动作记录表），以及一个可写、挂载正式质控路由的独立联调进程实际创建任务，二者均待用户授权。不能据单元测试宣称复检已在真实环境可用。

## 职责边界

- 模型只能调用 `preview_recheck`（医生当前病例）或 `preview_specialist_task`（管理者，仅本会话下钻/提醒中已出现的病例，≤20 份）生成预览卡；没有确认工具。
- 确认只来自用户点击卡片“确认执行”，请求只携带确认摘要；服务端重读授权病例子集、规则目录与发布范围、材料同步状态、病例在院/出院范围，任一变化返回 409 要求重新预览。
- 正式任务由既有 `POST /api/v1/qc/sichuan/workspace/batch-jobs` 创建（`rule_set_key`、明确 `rule_ids`、`scope`、三坐标 `record_refs`），不暴露执行策略等高风险参数，不走旧 `/tasks/{id}/re-analyze`。
- 幂等落在 `qc_business_actions`：`previewed → submitting` 条件更新只有一次成功，重复/并发确认返回既有状态，不再提交。
- 正式服务 4xx/503 记为“拒绝创建”；连接中断或 500/502/504 记为“结果未知”，不自动重发；刷新时只按本人任务列表唯一匹配（同病例集合、同规则、确认后创建）回查，多条或无匹配保持未知。
- 任务完成后，单病例复检并列预览时与当前的保存状态（正式原值）；若新任务结果尚未成为最新保存结果，如实说明。助手不重判、不关闭问题。
