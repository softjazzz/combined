# V3.6 质控结果身份与来源合同

## 目标与证据

同一份质控结果、自动缺陷和通知必须归属同一 `institute_id + patient_id + visit_id + source_key`。旧 `record_id` 只保留兼容展示，不再充当现代行的病例身份或关闭范围。现代写入身份不完整、来源不明确、CDM 病例不存在或目标 schema 未部署时，整个事务失败，不产出部分结果。

2026-09-24 业务库强制只读核对：revision44；`qc.qc_results` 的现有三坐标是可空 `TEXT`，其中 `institute_id` 有默认值 `LX001`，914 行历史结果的患者和就诊列均为空；`qc.qc_defects`、`qc.notifications` 尚无三坐标。`public` 三表也尚无身份列。已保存结算主表有 70 行，当前没有同一患者+就诊跨机构的重复；但服务在不传机构时取 `.first()`，源头仍须拒绝歧义。两种结算质控来源共用 `settlement::{visit_id}`，旧自动缺陷和通知 ID 会碰撞。这里描述的是代码及 schema 风险，不声称现有库发生了串案。

## 方案选择

1. 回填历史三坐标：旧结果缺少可证明的患者/就诊，`record_id` 也可能跨来源复用，无法无损推断，拒绝。
2. 新建独立身份映射表：可隔离旧 schema，但产生第二条资料链，结果、缺陷和通知仍需回查映射，增加失配与运维成本，暂不采用。
3. 在三表原行加现代身份标记、来源和三坐标：保持一个事实所有者和一条主资料链；历史行保留原样，只让显式现代行满足完整性约束。本阶段采用。

迁移 53 以 52 为父版本，在 `qc/public` 三表增加可空 `identity_version`、`source_key` 和缺失的三坐标。`identity_version=1` 时数据库要求来源及三坐标均非空非空白；历史 NULL 行即使只有机构号也不被回填或拒绝。现代索引按来源及三坐标检索，不给旧行套用新身份。升级前校验已有列、同名约束和索引，部分部署或漂移拒绝；降级遇新增列已有值拒绝删除，既有 `qc.qc_results` 三坐标绝不删除。

## 写入与读取

现代写入由调用方显式传入不可变的完整身份，持久化层核对结果载荷、来源及 CDM 复合主键；三张表的身份列必须已部署，不能因反射时缺列而静默丢字段。结果保留执行历史；自动缺陷的新稳定 ID 包含来源、三坐标、规则和位置，只扫描及关闭相同现代身份与已执行范围；通知 ID 包含来源、三坐标和接收人。三表在同一事务写入，冲突或所有者漂移整笔回滚。演示分析和仅有请求体、无权威病例来源的旧入口不能冒充现代结果。

现代病例读取必须由服务端接收完整三坐标和精确来源，仅选择 `identity_version=1` 且四维完全匹配的行，再按真实 `result.id` 关联缺陷及通知。历史 NULL/部分身份行可在专门的全局历史列表只读呈现，不凭当前 CDM 唯一就诊号推断归属，也不把无现代结果解释成“质控通过”。展示合成 issue ID 不得用于缺陷写接口；按真实 defect ID 的写操作仍须在服务端复核身份和权限。

## 失败语义与验收

- 同就诊号跨机构或患者、结算保存与生成两来源分别运行，结果、缺陷、通知彼此独立，重跑只关闭本来源本病例已执行范围。
- 缺任一坐标、来源不一致、CDM 不存在/歧义、schema 缺列或 ID 所有者冲突时，拒绝现代写入且三表均无部分提交。
- 历史仅机构列有值的结果、来源 NULL 的缺陷及旧通知在迁移后仍存在，但不进入现代病例详情；降级遇现代行必须拒绝。
- 先用纯 mock/SQL 编译反例，再在明确授权的非生产库执行 52–53 和合成病例竞争测试；业务库迁移、真实病例准确性、病历审核 owner 和人工缺陷状态属于后续验收，不由这份设计宣称完成。
