# 可视化条件编排实施计划

**目标：** 完成固定80项中的67，通过字段条件、文书存在条件、时效条件和且或条件组构建真实可执行的质控点，不以仅保存JSON作为交付。

**架构：** 复用66的用户草稿及`check_logic`，独立模块承担白名单目录、配置校验、可信事实适配和求值。既有执行入口仅增加该配置版本的明确分派；旧规则及执行器行为不变。测试与发布后执行必须消费同一规则定义。

**技术栈：** FastAPI、现有SQLAlchemy草稿服务、Python确定性求值、Vue/TypeScript、pytest/Vitest。

## 合同

- 配置固定为根组、条件组、条件三个层级，不接受任意路径、代码或表达式。根与组支持且/或；空组、未知字段、类型不符、无效操作符拒绝保存。
- 页面明确标注“缺陷触发条件”：确定为真表示触发缺陷，确定为假表示未触发。缺失事实不能伪造通过；未知的组合与输出沿既有执行状态合同处理并有反例测试。
- 字段目录由服务端提供类型、操作符及来源说明，只纳入当前可信病例/文书数据适配确实支持的字段。未加载文书不等于文书不存在；不把客户端提交的事实用于判定。
- 时效条件显式选择起止事实、比较符、阈值与单位，时间差由Python计算；不默设医学阈值，不交给LLM判定。多份文书的时间选择须在目录中明确，不能隐式取第一份。
- 同owner且仍为草稿才可编辑；沿用`expected_updated_at`冲突检查，条件变更清除旧测试证明。未知写入回执禁止盲重试，客户端账号/角色/草稿切换使迟到响应失效。
- 67不代表68已交付，不开放未经测试的发布按钮；既有发布搬运规则定义与执行选择必须验证，不能只有编辑器能保存。

## 实施与验收

1. 后端线：独立条件目录/校验/求值模块及聚焦测试；接草稿保存/回读，再接真实执行分派和可信事实适配。不迁移、不写真实数据库。
2. 前端线：独立条件编辑组件及类型/API，接基础草稿的条件编辑入口；覆盖组和条件增删、类型切换、回读、冲突、未知响应与账号隔离。
3. 独立复核：核对inline与发布后的完整调用链，重点排除LLM回退、未知冒充通过、客户端事实污染及旧测试证明复用。
4. 主协调：审查关键diff，运行聚焦pytest/Vitest、Ruff、编码、只读ESLint和类型检查；按实际结果记录，未满足整项合同不提升账本。
