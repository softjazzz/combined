# 固定测试病历验证实施计划

**目标：** 收口固定80项中的68，将固定测试病例选择、逐例结果查看与版本化发布门禁接入新建质控点流程。

**架构：** 复用固定测试池读取器、67确定性条件执行及现有用户草稿。独立验证服务生成服务端测试证明，保存在既有`last_test_summary`；发布端验证当前草稿与该证明一致。旧测试摘要和客户端伪造字段不能替代证明。

**技术栈：** FastAPI、SQLAlchemy草稿服务、既有测试池、Vue/TypeScript、pytest/Vitest。

## 冻结边界

- 从真实固定测试池选择1至20条active病例；按服务器保存的完整三坐标、病例版本与文书读取，不接收客户端事实或正文作为证明。
- 同owner且具明确可执行定义才可测试；空条件/空prompt不得借泛化fallback生成发布证明。沿用现有执行能力，不改医学规则或重写引擎。
- 测试开始冻结草稿版本，结束时在锁内CAS核对并保存证明。证明包含病例版本、逐例结果及执行失败，不保存患者全文。测试期间规则被编辑，旧执行结果不得授权新定义发布。
- 发现缺陷的`non_compliant`是有效测试结果，不因病例不符合而禁止发布。数据不足、技术错误、未完成测试不能冒充测试成功；结果必须实际呈现。
- 固定池版本标识证明使用的样本；不无依据要求之后样本永远不可修改，也不建立额外跨池版本系统。
- 发布读取服务器证明并核验当前草稿版本，不能只检查`success_count>0`。通用更新接口不能写入服务端状态、发布ID或伪造测试摘要；旧发布入口不能绕过新门禁。
- 前端区分未测试、测试中、结果未知、测试完成但不可发布、可发布、发布结果未知和已发布；账号、角色和草稿切换使旧响应失效。未知写入先回读，不盲重试。

## 分工与门禁

1. 后端：新验证服务、草稿持久化/发布守卫、HTTP入口及聚焦测试；复用67执行及固定池，不新增表或迁移。
2. 前端：独立选择与结果面板、严格DTO/API、创建页面接线及组件测试；沿用当前浅色工作台样式。
3. 独立复核：固定池真实事实来源、测试版本CAS、通用接口绕过、旧测试/worker摘要覆盖与发布失败语义。
4. 主协调：亲验关键调用链与diff，集中运行pytest/Vitest、Ruff、类型/编码/只读ESLint；仅本批文件中文提交。
