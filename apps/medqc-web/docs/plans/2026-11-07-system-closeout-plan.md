**Goal:** 收口0609现有修复、取材和模型调用链，形成一个版本明确、可回滚、可由DSH验收的业务系统候选版本。

**Tech Stack:** 现有Python后端、Vue前端、HTTP客户端、PostgreSQL与Linux离线升级工具；开发验证优先断网固定应答和内存SQLite。

## P1：最小离线业务闭环

**负责人：业务主协调；只补联合后新增的验证缺口。**

目标链：虚构病例材料 → Bundle/正式取材 → 任务与冻结 → 模型固定应答 → 0609执行 → Binding/Finalizer → Canonical保存 → API读取。

优先复用`06-01-04`已有专项及保存链夹具，不重跑27份，也不为冒烟建立新引擎。

步骤：
1. 盘点现有用例覆盖的入口，选择一份合成病例和一个检查事件，不从真实患者复制内容。
2. 沿实际调用链核对自建材料落库与Bundle同源、刷新失败不假成功、历史结果不覆盖。
3. 若已存在同版本完整闭环证据直接复用；缺失环节补一个最小失败用例，再修具体实现。
4. 仅补相关失败边界：取材失败、模型技术失败、局部未核完、成功结果保留、旧冻结不可补值、保存读取一致。
5. 默认CDM停用或失联时，历史列表与只读规则目录不应被无关依赖阻断；新任务不得悄悄回退旧源。

直接相关位置：
- `backend/app/services/custom_qc_sample_pool_service.py`
- `backend/app/services/customer_test_storage.py`
- `backend/app/services/bundles/refresh_manager.py`
- `backend/app/services/qc_input_adapters/running_final_bundle_runtime.py`
- `backend/app/services/sichuan_workspace_batch_worker.py`
- `backend/app/services/qc_workspace/canonical_result_store.py`

验证入口：后端目录使用`python -B scripts/run_pr8_offline_tests.py <直接相关测试文件或用例>`。新增测试按缺口命名，不为凑数量复制已有保护。

**退出标准：** 同一候选版本下，合成病例的正式输入、执行、保存及API读取一致；技术失败明确可追踪；模型调用为0，业务库连接为0。

## P2：模型、数据和设置的实际生效核对

**负责人：业务主协调；可以与P1的无依赖部分并行处理，不新增子代理要求。**

只处理实际不一致，不先建新配置页面或观测平台。

### 模型

- 分角色设置核对“配置身份 → 实际调用点 → 最终请求 → 新任务冻结身份”；已有角色测试相同代码时复用。
- 百炼Direct/Gateway保持同一主机代理路由；代理失败不直连、不切Provider。
- 保留最终Token预算准入和原输出要求；本地身份、Counter或消息形态未验证时拒绝发送，不拖垮历史查询及百炼能力。
- 只形成当前16K不兼容调用清单，不在本轮改造所有规则族。

相关位置：`backend/app/services/llm_config_loader.py`、`qc_llm_client.py`、`llm_token_budget.py`、`llm_observability.py`、`backend/app/core/http.py`、`backend/app/llm_gateway/`。

### 数据

- 普通病历固定东华CDM；1026/PDF材料继续按登记来源读取；不恢复双库切换。
- 复用只读依赖预检，核对必需表、列、SELECT权限及受控发布窗口；不得自动授权或改同步库。
- 未观察到出院信息不能等同确认在院；没有权威在院依据时，不承诺运行病历选样和定时质控已可用。
- 新任务取材与规则/补核读取使用同一材料版本；旧结果仍还原旧证据，不清理旧Bundle或冻结来解决问题。

相关位置：`backend/app/services/clinical_case_catalog.py`、`case_material_snapshot.py`、`backend/app/routers/clinical_sources.py`及当前交付工具的CDM只读预检入口。

### 设置与界面

- 仅走查已有模型配置、RabbitMQ开关、定时质控设置及来源就绪提示。
- 配置保存不应隐式启动任务；自动调度保持关闭；不要求安装MQ才能使用原Web任务路径。
- 新配置影响哪些新任务、哪些角色仍继承、历史任务为何不变，应有可理解的说明；发现实际误导再做最小V7.1界面修复。
- 端点、密钥和代理仍遵循既有部署配置边界，不新增前端密钥入口。

**退出标准：** 配置与实际请求身份一致；不兼容能力明确列出；没有静默回退或误导性“全部已生效”结论。现场依赖未就绪的项目明确保留限制。

## P3：一次候选交付与DSH现场冒烟

**需另行批准打包、部署及对应现场操作。**

代码收口后只构建一次精简Linux应用升级包，复用服务器已有依赖，不因报告变化反复重建。

工具位置：
- `scripts/linux_app_upgrade/check_compat.py`
- `scripts/linux_app_upgrade/stage_upgrade.py`
- `scripts/linux_offline/deploy/db-admin.py`

交付必须包含：完整Commit、外部SHA256文件、内部清单、依赖检查、实际迁移要求、快照目录解析结果、升级及回滚步骤。

默认策略：
- 不自动启用模型、RabbitMQ和自动任务，不擅自启用未验收CDM。
- 保留现场已授权配置，包括代理配置；不覆盖`.env`、密钥、激活或历史材料。
- 不修改同步服务、模型服务、PG容器或其他应用。
- 迁移按实际当前版本决定，保留既有表和数据；不假定服务器仍停在某个旧版本。

DSH现场顺序：
1. 只读核对包身份、运行Commit、库版本、目录权限、端口和现有任务。
2. 按获批窗口备份、暂存、执行必要迁移及切换；失败按已验证方案回滚。
3. 核对登录、历史1026样本池及结果可读，数量与切换前一致。
4. 单独获准后，用轮换后的Key和一份虚构病例，通过现有代理运行一个正式0609业务点。
5. 执行前固定规则范围、请求计划和真实HTTP预算，尝试、失败、重试均计数；不以“测试连接”按钮隐式推理。
6. 记录任务创建、取材就绪、模型请求、保存完成及API重读的时间；同时记录模型身份、Token、finish_reason和失败原因，不记录患者正文或Key。

**退出标准：** 最终交付版本的一份虚构病例正式链路可审计通过，结果保存重读一致；失败清单准确，其他服务和历史结果未受影响。不据此宣布医学质量等价或完整病历吞吐达标。

## P4：按需的小范围质量与吞吐验收

**独立授权后执行，不是继续开发的默认前置。**

- 先选少量具有明确参考答案的既有材料，限定规则与外发范围；不默认重跑27份。
- 覆盖语义改写、重复事件、冲突、明确缺失及输入不完整；程序直接确认的正例与模型语义正例分开统计。
- 参考答案先固定，保留争议与原答；模型一致率不等于准确率。
- 报告完整规则/病历完成率、技术失败率、资料缺口率、排队及保存耗时；真实完整病历吞吐须在获准的完整流程下单独测量。
- 固定应答的并发结果只证明调度，HTTP时长不代表病例吞吐；首次取材、冻结复用和模型缓存命中分开统计。

**退出标准：** 对本轮实际验证的规则和材料给出有限结论；数据不足、模型错误或不兼容路径明确列出，不扩大承诺。
