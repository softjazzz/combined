# 临床读取入口的 schema 对齐

## 范围与确认问题

独立分支 `codex/clinical-read-entrances-20261024`，基于已修复样本卡片的 `d04c5b64c`。检查同名临床表同时存在于public和cdm时的实际调用链，未修改集成分支。

除此前的病历收集和样本卡片，确认以下入口仍依赖未限定schema的ORM或SQL：通用病历仓库（首页、诊断、手术、费用、文书及科室统计）、运行病历池、终末列表、旧文书详情、首页导出与通用查表、首页预填/正文拼接/预览元数据、结算SQL补充、表式查询适配器，以及质控的主诊断/同病种首次病程辅助查询。样本重新匹配的临床候选查询也有同样问题。

字段探测还存在跨schema合并列或按search_path优先读取类型的问题，可能把旧表字段用于新表SQL。

## 修复方式

- 共用 `services/clinical_read.py`，复用Bundle既有来源判断。split模式限定cdm，single模式保留原行为，不改全局search_path或ORM元数据。
- 纯临床ORM查询按语句指定来源。终末列表混合临床和质控结果的JOIN仅限定三个临床模型，并验证原有分数、状态仍保留。
- 原始SQL明确临床表名；字段探测只读取同一个schema，不混入旧表列。缺失的cdm表/记录不回退public。
- 通用查询适配器的临床SELECT/count一致，使用同步目录及既有CDM兼容表范围；其写入方法不改。QC、系统及已明确限定schema的调用保持原来源。
- public内的持久Bundle、结果、系统/兼容数据不能一概迁入cdm。visit_index保留053确定的既有owner。未调整保存、同步写入、认证及历史快照入口。
