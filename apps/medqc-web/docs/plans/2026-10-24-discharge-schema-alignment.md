# 出院记录读取与迁移模式对齐

独立分支 `codex/discharge-schema-alignment-20261024`，基线 `612eba9ee`。

## 已确认根因

051 在 split 模式升级 `cdm.discharge_record`，同步/Bundle/规则材料也读取 cdm。病历收集仓库的 ORM 没有指定模式，实际搜索路径 public 在前，误读另一套同名表。public 缺签署时间和JSON列，导致启动质控在收集病历时500；C11首页/住院登记/入院及出院文书都只在cdm，单纯给public补列仍读不到正确资料。

## 最小修复

- 只在病历仓库自身的会话中，将未指定模式的ORM表映射到现有Bundle权威数据模式cdm，涵盖首页及三坐标补充锚点；不改全局search_path、不动ORM全局元数据、不把public和cdm记录拼接。
- 单模式数据库保留原有public/SQLite行为；split读取失败不回退public。
- 验收启动门禁检查cdm出院签署时间与JSON列，防止仅凭Alembic版本判断可用。
- 当前本机cdm已有051的两列，不需要改PG、不新增迁移、不补public影子表，也不搬迁临床记录。若后续只读验证发现确需改PG，再先完整备份后执行。

## 验证计划

1. SQLite附加cdm与默认模式两套同号反例，证明完整列表/筛选/收集及缺首页锚点只读cdm，三坐标隔离和单模式保持。
2. 启动门禁针对缺表/缺列/类型错误失败关闭，051目标合同不变。
3. 本机PG只读核对C11及1022的27份病历收集，不创建任务、不启动模型、不同步或刷新Bundle。
4. 提交后按同样的验收启动模式重启开发前后端，核对运行身份及真实认证GET；不调用run接口。

## 本轮验证

- 新增反例在修改前稳定失败：同号时返回public/main科室而非cdm；缺首页时会触发旧public出院表缺列异常。
- 修复后六文件定向集155项通过。旧记录服务文件另有10项SQLite夹具失败（构造服务时执行PG专用 `ADD COLUMN IF NOT EXISTS`）；以内存载入 `612eba9ee` 的原仓库复跑，同样10项失败，失败用例集合完全一致，无新增失败。没有修改无关DDL兼容逻辑。
- SQLite附加cdm的真实SQL覆盖同号双表、缺首页锚点、跨院同号隔离、缺cdm字段失败关闭、列表/过滤/计数/水合一致和single模式保持。051原迁移合同及新增启动门禁反例通过。
- 本机PG在只读事务及禁止写SQL保护下，五个CDM模型所需字段全部具备；C11成功读取1行，1022精确读取27行，三坐标集合完全一致。真实启动门禁通过。前后任务总数和最新更新时间一致，业务写入0、模型调用0、质控启动0。
- 无需修改本机PG，不执行DDL/迁移/补数，因此未创建无必要的数据库备份。原053版本及public、cdm两套数据保持；本轮不改全局search_path或旧051文件。
- Ruff、编码、秘密及diff检查按本次提交范围执行；不跑全量前后端检查。独立开发服务的加载证明与接口验收结果留在 `.tmp/0910-full-audit/runtime-discharge-schema-*-private`，不提交患者原文或认证令牌。
