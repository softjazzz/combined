# 质控规则测试、验收与上线最小闭环

日期：2026-09-28

状态：独立分支已完成最小工程闭环，待浏览器与客户材料验收；本文不代表任何新规则已通过临床验收或获准上线。

## 1. 目标与边界

让新增质控点有固定、可重复的测试和上线步骤，减少每次开发重新解释背景的成本。先复用客户样本验证和现有规则目录，后续测试病历管理使用同一套后端能力。

本任务不重构质控引擎，不引入插件运行框架、第二套执行状态机、密钥签章或重复摘要。普通新规则优先修改执行器、目录和相关测试；不以新增规则为理由重写聚合、保存或前端协议。

用户关切：同类规则可持续扩展、可共享事实抽取、新规则测试不影响成熟规则、通过验收后有明确的正式发布步骤。

## 2. 现有基础及证据边界

- `docs/PRD-内涵质控V3.6总需求与差距矩阵.md` 的质控点管理要求上线前选择测试病历并查看结果；6.4 节记录测试病历管理仍有模拟数据、关联与版本管理缺口。
- `测试病历模块PRD.md` 定义测试病历管理、规则关联和验证分析目标，不能视作已实现清单。
- `backend/app/routers/qc_sample_pools.py` 已有单规则选择和 `TestRecordGoldenAnswer`：预期状态、触发事实、证据关键词、人工理由；`TestRecordCreateRequest` 已有文书列表、重点规则及来源信息。
- 客户样本验证已有执行、结果查看基础；现有目录 `release_scope=acceptance_only` 支持新增规则默认不执行、通过样本显式选择验证。

以上仅证明存在能力或字段，不证明预期答案已完整保存、版本冻结、自动比较、人工验收和发布关联已闭环。实现前须追踪真实调用链。现有预期状态枚举含旧状态，须核对单规则交付合同，不能直接照搬成为新的验收标准。

## 3. 固定流程

| 步骤 | 操作 | 必须留下的依据 |
| --- | --- | --- |
| 登记 | 新规则进入待验收范围，明确所属规则族与事实依赖 | 稳定四段式编号、业务口径、实现版本 |
| 准备 | 选择真实病例或创建测试副本，人工标注预期 | 固定材料版本、预期状态、依据、标注人 |
| 验证 | 显式运行目标规则，走正式执行与保存链路 | 任务编号、执行范围、代码与模型配置版本、实际结果 |
| 复核 | 比较预期与实际，人工核对事实、证据和建议 | 差异项、复核结论、复核人、时间 |
| 发布 | 人工批准后修改目录发布范围，随代码版本交付 | 验收记录、批准记录、发布提交及构建版本 |

第一版不增加在线发布开关。规则目录继续是发布范围的唯一权威来源，避免数据库开关与代码配置各自决定是否执行。

## 4. 最小实现范围

### 4.1 测试病例与预期答案

一个病例可关联多条规则，各规则单独保存人工预期。优先补齐现有 `golden_answers` 的实际链路，不新建重复对象。

运行所用材料必须能定位到固定版本。编辑后的材料不得覆盖已验收材料；源库后续同步不得悄悄改变既有验收输入。先核实当前副本和快照是否满足，再补必要缺口，不预设全新版本系统。

人工答案只供运行后比较，禁止进入模型输入、执行器判定或任何可泄漏答案的运行上下文。开发集与独立验收集区分；揭盲后修规则需要新的独立验收样本，旧样本保留为回归保护。

### 4.2 验收结果

在客户样本验证上复用任务与结果展示，增加最小的“病例—规则—预期—实际—差异—人工结论”核对能力。自动比较状态；证据归属、事实准确性和建议可用性由人工复核。

任务完成不等于验收通过；状态一致也不等于证据正确。资料不足、调用失败、未触发等不能合并为合规。预期状态必须遵守对应规则合同。

验收记录绑定材料版本、规则实现版本和运行任务。代码、Prompt 或决定性输入发生变化后，旧验收不能自动证明新版可上线。优先引用现有构建信息和快照；不要求本阶段具备动态执行任意历史代码的能力。

### 4.3 上线与停用

通过复核后由人工批准，修改目录 `release_scope`，回归并随版本发布；不因一次测试通过自动转为默认启用。

保持现有待验收范围保护：默认任务和批量全选不自动纳入；样本显式选择可以验证。新任务按发布配置冻结范围，旧任务与历史结果保持原合同。规则紧急停止执行的需求需显式处理，不借停用清除历史结果，也不能将范围冻结误称为旧实现冻结。

## 5. 共享事实与回归范围

- 复用规则族的事实抽取，不依赖另一条规则的结论，也不通过调用0916引擎间接实现0609规则。
- 只新增独立判定：验证新规则和相关集成边界。
- 修改共享输入选择、门控、事实合同或Prompt：明确所有依赖规则，回归这些规则的保护样本。
- 对照状态、原因、事实、证据、建议、模型调用数、Token和耗时。固定模型响应验证程序行为，真实模型验证语义和稳定性，两种验证不能混称。
- 保持执行器判定、Renderer文案、Finalizer校验、Aggregator装配、保存/API/前端搬运的既定边界。

## 6. 首批试点与验收

建议试点：0916原025“手术记录缺项或描述不清”、原031“出院记录诊疗经过不全面或不详细”迁入0609后的规则。此处只指定试点，不表示迁移已完成；最终编号须查目录空位，不预先占号。新规则先保持待验收。

每条规则按适用合同覆盖合规、不合规、不适用、资料不足及必要的多事件边界。缺少某类真实病例时明确列为缺口，合成病例不能冒充客户验收。

完成条件：

- 固定样本及人工预期可保存、读取和复用，原始病例不被测试修改。
- 显式选择目标规则可以执行，默认任务不带入待验收规则。
- 执行→发布→实际保存→API读取→界面/导出可核对，业务字段和证据不丢失。
- 差异能追溯到病例版本、规则和任务，人工复核结论持久保存。
- 共享抽取受影响的旧规则保护集无未解释回归。
- 发布批准与具体验收版本绑定，代码级测试通过与客户/临床验收分开记录。

## 7. 实施顺序与接续卡

1. 只读审计一个测试病例：创建/副本→预期保存→选规则执行→实际结果读取，定位真正缺口。
2. 补齐最小的预期答案与固定材料关联，用一条规则跑通差异核对。
3. 补人工验收记录及发布检查清单，再以第二条规则验证可复用性。
4. 后续测试病历管理接入相同后端，逐步完成PRD的导入、导出、编辑、复制等需求。

接续时先读本文、滚动清单最新条目和工作区状态，再核对当前真实实现；不要从头重构测试平台。当前完成：方案文档。当前未完成：链路审计、产品实现、试点迁移、真实病例验收、上线批准。

本轮仅文档，无代码、数据库或发布范围修改。后续每步完成后更新本文进度和滚动清单，记录实际证据及未验证范围。

### 实际发现

1. 前端 `syntheticCaseBuilder.ts` 将 `form.goldenAnswers` 序列化为 `golden_answers`；现有模板使用四段式编号。`SyntheticCaseBuilderView.vue` 中发现模板装载预期答案逻辑，未发现人工预期答案编辑表单；不能宣称已有完整人工标注界面。
2. `qc_sample_pools.py` 的创建接口将请求传给 `create_customer_test_record()`。服务将预期写入 `manual_problem_sample_pool_items.raw_payload_json.golden_answers`，提交事务；样本序列化通过 `raw_payload` 返回。预期未作为临床文书写入 `rows_by_table`。
3. 本机当前搜索路径下自建测试池有85份记录，其中75份带预期答案，共191条答案均为旧三位编号，没有四段式答案。这是历史测试资料现状，不代表当前模板仍生成旧编号。不能直接把旧答案接到新编号比较器后视作不通过；应使用当前目录重建或受控转换测试基线，不引入运行时双身份。
4. 抽查一份自建测试病例：预期为旧017不合规；按测试条目或住院标识检索到13个关联历史任务，包含一个仅保存1条旧017不合规结果的完成任务，以及一个保存72条结果且含旧017不合规的完成任务。因此保存层可人工核对到同状态，但不是系统自动验收。75份有预期的样本其 `latest_job_id` 均为空，抽查病例却存在任务，说明该字段不能单独作为“未运行”的依据。
5. 运行入口冻结规则范围和所选样本ID；检查的任务filters没有 `golden_answers`，源码未发现将预期绑定到本次运行的版本快照或自动比较消费者。全局定向检索 `golden_answers/goldenAnswers` 的应用代码仅定位到构建、请求、保存和类型/模板等位置；未找到正式的预期—实际差异计算入口。
6. `QCRecordResultComparisonDrawer.vue` 将最新结果传给 `QCRecordCompareWorkbench`，显示原文与质控结果；这不是人工预期与实际结果比较。旧病例完成任务也不证明当前API能读取该旧合同，未做旧结果API/浏览器通路验收。

## 9. 独立工作树实现与当前边界（2026-09-28）

实现分支 `codex/rule-validation`，起点 `493cc418b`。不修改医学判据、目录发布范围或客户数据库。

- 人工预期：按修订号编辑、保存回读；每次运行深复制当前答案。人工理由/预期不进入任务filters、病历包或模型请求。
- 材料：入队前保存当前running/final病历包；首次正式执行时，保存执行器真正使用的EvidenceReadSession。复用既有freeze_execution_inputs/restore_execution_session及其类型校验，不新建签章或重复摘要。材料版本为验收run ID。两步读取不是源库同一事务时点的快照，版本表示本次实际使用的输入集合。
- 重试：同任务从已有病历包、会话恢复，不读后来更新的临床资料；病例、任务、用户、样本、范围和评价上下文不符即拒绝。失败规则范围变化不能冒用旧验收，须创建新运行。
- 版本：绑定正式任务已有lx0609_task_runtime、lx0609_task_settings、评价时间及规则范围；页面显示构建/提交、模型。无正式构建信息时明确为本地进程版本，不能当作某一发布提交的客户验收证据。
- 比较和复核：通过正式API比较已保存状态；人工核对证据和建议后追加意见，既不改正式结果，也不自动发布。没有已保存执行材料/版本的旧运行不得标记通过。
- 普通任务：无验收作用域时直接使用原会话构造器；并发验证ContextVar不串到其他任务，线程传播后按原作用域恢复。
- 存储：复用现有样本JSON；材料不经样本列表/验收元数据接口返回。单运行病历包+执行材料最多5MiB、单病例总存储最多20MiB、最多50次运行，超限受控停止，不删除旧材料；没有后台清理或跨环境迁移机制。

首批工程验证使用两条已存在的四段式规则（会诊建议执行、CT结果记录）的合成无事件病例，走真实HTTP→Worker→SQLite→Canonical读取→人工复核。它们证明流程可复用，不代表新增手术/出院规则已经迁移，也不能替代模型语义或客户病例验收。

后续测试病历模块复用本服务/API，不另造比较器。浏览器工具当前不可用；当前版本尚未合并、推送或部署，不能在日常3000页面中看作已生效。
