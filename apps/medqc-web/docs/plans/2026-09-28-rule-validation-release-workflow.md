# 质控规则验收与上线流程 PRD

日期：2026-09-28（2026-09-29 按原始意图重写）

状态：需求已确认，待按本文纠偏实现。本文不代表任何新规则已通过临床验收或获准上线。

## 1. 要解决的问题

0609 需要持续新增质控点（含从 0916 迁入、复用已有规则族抽取事实的规则）。目前每加一条规则，都要临时组织开发、挑病例、跑任务、人工对结果、再改代码上线，背景靠口头传递，容易遗漏。

目标：**围绕一条待验证的质控规则，组织测试病例和人工预期，运行并比较结果，记录验收结论，最终让规则有依据地进入正式质控集。**

一句话验收：质控管理员从“规则验收”菜单进入一条待验收规则，能在同一处完成“准备病例 → 标注预期 → 运行 → 对照复核 → 批准”，并拿到一份可交给开发的发布单；开发按发布单改代码上线后，平台能看到这条规则已上线、依据是哪次验收。

## 2. 已确认的产品决定

| 决定 | 内容 |
| --- | --- |
| 入口 | 左侧导航“规则”分组下新增二级菜单“规则验收”（`/workstation-v5/rules/validation`），与“质控规则”“自定义质控点”并列；“质控规则 → 语义规则 → 0609 规则集”列表显示待验收标签并可跳转。以规则为中心，不挂在单个测试病例上 |
| 上线方式 | 第一版**通过修改代码发布**：平台产出验收结论和批准记录，开发据此修改规则目录 `release_scope` 并随版本发布；平台不提供在线生效开关 |
| 保护集 | 第一版沿用已上线规则的验收病例：规则通过验收时的测试病例，自动成为它的保护集 |
| 版本一致性 | 客户环境：验收运行不是正式构建（本地进程版本）时禁止批准。开发环境：允许批准，但批准记录和发布单醒目标注“开发版本” |
| 测试病例固定 | 测试病例创建后即固定，不能编辑临床内容；需要修改就另建副本。因此不再单独冻结病历包或执行会话 |

不直接在线生效的原因：部分规则共用 LLM 抽取批次（已证实：检查检验族的抽取 Prompt 和 Schema 随所选规则变化，见 `exam_lab_fact_extraction.py` 的 `build_exam_lab_fact_prompt`），启用新规则会改变同族老规则的模型输入，风险需要经过代码评审和版本发布把关。

## 3. 用户与角色

| 角色 | 在本流程中做什么 |
| --- | --- |
| 质控管理员 / 临床专家 | 准备测试病例、标注人工预期、复核结果、给出验收结论 |
| 批准人 | 审阅验收结论和影响范围，批准或驳回上线 |
| 开发 | 实现规则（初始为待验收），按发布单修改目录并发布 |

第一版可以由同一人承担管理员和批准人，但批准动作单独记录操作人。

## 4. 用户流程

```
左侧导航「规则」
  ├─ 质控规则 → 语义规则 → 0609 规则集
  │     每条规则显示“待验收 / 已上线”标签，可筛选；待验收规则行“去验收”跳到下方详情
  └─ 规则验收（新二级菜单 /rules/validation）
       └─ 规则验收列表：所有待验收规则及其验收进度（工作队列）
            └─ 规则验收详情（/rules/validation/:ruleId，独立页面，不用抽屉）
            ① 测试病例与预期
            ② 运行验证
            ③ 对照复核
            ④ 验收结论与批准 → 生成发布单
            ⑤ 代码发布（开发，平台外） → 平台显示“已上线”
```

### 4.1 规则验收列表

- 列出目录中 `release_scope=acceptance_only` 的规则，以及近期已上线规则（便于查看依据）。
- 每行显示：四段式编号、规则名称、所属规则族、影响范围类型（见 4.6）、测试病例数、覆盖情况、最近一次运行结果、当前阶段。
- 阶段：待准备 → 验证中 → 待复核 → 待批准 → 已批准待发布 → 已上线；以及“验收不通过”。阶段由记录推导，不单独维护状态字段。
- 支持按规则族、阶段筛选。

### 4.2 ① 测试病例与预期

- 为这条规则关联测试病例，来源：
  - 从已有测试病例中选择（客户自建测试池）；
  - 新建测试病例（复用现有合成病例构建器）；
  - 复制已有病例后修改，生成新副本（原病例不变）。
- 对每个关联病例标注人工预期：预期状态（合规 / 不合规 / 不适用 / 资料不足，须符合该规则合同允许的状态）、人工依据（必填）、标注人和时间（系统记录）。
- 同一病例可以被多条规则关联，每条规则的预期分别保存。
- 预期有修订号，修改后产生新修订；已被运行引用的修订不可改写。
- **覆盖矩阵**：按预期状态统计病例数，缺少的类别标红显示“缺口”；多事件边界等规则特有场景可作为标签补充。合成病例与真实病例分开计数，合成病例不能冒充客户验收。
- 可标记病例用途：开发集 / 独立验收集。揭盲后修改了规则，需要新的独立验收病例，旧病例转为回归保护。

### 4.3 ② 运行验证

- 一键对本规则全部（或勾选的）测试病例运行，走正式执行、保存和读取链路。
- 运行时冻结：所用预期修订、病例列表、规则范围、代码构建与模型配置（引用任务已有的 `lx0609_task_runtime` / `lx0609_task_settings`）。
- 评价时间点：运行病历的时限类规则以测试病例自带的“评价时间点”为终点，不用运行当天日期，保证同一病例任何时候运行结果一致（见第 5 节）。
- 人工预期只用于运行后的比较，不得进入任务 filters、病历包、模型输入或执行器。
- **共享抽取规则（4.6 的 B 类）**：运行按“上线后的范围”执行，即同族已上线规则 + 本规则一起跑；同时对同族已上线规则的保护集运行回归。
- 运行列表显示每次运行的时间、构建版本（正式构建号 / 开发版本）、预期修订、完成情况。

### 4.4 ③ 对照复核

- 以病例为行显示：病例、预期状态、实际状态、比较结果（一致 / 不一致 / 缺少结果 / 重复结果 / 执行失败 / 进行中）、人工依据。
- 点开一个病例：并排查看原文、实际结果的事实、证据和修改建议，与人工预期依据对照。
- 逐例复核：人工确认“证据正确、建议可用”或记录问题。状态一致不等于证据正确，未逐例确认的不算复核完成。
- 资料不足、调用失败、未触发不能合并为合规。
- B 类规则额外显示“同族回归”：老规则在加入本规则前后的状态、事实、证据差异，以及 LLM 调用次数、Token 和耗时变化。

### 4.5 ④ 验收结论与批准

- 验收结论（规则级）：通过 / 不通过，附意见。“通过”的前提（后端校验）：
  - 选定运行已完成，全部病例比较一致且逐例复核完成；
  - 覆盖缺口已逐项说明（可接受缺口，但须写明原因）；
  - B 类规则的同族回归无未解释差异；同族规则没有保护集时，列为缺口并须显式确认；
  - 客户环境下该运行为正式构建。
- 批准：批准人审阅后批准或驳回，记录批准人、时间、意见和批准所依据的运行。
- 批准后生成**发布单**（可在页面查看和复制），内容见第 6 节。发布单是开发修改代码的依据。
- 验收只证明所运行的版本。代码、Prompt、模型或决定性输入变化后，旧验收不能自动用于新版本。

### 4.6 规则影响范围分类

| 类型 | 判定 | 验收要求 |
| --- | --- | --- |
| A. 独立判定 | 纯 Python 判定，或独立抽取，启用与否不改变其他规则输入 | 本规则验收通过即可批准 |
| B. 加入共享抽取批次 | 规则代码不改共享抽取，但启用后会改变同族抽取 Prompt / Schema / 输入 | 另须“上线后范围”运行和同族保护集回归 |
| C. 修改共享抽取代码 | 改了共享 Prompt 模板、事实合同、门控或输入选择 | 属于代码变更：同族所有规则须在新构建上回归，构建号变化使旧验收失效 |

分类由代码声明（在执行器注册信息中补充“是否参与共享抽取批次、所属族”），平台读取并自动列出需回归的同族规则，不由用户在页面手选。各族实际情况须逐族核实：目前仅确认检查检验族属于 B 类。

### 4.7 ⑤ 代码发布与上线回显

1. 开发按发布单修改规则目录中该规则的 `release_scope`（`acceptance_only` → `default`），提交信息引用发布单编号。
2. 随版本构建和部署。
3. 部署后，平台根据当前目录判断规则已上线，列表中阶段变为“已上线”，并链接到对应的批准记录。
4. 发布复验：部署后用该规则的验收病例在发布构建上再跑一次，结果须与批准时一致。发布提交若除 `release_scope` 外还改动了该规则族相关代码，必须复验通过才算完成上线。
5. 上线后，该规则的验收病例自动成为它的保护集。

停用同样通过修改代码实现；停用不删除、不改写历史结果。新任务按创建时的发布配置冻结范围，旧任务和历史结果保持原合同。

## 5. 数据与存储

- 测试病例：复用客户自建测试池（`manual_problem_sample_pool_items`），创建后临床内容不可编辑，修改走“复制为新病例”。
  - 2026-09-29 核查：无编辑/删除单病例接口；测试池不可删除；ETL 不写 `CUSTOMER_TEST` 机构；病历包由固定的临床表行和代码生成。唯一改写路径是对测试池执行源库匹配/同步（会改写病例绑定，甚至绑到真实患者），已在 `96f5f96ba` 中于服务层和前端禁止。
- 评价时间点：逐病例评价快照按病例自身场景确定终点。已出院（终末）病例以出院日为终点，本身稳定；未出院（运行）病例以任务创建当天为终点（`evaluation_horizon.py` 的 `task_frozen_date`），同一病例不同日期运行，时限类规则结果可能不同。已实现：
  - 创建测试病例时记录“评价时间点”（构建器可填写，留空取创建当天，不得早于入院日期），存于样本 `raw_payload.evaluation_as_of_date`，随病例固定；
  - 自建测试池运行时，未出院病例的评价快照以该时间点代替任务当天（`build_record_evaluation_horizon_snapshot` 的 `record_frozen_dates`）；终末病例和普通任务不变；
  - 验收运行记录所用评价时间点；历史测试病例没有该字段的，沿用任务当天，验收页标注“评价时间点未固定”，只能记录不通过。
- 人工预期：按“规则 × 病例”保存，带修订号和标注人；复用现有 `golden_answers` 结构，不新建平行的答案对象。
- 验收运行：记录规则、预期修订、病例列表、任务编号、构建与模型配置、比较结果。
- 复核与批准：逐例复核、规则级结论、批准记录，均只追加，不覆盖。
- 历史测试池中 191 条旧三位编号预期不自动转换；需要时按当前目录重建或受控转换，不引入运行时双编号。

## 7. 约束（实现时必须遵守）

- 不重构质控引擎，不引入插件框架或第二套执行链；运行走现有正式执行、保存、读取链路。
- 执行器判定、Renderer 文案、Finalizer 校验、Aggregator 装配、保存 / API / 前端搬运的边界不变；验收模块只读结果，不改写正式结果。
- 规则复用规则族的事实抽取，不依赖另一条规则的结论，不通过调用 0916 引擎间接实现 0609 规则。
- 待验收规则不进入默认任务和批量全选；只有在验收流程中显式选择时才执行。
- 固定模型响应验证程序行为，真实模型验证语义和稳定性，两者分开记录，不能混称。
- 代码级测试通过与客户 / 临床验收分开记录。
- UI 遵循 `docs/0418/UI/WorkstationV4-医疗浅色-DESIGN.md`：列表 / 详情分层，详情按 ①–④ 分区块，复杂编辑用抽屉或弹窗承载。

## 9. 完成条件

- 从“规则 → 规则验收”菜单及 0609 规则列表的“去验收”都能进入规则验收详情，①–④ 在同一详情页完成。
- 测试病例可关联、新建、复制；创建后内容固定；原始病例不被测试修改。
- 人工预期按规则 × 病例保存、回读、修订；不进入任何运行上下文。
- 运行后可按病例对照预期与实际，并追溯到病例、规则、预期修订、任务和构建版本。
- 逐例复核、规则级结论、批准记录持久保存；批准受第 4.5 节后端校验约束。
- B 类规则的上线后范围运行和同族回归可执行、可查看。
- 发布单可生成；按发布单改代码上线后，平台显示“已上线”并关联批准记录。
- 默认任务不带入待验收规则。

## 12. 入口选择依据

- 新增二级菜单：在 `components/layout/workstationNav.ts` 的“规则”分组中加“规则验收”（`/workstation-v5` 与 `/workstation-v4` 为同一套路由）。规则验收是跨病例、跨运行的工作队列，有自己的列表和详情，独立菜单最容易发现。
- 不放进“自定义质控点”（`/rules/custom-workspace`）：那里管理的是平台内编写、平台内发布的自定义质控点（草稿 → Prompt → 已发布），而 0609 规则由代码实现、改代码发布，两种发布机制混在一起容易误解。以后如果自定义质控点也要走验收，可复用本页面。
- 不做成 0609 规则集里的切换视图：`semantic-rules/SemanticRulesWorkspace.vue` 本身已是列表页，再嵌一层详情会过深；该页只补“待验收 / 已上线”标签、筛选和跳转（目前不显示 `release_scope`）。
- 规则验收详情包含 ①–④ 四个区块，信息量大，使用独立页面承载；病例预期编辑等局部操作可用抽屉。

### 接口（`/api/v1/qc/rule-validation`）

| 接口 | 作用 |
| --- | --- |
| `GET /rules` | 待验收规则列表及进度（阶段、病例数、覆盖、最近运行） |
| `GET /rules/{rule_id}` | 详情：规则信息、已关联病例与预期、覆盖矩阵、运行列表、结论与批准记录 |
| `PUT /rules/{rule_id}/cases/{item_id}` | 关联病例或修改该规则的预期（带预期修订号防并发覆盖） |
| `DELETE /rules/{rule_id}/cases/{item_id}` | 取消关联（历史运行快照不受影响） |
| `POST /rules/{rule_id}/runs` | 对已关联（或勾选）病例运行本规则，走正式样本池执行链 |
| `GET /runs/{run_id}` | 逐例对照：预期、实际、比较结果、逐例复核 |
| `POST /runs/{run_id}/cases/{item_id}/reviews` | 逐例复核（证据正确、建议可用 / 记录问题） |
| `POST /rules/{rule_id}/conclusion` | 规则级验收结论（通过需满足 PRD 4.5 校验） |
| `POST /rules/{rule_id}/approval` | 批准 / 驳回，生成发布单 |

### 阶段推导（不存状态字段）

无病例 → 待准备；有病例无运行 → 待运行；最近运行未完成 → 验证中；已完成未逐例复核完 → 待复核；复核完无结论 → 待结论；结论通过未批准 → 待批准；已批准且目录仍为待验收 → 已批准待发布；目录已为 `default` → 已上线；最近结论不通过 → 验收不通过。
