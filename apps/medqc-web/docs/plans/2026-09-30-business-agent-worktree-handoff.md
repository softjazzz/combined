## 已确定的方向

首选验证组合为 DSH＋WeKnora＋SQLBot＋现有 MedQC。尚未完成最终选型或客户部署验收。先做 DSH＋WeKnora 与现有业务接口的最小闭环，管理问数先走现有统计接口，SQLBot 开放式问数后续接入。不并行实现 Pi、PydanticAI 等替代方案。

一个统一的业务 Agent 编排入口，用户会话与患者上下文隔离。DSH 管模型/工具执行过程；MedQC 管权限、业务结果和任务；WeKnora 管规范资料与原文；规则启用状态仍查规则目录。不要把产品做成仅能通用问答的聊天框，也不要重写质控引擎。

## 下一步工作顺序

1. 核实当前基线的助手入口、鉴权、会话和业务 API，确定 DSH 适配边界；不要在现有 Python 编排器内再写第二套模型循环。确认 DSH、WeKnora 和插件的可用固定版本，核对已部署服务；未验证就不填写“兼容”。
2. 先接一条医生流程：当前病例→已保存结果→具体问题→病历证据→规范原文→连续追问。优先使用 WeKnora 检索和原文读取，不启用委托问答；引用要能打开，不能仅输出不可定位的文字。
3. 再接一条管理流程：授权科室和日期→现有指标查询→病例下钻→缺陷详情。固定统计口径，不自行生成另一套正式指标或在院人数算法。
4. 做实际接口与浏览器验证：患者 A→B→A、迟到响应、刷新、停止、工具失败、知识片段截断；记录版本、调用数、Token、耗时、应用空闲占用和建库峰值。模拟测试与真实服务验证分别报告。

首阶段不自动重新质控，不自动修改病历或启用规则；复检、分派和催办按 PRD M2 推进。客户样本、源码和规则不能作为框架演示数据任意上传到外部服务。
