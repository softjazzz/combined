# Luxian0916-015/016 独立抽取闭环实施方案

> 状态：合同冻结前调查完成，生产接入未开始
> 范围：仅 `LX0916-015`、`LX0916-016`；禁止修改或复用任何 Luxian0609 脚本
> 原则：原子事实分别提取，Python 统一判定；0916 任一失败不得影响 0609

## 1. 问题证据

### 1.1 固定输入和固定响应后的归因

- 同一批 30 份病例的完整 0916 输入、Prompt 与模型响应被冻结后，原样重放的抽取事实、状态、原因码和证据坐标一致，未发现 Python 随机分支。
- 相同 Prompt 再次请求同一模型时，响应和 `disease_changes` 事实发生变化，015/016 的状态或原因码随之变化。关闭思考显著降低 Token、耗时和漂移，但仍有稳定语义错误，不能作为上线结论。
- 保存的 replay 不是 run32 当时的原始模型响应，不能把 run32 的具体结果归因到某一次模型回答。它只能证明共享合同和保存格式的行为。

结论：当前漂移的直接入口是模型响应差异；Python 判定链在相同事实下可重放。模型响应为何变化还需按事实合同逐项验证，不能笼统归因于“大 Prompt”或采样参数。

### 1.2 当前生产链的共同依赖

`batch_worker._execute_record` 对 32 条规则只调用一次 `extract_luxian_0916_facts`。同一个模型响应同时包含入院、病程、手术和出院事实。合同失败、输出截断或事件抽取偏差会同时影响多个规则模块。

015/016 共用 `event_facts.disease_changes`。单个事件对象同时承载：

- `trigger_confirmed`
- `evaluation_window_mature`
- `documentation.record_present/complete`
- `documentation.analysis_recorded/specific_management_recorded`
- 一个 `source_type/document_id`

Python 规则层没有用分析或处理字段反推触发；但是当前模型合同没有要求这些事实独立，也不能表达“从 A 文书发现变化、到 B 文书核对记录”。已保存 replay 和 run32 的交付事实均只有一个文书坐标，这个复核缺口已经实证。

### 1.3 来源覆盖的已验证事实与更正

此前“通用场景包只保留 3 份日常病程，因此 0916 会把前三份当作全量”的推断不完整。只读回放确认：

- 场景包每类文书确实只投影 3 份，并记录 `scene_projection.per_source.*.has_more`。
- `build_programmatic_evidence_payload` 随后会从源表补查日常病程；run32 的 30 份病例实际获得 0–7 份日常病程。
- 其中 4 份病例超过 3 份，现有 `event_source_state_by_rule` 均输出 `partial`，没有输出 `selected`。
- 30 份病例中，9 份没有日常病程；21 份共有 48 份日常病程；4 份超过 3 份，3 份超过 4 份，最多 7 份；本批没有单份正文超过 1000 字。

所以，当前确定性缺陷不是“超量仍被当作完整”，而是：最多只送入 4 份，超量病例只能安全降级为资料不足，仍无法发现未送入文书中的事件。后续不得再按“现有 partial 门禁失效”设计修复。

### 1.4 权威业务边界

四川省 2023 版标准第 4.2.5 条为“病程记录重要病情变化（症状及体征）未记录或记录不全”；第 4.3.1 条为“病程记录中对病情变化无分析判断或无具体处理意见”。国家《病历书写基本规范》第二十二条将病程记录定义为连续记录，并列明病情变化、分析讨论、诊疗措施及效果等内容。

据此冻结以下边界：

- 015 的触发事实是“重要的症状或体征变化”。诊断修订不能单独触发 015。
- 016 的触发事实是“已经发生的病情变化”，不以分析或处理是否存在作为触发前提。
- 诊断修订的理由和依据属于 `LX0916-020`。V12 私有 POC 的 `diagnosis_revision` 不能直接接入 015/016。
- 分析和处理是 016 的被检事实，禁止反向作为病情变化或重要性的证明。

标准没有给出可直接编码的“重要”完整枚举，也没有把 4.2.5 和 4.3.1 对应到具体数据库 `source_type`。当前只能把严重程度、功能影响和生命体征不稳定作为待验证的私有证据维度；不能在业务答案冻结前直接把它们变成客户“不合规”的硬条件，也不能凭代码分组推断 015/016 的最终来源范围。

## 2. 根因判断

1. 015/016 与其他规则共用语义抽取，失败范围超过业务边界。
2. 触发、时点、记录、分析和处置由同一模型事件对象一次生成，事实职责没有隔离。
3. 事件发现与文书核对共用一个坐标，保存产物无法完整回放跨文书判断。
4. 015 与 016 需要不同的触发资格；当前共用同一 `disease_changes`，生产合同也没有 015 的重要性事实。
5. 私有 V12 把诊断修订纳入变化候选，超出了 015 的权威范围；第五批盲测另有一条“恢复较前平稳”业务答案歧义，不能据此接入生产。

## 3. 最小闭环设计

### 3.1 阶段与唯一事实所有者

```text
0916 专属病程来源
  -> Stage 1：病情变化原子提取
       已冻结的目标来源完整 + 所有输入分句均已检查 + 无变化 -> Stage 1 no_trigger
       缺源/抽取或合同整体失败 -> 仅 015/016 资料不足，停止
       来源部分覆盖或存在不清事实 -> 保留已确认变化，但禁止不适用和合规
       有已确认变化 -> Stage 2A：015 重要性原子提取
                Stage 2B：记录完整性原子提取
                Stage 2C：分析事实原子提取
                Stage 2D：具体处理事实原子提取
  -> Python：来源覆盖、事件关联、字段组合、场景成熟度和最终状态
```

- 模型只负责语义原子事实。
- Python 负责来源覆盖、确定性时间事实、关联和最终判定；模型不得自行生成通用“成熟时间窗”。
- 规则执行器负责唯一业务结论。
- Renderer、Finalizer、Aggregator、数据库、API 和前端只搬运，不重新解释状态。

优先级固定为：已由完整局部证据确认的不合规 > 部分覆盖或未解决事实导致的资料不足 > 全量覆盖后的合规/不适用。partial 不能遮蔽确定问题，也不能支撑合规或不适用。Stage 1 的 `no_trigger` 只表示本次已冻结来源范围内没有变化；在 015/016 各自的目标来源集合尚未冻结前，它不得直接下译为客户可见的“不适用”。

### 3.2 Stage 1 变化合同

每条事实只返回：

```yaml
clause_id: string
change_type: symptom_change | sign_change | global_condition_change
direction: new | worse | better | resolved_or_recovered
entity_explicit: true | false
direction_explicit: true | false
actual_change: true | false | unclear
```

约束：

- 不返回 `quote`、`entity_quote` 或自由文本理由；Python 按 `clause_id` 回填原文证据。
- 只确认患者已经发生的时间性变化。计划、风险告知、否定事件、静态异常、一般恢复过程描述和单纯诊断名称调整均不得确认为变化。
- `actual_change=unclear` 不得下译为“未触发”。
- Stage 1 不读取分析、处理、记录完整性字段。
- 结构化事实提取固定 `temperature=0`、`top_p=1`、`enable_thinking=false`，不保存或使用模型思考内容；同一设置同时用于冻结回放和生产候选版本。

Stage 1 还必须由 Python 保存覆盖合同：输入文书坐标、每份文书的分句总数、已返回且合同有效的分句数、正文是否截断、来源是否有更多记录。只有每份输入的 `checked_clause_count == clause_count`、所有目标来源完整且所有事实均为 `actual_change=false` 时，才允许输出 `no_trigger`。有 `true` 与 `unclear` 并存时保留 `true`，同时标记未解决事实；不得让一条不清事实覆盖另一条已确认变化。

### 3.3 Stage 2 原子合同

针对单个已确认事件，Python 先构建受控窗口；每个提取器只回答一个问题，并绑定输入 `event_id`，返回完整 `(source_type, document_id, clause_id)`：

- 015 重要性候选证据：严重程度、功能影响、生命体征不稳定分别使用 `present | absent | unknown` 三态；字段缺失不得当作 `absent`。
- 015 记录：先提取可复核的变化主体、方向、严重程度和上下文坐标；哪些元素构成“记录完整”必须由独立业务答案冻结，不能直接把四字段全部设为客户硬条件。
- 016 分析：是否存在医生对该变化的独立分析判断。
- 016 处置：是否存在针对该变化的具体处理意见。

同一句普通“好转”不能同时作为变化事实和疗效分析事实。分析必须是独立的医生判断；具体处理必须包含可执行的观察、检查、用药、操作或诊疗调整内容。

Stage 2 响应中的 `event_id` 必须等于当前单事件输入，事实坐标必须在 Python 提供的受控窗口内且全局唯一。坐标存在只能证明原文可回填；业务验收还必须独立核对该事实确实关联到指定事件。

### 3.4 场景成熟度

四川标准没有为 4.2.5、4.3.1 定义统一的“变化后 X 小时”窗口，文书记录时间也不能自动等同于事件发生时间。因此：

- 不再让模型输出 `evaluation_window_mature`。
- final 场景可以用已出院作为记录闭合事实，但仍需事件来源时间可定位；时间不明保持资料不足。
- running 场景只交付已经存在且明确缺项的记录问题；对于“完全未记录”或仍可能补记的事件，在院方时限口径冻结前保持未执行或资料不足。
- 若后续业务口径给出明确时限，Python 只根据受控事件时间来源和文书时间计算；没有可靠事件时间时不得计算。

### 3.5 双坐标合同

每个事件至少保存：

```yaml
event_id: string
event_source_type: string
event_document_id: string
event_clause_id: string
documentation_facts:
  - fact_kind: record | analysis | management | importance
    event_id: string
    source_type: string
    document_id: string
    clause_id: string
```

事件 ID 使用已有文书坐标和 clause 序号组合，不新增摘要哈希。交付证据可投影为客户可见坐标；调试快照保留受控坐标和固定枚举，不保存整份病历或模型思考内容。

### 3.6 来源范围

- 4.2.5 与 4.3.1 的缺陷文字都使用“病程记录”；4.2 的基本要求描述日常病程，国家规范又把首次病程、日常病程、上级查房、抢救、会诊等均纳入病程记录体系。由此只能提出“015可能偏日常、016可能更广”的待验证假设，不能直接冻结成数据库来源映射。
- 两条规则分别建立候选来源清单，至少评估首次病程、日常病程、上级医师查房、抢救、术后首次病程、转科/交接、阶段小结和会诊；最终集合、替代关系和排除关系必须由客户规则原文或独立业务答案冻结。
- 候选来源必须先用真实 30 份病例统计存在率、文书 ID 完整率、单次住院条数、正文截断和跨文书补全案例，再冻结最终集合。
- 在完整来源范围冻结前，局部无事件不得输出“不适用”；确定缺项可输出“不合规”。
- 上级医师查房、抢救等文书已有 4.13.3、4.15 等专项规则。015/016 若读取这些来源，必须在各自规则执行器内冻结事件归属和重复缺陷抑制，不新增聚合器二次解释，也不得让同一事实以多个0916规则重复交付。

run32 同一批 30 份病例的只读聚合显示：首次病程 30/30、上级医师查房 30/30（142 份）、日常病程 21/30（48 份）、会诊记录 22/30（58 份）、术后首次病程 14/30（14 份）、抢救记录 1/30、转入记录 2/30、转出记录 1/30。上述已出现记录的 `document_id` 均完整；上级医师查房有 25 份、首次病程有 15 份、转科记录有 3 份组装正文超过 1000 字。由此可确认两条规则都不能在未经验证时机械沿用“最多 4 份日常病程、每份 1000 字”的单一输入边界；最终来源、字符和条数上限仍需按事件覆盖率、重复计分风险与成本共同冻结。

当前 `sample_programmatic_evidence` 的固定来源没有交接班、转科和阶段小结，`add_luxian_0916_evidence_sources` 也只补充知情同意书。私有 POC 不得假设这些正文已可用；生产候选若需要它们，应在 0916 独立模块内读取已有 bundle inventory、验证坐标与正文，缺失时按资料不足处理，不能扩大全局 evidence 合同。

## 5. 实施顺序

1. 冻结本合同；更正 V12 的诊断修订边界，不改生产。
2. 用既有已揭盲集开发私有新合同；不得将已揭盲结果计入泛化准确率。
3. 从未使用病例建立新的冻结盲测，至少覆盖：明确加重、新发症状/体征、明确好转、普通恢复、静态异常、否定事件、多事件混合、来源不全。
4. 先验收 Stage 1；不通过就停止，不开发 Stage 2。

6. 私有闭环全部通过后，才做生产最小接入和同一批 30 份病例回放。
7. 达到本任务验收条件后提交并暂停，不顺手扩展 017–020 或 0609。

## 6. 验收指标

### 6.1 合同和稳定性

- 合同可用率 100%。
- 决策相关原子事实与独立业务审查答案 100% 一致。
- 两轮相同输入的最终原子事实漂移为 0。
- 证据 `clause_id` 100% 可回填到冻结原文。
- 015/016 任一抽取失败只产生对应规则资料不足，不影响其余 0916 规则，更不影响 0609。

### 6.2 业务结果

- 015 只由已确认的重要症状/体征变化触发；诊断修订单独不触发。
- 016 不得因缺少分析或处理而把变化本身排除。
- 一个未到检查时点或资料不足事件不得覆盖其他已确认问题。
- 来源部分覆盖时不得由空事件输出“不适用”或由局部完整事实输出“合规”。
- 事件坐标与记录/分析/处置坐标均可独立复核。

### 6.3 成本和性能

- 无变化且来源完整的病例只进行 Stage 1 调用。
- 不再对所有病例无条件提取 015/016 的分析、处置和无关客观事实。
- 记录每病例调用数、Prompt/Completion Token、模型耗时和端到端耗时；与当前共享抽取的同批 30 份病例比较。
- 继续使用项目全局 40 个 HTTP 槽位上限，不建立 0916 私有并发配置。

## 7. 剩余风险

- 当前泸县可查询的真实诊断修订病例已经进入既往开发或盲测材料；这不再是 015/016 的目标正例，但仍需用于 020 的独立回归。
- 标准没有给出“重要病情变化”的完整机器枚举；保守合同会增加资料不足，扩大口径前必须有客户或独立业务标注支持。
- 仅从医师病程可能无法发现“完全未记录”的症状/体征变化。若需覆盖该能力，必须先证明护理、生命体征或其他独立临床来源可用，不能用模型猜测缺失事件。
- 015/016 各自的病程候选来源、替代关系和重复缺陷抑制仍需真实数据与独立业务答案冻结；在此之前不进入生产。
