# LX0609 结果链路技术债稳定化账本

## 目标与边界

本账本用于把 LX0609 客户样本验证中的结果问题拆成可独立验收的小闭环，避免把规则判断、结果保存、客户投影和页面展示混在一起修改。

本轮目标：任意已保存的单病历结果可安全打开“病历原文 + 质控结果”对照页；确定性问题必须说明具体原因、核对标准、实际情况和可定位的证据；不得展示“发现该质控点对应的明确问题”这一类空泛占位结论。

本轮不做：会诊 020/023 默认启用、全新 Evidence Graph、对历史结果做不可逆重写。

## 当前基线（2026-07-29）

### 单病历结果入口

目标入口固定为：

```text
病历池单病历“查看结果”
  -> QCRecordResultComparisonDrawer
  -> QCRecordCompareWorkbench
  -> 安全文书列表 / 安全医嘱列表 / 当前病历结果
```

批量任务结果页不承担单病历对照职责。历史结果缺少任务内授权 `record_ref` 时必须停止展示，不能猜测或回退到其他病历。

### 已确认的系统性债务

1. 已在前端归一化与原生聚合客户出口同时加固解释质量门：未知不合规原因不会再退回“发现该质控点对应的明确问题”，而是降为“建议确认”。后续仍需逐族补齐事实，不能把该降级当作解释完成。
2. 一部分原生执行器仅返回状态和通用 `reason_code`，没有 `customer_display_facts` 或完整解释合同；聚合、保存、API 与前端因此无法恢复具体事实。
3. 一部分旧测试仍把已经迁出的规则当作旧执行器的成员，例如 029 已由手术文书执行器承担，但旧 `native_execution` 测试仍期待它属于该执行器。
4. 单病历对照页、批量任务页和旧抽屉历史上曾同时存在结果入口；任何入口修改都必须回归“单病历只进对照页”。
5. 包计划当前存在“原生执行”和“统一 RuleDecision”两个不同层次；不能把前者误表述为后者。另有 029 的兼容派发例外，以及仍被只读诊断脚本使用的旧会诊公共读取工具，均须先用包计划测试锁定边界后再清理。
6. 020–023 的实际派发受两阶段会诊开关控制；本轮不改变其默认启用状态，也不将其未完成的关联语义包装成已验收能力。

## 每个小闭环的质量门

1. **执行事实**：确认规则最终状态、原因码和事实来自同一规则、同一病历。
2. **保存回读**：持久化后通过客户 API 回读，字段不丢失、不串病历。
3. **安全定位**：只使用服务端授权的 `record_ref -> document_ref -> evidence_ref`；精确定位失败时只定位到文书，绝不按相似正文猜测。
4. **客户解释**：确定性问题必须包含“为什么不合规”；不允许通用占位文案通过展示质量门。
5. **测试**：定向单元/接口测试 + 一份真实或已批准合成病历回读；只有共享 DTO、API 边界或提交前才跑完整类型检查。

## 已知非阻塞项

- 029 的旧 `native_execution` 归属断言已改为迁移回归：旧执行器只覆盖 030/032，029 继续由手术文书执行器覆盖（48 条聚焦回归通过）。
- 模型输出、提示词与会诊执行关联不在本账本的默认启用范围内。
- 没有受控事实的历史/兼容不合规结果会在客户出口降为“建议确认”；其后端原始状态仍用于内部审计，不能据此当作客户确定缺陷。
- 旧规则版本或缺失 `rule_version` 的结果不参与当前规则契约的客户结果数；页面如展示历史任务，必须明确“需重新质控”，不能把任务规则数当作可展示的当前结果数。
