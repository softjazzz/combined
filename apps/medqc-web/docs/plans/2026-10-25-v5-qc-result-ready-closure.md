# V5 结果就绪通知与医生提交回执

## 范围

独立适配分支 `codex/pr8-business-report-adapt-20261023`，承接 `a8def1134`。只补运行/终末任务结果就绪通知，并补验医生提交整改的浏览器正例。核心制度继续阻塞，不改引擎判定、Canonical 读取合同、旧迁移或 V7.1 保护文件；不推送、不合并、不写业务库。80 项完成台账维持 61/80，不将本轮消息链增补重复计项。

## 实现

- 在叶子根任务、父任务聚合的成功保存入口接入持久通知，与合法信封、任务完成同事务提交。子任务、失败/部分失败、取消、旧执行令牌、空交付和不保存结果的路径不发送成功通知。消息插入失败则整笔回滚。
- 复用 `qc.notifications`，新增来源 `v5_qc_result_ready`，只通知实际存在且启用的任务发起账号。沿现有账号 owner 读取角色和机构，不用令牌传入角色代替持久授权，不群发给医生或其他质控员。
- 执行轮次及保存内容确定去重身份。父任务重复刷新只更新同轮结果指针，不新增通知、不清除已读；重试后旧通知失效，不跳到新一轮或其他同号病例。正式结果不存在、角色/机构或冻结三坐标不符时，列表、计数、已读、下钻统一拒绝。
- 消息精确携带通知 ID；新增 V5 `qc-result?notification_id=...` 适配入口，复用原 V7.1 任务结果抽屉，未改其源码/样式。下钻在根任务共享锁内复用原 Canonical 加载与客户安全投影，构造只读 workspace，不运行建表/补列。失效和失败显示错误，不回退到最新结果或旧版页面。
- 无新迁移。旧通知表尚无现代身份列时不启用此类通知，原保存路径不新增此依赖；这不代表整个分支可部署到任意旧 revision。

## 隔离实测

仅使用原 3011/8011 和 `medqc_pr8_reports_acceptance_20261023_2aefa0`，实际库名/本机地址/端口有连接守卫，禁止外部库与模型网络；3012/8012 注册环境未动，迁移版本仍为 `20261003_000084`。

1. 从原合成病历复制两份新的三坐标病历，不覆盖原病例。使用真实程序化执行器运行一条受控规则，禁止模型调用，通过正式创建、认领、完成和 Canonical 保存方法分别完成运行、终末任务。
2. 持久主管在统一消息面板实际看到两条“质控结果已就绪”，分别点击定位，V5 原结果抽屉显示对应新任务及一条已保存结果。HTTP 核对同一任务 ID；其他质控员、医生各两次读取均 404。
3. 正常 HTTP 在仍可用的终末受领任务录入并审核一条新合成人工缺陷、派发医生。原运行受领任务因当前结果变化被拒绝，保留拒绝，不改读取口径、不改其历史结果。
4. 医生在 V5 点击新整改通知，填写合成说明并点击“提交整改”。主管统一面板出现对应缺陷的“医生提交了整改”及 1 未读；点击后定位到同一个整改 ID，状态为待验收，历史包含本次提交。
5. 主管在浏览器提交合成验收通过；医生收到并打开验收通过通知，同一任务显示已通过及三条连续历史。两条结果就绪、派发、医生提交、验收共 5 条新通知全部已读，双端最终未读 0。
6. 本次正文对照返回“空正文不可比较”，页面如实显示。仅证明消息、状态和回执闭环，不宣称文书实际修改或医学整改成功。

数据库前后核对 300 张表：仅 12 张授权表允许本轮合成新增或账号登录时间变化；所有原行仍保留、账号角色/机构/科室/启停未变，288 张其他表的结构、索引和行指纹不变。原病例、历史信封、旧整改、旧消息和迁移版本保留。未调用真实 LLM。

私有证据保存在忽略目录 `.tmp/0910-full-audit/`：`qc-ready-acceptance-private.json`、两场景结果截图、`qc-doctor-submit-unread-private.png`、详情和已通过截图。不提交凭据、患者正文或验收种子。

- 抽屉沿用原高级操作；本轮验收限于结果打开/消息回执，未执行导出、深度复核或真实模型任务，亦未声称它们增加了新的并发执行轮次保护。
