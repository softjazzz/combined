## 4. 候选方案的具体合同

### 4.1 输入：原文保留，证据用途由 Python 标注

每个事件复用现有业务键和 `event_position`，标注以下材料：

- 目标报告：完整结果描述和结论，保持原字段来源与正文顺序。
- 窗口内候选病程：按当前合同时间过滤，保留完整相关文书，不能先让 LLM 摘要。
- 背景病程及超时病程：如沿用现有投影则继续保留，明确标记 `background_only` / `late_only`；可辅助理解和说明迟记，不能单独证明24小时内合规。
- 同次住院其他事件：保留已有身份目录用于排除串用，不将其报告全文无条件复制给每个事件，也不因一句同时讨论两个报告就禁止合法共用。
- 窗口用途、来源缺口由 Python 生成，模型不得自行修改时间或完整性。

长文书不再静默丢掉中间来证明“没有分析”。在同一冻结 MaterialStore 中取回完整正文；超过本轮预算则返回试验内部 `budget_exceeded`，不能伪装成临床资料缺失。第一轮不新增分块摘要、向量检索或缓存数据库。

给原文段落/句子编号只用于定位，**全部允许正文仍展示给模型**。句子编号应能还原到原文位置、字段及文书；不用模型回抄长原句，不把编号本身当作语义已验证。

### 4.2 输出：同一事件只产生一份语义事实

只有输入用途修正仍不能通过时，才启用此实验合同。一次回答同时支持011/012，不让两条规则分别重新判断同一事实。015复用思想，先单独测试。

建议的最小JSON骨架如下；值为合成格式示例，不携带真实病例：

```json
{
  "events": [
    {
      "event_position": 1,
      "positive_state": "positive",
      "report_evidence": ["R1-S2"],
      "record_state": "present",
      "record_evidence": ["D2-S4"],
      "analysis_state": "present",
      "analysis_links": [
        {
          "target_report_spans": ["R1-S2"],
          "course_anchor_spans": ["D2-S4"],
          "assessment_spans": ["D2-S7", "D2-S8"],
          "kind": "clinical_interpretation"
        }
      ]
    }
  ]
}
```

字段限制：

- `positive_state`：positive / negative / unknown。强结构化阳性或阴性沿用既有可靠所有者；未能确定时才由这一次模型解释报告。冲突必须报内部失败，不能让第二个LLM重判后覆盖。
- `record_state`、`analysis_state`：present / absent / unknown。unknown可存在于实验内部，用于诚实测量失败率；不可作为已解决结果交付。
- 两个state表示在本次提供的候选集合中是否找到语义，证据保持其 `within_window` / `late_only` / `background_only` 用途；是否按时由Python单独判断。背景或超时证据绝不单独产生合规。评分分别统计语义识别与按时满足规则，不能把两者合成一个含混标签。
- `kind`：clinical_interpretation / management_decision / both。只描述已在文书中出现的解释或决策，不评价具体治疗是否合理。
- present必须附有相应证据；absent/unknown相应证据数组为空。没有模型自报置信度阈值，没有可直接给客户用的合规状态字段。
- `analysis_links`必须同时指向目标报告发现、病程中的关联依据以及医生判断/决策，允许分布在不同段落或多份合法文书。不能要求原文必须出现“结合CT”“分析”等固定词。
- 已作出的随访、复查、不处理、维持治疗决定也可能是分析证据；关键是其与本次异常存在可核对联系。“待结果后再决定”“请日后分析”与已经作出的决定分开，不能一律按“计划”关键词否定。
- 报告自带的“考虑某病/建议复查”即使被复制进病程，也不能自动充当医生已作判断的证据。独立诊断列表与报告相同也不自动成立；需要本次事件的上下文联系。

这仍然是受控语义提取，模型有可能给出错误关系。Python只能证明编号存在、资料范围合法和时间成立，不能凭编号或两个关键词的重叠证明临床语义正确。正确性必须由独立参考证据和反例验证。

### 4.3 Python：验证事实、保留错误类别、映射结果

校验顺序：事件覆盖及唯一性 → 字段/枚举 → 引用来自本次发送的原文 → 目标报告与证据用途 → 强结构化事实冲突 → 原有时间和事件归约。

规则：

1. 使用稳定原始文书坐标映射编号，不能先排序结果后又把位置误当原编号；输出顺序改变不应改变判定。
2. 明确不同报告业务ID、不同标本等结构化矛盾可拒绝关联；缺少模态简称或出现“历史”字样不能直接拒绝整份文书。
3. 一条已验证的同事件分析通常同时包含记录事实，但不能简单用 `012=合规` 强行把011改合规。011记录覆盖与012分析覆盖分别核对，矛盾返回内部诊断。
4. 同事件有多份有效证据，不要求模型每次选完全相同的全部句子。主证据按“窗口内、时间、原文坐标”固定排序；另外统计语义有效证据一致性和逐字/集合一致性，不能排序后掩盖引用换到另一事件。
5. absence成立需要完整合法候选集合与成熟窗口。模型漏掉引用、解析失败或绑定失败，不等于临床没有分析；不强改为不合规。
6. 使用已有 `resolve_evaluation_window_state` 与事件归约；明确不合规事件不能被另一个事件资料缺口覆盖。检查主执行器先行 `any(missing_time)` 等门控是否挡住事件级结论；若真实复现，单列确定性缺陷，不混入模型方案收益。
7. 在实验中分别保留 `source_missing`、`input_truncated`、`model_semantic_unknown`、`invalid_output`、`binding_conflict`、`budget_exceeded`。它们是排障标签，不是新增的客户状态。
8. 当前012存在 unknown映射为data_gap的兼容行为，015还可能经过evaluation_unknown。A组如实记录；候选组不得靠重命名状态提高得分。源数据完整但模型失败的项按模型失败计；生产接入前必须有允许的恢复/任务失败合同，未恢复不能充作完整客户质控结果。
