# C11 输血医嘱判定耗时与可并行范围

## 范围和结论

本轮仅分析和离线验证。在独立分支 `codex/transfusion-order-analysis-20261024`，
以 `c6750aa4b` 为代码对照；不修改正式批次调度、提示词、模型或并发配置，
不改集成分支、不写业务库、不启动新质控任务、不调用模型，也不重启运行服务。

最有价值的候选优化是：医嘱语义去重完成后，最多同时处理两个独立批次。
它可减少串行等待，不减少初次判定需要的五次请求。
当前三条规则已经共用医嘱识别，不应再把它们各自并行重跑。

## 真实调用链和依赖

- `native_transfusion_execution.py:3460` 的 `get_order_trigger_task` 为同次执行创建共享任务。
  `07-01-02`、`07-02-01`、`07-02-02` 共用它；同步兼容分支也使用同一个结果缓存。
- `native_transfusion_execution.py:3512` 已并行预取医嘱、实施病程和术中文书。
  再把这三个门控改成并行，不能消除当前五批医嘱的内部串行。
- `transfusion_order_trigger.py:300` 先按全部语义字段去重；`:306` 的批次循环内逐次等待
  `llm_client.generate`。每批只依赖本批输入，不需要上一批分类结果。
- 每批的协议补核依赖该批首次应答，必须保留在批内串行，仍最多两次。
  全部批次结束后才汇总阳性、未知和取消状态，并恢复原始医嘱身份及顺序。
- 该分类器在其他族没有第二条真实调用链。C11中五次调用是五批不同输入，
  不能把它们误认为跨族重复请求，更不能只因为这例均为阴性就用关键词跳过完整医嘱。

## 输出为何仍多

五次医嘱请求共返回9800个输出token，约占本次输血族输出的98.6%。
较早保存的五份同协议应答全部关闭thinking，既没有think标签，也没有reasoning_content。
因此已保存证据支持的原因是逐行JSON的字段、名称引用和格式开销，而非长段推理。
最新一次未保存原始应答，不把旧应答冒称为最新一次的逐字内容。

旧实录共26303字符，保留完整JSON和逐字名称、仅去除格式空白后为17171字符，减少34.7%；
名称引用本身2242字符，只占紧凑JSON的约13.1%。
所以删除名称引用既破坏现有绑定保证，也不能消除大部分输出，不建议这样做。
要求紧凑JSON可作为第二项小优化，但字符减少比例不等于token或耗时减少比例，
离线格式转换也不能证明模型将遵从新的提示词。

## 最小后续实现建议

1. 将单批的调用、解析、最多一次补核及用量收集提为独立批次函数；
   完整去重后采用两个有界worker，不创建无限量请求，也不改变8/4规则族与全局HTTP配置。
2. 按原批次序汇总经校验的事实，依旧检查全部代表；不因某批阳性提前忽略其他批次错误。
   一批失败不得产生正常阴性结论。取消时停止领取新批，清理待办并正确观测已发HTTP，
   实际发出的请求和token应完整记账，不采用本次实验客户端的预取方式直接上线。
3. 先只改调度，不同时改模型、prompt或JSON协议，便于比较同一材料的结果与真实耗时。
   增加失败批次、漏行补核、乱序、取消、重复身份恢复及批量并发边界测试。
4. 若后续优化重复运行，再考虑接入已有事实冻结owner；本分类器当前没有持久事实复用入口。
   缓存必须绑定三坐标、来源身份、全部语义输入、协议/提示词和实际模型配置，
   材料变更立即失效，未知或失败不冻结；不能跨院按药品名共享。
