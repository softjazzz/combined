## 1. LX0609-055 抗菌药物效果评价窗口

### 1.1 背景与问题

LX0609-055 用于核对抗菌药物计划开始或实际启用后 48～72 小时内是否记录效果评价。

当前实现发现抗菌药物医嘱后，会立即检查是否存在 48～72 小时内的效果评价；若未找到，可能直接生成 `non_compliant / threshold_exceeded`。这会把尚未进入评价窗口或评价窗口尚未结束的在院病例提前判为确定问题。

本问题不属于资料缺失：当抗菌药物名称、启用时间和任务评价时点均已明确时，系统已经具备判断窗口是否成熟的全部资料。

### 1.2 已确认业务口径

以每一次抗菌药物计划开始或实际启用时间 `T0` 为起点，以任务创建时冻结的病例评价时点 `T_eval` 为判定终点。多条医嘱必须逐事件计算，不得以某一条医嘱的成熟状态覆盖其他医嘱。

| 场景                                         | Canonical 状态   | 原因码                          | 含义                               |
| -------------------------------------------- | ---------------- | ------------------------------- | ---------------------------------- |
| 未使用抗菌药物                               | `not_applicable` | `trigger_absent_complete`       | 本质控点未触发                     |
| `T_eval < T0`                                | `data_gap`       | `authoritative_time_conflict`   | 时间轴冲突，不能可靠判定           |
| `0 ≤ T_eval - T0 < 48小时`                   | `not_applicable` | `evaluation_window_not_started` | 尚未进入 48～72 小时评价窗口       |
| `48小时 ≤ T_eval - T0 < 72小时`              | `not_applicable` | `evaluation_window_not_mature`  | 评价窗口进行中，尚未到最终判定时点 |
| `T_eval - T0 ≥ 72小时`，窗口内存在有效评价   | `compliant`      | `requirement_within_threshold`  | 已在规定窗口完成评价               |
| `T_eval - T0 ≥ 72小时`，窗口内不存在有效评价 | `non_compliant`  | `threshold_exceeded`            | 已超过最终时限，确定缺少评价       |
| 启用时间或评价时点缺失                       | `data_gap`       | `authoritative_time_missing`    | 缺少完成时间计算所需的权威资料     |

“不适用”表示在本次冻结评价时点尚不能启动最终质控判定，不等同于永久不适用。重新创建任务后，应使用新的冻结评价时点重新计算。

### 1.3 多事件合成规则

1. 每条抗菌药物启用事件分别计算窗口状态。
2. 尚未到期的药物不得进入 `unmatched_antimicrobials`。
3. 只有已经达到或超过 72 小时、且窗口内未找到有效评价的药物，才能进入 `unmatched_antimicrobials`。
4. 同一病例同时存在成熟和未成熟事件时：
   - 任一成熟事件违反要求，病例结果为 `non_compliant`，结论只列出已到期但未评价的事件；
   - 成熟事件均合规、其余事件尚未成熟时，病例结果为 `not_applicable`，展示尚未到期的事件；
   - 所有事件均已成熟且均合规时，病例结果为 `compliant`。
5. 事件关联不唯一时继续使用现有安全边界，不得猜测评价记录对应的药物事件。

### 1.4 客户展示文案

不足 48 小时：

> 抗菌药物启用后尚未进入 48～72 小时效果评价窗口，本次暂不适用。

已满 48 小时但不足 72 小时：

> 抗菌药物效果评价窗口尚未结束，本次暂不判定为质控问题。

已超过 72 小时且无评价：

> 已超过抗菌药物启用后 72 小时，未找到 48～72 小时内的效果评价记录。

客户展示事实至少保留：药物名称、启用时间、冻结评价时点、已间隔小时数、窗口起止时间和逐事件状态。不得在客户文案或普通日志中展示患者身份信息。

### 1.5 统计口径

- `not_applicable` 必须从合规率分子和分母中排除。
- 尚未到期的事件不得计入确定问题、资料待核实或合规数量。
- `evaluation_window_not_started` 与 `evaluation_window_not_mature` 必须可以在调试信息中区分。

### 1.6 后续最小实施范围

本次仅冻结业务口径，不修改执行代码。后续实现应保持现有 LX0609 主链不变，仅完成以下小闭环：

1. LX0609-055 读取现有 `evaluation_context.horizon`，不得新增第二套评价时点来源。
2. 在规则执行器内增加逐事件 72 小时成熟门。
3. Renderer 仅根据规则事实生成上述客户文案，不重新判断状态。
4. Finalizer、Aggregator、数据库、API 和前端继续原样搬运 Canonical 状态与原因码。
5. 不增加新的 Bundle、Resolver、状态机或兼容回退链。

### 1.7 最小验收用例

至少冻结以下回归用例：

1. 启用后 24 小时、无评价：`not_applicable / evaluation_window_not_started`。
2. 启用后 60 小时、无评价：`not_applicable / evaluation_window_not_mature`。
3. 启用后 73 小时、在第 60 小时有有效评价：`compliant / requirement_within_threshold`。
4. 启用后 73 小时、无有效评价：`non_compliant / threshold_exceeded`。
5. 两条药物事件，一条已到期缺评价、一条尚未到期：结果为 `non_compliant`，且 `unmatched_antimicrobials` 只包含已到期事件。
6. 启用时间晚于冻结评价时点：`data_gap / authoritative_time_conflict`。
7. 缺少启用时间或冻结评价时点：`data_gap / authoritative_time_missing`。

真实病例验收还需确认：结果卡片状态、解释文案、调试信息中的逐事件时间，以及证据文书定位保持一致。

## 2. LX0609-004 抢救记录完成时限

### 2.1 背景与问题

LX0609-004 用于核对抢救结束后 6 小时内是否完成抢救记录。

当前实现仅读取 `rescue_record`，同时使用同一来源判断“本次住院是否发生抢救”和“抢救记录是否按时完成”。当该来源查询成功但结果为 0 条时，当前固定返回 `data_gap / applicability_source_gap`。

真实病例人工确认未发生抢救时，客户期望结果为“不适用”，而不是“数据不足”。但仅凭“抢救记录为 0 条”不能区分：

1. 本次住院确实未发生抢救；
2. 本次住院发生了抢救，但抢救记录漏写或漏同步。

因此不能在未确认来源合同前，直接把所有空抢救记录统一改为不适用。

### 2.2 本机数据库只读核查

核查范围为本机 CDM，不输出患者身份或病历正文。结果如下：

| 核查项                           |   数量 |
| -------------------------------- | -----: |
| `inpat_nondrug_order` 总医嘱行数 | 36,137 |
| 名称或内容包含“抢救”的医嘱       |  17 行 |
| 涉及住院事件                     |  13 次 |
| `rescue_record` 文书             |  27 份 |
| 有抢救记录的住院事件             |  22 次 |
| 同时具有抢救医嘱和抢救记录       |  13 次 |
| 仅有抢救医嘱、没有抢救记录       |   0 次 |
| 有抢救记录、没有抢救医嘱         |   9 次 |
| 费用表中包含“抢救”的事件         |   0 次 |

本机出现的抢救医嘱名称为“小抢救”“中抢救”“小抢救（无费用）”，医嘱类别均为“治疗”。

结论：抢救医嘱在本机数据中具有较高触发价值，但覆盖不完整。13 次抢救医嘱均能找到抢救记录，但 22 次有抢救记录的住院中有 9 次没有抢救医嘱。因此抢救医嘱可以作为“发生抢救”的辅助触发证据，不能作为唯一触发来源；“没有抢救医嘱”也不能证明“没有发生抢救”。医嘱开立时间不是抢救结束时间，不能直接作为 6 小时时限的计算起点。

### 2.3 重新梳理后的规则合同

本规则只回答一个问题：**本次住院发生抢救后，对应抢救记录是否在抢救结束后 6 小时内完成。**

规则分为“确认是否发生抢救”和“计算记录完成时限”两步，不能再由同一个空文书列表同时承担两种含义。全程使用结构化字段和确定性 Python 解析，不调用 LLM。

#### 第一步：确认是否发生抢救

触发来源按以下口径使用：

1. 存在 `rescue_record`：直接确认本次住院发生过抢救，不要求同时存在抢救医嘱。
2. 没有 `rescue_record`，但存在有效的明确抢救医嘱：确认存在抢救触发信号，但由于目标文书缺失，不能计算时限。
3. `rescue_record` 和明确抢救医嘱均查询成功、完整且为空：认定本次住院未触发抢救，本规则返回不适用。
4. `rescue_record` 已明确存在时，不再要求抢救医嘱来源必须可用；只有 `rescue_record` 为空时，才需要用完整的明确抢救医嘱来源排除“有抢救触发但目标文书缺失”。此时若相关来源不可用、查询失败或被截断，不能用空结果证明未发生抢救，返回数据不足。

抢救医嘱只接受院方确认的明确项目，例如本机已出现的“小抢救”“中抢救”“小抢救（无费用）”。明确取消、撤销或作废的医嘱不触发；“停止/已停止”可能表示执行后停止，仍应视为曾经触发；状态为空或语义未确认时返回数据不足，不能当作无抢救医嘱。普通病程中的“抢救”“抢救治疗”等自然语言不作为触发源，也不让 LLM 推断是否发生抢救。

由于本机存在“有抢救记录但无抢救医嘱”的病例，抢救医嘱只能作为文书缺失时的辅助触发证据，不能作为必要条件或抢救事件计数依据。当前缺少稳定业务键时，也不对医嘱与抢救记录强行做一一关联。

#### 第二步：取得两端权威时间

每份抢救记录需要两个时间：

1. **抢救结束时间（计算起点）**
   - 优先读取来源库可提供的结构化 `rescue_end_datetime` 或等价权威字段；
   - 当前 CDM 未提供独立结构化字段时，仅允许从 `record_content` 中确定性提取完整标签，例如“抢救结束时间：2026-09-01 09:00”；
   - 只接受完整日期和时分，模糊表述、只有日期、只有时刻或上下文推测均不采用；
   - 解析由 Python 严格格式完成，不调用 LLM。
2. **抢救记录完成时间（计算终点）**
   - 当前沿用文书权威时间优先级：`record_time` → `record_datetime` → `submit_time` → `submit_datetime`；
   - 不使用 `update_time`、同步时间或前端展示时间替代完成时间；
   - 若院方后续确认 `submit_datetime` 才代表正式提交完成，应单独调整此优先级并用真实病例冻结，不在本轮猜测修改。

医嘱开立时间不等于抢救结束时间，不能替代计算起点。文书完成时间早于抢救结束时间属于权威时间冲突，不能按绝对值或零小时判合规。

#### 第三步：逐次计算并汇总

对每份抢救记录独立计算：

```text
elapsed_hours = 记录完成时间 - 抢救结束时间
```

- `0 <= elapsed_hours <= 6`：该次抢救记录按时完成；
- `elapsed_hours > 6`：该次抢救记录超时；
- `elapsed_hours < 0`：时间冲突；
- 任一时间缺失：该次事件资料不足。

同一住院有多次抢救时，结果按以下优先级汇总：

1. 任一次已确定超过 6 小时：整条规则为确定问题；
2. 没有确定超时，但任一次缺少时间或时间冲突：整条规则为数据不足；
3. 所有已识别抢救记录均在 6 小时内完成：整条规则合规。

不能因为一份记录按时，就覆盖另一份超时或无法核对的记录。

### 2.4 状态与原因码

| 事实形状                         | 结果             | 原因码                                | 客户说明                                                     |

### 2.5 证据与展示合同

客户结果和脱敏调试信息至少保留以下结构化事实，不输出无关的大段正文：

- 是否发现抢救记录、是否发现明确抢救医嘱；
- 两类来源的查询状态和完整性；
- 每次抢救的文书 ID、文书标题、抢救结束时间、记录完成时间、实际间隔和事件状态；
- 超时事件的超出时长；
- 时间缺失或冲突对应的具体事件索引和原因码。

前端默认展示结论和逐次时间摘要，原文只通过文书 ID 定位查看。Renderer 只组织文案，不重新判断适用性、时间或状态。

### 2.7 最小验收用例

1. 无抢救记录、无抢救医嘱、两类来源均完整：`not_applicable / trigger_absent_complete`。
2. 有有效抢救医嘱、无抢救记录：`data_gap / rescue_record_missing_after_trigger`，不得返回不适用、合规或确定问题。
3. 有抢救记录、无抢救医嘱：仍按抢救记录计算，不得因缺少医嘱变为数据不足。
4. 抢救结束后恰好 6 小时完成：`compliant / requirement_within_threshold`。
5. 抢救结束后超过 6 小时完成：`non_compliant / threshold_exceeded`，展示结束时间、完成时间和超出时长。
6. 抢救记录缺少结束时间：`data_gap / rescue_end_time_missing`，不得使用医嘱时间代替。
7. 抢救记录缺少完成时间：`data_gap / document_completion_time_missing`。
8. 完成时间早于抢救结束时间：`data_gap / authoritative_time_conflict`。
9. 两次抢救一份按时、一份超时：整条规则为确定问题，并逐次展示两份结果。
10. 两次抢救一份按时、一份时间缺失：整条规则为数据不足，并指明未完成核对的事件。
11. 两次抢救一份超时、一份时间缺失：整条规则仍为确定问题，同时保留资料不足事件，不能让资料缺口覆盖已证实问题。
12. 任一必需来源查询失败或被截断：数据不足，并保留真实来源错误码。

## 3. LX0609-006 入院后 72 小时内最高级别医师首次查房

### 3.1 背景与当前问题

LX0609-006 用于核对患者入院后 72 小时内，是否有副主任医师或主任医师首次查房记录。

当前执行器已经能够根据入院时间和冻结评价时间识别“72 小时窗口尚未结束”，并生成 `evaluation_window_not_mature`；但公共缺失目标文书分支把该原因构造成 `data_gap`，最终页面显示“数据不足”。这会把正常等待期误解为资料缺失。

本规则的“评价窗口尚未结束”是明确的时间事实，不是缺少资料。只要入院时间、冻结评价时间和查房来源完整，就应返回不适用。

### 3.2 建议规则合同

1. 先读取本次住院的权威入院时间和冻结评价时间；任一缺失才返回 `data_gap / authoritative_time_missing`，两者冲突返回 `data_gap / authoritative_time_conflict`。
2. 读取日常病程和上级医师查房来源；来源不可用、查询失败或被截断时，保留实际资料错误状态。
3. 对候选查房记录识别医师级别和权威记录时间：
   - 明确为副主任医师或主任医师且有权威时间，作为有效候选；
   - 已有明确高级别查房文书但时间为空，只有在规则已需要作出结论时才返回 `data_gap / authoritative_time_missing`；
   - 医师级别无法确认时，可沿用现有一次受控语义识别，但 LLM 只判断医师角色，不参与时间计算、成熟期判断或最终状态映射。
4. 存在入院后 0～72 小时内的有效高级别查房记录：`compliant / requirement_within_threshold`。
5. 尚无有效高级别查房记录，且冻结评价时间距离入院时间不足 72 小时：`not_applicable / evaluation_window_not_mature`。
6. 冻结评价时间距离入院时间达到或超过 72 小时，完整来源仍无有效高级别查房记录：`non_compliant / required_document_missing`。
7. 只找到 72 小时以后完成的首次高级别查房记录：`non_compliant / threshold_exceeded`，展示入院时间、首次查房时间、实际间隔和超出时长。

到期边界采用闭区间：在入院后恰好 72 小时完成视为按时；到达 72 小时评价点仍无记录，视为缺失。

### 3.3 状态与客户文案

| 事实形状                               | 结果             | 原因码                                           | 客户说明                                                         |
| -------------------------------------- | ---------------- | ------------------------------------------------ | ---------------------------------------------------------------- |
| 尚未满 72 小时，暂无有效高级别查房     | `not_applicable` | `evaluation_window_not_mature`                   | 入院尚未满 72 小时，首次高级别医师查房时限尚未到期，本次暂不评价 |
| 72 小时内已有有效高级别查房            | `compliant`      | `requirement_within_threshold`                   | 已在入院后 72 小时内完成首次高级别医师查房                       |
| 已满 72 小时，完整来源无有效高级别查房 | `non_compliant`  | `required_document_missing`                      | 入院后 72 小时内未找到副主任医师或主任医师首次查房记录           |
| 首次有效高级别查房超过 72 小时         | `non_compliant`  | `threshold_exceeded`                             | 首次高级别医师查房超过规定时限                                   |
| 入院时间或冻结评价时间缺失             | `data_gap`       | `authoritative_time_missing`                     | 缺少成熟期计算所需的权威时间                                     |

| 医师级别语义仍无法确认                 | `data_gap`       | `semantic_output_unknown` 或明确的角色缺口原因码 | 暂无法确认候选文书是否属于高级别医师首次查房                     |
| 必需来源失败、不可用或被截断           | `data_gap`       | 保留实际来源错误码                               | 资料链不完整，暂无法完成核对                                     |

### 3.4 最小实施与验收

最小修改应集中在现有 `basic_timeliness` 执行器：让 `missing_target_decision` 或 006 调用分支将 `evaluation_window_not_mature` 构造为 `not_applicable`，并在窗口成熟且来源完整为空时生成确定缺失结果。不得新增执行链或让 Renderer 二次改状态。

至少覆盖以下用例：

1. 入院 24 小时、无高级别查房：不适用。
2. 入院 71 小时 59 分、无高级别查房：不适用。
3. 入院恰好 72 小时、无高级别查房：确定问题。
4. 第 72 小时完成高级别查房：合规。
5. 第 72 小时零 1 分完成首次高级别查房：确定问题。
6. 未满 72 小时但已完成有效高级别查房：合规。
7. 已有候选高级别文书但时间为空：到期后数据不足，不能误判缺失或合规。
8. 查房来源完整为空且已到期：确定问题，不再返回 `source_empty`。
9. 来源不可用或被截断：数据不足，不得由成熟期逻辑覆盖来源错误。
10. 冻结评价时点之后才形成的高级别查房不得用于本次任务判定。

## 4. LX0609-007 稳定患者每 3 天查房病程记录

### 4.1 背景与当前问题

LX0609-007 用于核对未下病危、病重医嘱的稳定患者，在连续稳定住院期间是否存在超过 72 小时没有查房病程记录的区间。

当前实现已读取入院时间、冻结评价时间、病危病重医嘱以及日常/上级医师病程记录，并计算“入院至首条、相邻记录之间、末条至评价时点”的区间。但当病程来源完整且一条记录也没有时：

- 未满 72 小时会被当作合规；
- 超过 72 小时会被当作 `data_gap / authoritative_time_missing`。

这两种映射都混淆了“记录不存在”和“已有记录但时间字段缺失”。对于刚入院患者，首个 72 小时检查点尚未成熟，应为不适用；对于已经到期且完整来源确认没有记录的患者，应为确定问题。

### 4.2 建议规则合同

1. 先判断稳定患者适用性：
   - 存在本次住院有效病危或病重医嘱：`not_applicable / eligibility_not_met`；
   - 病危病重医嘱来源不可用或状态无法确认：`data_gap / applicability_source_gap`；
   - 完整来源确认无病危病重医嘱：进入稳定患者时限核对。
2. 入院时间和冻结评价时间是区间边界；缺失返回 `data_gap / authoritative_time_missing`，前后冲突返回 `data_gap / authoritative_time_conflict`。
3. 只使用来源合同明确为查房病程、且具有权威记录时间的记录建立时间序列；普通病程、术后记录等非查房文书不得填补查房间隔。依次核对：
   - 入院时间至第一条查房记录；
   - 每两条相邻查房记录之间；
   - 最后一条查房记录至冻结评价时间。
4. 完整来源无任何查房记录时：
   - 入院至评价时间不足 72 小时：`not_applicable / evaluation_window_not_mature`；
   - 入院至评价时间达到或超过 72 小时：`non_compliant / threshold_exceeded`。
5. 已有至少一条有效查房记录时，只要所有已经形成的完整区间均不超过 72 小时，即可判合规；末段尚未满 72 小时不单独产生“不适用”。
6. 任一完整区间超过 72 小时：`non_compliant / threshold_exceeded`，展示最长超时区间两端及超出时长。
7. 存在正文有效但权威时间为空的候选查房记录时，该记录可能落在任何表面超时区间并改变结论；除非另有权威位置事实能够证明它不影响该区间，否则统一返回 `data_gap / authoritative_time_missing`。不能把“来源完整且记录数为 0”归入时间字段缺失。

到期边界与 006 一致：查房记录发生在区间起点后恰好 72 小时视为按时；到达第一个 72 小时评价点仍无记录，视为缺失。

### 4.3 状态与客户文案

| 事实形状                                               | 结果             | 原因码                         | 客户说明                                          |
| ------------------------------------------------------ | ---------------- | ------------------------------ | ------------------------------------------------- |
| 有有效病危或病重医嘱                                   | `not_applicable` | `eligibility_not_met`          | 患者处于病危或病重阶段，本稳定患者规则不适用      |
| 稳定患者入院未满 72 小时且无查房记录                   | `not_applicable` | `evaluation_window_not_mature` | 当前稳定住院时长尚未满 3 天，本次暂不评价查房间隔 |
| 稳定患者已满 72 小时且完整来源无查房记录               | `non_compliant`  | `threshold_exceeded`           | 入院后连续 3 天内未找到查房病程记录               |
| 所有已形成的区间均不超过 72 小时                       | `compliant`      | `requirement_within_threshold` | 稳定住院期间查房病程记录间隔符合要求              |
| 任一完整区间超过 72 小时                               | `non_compliant`  | `threshold_exceeded`           | 稳定住院期间存在超过 3 天无查房病程记录的区间     |
| 入院时间、冻结评价时间或可能改变结论的候选记录时间缺失 | `data_gap`       | `authoritative_time_missing`   | 缺少完成区间核对所需的权威时间                    |
| 时间前后冲突                                           | `data_gap`       | `authoritative_time_conflict`  | 入院、查房或评价时间存在冲突                      |
| 病危病重医嘱来源无法确认                               | `data_gap`       | `applicability_source_gap`     | 暂无法确认患者是否适用稳定患者规则                |
| 病程来源失败、不可用或被截断                           | `data_gap`       | 保留实际来源错误码             | 查房病程资料链不完整                              |

### 4.4 最小实施与验收

最小修改应只调整现有 `course_quality/rule_007.py` 的判定顺序和空记录状态映射，继续复用既有入院、评价时点和查房时间序列，不新增 Bundle、回退来源或 LLM 调用。

至少覆盖以下用例：

1. 稳定患者入院 24 小时、无查房记录：不适用。
2. 稳定患者入院 71 小时 59 分、无查房记录：不适用。
3. 稳定患者入院恰好 72 小时、无查房记录：确定问题。
4. 首条查房在入院后恰好 72 小时：合规。
5. 首条查房在入院后 72 小时零 1 分：确定问题。
6. 入院 24 小时已有一次查房，评价时点为入院后 48 小时：合规。
7. 入院至首条合规、相邻记录间隔超过 72 小时：确定问题，并定位该区间两端文书。
8. 前段均合规、末条记录至评价时点超过 72 小时：确定问题。
9. 完整来源有候选正文但时间为空，且其可能填补超时区间：数据不足。
10. 完整来源一条记录也没有：未到期不适用、到期后确定问题，均不得返回 `authoritative_time_missing`。
11. 有病危或病重医嘱：不适用，不继续计算稳定阶段查房间隔。
12. 医嘱或病程来源不可用、查询失败或被截断：数据不足，并保留实际来源错误码。

## 5. LX0609-010 CT/MRI 检查前病程原因记录

### 5.1 背景与当前问题

LX0609-010 用于核对**已经实际实施的 CT/MRI 检查**，检查前病程记录中是否说明本次检查原因。检查医嘱只是诊疗计划，不等同于检查已经执行。

真实病例出现 1 条 CT/MRI 医嘱，但 `exam_master_count=0`、检查报告也为空，检查实际上尚未执行。当前规则仍要求医嘱与检查主记录逐条关联，并返回 `data_gap / association_failed`。现有单测 `test_010_effective_order_without_exam_master_stays_data_gap` 也冻结了这一旧行为，证明当前实现把“已开医嘱但未执行”和“已执行但主记录缺失”混为一类。

### 5.2 建议规则合同

1. 先确认本次住院是否存在实际 CT/MRI 检查事件，再核对检查前病程；不得由检查医嘱单独触发本规则。
2. 实际执行事实按以下来源判断：
   - 存在当前住院、检查类型为 CT/MRI 的检查主记录，并具有可核对的检查事件时间：确认检查已执行；
   - 存在 CT/MRI 正式报告，但对应检查主记录或检查时间缺失：已有执行信号，但事件资料不完整，返回数据不足；
   - 医嘱状态只有在院方确认某个结构化状态明确代表“检查已执行”后，才可作为辅助执行事实；“新开”“已下达”“有效”等状态不能等同于已执行；
   - 只有检查医嘱、没有检查主记录和报告等执行事实：视为检查尚未执行，本规则不适用。
3. 检查主记录和报告来源查询成功、完整且均为空时，未执行医嘱不得产生 `association_failed`。
4. 一旦确认存在实际检查事件，继续沿用现有逐事件核对：以检查事件时间为锚点，读取检查前规定范围内的病程记录，并用现有受控语义判断病程是否真实说明该次检查原因。
5. 多条检查医嘱中只有部分已经执行时，只核对已执行事件；尚未执行的医嘱不得使已执行事件的结果变为资料不足。
6. `association_failed` 只用于“已存在检查执行事实，但订单、检查主记录、报告或事件时间无法可靠关联”的场景，不得用于单纯的待执行医嘱。

### 5.3 状态与客户文案

| 事实形状                                                     | 结果             | 原因码                                    | 客户说明                                                     |
| ------------------------------------------------------------ | ---------------- | ----------------------------------------- | ------------------------------------------------------------ |
| 只有 CT/MRI 医嘱，完整检查主记录和报告来源均为空             | `not_applicable` | `trigger_absent_complete`                 | 本次仅发现 CT/MRI 医嘱，尚未发现已实施检查，本质控点暂不适用 |
| 无医嘱、无检查主记录、无报告，相关来源均完整                 | `not_applicable` | `trigger_absent_complete`                 | 本次住院未实施 CT/MRI 检查，本质控点不适用                   |
| 有检查主记录及权威检查时间，检查前有明确原因记录             | `compliant`      | 保留现有满足原因码                        | 已在本次检查前记录检查原因                                   |
| 有检查主记录及权威检查时间，检查前无原因记录                 | `non_compliant`  | 保留现有缺失原因码                        | 本次 CT/MRI 检查前未找到说明检查原因的病程记录               |
| 有报告或明确执行信号，但缺检查主记录、检查时间或唯一事件关联 | `data_gap`       | `association_failed` 或具体权威时间原因码 | 已发现检查执行信号，但缺少完成逐事件核对的关联或时间资料     |
| 检查主记录或报告等必需执行来源不可用、查询失败或被截断       | `data_gap`       | 保留实际来源错误码                        | 当前无法确认检查是否已经实施                                 |

`not_applicable` 表示截至本次冻结评价时点检查尚未实施。后续检查完成后重新创建质控任务，应按新的执行事实再次评价。

### 5.4 最小实施与验收

最小修改应位于现有 `native_exam_lab_execution` 的 010 触发和事件关联分支：将检查主记录/可靠执行事实作为适用性触发，将医嘱降为事件关联和展示的辅助资料。继续复用现有检查前病程语义判断，不新增 Bundle、执行器或 LLM 调用。

至少覆盖以下用例：

1. 一条“新开”CT医嘱，检查主记录和报告完整为空：不适用。
2. 多条待执行 CT/MRI 医嘱，检查主记录和报告完整为空：不适用，不返回 `association_failed`。
3. 一条已关联检查主记录，另有一条待执行医嘱：只核对已执行检查，待执行医嘱不污染结果。
4. 有 CT/MRI 报告但无检查主记录或检查时间：数据不足，保留执行信号和关联缺口。
5. 有检查主记录及检查时间、无医嘱：仍按实际检查事件核对，不因缺医嘱直接判不适用。
6. 已执行检查前有明确原因病程：合规，并定位对应病程与检查事件。
7. 已执行检查前没有原因病程且来源完整：确定问题。
8. 两次已执行检查必须逐次核对，一次有原因不能覆盖另一次缺失。
9. 检查主记录、报告或病程来源不可用/被截断：数据不足，不得伪装为未执行。
