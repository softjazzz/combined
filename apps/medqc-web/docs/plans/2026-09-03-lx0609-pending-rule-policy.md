# LX0609 待修改质控点口径清单

## 文档用途

本文档集中记录已由真实病例暴露、但尚未统一修改代码的 LX0609 质控点。每个质控点分别冻结问题证据、业务口径、最小实施边界和验收用例，后续按小闭环逐条修改，不将多个规则混入同一次实现。

## 1. LX0609-055 抗菌药物效果评价窗口

### 1.1 背景与问题

LX0609-055 用于核对抗菌药物计划开始或实际启用后 48～72 小时内是否记录效果评价。

当前实现发现抗菌药物医嘱后，会立即检查是否存在 48～72 小时内的效果评价；若未找到，可能直接生成 `non_compliant / threshold_exceeded`。这会把尚未进入评价窗口或评价窗口尚未结束的在院病例提前判为确定问题。

本问题不属于资料缺失：当抗菌药物名称、启用时间和任务评价时点均已明确时，系统已经具备判断窗口是否成熟的全部资料。

### 1.2 已确认业务口径

以每一次抗菌药物计划开始或实际启用时间 `T0` 为起点，以任务创建时冻结的病例评价时点 `T_eval` 为判定终点。多条医嘱必须逐事件计算，不得以某一条医嘱的成熟状态覆盖其他医嘱。

| 场景                                         | Canonical 状态   | 原因码                          | 含义                               |
| -------------------------------------------- | ---------------- | ------------------------------- | ---------------------------------- |
| 未使用抗菌药物                               | `not_applicable` | `trigger_absent_complete`       | 本质控点未触发                     |
| `T_eval < T0`                                | `data_gap`       | `authoritative_time_conflict`   | 时间轴冲突，不能可靠判定           |
| `0 ≤ T_eval - T0 < 48小时`                   | `not_applicable` | `evaluation_window_not_started` | 尚未进入 48～72 小时评价窗口       |
| `48小时 ≤ T_eval - T0 < 72小时`              | `not_applicable` | `evaluation_window_not_mature`  | 评价窗口进行中，尚未到最终判定时点 |
| `T_eval - T0 ≥ 72小时`，窗口内存在有效评价   | `compliant`      | `requirement_within_threshold`  | 已在规定窗口完成评价               |
| `T_eval - T0 ≥ 72小时`，窗口内不存在有效评价 | `non_compliant`  | `threshold_exceeded`            | 已超过最终时限，确定缺少评价       |
| 启用时间或评价时点缺失                       | `data_gap`       | `authoritative_time_missing`    | 缺少完成时间计算所需的权威资料     |

“不适用”表示在本次冻结评价时点尚不能启动最终质控判定，不等同于永久不适用。重新创建任务后，应使用新的冻结评价时点重新计算。

### 1.3 多事件合成规则

1. 每条抗菌药物启用事件分别计算窗口状态。
2. 尚未到期的药物不得进入 `unmatched_antimicrobials`。
3. 只有已经达到或超过 72 小时、且窗口内未找到有效评价的药物，才能进入 `unmatched_antimicrobials`。
4. 同一病例同时存在成熟和未成熟事件时：
   - 任一成熟事件违反要求，病例结果为 `non_compliant`，结论只列出已到期但未评价的事件；
   - 成熟事件均合规、其余事件尚未成熟时，病例结果为 `not_applicable`，展示尚未到期的事件；
   - 所有事件均已成熟且均合规时，病例结果为 `compliant`。
5. 事件关联不唯一时继续使用现有安全边界，不得猜测评价记录对应的药物事件。

### 1.4 客户展示文案

不足 48 小时：

> 抗菌药物启用后尚未进入 48～72 小时效果评价窗口，本次暂不适用。

已满 48 小时但不足 72 小时：

> 抗菌药物效果评价窗口尚未结束，本次暂不判定为质控问题。

已超过 72 小时且无评价：

> 已超过抗菌药物启用后 72 小时，未找到 48～72 小时内的效果评价记录。

客户展示事实至少保留：药物名称、启用时间、冻结评价时点、已间隔小时数、窗口起止时间和逐事件状态。不得在客户文案或普通日志中展示患者身份信息。

### 1.5 统计口径

- `not_applicable` 必须从合规率分子和分母中排除。
- 尚未到期的事件不得计入确定问题、资料待核实或合规数量。
- `evaluation_window_not_started` 与 `evaluation_window_not_mature` 必须可以在调试信息中区分。

### 1.6 后续最小实施范围

本次仅冻结业务口径，不修改执行代码。后续实现应保持现有 LX0609 主链不变，仅完成以下小闭环：

1. LX0609-055 读取现有 `evaluation_context.horizon`，不得新增第二套评价时点来源。
2. 在规则执行器内增加逐事件 72 小时成熟门。
3. Renderer 仅根据规则事实生成上述客户文案，不重新判断状态。
4. Finalizer、Aggregator、数据库、API 和前端继续原样搬运 Canonical 状态与原因码。
5. 不增加新的 Bundle、Resolver、状态机或兼容回退链。

### 1.7 最小验收用例

至少冻结以下回归用例：

1. 启用后 24 小时、无评价：`not_applicable / evaluation_window_not_started`。
2. 启用后 60 小时、无评价：`not_applicable / evaluation_window_not_mature`。
3. 启用后 73 小时、在第 60 小时有有效评价：`compliant / requirement_within_threshold`。
4. 启用后 73 小时、无有效评价：`non_compliant / threshold_exceeded`。
5. 两条药物事件，一条已到期缺评价、一条尚未到期：结果为 `non_compliant`，且 `unmatched_antimicrobials` 只包含已到期事件。
6. 启用时间晚于冻结评价时点：`data_gap / authoritative_time_conflict`。
7. 缺少启用时间或冻结评价时点：`data_gap / authoritative_time_missing`。

真实病例验收还需确认：结果卡片状态、解释文案、调试信息中的逐事件时间，以及证据文书定位保持一致。

## 2. LX0609-004 抢救记录完成时限

### 2.1 背景与问题

LX0609-004 用于核对抢救结束后 6 小时内是否完成抢救记录。

当前实现仅读取 `rescue_record`，同时使用同一来源判断“本次住院是否发生抢救”和“抢救记录是否按时完成”。当该来源查询成功但结果为 0 条时，当前固定返回 `data_gap / applicability_source_gap`。

真实病例人工确认未发生抢救时，客户期望结果为“不适用”，而不是“数据不足”。但仅凭“抢救记录为 0 条”不能区分：

1. 本次住院确实未发生抢救；
2. 本次住院发生了抢救，但抢救记录漏写或漏同步。

因此不能在未确认来源合同前，直接把所有空抢救记录统一改为不适用。

### 2.2 本机数据库只读核查

核查范围为本机 CDM，不输出患者身份或病历正文。结果如下：

| 核查项                           |   数量 |
| -------------------------------- | -----: |
| `inpat_nondrug_order` 总医嘱行数 | 36,137 |
| 名称或内容包含“抢救”的医嘱       |  17 行 |
| 涉及住院事件                     |  13 次 |
| `rescue_record` 文书             |  27 份 |
| 有抢救记录的住院事件             |  22 次 |
| 同时具有抢救医嘱和抢救记录       |  13 次 |
| 仅有抢救医嘱、没有抢救记录       |   0 次 |
| 有抢救记录、没有抢救医嘱         |   9 次 |
| 费用表中包含“抢救”的事件         |   0 次 |

本机出现的抢救医嘱名称为“小抢救”“中抢救”“小抢救（无费用）”，医嘱类别均为“治疗”。

结论：抢救医嘱在本机数据中具有较高触发价值，但覆盖不完整。13 次抢救医嘱均能找到抢救记录，但 22 次有抢救记录的住院中有 9 次没有抢救医嘱。因此抢救医嘱可以作为“发生抢救”的辅助触发证据，不能作为唯一触发来源；“没有抢救医嘱”也不能证明“没有发生抢救”。医嘱开立时间不是抢救结束时间，不能直接作为 6 小时时限的计算起点。

### 2.3 建议状态口径

| 来源状态                                                       | 建议结果                       | 原因码                     | 说明                                                                                       |
| -------------------------------------------------------------- | ------------------------------ | -------------------------- | ------------------------------------------------------------------------------------------ |
| 抢救记录或抢救医嘱来源查询失败、不可用或被截断                 | `data_gap`                     | 对应来源错误码             | 资料链不完整，不能判断适用性                                                               |
| 存在抢救记录，且结束时间和记录完成时间完整                     | `compliant` 或 `non_compliant` | 现有时限原因码             | 按 6 小时阈值计算                                                                          |
| 存在抢救记录，但缺少结束时间或完成时间                         | `data_gap`                     | `required_field_missing`   | 缺少时限计算字段                                                                           |
| 存在抢救医嘱但无抢救记录                                       | `data_gap`                     | 待定义                     | 已有抢救触发信号，但缺少目标文书和权威结束时间；需区分文书缺失与同步缺口，不能伪造时限结论 |
| 抢救记录与抢救医嘱均为空，且院方确认两类来源足以判定未发生抢救 | `not_applicable`               | `trigger_absent_complete`  | 本次住院未触发该质控点                                                                     |
| 抢救记录与抢救医嘱均为空，但院方尚未确认来源完整性             | `data_gap`                     | `applicability_source_gap` | 继续保留安全边界                                                                           |

客户希望将“人工确认未发生抢救”的真实病例归为：

> 本次住院未发生抢救，本质控点不适用。

### 2.4 待确认事项

代码修改前需要向院方或源库接口负责人确认：

1. 所有实际抢救是否必然生成“小抢救/中抢救”等非药品医嘱；
2. 抢救医嘱是否可能取消、补录或仅用于计费，医嘱状态如何识别；
3. 是否存在独立的抢救事件表、护理抢救事件或结构化抢救开始/结束时间；
4. `rescue_record` 查询成功且为空时，院方是否接受“未发生抢救”的业务解释。

若院方明确确认第 4 项，可以按简化合同将完整空来源直接归为 `not_applicable / trigger_absent_complete`；否则必须保留数据不足，不能用空文书反推未发生抢救。

### 2.5 后续最小实施范围

1. 继续以 `rescue_record` 作为时限计算和证据定位来源。
2. 将 `inpat_nondrug_order` 中明确的“小抢救/中抢救”有效医嘱作为辅助适用性触发，不将普通“抢救”叙述当成医嘱事件。
3. 不使用医嘱开立时间替代抢救结束时间。
4. 根据院方确认后的空来源合同，修改 `rescue_record` 完整空结果的状态映射。
5. 不新增第二套 Bundle 或公共状态机；修改限于004执行器、来源声明及对应测试。

### 2.6 最小验收用例

1. 无抢救记录、无抢救医嘱、两类来源均完整：按最终确认口径返回不适用或安全数据不足。
2. 有有效抢救医嘱、无抢救记录：不得返回不适用或合规。
3. 有抢救记录、无抢救医嘱：仍按抢救记录正常计算，不得因缺少医嘱而变为数据不足。
4. 抢救结束后恰好 6 小时完成：合规。
5. 抢救结束后超过 6 小时完成：确定问题，并展示结束时间、完成时间和超出时长。
6. 抢救记录缺少权威结束时间：数据不足，不得用医嘱开立时间代替。
7. 任一必需来源查询失败或被截断：数据不足，并保留真实来源错误码。
