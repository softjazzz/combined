# 终末内涵质控双轨 POC 实施计划

## 1. 背景与目标

当前终末病历内涵质控已经具备基础闭环能力，但真实测试暴露出两个核心矛盾：

1. 准确性依赖多轮 `fallback / single retry / selective refine`，导致批量任务容易退化为伪串行执行。
2. 客户对首轮结果的可接受标准首先是“够快、够稳、能看懂”，而不是“所有规则一次性自动硬判到位”。

基于前面的真实病历测试，POC 不再追求“所有内涵规则一次性自动终判”，而是采用 **双轨策略**：

- **快速初筛轨**：面向默认批量场景，强调速度、稳定性、疑点发现。
- **深度复核轨**：面向人工点选复核或少量高价值规则，强调解释完整性和精审质量。

POC 目标：

1. 在终末病历页提供客户可接受的首轮批量内涵质控体验。
2. 把单份病历首轮结果时间压到可演示、可上线试点的范围。
3. 保留后续精审能力，但不再阻塞默认批量链路。

---

## 2. 现状判断

### 2.1 真实测试结论

针对 `visit_id=2248248` 的真实测试已经证明：

1. 当前完整链路的主要瓶颈不是输出过长，而是 **重复输入过多**。
2. `prompt_tokens` 明显高于 `completion_tokens`，说明时间主要花在上下文反复输入，而非结果生成。
3. 一旦启用多轮 `fallback / retry / refine`，批量任务会退化为多轮重跑，墙钟时间显著上升。
4. “同类文书 + 一次跑完”的方向成立，但**同一文书内仍需按判断层次拆包**。

### 2.2 关键实测信号

#### 完整链路（带 fallback / refine）

- `qwen3.5-35b-a3b`
  - 墙钟约 `120s`
  - 总 token 约 `84080`
- `qwen3.6-35b-a3b`
  - 墙钟约 `77s`
  - 总 token 约 `80947`

#### 简化脚本模式（无 fallback / 无 refine）

- 同文书分 3 包跑一次：
  - 总 token 约 `17667`
  - 首轮结果最早约 `3.58s`
- 说明去掉回退风暴后，吞吐和成本会明显改善。

#### 首次病程记录规则分包测试

- `SC-023~027` 五条一包：效果差，全部塌成低置信结果。
- 拆成 `2 + 3` 两包后明显改善：
  - `SC-023 + SC-024`
  - `SC-025 + SC-026 + SC-027`

结论：**双轨 POC 的主路径必须优先压缩重复输入，而不是继续堆复杂回退策略。**

## 3. POC 总体策略

## 3.1 双轨定义

### A. 快速初筛轨

面向默认批量入口，定位为：

- 快速发现问题
- 输出疑点和待复核提示
- 提供最小可读证据
- 不追求全部自动硬判

特点：

- 按文书域与判断层次固定分包
- 每包固定规则数，不动态扩缩
- **禁用 fallback**
- **禁用 single retry**
- **禁用 selective refine**
- 结果不稳定时直接输出 `uncertain`

### B. 深度复核轨

面向人工点选和专项复核，定位为：

- 对少数高价值规则或问题做精审
- 输出更完整的结论、证据和建议
- 不作为默认批量首轮阻塞步骤

特点：

- 可以走单条或小包精审
- 可以允许较重的 prompt
- 仅在用户触发时执行

## 5. 快速初筛轨设计

## 5.1 分包规则

快速初筛轨采用**固定分包**，不做动态分包：

### 首次病程记录

包 A：

- `SC-023`
- `SC-024`

包 B：

- `SC-025`
- `SC-026`
- `SC-027`

理由：

- 这两包已通过脚本验证，明显优于五条混跑。

### 日常病程记录

包 C：

- `SC-032`
- `SC-033`
- `SC-036`

### 出院记录

包 D：

- `SC-121`
- `SC-122`
- `SC-123`
- `SC-125`

### 分包原则

1. 同文书域
2. 同判断层次优先
3. 每包规则数固定且尽量小
4. 每包上限不超过 `10`

---

## 5.2 执行策略

快速初筛轨统一执行约束：

1. **不做 fallback**
2. **不做 single retry**
3. **不做 selective refine**
4. `parse_error` 时整包规则直接标记为 `uncertain`
5. `missing_rule_ids` 时对应规则直接标记为 `uncertain`

这是一个有意为之的取舍：

- 用“可控的不确定性”替代“高成本的重复重跑”
- 用“快速首轮可读结果”替代“伪批量串行精审”

---

## 5.3 输出协议

批量首轮只输出**短版结构化结果**，每条问题控制在约 `<=100 token`。

建议字段：

- `status`
- `finding_short`
- `evidence_short`
- `suggestion_short`
- `confidence`

建议长度控制：

- `finding_short`：20~30 token
- `evidence_short`：30~40 token
- `suggestion_short`：20~30 token

原则：

1. 批量首轮只做摘要，不输出长篇分析。
2. 批量首轮以卡片展示为主，便于扫描。
3. 长文案只在深度复核轨或详情查看时生成。

---

## 6. 深度复核轨设计

### 6.1 触发方式

深度复核轨不默认运行，仅在以下场景触发：

1. 用户点击某条问题卡片的“深度复核”
2. 用户在单病历详情页手动要求精审
3. 导出详细复核报告时，按需生成长版说明

### 6.2 执行范围

仅对以下对象执行：

1. 硬判定候选规则
2. 用户显式点选的问题
3. 特定高风险病历

### 6.3 输出目标

深度复核轨可以输出：

- 完整 findings
- 证据全文定位
- 详细建议
- 长版解释

但它不应阻塞快速初筛轨。

---

## 7. 模型策略

### 7.1 快速初筛默认模型

POC 推荐默认模型：

- `qwen3.6-35b-a3b`

原因：

1. 当前真实测试中，首轮返回和总时长更有优势。
2. 结果相对更保守，更适合快速初筛口径。

### 7.2 对照模型

保留：

- `qwen3.5-35b-a3b`

用途：

- 作为真实样本补测对照
- 避免过早把默认模型切死

### 7.3 COT 策略

POC 默认：

- `enable_thinking = false`

原因：

1. 当前测试已明确两次主模型跑数都未启用 COT。
2. 当前主问题在重复输入，不在 CoT。
3. POC 期间优先控制吞吐和稳定性。

高级技术信息折叠：

- pack 统计
- debug 快照

### 8.3 结果文案

对客户的对外口径：

- 快速初筛 = 自动发现疑点
- 深度复核 = 人工或系统按需精审

避免在默认批量页面上给出“系统已经完成最终医学裁决”的误导性表述。

## 9. 验收指标

## 9.1 性能指标

快速初筛轨目标：

1. 单份病历首轮结果时间 `< 30s`
2. 第一轮结果出现时间 `< 5s`
3. 单份病历总 token `< 20000`

## 9.2 结果指标

1. 不再出现大规模 fallback 风暴
2. `uncertain` 成为合理灰区承接，不再强行硬判
3. 问题卡片可读、可理解、可复核

## 9.3 体验指标

1. 用户能快速看到首轮结果
2. 批量任务不再长时间停留在“准备中”
3. 默认抽屉页信息聚焦，不再技术化铺满

## 10. POC 执行步骤

## P0：脚本验证

目标：

- 不改正式链路，先把快速初筛策略跑通。

动作：

1. 按固定分包跑 `2248248`
2. 再选 `MV2-REAL-001` 做同样验证

   - wall time
   - first result latency

## 11. 风险与应对

### 风险 1：初筛结果过松

表现：

- 太多 `uncertain`
- 硬判定太少

应对：

- 先接受这是 POC 的有意取舍
- 后续在深度复核轨逐步补强

### 风险 2：某一包仍然结果塌缩

表现：

- 同包规则全部 `compliant`
- 全部低置信

应对：

- 继续按判断层次细拆
- 不再强行追求大包

### 风险 3：客户误解“待复核=系统不准”

应对：

- 明确产品文案：这是“疑点发现+人工复核协同”能力
- 不承诺首轮就是最终裁决

---

## 12. 最终建议

站在当前项目节点，最可行的 POC 不是继续堆复杂回退策略，而是：

**用快速初筛轨解决“速度和成本”，用深度复核轨解决“解释和精度”。**

对客户而言，先看到：

1. 终末病历能快速出结果
2. 问题卡片能看懂
3. 高风险问题能被定位
4. 需要时还能点开深审

这比首轮把所有规则都做成多轮自动精审，更容易被接受，也更符合当前系统成熟度。
