# 2026-04-28 客户样本验证质控点实施计划

## 1. 目标

本计划只服务于**客户样本验证页**的质控能力建设，不包含 dashboard 常规运行病历质控，也不包含 dashboard 终末病历批量质控。

唯一目标：

- 以 `docs/运行病历质控记录.xls` `Sheet2` 的“存在问题”为来源
- 在客户样本验证页中
- 将这批客户样本的问题，尽可能稳定、可解释地通过质控系统复现出来

一句话收口：

**验证对象是 `Sheet2`，验证入口是样本池验证链路，验收标准是人工问题能否被系统复现。**

## 2. 范围边界

本计划包含：

- 客户样本池 `0426`
- 样本验证页执行链路
- `Sheet2` 问题文本归一与规则映射
- `programmatic` 硬门槛规则
- 第一批 `semantic` 语义规则

本计划不包含：

- dashboard 页面功能重构
- 正式 `qc_defects` 入库

- 第二批大规模规则扩展
- 与样本验证无关的产品 UI 优化

## 3. 实施原则

### 3.1 先保证样本验证页链路正确，再测规则

如果样本验证页拿到的不是完整 bundle 证据，而是瘦首页 record，则后续规则测试不成立。

因此链路优先级高于规则优先级：

1. 先修证据入口
2. 再跑真实样本
3. 再判断规则是否有效

### 3.2 不做“全量乱跑”，只做“问题族 -> 最小规则集”

样本验证不是把所有 `SC` / `LX` 规则都跑一遍，而是：

- 先把 `Sheet2` 问题归一成问题族
- 再为每个问题族配置最小必要规则集
- 用最小规则集验证该问题能否命中

### 3.3 分三层规则体系推进

- `programmatic`
  - 硬门槛、时效、存在性、签名、连续病程
- `semantic-existing`
  - 先复用项目库中已有 `SC` / `LX` / `LXE` 规则
- `semantic-new`
  - 现有规则无法承接时，再新增规则

## 6. 当前核心问题

### 6.1 现在最大的问题不是 bundle 入口，而是规则集过宽

最新真实批次已经证明：

- 客户样本验证页链路现在能走 bundle
- 但 `sc` 模式仍然会把候选规则动态扩展得过宽

直接后果：

- 同一条样本被无关规则污染
- batch 结果解释困难
- `failed_records` / `result_missing` 增多
- 很难判断一条样本到底是“目标问题命中”，还是“被其他规则顺手打中”

### 6.2 现在需要把“规则映射”升级成“执行白名单”

当前不能再只做：

- `issue_category -> candidate_rule_ids`

需要升级成：

- `issue_category -> primary_rule_ids`
- `issue_category -> optional_rule_ids`
- `validation execution whitelist`

也就是客户样本验证页执行时，不能继续全量动态扩候选规则。
