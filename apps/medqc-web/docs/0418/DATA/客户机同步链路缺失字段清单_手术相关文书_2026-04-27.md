# 客户机同步链路缺失字段清单（手术相关文书）

更新时间：2026-04-27  
适用项目：`D:\LLM\LX888` / `apps/medqc-web`

## 1. 问题概述

本次排查的直接现象是：

在本机病历联审页面中，以下手术相关单据显示为空：

1. `术前小结` `document_id = 4536585||18`
2. `麻醉记录` `document_id = 47809`
3. `手术安全核查记录` `document_id = 47809`

经比对：

- 客户源库 `public.*`
- 客户机本地 PG `cdm.*`
- 本机导入后的 `cdm.*`
- 联审 bundle

最终确认：

**问题根因不在本机前端，也不在本机 bundle，而在“客户源库 -> 客户机本地 PG”同步链路和本地 `cdm` 表结构本身。**

更准确地说：

1. 源库中这几类文书存在大量结构化字段
2. 客户机本地 PG 对应 `cdm` 表结构严重缩水
3. 这些缺失字段在客户机本地 PG 中根本没有列可承载
4. 因此即使源库有内容，客户机本地 PG 也只能留下“标题壳 + 空 `record_content`”

本次重点排查表：

1. `public.anesthesia_record` -> `cdm.anesthesia_record`
2. `public.presurg_summary` -> `cdm.presurg_summary`
3. `public.surgery_safecheck_record` -> `cdm.surgery_safecheck_record`

重点病历：

- 姓名：韦光伦
- 住院号：199702
- `visit_id = 2277183`

## 3. 已确认事实

## 3.1 客户机本地 PG 当前表结构是瘦表

客户机本地 PG 中这 3 张 `cdm` 表当前只有：

- 基础身份字段
- 基础文书元数据
- `record_content`

没有任何额外的结构化正文列。

## 3.2 源库对应 `public.*` 表字段更丰富

同名源表中存在大量结构化字段，例如：

- 科室 / 病房 / 床号
- 术前指征
- 麻醉方式
- 生命体征
- 术前准备
- 讨论摘要
- 护士/麻醉医生/主刀声明
- 开始/结束时间

说明：

**源库不是没内容，而是客户机本地 PG 的同步结果没有把这些字段带下来。**

## 3.3 本仓库 `cdm` 模型定义本身也是瘦模型

代码位置：

- [cdm.py](D:/LLM/LX888/apps/medqc-web/backend/app/database/models/cdm.py)

以下模型当前都只定义了：

- 主键/元数据
- `visit_type`
- `record_content`

对应类：

- [PresurgSummary](D:/LLM/LX888/apps/medqc-web/backend/app/database/models/cdm.py)
- [SurgerySafecheckRecord](D:/LLM/LX888/apps/medqc-web/backend/app/database/models/cdm.py)
- [AnesthesiaRecord](D:/LLM/LX888/apps/medqc-web/backend/app/database/models/cdm.py)

因此问题不是单一 SQL 漏字段，而是：

**本地表结构设计就不完整，导致同步链路即使想落字段，也无表结构承接。**

## 5. 根因判断

## 5.1 不是本机前端问题

本机联审页面的空展示只是对客户机本地 PG 导出结果的忠实反映。  
当前缺口发生在更前面的数据链路。

## 5.2 不是本机导入问题

本机导入脚本已经支持自动补列。  
但导入的前提是 CSV 本身有这些列。  
客户机本地 PG 导出的 CSV 已经是瘦字段，所以本机无法凭空恢复这些内容。

## 5.3 不只是同步 SQL 漏字段

更深层问题是：

1. 客户机本地 PG 物理表结构本身就没这些列
2. 本仓库 ORM 模型定义也只建了瘦字段

因此当前问题应定性为：

**本地 `cdm` 表结构设计不完整 + 同步链路字段映射不完整的组合问题。**

## 6. 建议开发修复方案

建议按三层修，不要只修其中一层。

## 6.1 第一层：补本地 `cdm` 表结构

优先补表：

1. `cdm.anesthesia_record`
2. `cdm.presurg_summary`
3. `cdm.surgery_safecheck_record`

最少要求：

- 补齐上文列出的关键结构化字段
- 允许客户机本地 PG 存下源库真实字段

## 6.2 第二层：补同步链路字段映射

需要检查并修改：

- `web.anesthesia_record`
- `web.presurg_summary`
- `web.surgery_safecheck_record`

以及项目内 ETL/sync 映射配置，确保：

- 源库字段 -> 客户机本地 PG `cdm` 列

能完整落地，而不是只保留 `record_content`。

## 6.3 第三层：补联审装配与展示

在字段真正进入本地 `cdm` 表后，再补：

1. `assembler.py`
2. `QCReviewDrawer.vue`

建议方向：

- `anesthesia_record` 用结构化字段展示生命体征、麻醉方式、开始结束时间
- `presurg_summary` 用结构化字段展示术前指征、拟施手术、术前准备、手术要点
- `surgery_safecheck_record` 用结构化字段展示三方声明和核查信息

## 7. 优先级建议

如果开发资源有限，建议优先级：

- `anesthesia_record`
- `presurg_summary`

- 这三张表已经明确存在“源库有字段、本地 PG 无列”的问题

## 8. 可以直接转开发的一句话结论

> 已确认客户机本地 PG 的 `cdm.anesthesia_record`、`cdm.presurg_summary`、`cdm.surgery_safecheck_record` 三张表结构与源库 `public.*` 对应表严重不一致。源库中存在大量结构化字段，但客户机本地 PG 本身没有这些列，导致同步链路无法完整落库，只保留了空 `record_content` 壳。该问题需要同时补本地表结构、同步字段映射和联审装配逻辑，不能仅通过前端展示修复。
