## 基线原则与来源标注

1. V3.6 用户手册列出的一级模块、二级功能、关键操作、状态、统计指标和规则管理能力均进入目标范围，不因当前尚未实现或优先级较低而删除。
2. MedQC 可以采用更好的交互、自动化和技术实现替代原手册方案，但替代后必须仍能完成原业务目标，并提供可验证的迁移或等价说明。
3. MedQC 新增的 AI 质控、客户样本验证、规则集隔离、证据链、诊断包、数据完整性治理等能力属于产品扩展，不能用来替代手册基线中的任务、整改、统计和规则管理闭环。
4. 功能项按来源分为：
   - **手册明确**：原文直接描述，属于必须覆盖能力；
   - **手册推导**：原文以“与其他模块类似”等方式引用，需按被引用模块实现等价能力；
   - **MedQC 扩展**：由当前项目增加，需单独说明业务依据和验收合同。
5. 本文是目标能力与差距矩阵；当前产品的版本边界、非目标、发布范围和最终合同应由独立的 MedQC V5 产品 PRD 承载。

## 背景

《病历内涵质控平台 V3.6 用户操作手册》描述的是一个成熟的病历内涵质控后台，覆盖工作台、病历质控、任务管理、统计分析、规则配置、质控点管理、文书管理和测试病历管理等完整业务闭环。

MedQC 当前已经具备 `dashboard` 管理端、`workstation-v5` 工作台、四川/泸县规则执行、病案首页生成、DRG/DIP 相关能力和部分质控任务链路；部分代码目录仍沿用 `workstation-v4` 命名。本文档用于明确：

1. V3.6 手册全量功能如何进入 MedQC 产品范围，并建立逐项可追踪的覆盖关系。
2. 当前 MedQC 已包含哪些能力。
3. 每个功能点还缺什么。
4. 后续开发优先级和验收口径。

## 产品定位

MedQC 的内涵质控 V3.6 总需求定位为“医院病历内涵质控闭环平台”，而不只是单病例 AI 质控工具。目标是把病历数据、规则执行、缺陷审核、整改追踪、统计分析和规则生命周期串成可运营、可审计、可复核的后台系统。

V3.6 手册能力是目标下限，不是产品上限。路线图中的优先级只决定交付顺序，不改变功能是否纳入目标范围。

本 PRD 不要求一次性实现所有功能。当前建议采用分阶段落地：

- P0：跑通病历质控主链路，包括工作台待办、门急诊/运行/终末列表、详情联审、催办、通过、存疑、重质控、任务创建和进度。
- P1：补齐整改闭环、筛选模板、自定义列、导出、任务分配和规则管理基础能力。
- P2：建设统计分析、质控员工作分析、专项报表、27 项指标、18 项核心制度。
- P3：完善高级规则编排、文书管理、测试病历场景化验证和运维治理。

## 验收标准

### 文档级验收

- V3.6 手册中的一级模块、二级功能、关键操作、状态、统计指标和规则管理能力均有对应条目，不以“主要功能已覆盖”替代逐项追踪。
- 每个功能点均标注覆盖状态、现有依据、主要差距、优先级和验收口径。
- 每个功能点标注“手册明确、手册推导或 MedQC 扩展”；扩展能力不得覆盖、删除或弱化手册基线。
- 不把 mock、提示占位、未接后端接口写成已完成能力。
- 明确区分 `dashboard` 管理端能力与 `workstation-v5` 工作台能力。

### 产品级验收

- 质控管理员能从工作台进入任务、缺陷、病历三个待办列表。
- 质控员能处理门急诊、运行、终末病历的缺陷审核和整改派发。
- 管理员能创建抽查任务、查看任务进度、重新质控并导出结果。
- 规则管理员能维护评分标准、规则、质控点和测试病历验证。
- 管理层能查看病历质量、质控员工作、专项指标和核心制度报表。
- 发布验收应维护“手册功能 → MedQC 页面/API/测试”的追踪表；未实现项可以按路线图延期，但必须保留在产品待办中并明确状态。

### 技术级验收

- 所有关键页面使用真实 API 或明确的不可用状态，不使用静默 mock 冒充数据。
- 所有批量操作具备权限校验、二次确认、操作结果和审计记录。
- 所有导出遵守筛选条件、导出上限、字段模板和权限范围。
- 任务、缺陷、整改、申诉、规则变更均有可追踪历史。
- 涉及真实患者数据时，导出和日志不得暴露敏感信息。
