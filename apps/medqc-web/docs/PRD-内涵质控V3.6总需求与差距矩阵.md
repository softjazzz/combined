## 基线原则与来源标注

1. V3.6 用户手册列出的一级模块、二级功能、关键操作、状态、统计指标和规则管理能力均进入目标范围，不因当前尚未实现或优先级较低而删除。
2. MedQC 可以采用更好的交互、自动化和技术实现替代原手册方案，但替代后必须仍能完成原业务目标，并提供可验证的迁移或等价说明。
3. MedQC 新增的 AI 质控、客户样本验证、规则集隔离、证据链、诊断包、数据完整性治理等能力属于产品扩展，不能用来替代手册基线中的任务、整改、统计和规则管理闭环。
4. 功能项按来源分为：
   - **手册明确**：原文直接描述，属于必须覆盖能力；
   - **手册推导**：原文以“与其他模块类似”等方式引用，需按被引用模块实现等价能力；
   - **MedQC 扩展**：由当前项目增加，需单独说明业务依据和验收合同。
5. 本文是目标能力与差距矩阵；当前产品的版本边界、非目标、发布范围和最终合同应由独立的 MedQC V5 产品 PRD 承载。

## 背景

《病历内涵质控平台 V3.6 用户操作手册》描述的是一个成熟的病历内涵质控后台，覆盖工作台、病历质控、任务管理、统计分析、规则配置、质控点管理、文书管理和测试病历管理等完整业务闭环。

MedQC 当前已经具备 `dashboard` 管理端、`workstation-v5` 工作台、四川/泸县规则执行、病案首页生成、DRG/DIP 相关能力和部分质控任务链路；部分代码目录仍沿用 `workstation-v4` 命名。本文档用于明确：

1. V3.6 手册全量功能如何进入 MedQC 产品范围，并建立逐项可追踪的覆盖关系。
2. 当前 MedQC 已包含哪些能力。
3. 每个功能点还缺什么。
4. 后续开发优先级和验收口径。

## 目标用户

| 用户角色     | 核心诉求                                                               |
| ------------ | ---------------------------------------------------------------------- |
| 质控管理员   | 统一管理运行、终末、门急诊病历质控任务，审核缺陷、派发整改、追踪闭环。 |
| 质控员       | 处理分配给自己的质控任务，查看病历和缺陷详情，完成审核和复审。         |

| 规则管理员   | 配置评分标准、规则集、质控点、上线状态、测试病历和规则验证流程。       |
| 临床医生     | 接收催办、查看缺陷、完成整改或申诉。                                   |
| 系统管理员   | 配置权限、数据范围、任务队列、通知和审计。                             |

## 产品定位

MedQC 的内涵质控 V3.6 总需求定位为“医院病历内涵质控闭环平台”，而不只是单病例 AI 质控工具。目标是把病历数据、规则执行、缺陷审核、整改追踪、统计分析和规则生命周期串成可运营、可审计、可复核的后台系统。

V3.6 手册能力是目标下限，不是产品上限。路线图中的优先级只决定交付顺序，不改变功能是否纳入目标范围。

本 PRD 不要求一次性实现所有功能。当前建议采用分阶段落地：

- P0：跑通病历质控主链路，包括工作台待办、门急诊/运行/终末列表、详情联审、催办、通过、存疑、重质控、任务创建和进度。
- P1：补齐整改闭环、筛选模板、自定义列、导出、任务分配和规则管理基础能力。
- P2：建设统计分析、质控员工作分析、专项报表、27 项指标、18 项核心制度。
- P3：完善高级规则编排、文书管理、测试病历场景化验证和运维治理。

## 数据、权限、状态、任务和报表要求

### 数据要求

| 领域       | 要求                                                                     | 当前差距                                                                              |
| ---------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| 病历主数据 | 统一登记号、流水号、病案号、住院号、患者、科室、医生、出入院时间。       | `records`、CDM、bundle 和历史 `medical_records` 存在多套来源，需要统一展示契约。      |
| 缺陷数据   | 缺陷需包含状态、严重程度、规则来源、证据、整改状态、申诉状态、操作历史。 | `qc_defects`、`qc_results`、`qc_remediation_tasks` 有基础，但状态闭环未全部接入页面。 |
| 任务数据   | 任务需包含类型、场景、进度、分配、抽样、期望完成时间、实际完成时间。     | 新建任务必须显式选择场景和匹配规则集，并由服务端锁定目录版本；历史 NULL 仅只读兼容，不推断或回填。`qc_tasks.scene`、`record_refs`、`rule_set_key`、`rule_set_version`、关联三坐标、`task_qc_runs` 与 `run_scope` 迁移 45–51 已编写但未执行，业务库仍为 revision44。已验证三坐标候选可走现代事务保存/重放；候选服务现仅对显式当前在院子范围开通运行任务，完整运行与终末缺权威归档判定而拒绝。任务/job 同事务关联、按 job_id 及关联三坐标读取 LX0609、LX0916 和 SC 单病历客户结果的代码合同通过隔离测试。SC 旧稀疏结果不可展示，容量和客户详情文案仍待验收；静态规则集目录无发布状态或不可变定义合同。门急诊无匹配规则集且正样本为 0，默认远端来源超时；job 结果不会自动更新任务病历状态，评分/缺陷数与人工完成语义未定。真实执行、任务状态回写、复杂抽样与定时任务未验收。 |
| 规则数据   | 规则需支持评分标准、项目组、质控点、文书、生效科室、医生端生效、版本。   | `qc_rules`、`scoring_rules`、四川/泸县规则并存，需统一规则生命周期。                  |
| 报表数据   | 需形成运行、终末、门急诊、首页、质控员、专项指标的稳定聚合视图。         | 当前统计 API 偏概览，专题报表缺少数据集市和导出口径。                                 |

### 状态要求

| 状态域                         | 要求                                                                                                                                             | 当前差距                                                                   |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| 工作台待办标签                 | 倒计时 1 天、进行中、未开始等只用于待办聚合和提醒，不充当任务执行状态。                                                                          | 当前部分页面可能把待办标签与任务状态混用。                                 |
| 任务状态与质控状态             | 分开保存任务状态和质控状态；覆盖手册明确出现的进行中、已完成、已超时、待分配、质控中等状态。MedQC 新增的取消、失败和恢复状态需单独定义转换条件。 | 需要核对任务表、API 和前端枚举，避免同名异义或遗漏“已超时/待分配”。        |
| 病历审核状态                   | 待审核、待复审、审核通过、审核存疑等状态需全链路一致。                                                                                           | 当前病历级和缺陷级状态混用，需要统一映射。                                 |
| 缺陷整改与申诉状态             | 区分临床申诉、申诉驳回、申诉通过、催办待整改、医生自行整改、未催办待整改、催办已整改；催办/撤回催办属于动作和通知记录。                          | 缺陷状态有基础，但撤回催办、整改前后对比和申诉链路不完整。                 |
| 专项规则交付状态（MedQC 扩展） | 每条规则只允许输出其权威规则目录规定的状态；`uncertain`、`technical_error` 仅可作为内部诊断信息，不得进入 LX0609 客户交付结果。                  | 需要按规则号校验允许状态，并将技术失败保留在任务日志、调试快照或诊断包中。 |

### 报表要求

所有报表必须支持：

1. 时间范围查询。
2. 科室维度查询。
3. 任务维度查询。
4. 明细下钻。
5. 列表导出。
6. 指标口径说明。
7. 权限过滤。

当前 MedQC 需要优先补齐报表数据来源和指标定义，避免仅用前端模拟数据展示。

## 验收标准

### 文档级验收

- V3.6 手册中的一级模块、二级功能、关键操作、状态、统计指标和规则管理能力均有对应条目，不以“主要功能已覆盖”替代逐项追踪。
- 每个功能点均标注覆盖状态、现有依据、主要差距、优先级和验收口径。
- 每个功能点标注“手册明确、手册推导或 MedQC 扩展”；扩展能力不得覆盖、删除或弱化手册基线。
- 不把 mock、提示占位、未接后端接口写成已完成能力。
- 明确区分 `dashboard` 管理端能力与 `workstation-v5` 工作台能力。

### 产品级验收

- 质控管理员能从工作台进入任务、缺陷、病历三个待办列表。
- 质控员能处理门急诊、运行、终末病历的缺陷审核和整改派发。
- 管理员能创建抽查任务、查看任务进度、重新质控并导出结果。
- 规则管理员能维护评分标准、规则、质控点和测试病历验证。
- 管理层能查看病历质量、质控员工作、专项指标和核心制度报表。
- 发布验收应维护“手册功能 → MedQC 页面/API/测试”的追踪表；未实现项可以按路线图延期，但必须保留在产品待办中并明确状态。

### 技术级验收

- 所有关键页面使用真实 API 或明确的不可用状态，不使用静默 mock 冒充数据。
- 所有批量操作具备权限校验、二次确认、操作结果和审计记录。
- 所有导出遵守筛选条件、导出上限、字段模板和权限范围。
- 任务、缺陷、整改、申诉、规则变更均有可追踪历史。
- 涉及真实患者数据时，导出和日志不得暴露敏感信息。
