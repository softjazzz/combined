# 任务调度技术方案

## 1. 文档目的

- 本文档用于冻结第一阶段任务调度与异步执行技术选型。
- 覆盖范围：
  - 定时抽查任务
  - 异步抽样与分配
  - 批量质控任务
  - 任务执行状态跟踪
  - 失败重试与死信处理

## 2. 结论先行

第一阶段推荐方案：

- `PG` 作为主数据源和最终状态落库
- `Redis` 作为调度队列、延迟任务、worker 通信层
- `Celery Worker + Celery Beat` 作为执行器与定时调度器

明确不采用：

- `RabbitMQ`
- `RocketMQ`

## 3. 为什么这样选

### 3.1 当前代码证据

- 后端依赖已包含：
  - `celery==5.3.4`
  - `aioredis==2.0.1`
- 当前任务业务表已存在：
  - `qc_tasks`
  - `qc_task_records`
- 当前仓库已有异步任务存储能力：
  - `qc.qc_async_jobs`
  - `qc.qc_async_job_events`
  - `qc.qc_async_job_dead_letters`

也就是说，第一阶段所需的关键积木大部分已经在仓库里，只是还没有真正拼成调度闭环。

### 3.2 选 Redis 不选 RabbitMQ / RocketMQ 的原因

#### 选 Redis

- 与现有依赖最匹配，接入成本最低。
- 适合当前“定时任务 + 异步工作队列”场景。
- 运维复杂度低，适合第一阶段快速落地。
- 能满足：
  - broker
  - 延迟调度
  - worker 通信
  - 基础限流/锁

#### 不选 RabbitMQ

- 功能强，但第一阶段会增加额外运维与配置复杂度。
- 当前项目核心问题不是消息可靠性上限不够，而是压根没有执行闭环。

#### 不选 RocketMQ

- 更适合跨系统、大吞吐、事件驱动链路。
- 当前项目是院内单系统任务调度，不需要先上 RocketMQ 这一级别的复杂度。

## 4. 目标架构

```text
Frontend
  -> FastAPI API
       -> PG(qc_tasks / qc_task_records / qc_async_jobs / ...)
       -> Redis(broker / schedule / lock)
       -> Celery Beat
       -> Celery Worker
            -> Sampling / Assignment / QC Execution / Statistics Jobs
            -> PG update + audit + events
```

## 5. 组件职责

### 5.1 PG

负责保存最终业务状态和可审计结果：

- `qc_tasks`
  - 任务定义
  - 调度配置 `schedule_config`
  - 任务状态
- `qc_task_records`
  - 任务与病历的分配关系
  - 单条病历执行状态
- `qc_async_jobs`
  - 异步任务实例
  - 进度、状态、重试信息、心跳
- `qc_async_job_events`
  - 状态流转日志
- `qc_async_job_dead_letters`
  - 超过重试阈值的失败任务

### 5.2 Redis

负责保存短期调度状态，不承载最终业务真相：

- Celery broker
- 延迟执行与周期触发中间状态
- Worker 抢占与通信
- 可选分布式锁

### 5.3 Celery Beat

负责定时扫描并触发：

- 周期抽查任务
- 到期执行任务
- 可选重试补偿扫描

### 5.4 Celery Worker

负责执行具体业务任务：

- 抽样
- 分配
- 批量质控
- 统计汇总
- 失败重试

## 6. 任务模型分层

### 6.1 业务任务

业务任务仍以 `qc_tasks` 为核心，表示“用户看得见、管理者能操作”的任务。

例如：

- 单次抽查任务
- 定时抽查任务
- 批量重新质控任务

### 6.2 执行任务

执行任务以 `qc_async_jobs` 为核心，表示“系统实际调度执行的异步作业”。

例如：

- `task_sampling_job`
- `task_assignment_job`
- `batch_qc_job`
- `statistics_refresh_job`

### 6.3 两者关系

建议关系：

- 一个 `qc_task`
  - 可对应多个 `qc_async_jobs`
- 一个 `qc_async_job`
  - 通过 `business_type + business_id` 回指业务任务

建议映射：

- `business_type = qc_task`
- `business_id = qc_tasks.id`

## 7. 推荐 Job 类型

第一阶段建议至少定义以下 job type：

1. `qc_task_schedule_trigger`
   - 定时任务触发器
2. `qc_task_sampling`
   - 任务抽样
3. `qc_task_assignment`
   - 分配病历到人
4. `qc_batch_execute`
   - 批量发起质控
5. `qc_statistics_refresh`
   - 统计汇总刷新

## 8. 推荐队列划分

建议先保持简单，只分 3 条队列：

1. `qc.schedule`
   - 定时触发
   - 调度类任务
2. `qc.execute`
   - 抽样
   - 分配
   - 质控执行
3. `qc.report`
   - 统计汇总
   - 大批量导出

不要第一阶段就按几十条队列切分，否则排障复杂度会过高。

## 9. 状态机建议

### 9.1 `qc_tasks.status`

建议业务任务状态保留：

- `draft`
- `scheduled`
- `pending`
- `running`
- `paused`
- `completed`
- `failed`
- `cancelled`

### 9.2 `qc_async_jobs.status`

建议执行任务状态沿用现有 async job store：

- `accepted`
- `queued`
- `running`
- `retry_waiting`
- `succeeded`
- `failed`
- `cancelled`

### 9.3 状态职责划分

- `qc_tasks.status` 关注业务视角
- `qc_async_jobs.status` 关注系统执行视角

不要把二者混成一套状态，否则页面和调度器会互相污染。

## 10. 调度流程

### 10.1 单次任务

1. 前端提交 `qc_task`
2. 后端写入 `qc_tasks`
3. 后端立即创建 `qc_async_job`
4. Celery Worker 执行：
   - 抽样
   - 分配
   - 可选批量质控
5. 更新：
   - `qc_task_records`
   - `qc_tasks.progress/status`
   - `qc_async_jobs/events`

### 10.2 定时任务

1. 前端提交带 `schedule_config` 的 `qc_task`
2. 后端写入 `qc_tasks.status = scheduled`
3. Celery Beat 按周期扫描到期任务
4. 为到期任务创建新的 `qc_async_job`
5. Worker 执行具体逻辑
6. 执行结果回写 PG

## 11. `schedule_config` 建议结构

建议最小结构：

```json
{
  "enabled": true,
  "timezone": "Asia/Shanghai",
  "type": "daily",
  "start_at": "2026-03-30T08:00:00+08:00",
  "end_at": null,
  "time_of_day": "08:00",
  "days_of_week": [1, 3, 5],
  "cron": null
}
```

第一阶段建议支持：

- `once`
- `daily`
- `weekly`

不建议第一阶段直接开放任意 cron 表达式给业务用户。

## 12. 幂等与重试

### 12.1 幂等

每个执行任务应带 `idempotency_key`，避免重复触发导致：

- 重复抽样
- 重复分配
- 重复写入任务记录

建议规则：

- `task_id + job_type + scheduled_fire_time`

### 12.2 重试

建议：

- 默认重试次数：`3`
- 重试退避：`30s / 2min / 10min`
- 重试状态写入 `retry_waiting`

### 12.3 死信

超过最大重试次数后：

- 写入 `qc_async_job_dead_letters`
- 同步把 `qc_tasks.status` 更新为 `failed` 或 `partial_failed`

## 13. 并发与锁

### 13.1 为什么需要锁

定时任务场景下，可能出现：

- Beat 重复触发
- 多 worker 同时抢同一任务
- 重试任务和新任务并发执行

### 13.2 推荐做法

- 用 Redis 分布式锁控制“同一 `task_id + fire_time` 只能执行一次”
- 关键写操作依赖 PG 唯一约束兜底：
  - 如 `qc_task_records(task_id, record_id)` 唯一索引

## 14. 监控与审计

第一阶段至少要有：

1. 任务创建量
2. 成功率
3. 失败率
4. 重试次数
5. 死信数量
6. Worker 心跳
7. 平均执行时长

建议展示入口：

- 管理端调度监控页
- 或先落到内部运维接口

## 15. API 影响范围

需要补充或调整的接口建议：

1. `POST /tasks`
   - 增加 `schedule_config` 校验
2. `POST /tasks/{id}/schedule/activate`
3. `POST /tasks/{id}/schedule/pause`
4. `POST /tasks/{id}/run-now`
5. `GET /tasks/{id}/jobs`
   - 查看关联执行任务
6. `GET /async-jobs`
   - 系统异步任务列表
7. `GET /async-jobs/{id}`
8. `POST /async-jobs/{id}/retry`
9. `POST /async-jobs/{id}/cancel`

## 16. 部署建议

第一阶段建议部署为 3 类进程：

1. `API`
   - FastAPI
2. `Worker`
   - Celery Worker
3. `Scheduler`
   - Celery Beat

依赖基础设施：

1. `PG`
2. `Redis`

如果环境资源有限，也可以先：

- 1 个 API 实例
- 1 个 Worker 实例
- 1 个 Beat 实例

先保证闭环，再谈横向扩容。

## 17. 与现有脚本的边界

- 本方案以 `workstation v4` 现有前后端为基座。
- 第一阶段允许：
  - 新增调度模块
  - 新增 Celery 配置模块
  - 新增 worker/beat 启动入口
  - 新增任务监控接口
- 第一阶段默认不直接修改现有项目脚本：
  - 启动脚本
  - 构建脚本
  - 发布脚本
  - 部署脚本

如果后续需要把 worker/beat 纳入统一脚本体系，必须先人工确认。

## 18. 为什么不是 APScheduler

`APScheduler` 可以做简单定时任务，但不适合作为第一阶段主方案，因为：

- 当前需求不只是“定时触发”，还需要异步执行、重试、状态跟踪、死信处理。
- Celery 已经更接近完整任务平台。
- 如果先用 APScheduler，后面大概率还要再迁一次。

## 19. 实施顺序建议

### 第一步

- 完成 Celery 基础配置
- 接通 Redis broker
- 保持 PG 为主落库

### 第二步

- 打通 `qc_task -> qc_async_job -> worker execute -> PG 回写`

### 第三步

- 打通 `Celery Beat -> schedule_config -> 到期触发`

### 第四步

- 增加重试、死信、监控

## 20. 验收标准

1. 单次任务可异步执行并回写状态。
2. 定时任务可按 `schedule_config` 到期触发。
3. 失败任务可自动重试。
4. 超过重试上限的任务可进入死信表。
5. API 页面可查看任务执行状态。
6. 全流程仍以 PG 数据为最终真相。

## 21. 一句话方案结论

第一阶段最稳妥的方案就是 `PG + Redis + Celery`：PG 管最终状态，Redis 管调度通道，Celery 管执行与定时；先把医院内网任务闭环做出来，再考虑 RabbitMQ、RocketMQ 这类更重的消息中间件。
