# 首页批量质控工作台-数据视图与接口开发计划

## 背景

`workstation v4` 当前首页批量质控列表、编码质控、结算清单质控，仍主要依赖前端本地拼接阶段状态与风险原因：

- 阶段状态由当前筛选 stage 文案硬编码
- 风险原因没有稳定后端数据源
- 列表页看不到“最近一次结果 + 当前活跃问题 + 最新消息”这一组真实状态

现有基础表已经具备：

- `medical_records / mr`
- `qc_results`
- `qc_defects`
- `notifications`

问题不在于缺表，而在于缺少“当前状态聚合层”。

## 目标

为 `workstation v4` 增加 3 条正式工作台聚合能力：

- 首页批量质控工作台
- 编码质控工作台
- 结算清单质控工作台

让前端列表页稳定展示：

- 当前队列状态
- 最新质控结果
- 活跃缺陷数
- 风险原因
- 最新消息状态

并为详情页提供 snapshot 接口，避免直接拼历史流水。

## 统一数据口径

- `frontpage`

- 首页：`record_id = frontpage::{visit_id}`
- 编码：`record_id = coding::{visit_id}`

## 接口方案

### worklist 接口

- `GET /api/v1/workstation/frontpage-qc/worklist`
- `GET /api/v1/workstation/coding-qc/worklist`
- `GET /api/v1/workstation/settlement-qc/worklist`

统一参数：

- `department`
- `keyword`
- `queue_status`
- `page`
- `page_size`
- `sort_by`
- `sort_order`

统一返回：

```json
{
  "success": true,
  "data": {
    "items": [],
    "total": 0,
    "page": 1,
    "page_size": 50,
    "departments": []
  }
}
```

### snapshot 接口

- `GET /api/v1/workstation/frontpage-qc/{visit_id}/snapshot`
- `GET /api/v1/workstation/coding-qc/{visit_id}/snapshot`
- `GET /api/v1/workstation/settlement-qc/{visit_id}/snapshot`

每个 snapshot 返回：

- 最近一次 `qc_results`
- 当前活跃 `qc_defects`
- 最新聚合 `notification`
- 最近 5 次历史结果

## 风险原因聚合规则

风险原因统一由后端生成，不让前端再本地猜。

规则：

- 只取 `status != completed` 的活跃 defect
- 严重级别排序：`error > warning > info`
- 取前 1 到 3 条
- 输出：
  - 1 条：`{rule_name}: {description}`
  - 多条：`第一条问题描述 等 N 条问题`

## 后端实现

### 第一阶段

新增聚合 service：

- `backend/app/services/workstation/worklist_service.py`

能力包括：

- `get_frontpage_worklist(...)`
- `get_coding_worklist(...)`
- `get_settlement_worklist(...)`
- `get_frontpage_snapshot(...)`
- `get_coding_snapshot(...)`
- `get_settlement_snapshot(...)`

实现口径：

- 基础病历：`cdm.mr`
- 结算基础数据：`cdm.medical_insurance_settlement`
- 最新结果：`qc.qc_results`
- 当前问题：`qc.qc_defects`
- 最新消息：`qc.notifications`

第一阶段不新增物理表，不改 `mr / diagnosis / mr_surgery / mr_cost`。

### 第二阶段

当口径稳定后，再评估下沉为数据库视图：

- `v_frontpage_qc_worklist`
- `v_coding_qc_worklist`
- `v_settlement_qc_worklist`

如数据量继续增大，再评估物化视图。

## 前端改造边界

### 列表页

- `WorkstationV4View` 在 `frontpage_qc / settlement_qc` 阶段，改为调用正式 worklist 接口
- `riskReason` 不再本地生成，直接消费接口返回
- `queue_status` 以后端为准

### 详情页

- 进入病历详情时，调用 snapshot 接口
- `QCResultTab` 优先展示最近一次持久化后的当前问题
- 结算页优先展示最近一次结算 snapshot

### 保留边界

- `mr / diagnosis / mr_surgery / mr_cost` 继续只读
- demo/test/debug 页面不纳入本次改造范围

## 测试计划

### 接口测试

- 首页 worklist 返回待首页质控病历，且每个 `visit_id` 只出现一行
- 编码 worklist 返回待编码质控病历
- 结算 worklist 返回待结算质控病历
- snapshot 返回最近一次结果、当前问题、最新消息

### 数据口径测试

- 同一病历重复质控后：
  - `qc_results` 继续追加历史
  - worklist 仍只有一行
  - `risk_reason` 仅取当前活跃问题
- 问题修复后再次质控：
  - `qc_defects` 已解决项转 `completed`
  - worklist 的 `active_defect_count` 下降
  - `risk_reason` 更新
- 无问题编码质控：
  - 允许不新增“通过消息”
  - worklist 仍能显示最新结果

### 前端测试

- 首页批量质控列表显示真实风险原因
- 结算清单列表显示真实风险原因
- 打开详情后，右侧质控区和列表状态一致
- 执行质控后，worklist、snapshot、消息面板同步刷新
