# 实施路线图：先补哪些页面、先补哪些接口

## 1. 路线图目标

- 目标不是“把所有页面都补齐”，而是先把 V3.6 的主链路补成一个能闭环、能演示、能验收的产品。
- 基础设施口径补充：
  - `PG` 继续作为主数据源
  - `Redis` 作为任务调度与异步执行基础设施
  - 第一阶段优先采用 `Celery + Redis`
  - 第一阶段不引入 RabbitMQ / RocketMQ
- 登录模块按最新范围收敛为：
  - `用户名/密码登录`
  - `手机号/密码登录`
  - 手机号作为同一账户的备用登录标识
  - 当前认证实现仍基于内存用户源，后续需要持久化
  - 不做扫码登录
  - 不做短信验证码
- 实施原则：
  - `先主链路，后专题`
  - `先页面骨架，后高级配置`
  - `先真实数据，后样式优化`
  - `先统一产品模型，后做功能扩张`

## 2. 总体阶段划分

| 阶段 | 目标 | 交付重点 |
| --- | --- | --- |
| Phase 0 | 产品收口 | 明确复刻范围，收口菜单与入口 |
| Phase 1 | 病历质控主链路 | 门急诊 + 运行/终末详情台 + 筛选模板 + 自定义列 |
| Phase 2 | 任务与首页闭环 | 任务分配/定时执行 + 工作台联动 |
| Phase 3 | 统计分析真实化 | 四类病历质量分析 + 质控员分析 + 专项报表一期 |
| Phase 4 | 规则运营后台 | 评分标准/评分详情/项目组/质控点/文书/测试病历 |
| Phase 5 | 登录增强与收尾 | 手机号备用登录标识、验收清单、清理 demo/mock |

## 3. Phase 0：先做产品收口

### 3.1 先补哪些页面

- 收口主导航，只保留：
  - 登录
  - 工作台
  - 病历质控
  - 任务管理
  - 统计分析
  - 质控规则管理
- 将 demo/test/workstation/DRG 等入口移出主产品菜单，避免干扰复刻目标。

### 3.2 先补哪些接口

- 暂不新增业务接口。
- 先做枚举、权限、菜单配置收口。

### 3.3 交付结果

- 得到一个“长得像手册产品”的导航骨架。
- 后续开发不会继续在混合菜单上叠加成本。

## 4. Phase 1：优先补病历质控主链路

这是第一优先级，也是整个复刻成败的关键。

### 4.1 先补页面

1. `门急诊病历页`
   - 新增缺陷列表/病历列表双视图
   - 对齐运行病历页的基本交互骨架
2. `病历详情审核运营台`
   - 统一门急诊/运行/终末的详情页模型
   - 支持结构化查看、评分标准切换、审核通过、审核存疑、催办、重新质控、查看整改
3. `筛选模板弹窗`
   - 新建筛选
   - 提交并保存模板
   - 快捷筛选
   - 修改模板
4. `自定义列表头配置`
   - 列选择
   - 排序
   - 个人配置持久化

### 4.2 先补接口

1. `GET /records/outpatient-emergency`
   - 门急诊病历分页查询
   - 支持时间、评分标准、病历信息检索
2. `GET /records/{id}/qc-detail`
   - 病历详情聚合接口
   - 返回病历基础信息、电子病历、缺陷、整改、操作历史
3. `POST /filters/templates`
   - 保存筛选模板
4. `GET /filters/templates`
   - 获取个人筛选模板
5. `DELETE /filters/templates/{id}`
   - 删除筛选模板
6. `PUT /users/preferences/record-columns`
   - 保存自定义列配置

### 4.3 为什么先做这批

- 这是手册最核心的业务界面。
- 当前系统最接近这一块，复用价值最高。
- 一旦门急诊补齐，病历质控主链路才完整。

## 5. Phase 2：再补任务与工作台闭环

### 5.1 先补页面

1. `全部任务页`
   - 批量分配
   - 单个分配
   - 修改任务
2. `新建抽查任务页`
   - 单次任务
   - 定时任务
   - 抽样方式配置
3. `工作台`
   - 待办卡片与任务、病历、缺陷列表真实联动
   - 场景切换口径统一为“全部/终末/运行/门急诊”

### 5.2 先补接口

1. `POST /tasks`
   - 完善定时任务字段校验
2. `POST /tasks/{id}/schedule/activate`
   - 激活定时任务
3. `POST /tasks/{id}/schedule/pause`
   - 暂停定时任务
4. `POST /tasks/{id}/assign`
   - 扩展按科室/按比例/重新分配
5. `GET /dashboard/todo-stats`
   - 移除示例数据分支
6. `GET /dashboard/performance`
   - 移除示例排名分支
7. `GET /dashboard/todo-stats?scene=...`
   - 按场景统一返回任务、缺陷、病历聚合

### 5.2A 基础设施实施建议

1. `Celery Worker`
   - 执行抽样、分配、批量质控、异步统计任务
2. `Celery Beat`
   - 执行定时任务触发
3. `Redis`
   - 作为 broker 和调度中间层
4. `PG`
   - 保存任务定义、执行记录、任务状态、失败重试审计

### 5.3 为什么第二阶段做

- 没有任务闭环，病历质控只能算“人工列表操作”，不是医院级运营后台。
- 首页如果继续带 fallback，会直接影响产品可信度。

## 6. Phase 3：把统计分析从展示页改成真实业务页

### 6.1 先补页面

1. `统计分析首页`
   - 重组为手册结构导航
2. `运行病历质量分析页`
3. `终末病历质量分析页`
4. `病案首页质量分析页`
5. `质控员工作情况分析页`

门急诊分析和专项报表可放本阶段后半程。

### 6.2 先补接口

1. `GET /statistics/running/overview`
2. `GET /statistics/running/details`
3. `GET /statistics/final/overview`
4. `GET /statistics/final/details`
5. `GET /statistics/frontpage/overview`
6. `GET /statistics/staff-workload`
7. `GET /statistics/export`

### 6.3 本阶段不要先做什么

- 不要先做 27 项指标和 18 项核心制度全量细节。
- 先把运行/终末/首页三块真实数据做出来，再补高级专题。

## 7. Phase 4：重做规则运营后台

### 7.1 先补页面

1. `规则配置首页`
   - 区分门急诊规则配置、住院规则配置
2. `评分标准管理页`
3. `评分详情管理页`
4. `评分项目组管理页`
5. `质控点管理页`
6. `文书管理页`
7. `测试病历管理页`

### 7.2 先补接口

1. `GET/POST/PUT/DELETE /rule-standards`
2. `GET/POST/PUT/DELETE /rule-standards/{id}/levels`
3. `GET/POST/PUT/DELETE /rule-project-groups`
4. `GET/POST/PUT /qc-points`
5. `POST /qc-points/{id}/online`
6. `POST /qc-points/{id}/offline`
7. `POST /documents/import`
8. `GET /documents`
9. `GET/POST/PUT/DELETE /test-records`

### 7.3 为什么放在第四阶段

- 规则后台复杂度高，且依赖前面主链路和统计口径稳定。
- 如果主链路没统一，规则后台先做会继续放大模型混乱。

## 8. Phase 5：登录增强与收尾

### 8.1 先补页面

- 登录页手机号登录入口
- V3.6 回归验收页或验收文档

### 8.2 先补接口

- 认证用户源迁移到持久化存储
- 用户账户补充手机号唯一字段与索引
- 手机号+密码登录鉴权接口
- 用户名/手机号双标识登录判定规则
- 回归验收所需的测试数据与环境脚本

## 9. 推荐交付顺序

### 第 1 批：必须先做

- 门急诊病历页
- 统一病历详情台
- 筛选模板
- 自定义列
- 全部任务页真实分配
- 定时任务执行器
- 首页 fallback 清理

### 第 2 批：紧接着做

- 运行病历分析
- 终末病历分析
- 病案首页分析
- 质控员工作分析
- 统计导出

### 第 3 批：最后做

- 评分标准/评分详情/项目组
- 质控点管理
- 文书管理
- 测试病历管理
- 手机号备用登录

## 10. 里程碑定义

### M1：主链路可验收

- 三条病历线齐全
- 任务可创建、抽样、分配、执行
- 工作台数据真实

### M2：运营可用

- 统计分析真实可下钻
- 导出能力可用
- 终末病历归档/报告闭环

### M3：配置可运营

- 规则、评分、质控点、文书、测试病历后台齐全
- 登录形态与手册基本对齐

## 11. 最后建议

如果资源有限，不建议平均发力。正确顺序应该是：

1. 先把 `病历质控后台` 做完整
2. 再把 `统计分析` 做真实
3. 最后把 `规则管理后台` 做成运营平台

这样做，最短路径就能把当前系统从“混合产品”拉回到“接近 V3.6 手册”的形态。
