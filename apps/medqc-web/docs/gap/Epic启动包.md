# Epic 启动包

## 1. 文档用途

- 本文档用于启动 `MedQC 对齐 V3.6` 项目。
- 使用场景：
  - 立项会
  - Epic 启动会
  - 技术方案对齐会
  - 开发排期拆分会
- 目标不是重复所有 gap 文档，而是把开工必须统一的事项压缩成一份执行基线。

## 2. 项目目标

### 2.1 目标定义

本项目的目标不是“继续扩张现有混合系统”，而是把当前系统收口为一套能对齐 V3.6 主链路的病历内涵质控产品。

第一阶段目标：

1. 拉通 `登录 -> 工作台 -> 病历质控 -> 任务管理 -> 统计分析 -> 规则后台` 主骨架。
2. 补齐 `门急诊 / 运行 / 终末` 三条病历质控主线。
3. 清理 mock、fallback、内存认证、口径不统一等基础风险。
4. 形成可演示、可验收、可持续开发的版本基线。

### 2.2 成功标准

- 登录支持用户名/手机号双标识登录。
- 工作台与统计页核心数字来自真实数据。
- 门急诊病历列表和详情审核运营台可用。
- 任务系统具备单次任务闭环，定时任务具备可执行骨架。
- 规则后台至少具备最小可运营模型。

## 3. 范围冻结

### 3.1 本期纳入范围

- 登录
- 工作台
- 病历质控
- 任务管理
- 统计分析
- 质控规则管理

### 3.2 本期不纳入范围

- 扫码登录
- 短信验证码
- DRG 相关功能
- 工作站/同步类入口
- 与 V3.6 主手册无关的 demo/test 页面
- 27 项指标全量专题
- 18 项核心制度全量专题

### 3.3 登录口径冻结

- 同一账户维护：
  - 用户名
  - 手机号
  - 密码
- 登录支持：
  - `用户名 + 密码`
  - `手机号 + 密码`
- 手机号仅为备用登录标识。
- 不单独建设手机号账户体系。

## 4. 当前必须先认清的风险

### 4.0 实施约束

- 本项目明确基于 `workstation v4` 现有前后端继续开发。
- 允许新增页面、接口、聚合层和数据模型。
- 默认不改现有项目前后端脚本。
- 若必须修改现有脚本，必须人工确认后再进入实施。
- 所有前端 subagent 默认使用 `frontend-skill`。
- 基础设施口径明确为：
  - `PG` 继续作为主数据源
  - `Redis` 作为任务调度与异步执行基础设施
  - 第一阶段优先采用 `Celery + Redis`
  - 第一阶段不引入 `RabbitMQ / RocketMQ`

### 4.1 认证风险

- 当前认证仍基于内存 `users_db`。
- 登录字段语义仍是 `email`，不适合正式演进。

### 4.2 数据风险

- 工作台和统计分析存在 fallback/示例数据。
- 统计页前端仍有 mock 数据源。
- `Dashboard` 场景分类前后端口径未完全一致。

### 4.3 业务风险

- 门急诊主线缺失。
- 病历详情审核运营台不完整。
- 定时任务只有 `schedule_config`，没有执行闭环。
- 调度技术栈尚未在文档中固定，容易导致后续实现分叉。

### 4.4 规则风险

- 当前 `scoring_rules` 只能支撑扣分项管理，不能支撑完整规则运营后台。
- 第一阶段规则基线应优先复用库里已有的 `四川省 146 条质控规则`，而不是从零重建规则内容。

| --- | --- | --- | --- | --- |

## 6. 推荐启动顺序

### Wave 0：启动准备

- 冻结范围
- 确认数据源
- 确认统计口径
- 确认认证方案
- 确认规则模型
- 确认脚本变更审批边界
- 确认四川 146 条规则的接入方式
- 确认调度技术栈为 `Celery + Redis + PG`

### Wave 1：主链路起盘

- `EPIC-06`
- `EPIC-02`
- `EPIC-03`

理由：

- 先把产品骨架、门急诊主线、详情台、任务链路立住。

### Wave 2：可信数据化

- `EPIC-04`
- `EPIC-01`

理由：

- 工作台、统计分析、认证体系是“能不能上线和能不能被相信”的关键。

### Wave 3：后台可运营化

- `EPIC-05`

理由：

- 规则后台复杂度最高，依赖前面业务链路和统计口径稳定后再做最稳妥。

## 8. 依赖关系

### 8.1 关键依赖链

1. `统一病历聚合口径`
   - 依赖项：
     - 门急诊数据源确认
     - `running/final` 状态边界确认
   - 影响：
     - 工作台
     - 病历列表
     - 统计分析
     - 任务抽样

2. `认证持久化`
   - 依赖项：
     - 账户表设计
     - 用户迁移策略
   - 影响：
     - 登录改造
     - 权限
     - 用户偏好持久化

3. `规则领域模型`
   - 依赖项：
     - 标准、项目组、评分项、质控点边界确认
     - 四川 146 条规则的接入策略确认
   - 影响：
     - 规则后台接口
      - 规则后台页面
      - 统计分析维度

4. `任务调度技术栈`
   - 依赖项：
     - Redis 可用
     - Celery worker/beat 部署方式确认
   - 影响：
     - 定时任务闭环
     - 异步质控任务
     - 批量任务执行稳定性

### 8.2 不建议并行乱开的内容

- 不要在规则模型未冻结前，同时开多人写规则后台接口。
- 不要在场景口径未冻结前，同时开工作台、统计分析、门急诊列表。
- 不要在认证持久化方案未定前，同时改登录页和权限体系。
- 不要在未经人工确认的情况下改现有项目前后端脚本。

## 9. 组织方式建议

### 9.1 团队拆分

- FE-1：登录、统一入口、导航收口
- FE-2：病历质控列表、详情台、筛选模板、自定义列
- FE-3：工作台、统计分析
- FE-4：规则后台
- BE-1：认证、权限、用户偏好
- BE-2：病历聚合、详情接口、门急诊查询
- BE-3：任务、调度器、分配策略
- BE-4：统计分析、Dashboard 聚合
- BE-5：规则模型、规则配置接口
- QA：回归用例、V3.6 验收清单

### 9.2 Owner 原则

- 一个聚合接口只允许一个后端 owner。
- 一个领域模型只允许一个后端 owner。
- 一个主页面只允许一个前端 owner。

## 10. 里程碑建议

| 里程碑 | 目标 | 判定标准 |
| --- | --- | --- |
| M0 | 开工基线完成 | 范围、口径、认证方案、规则模型已冻结 |
| M1 | 病历质控主链路可跑 | 门急诊/运行/终末可查，可进详情台，可完成审核闭环 |
| M2 | 任务与工作台可信 | 工作台无 fallback，任务分配和定时执行具备骨架 |
| M3 | 统计分析可运营 | 运行/终末/首页三块统计为真实数据 |
| M4 | 规则后台最小闭环 | 标准、项目组、评分项、质控点可管理 |
| M5 | 第一阶段验收 | 通过 V3.6 主链路验收清单 |

## 11. 启动会建议议程

1. 复述项目目标和不做范围。
2. 逐条确认登录口径。
3. 逐条确认 `all / outpatient_emergency / running / final` 场景口径。
4. 确认门急诊、运行、终末的数据来源。
5. 确认认证持久化方案。
6. 确认规则模型最小实体。
7. 确认四川 146 条规则的接入方式与归属实体。
8. 确认脚本变更审批规则。
9. 拆 owner 和首批 Story。
10. 确认里程碑和验收责任人。

## 14. 一句话启动结论

这个项目现在已经不缺“方向判断”，缺的是 `冻结范围 + 锁定口径 + 明确依赖 + 拆 owner + 先打主链路`。Epic 启动包的作用，就是把这五件事一次性压实，避免项目一开工就重新发散。
