## 4. 全链路复核

### 4.1 数据同步和病例范围

- 病例身份使用 `institute_id + patient_id + visit_id`。
- 在院范围按医院当前自然日识别，不把历史日期范围内曾经在院、当前已经出院的病例继续当作运行病历。
- 出院范围使用权威出院记录/出院时间；“全院”不应被解释为一个名为“全院”的科室。
- 明细抽取完成后统一刷新该病例的全部 Bundle 变体。
- `source_state` 与规则 `data_gap`、任务 `technical_error` 分开，不按文书数量猜资料完整。

### 4.2 病历池、任务和结果

- 病历池服务端分页、科室、医生、日期、住院状态和汇总使用同一筛选范围；缺 `mr_no` 不应排除三坐标完整病例。
- 新质控任务冻结 `record_refs`，不能用 `visit_id[]` 作为授权身份。
- 病历级默认并发为 4；主 FastAPI 进程内模型调用共享并发预算 4。多进程部署时仍是每进程一份预算，不是跨进程全局预算。
- Canonical Envelope 与任务完成写入保持失败关闭；最新结果使用三坐标和当前规则版本选择。
- 在院病历出院后，旧运行质控结果不会直接成为终末结论；系统需要重新执行终末质控。运行/终末结果列表按当前住院状态互斥展示，避免同一病例同时出现在两页。

### 4.3 导出

- 单病历 HTML、批量任务 HTML、当前筛选 Excel 均读取 Canonical 结果，不回退旧 `items_json`、Bundle 或历史 QCResult。
- Excel 使用批量选择器，避免逐病例 N+1 查询，并防止公式注入。
- 批量 HTML 按病例分组；冻结病例范围、Envelope 数量或版本不一致时失败关闭。

## 5. 75 条质控结果真实数据复核

对本地数据库当前规则版本、每个三坐标最新 Canonical Envelope 做只读统计：

- 最新病历 Envelope：45 份；
- 结果条目：941 条；
- 覆盖规则：75 条；
- `compliant` 194、`not_applicable` 535、`data_gap` 113、`non_compliant` 88、`uncertain` 11；
- 关注结果（确定问题、资料待核实、待判断）共 212 条没有可定位证据，分布于 81 个“规则 × 状态”组合。

结论：Renderer、Finalizer、Aggregator 聚焦测试虽然通过，但“客户能否定位并复核”仍有真实 P1。不能仅凭客户文案存在就判定结果可交付。应按发生量和风险逐规则闭环，优先处理真实高频且没有证据的 `non_compliant/data_gap/uncertain`，每次只处理一个规则或低耦合规则族。

## 6. 性能基线

本地同一服务进程只读测量 10 次：

| 接口/服务           |       P50 |       P95 | 说明                  |
| ------------------- | --------: | --------: | --------------------- |
| 病历池首页（15 行） | 1678.8 ms | 1787.4 ms | 当前范围约 464 份病历 |
| 工作台首页聚合      | 1773.6 ms | 2004.2 ms | 已接近 2 秒目标边界   |

结论：功能可用，但没有性能余量。下一步应先通过 SQL 计时和查询计划定位重复扫描，再决定索引、批量投影或短时缓存；不建议无证据增加新的缓存层。
