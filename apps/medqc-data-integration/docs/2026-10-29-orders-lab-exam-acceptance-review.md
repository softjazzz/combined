## 临时抽取器的未闭合问题

以下行号均指 ZIP 内 `extractor-review/ingest_more_raw.py`，不是开发机正式服务。

1. **元数据与数据分两次提交（第 257–268 行）。** raw 和 succeeded 批次先在第 264 行提交，schema 元数据随后才提交。中途退出会留下“批次成功但元数据缺失”的状态。修复必须将 schema 注册与 raw 写入纳入同一个数据事务。
2. **读取先于审计，失败审计未独立持久化（第 184–193 行及异常退出路径）。** 源查询失败时还没有 running 批次；数据写入失败时，批次也随事务回滚，未见独立的 failed 回写。成功的 36 个批次不能证明失败路径安全。
3. **已有行更新遗漏 schema 指针（第 234–248 行）。** 更新 payload/row_hash 时没有同时写 schema_hash/schema_hash_version。新行插入修复不能覆盖已有行变化的路径。历史空哈希是否补修应独立授权，不能顺带改写历史。
4. **尚不适合作为常驻执行器。** 全量 `fetchmany` 后仍将所有行累积到列表；无接口 advisory lock；读取业务后端 `.env` 的数据库身份；备份会设置进程级 `PGPASSWORD`；dry 路径也会连接 PG 并备份。正式服务应使用专用凭据、真正流式处理、受控错误分类和独立的备份步骤。

5 项元数据 helper 测试仅证明哈希函数和部分 SQL 文本，未覆盖上述真实编排事务、更新路径和失败路径。脱敏抽取器只供代码审查，不能作为可直接执行的交付件。

## 正式服务整合顺序

1. 将六接口加入正式注册表，处理单日期和双日期参数；双日期接口按已验证的日期调用合同执行。当前正式执行器仍按单参数接口调用，不能仅复制注册项。
2. 将六接口合同接入正式 CDM 发布器：保留按接口的字段别名、检验多结果粒度及 `cache-exam-v1` 技术文书键。技术键不是临床编号，也不引入 HIS/PACS 医嘱关联。
3. 对齐两套 ingest 存储合同后再提供显式迁移方案。客户验收表使用 `column_names_json`，正式服务使用 `column_names`，且客户有 `source_record_version`；当前正式初始化脚本没有该版本表。不能直接把正式服务指向验收库并假定兼容，也不能默默丢弃历史版本。
4. 复用正式服务已有的 advisory lock、独立批次审计、数据事务和分块写入。schema 注册、raw 与增量 checkpoint 同事务；失败只保留受控错误码。补足 schema 漂移更新、并发抢锁、查询失败、分块失败与元数据写入失败的针对性测试。
5. 正式默认继续拒绝空 schema 哈希。历史一次性放行凭据应限定接口、准确批次集合、数据指纹和字段合同，不把“空哈希可放行”写成全局规则。
6. 使用独立抽取/发布身份，不继承业务后端身份；dry 不连接 PG。将备份与恢复验收作为独立部署步骤，所有外部命令检查退出码。
7. 开发机完成整合与离线测试后，向 DSH 提供固定版本验证包，仅在独立克隆验收库做增量验证。沿用现有 raw，不重抽、不清库、不动正式业务库或现有同步 checkpoint。

当前不需要客户机扩大接口范围或再做一轮字段探查。下一阶段工作是开发机正式服务整合。
