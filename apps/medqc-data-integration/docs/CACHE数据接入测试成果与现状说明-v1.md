版本：v1。状态基准：第二批归档接管已验收，第二批真实源验证包已交付，尚未收到该包的客户机执行结果。

本文用于项目交接、成果确认和后续实施。仅记录连接信息、接口名、字段合同、统计及验收边界，不含密码、患者标识、病历正文或数据库备份。客户结果来自DSH实测回传；开发机进行代码、交付包及结果包复核，未直接连接医院Caché或客户业务库。

## 1. 任务目的与当前结论

建设可独立维护的数据接入链路，减少对原有homo/clinical等中间库同步状态的依赖。原库不稳定是本项目的业务背景；此前PG表统计本身不能独立证明哪一层发生了数据丢失。

已实现的主链路：

```text
东华 Caché 存储过程接口
  → ODBC35 / Python抽取工作程序
  → 独立ingest数据库：完整raw、版本历史、源结构、批次审计
  → 明确字段合同与CDM发布器
  → 独立CDM数据库
  → 项目正式bundle / LX0609来源读取入口
```

**当前不是“仍不知道怎么连接Caché”，而是连接和取数已跑通，已完成主要接口的映射与工程化验证。** 最新状态如下：

| 第一批13接口 | 真实Caché读取、raw/CDM接管、发布幂等、故障恢复及备份恢复验收 | 定时任务正式启用、正式业务数据源切换 |
| 第二批17接口中的13个有数据来源 | 真实源初始快照、完整raw、CDM投影、读取入口核查、元数据适配、独立归档服务接管 | 新服务的真实源显式日期读取/发布验证结果待回传 |

这些`web.xxx`是厂商开放的SQL存储过程接口，不等于可直接任意查询的普通表。已验证的基本调用形式：

```sql
CALL web.mr('2026-10-28');
CALL web.inpat_drug_order('2026-10-26', '2026-10-28');
```

Python使用ODBC参数绑定，例如`{CALL web.mr(?)}`。不同过程的参数个数以登记合同为准；不能因多余参数被驱动/过程忽略，就认定存在重载或“按修改时间”模式。

## 6. 字段映射、去重及正文保存的确定做法

### 6.1 raw先完整保存，CDM再按合同投影

接口返回的完整字段落入raw JSONB；CDM只接收已明确含义、类型和来源的目标字段。仅保留在raw的字段不等于丢失。发布不根据相似字段名猜测临床语义，不将不同接口的正文或结果混成一行。

`inpatno/inpat_no`、`mrno/mr_no`、`documentid/document_id`等差异按接口合同适配，不依赖统一改名。存在多个就诊时，不能用病案号、患者姓名或单一住院号替代完整病例键。

### 6.2 去重按来源的业务粒度

| 数据类别 | 已采用的来源键口径 |
| --- | --- |
| 病例身份 | 机构＋患者＋就诊 |
| 病案首页 | 病例三键 |
| 主要文书 | 病例三键＋源文书号；各接口按其实际列名映射 |
| 药品/非药品医嘱 | 病例三键＋order_id |
| 检验申请 | 病例三键＋test_id |
| 检验项目 | 病例三键＋test_id＋test_item_id |
| 检验结果明细 | 病例三键＋test_id＋print_order_id |
| 检查报告 | 病例三键＋exam_id＋exam_item_id；目标文书号使用明确标识的稳定技术键 |
| 首页手术明细 | raw额外保留document_id＋surgery_id；目标粒度按surgery_id合同核验 |
| 风险评估/申请类 | 按实际application_id等列，不能假定都有document_id |
| 首页输血明细 | raw保留document_id＋bloodtrans_id＋bloodbag_id，发布前核验目标粒度碰撞 |

相同字段名出现在不同表是正常现象，不跨接口删除记录。同键同内容视为unchanged，同键异内容更新current并保留历史版本；不同源键映射到同一目标键时停止，不强行覆盖。

`print_order_id`仅是已验证窗口内可用的结果行标识，不是已证明的医嘱号；短时稳定和三日唯一性不能推断其全部历史或长期语义。

### 6.3 正文与时间证据

- 六类主要文书1,634行的raw→CDM正文哈希一致；另有20例、195份文书的raw/CDM/bundle/目录对照一致。
- 病案首页`cdm.mr.record_content`列**存在**，源169行均为NULL；不是投影丢失，也不是“目标没有正文列”。
- 日常病程源`record_datetime`263/263非空。通过000056正式字段/迁移补齐，第二轮回填0变化，源与目标263/263相等。
- 日常病程另外20例84份文书在bundle和LX0609公开源入口中均正确读取记录时间；记录时间与提交时间独立，没有用提交时间伪造。
- 不同20例队列曾分别含42份和84份日常病程，原因是选样口径不同，不能解释为数据增加或丢失。

### 6.4 签署与元数据不能越义解释

部分文书源接口不提供独立签署字段；日常病程提供的两个签署字段在样本中全空；会诊源/目标均无独立签署列。这些只能表述为“源未提供/源值为空”，不能判定医生未签署。

围手术期reader最小适配补齐风险评估、手术清点和麻醉记录的12项元数据。客户只读回归通过：缺口统计307→295，其余字段、LX0609投影、记录时间及调用量不变。295代表保持原批准投影，不是295个待修缺陷。

风险评估在系统source_registry已有声明，但当前snapshot读取器没有实现该来源读取；不能表述为整个系统未注册。护理和清点未因此扩大到LX0609规则范围。麻醉记录单签署不能替代术前/术后访视或麻醉同意书签署。

## 7. 日期窗口、增量与重取已经验证到什么程度

早期`web.mr`单接口POC完成`2026-09-16..2026-10-28`共43日回补，2,803条唯一记录；随后43窗口replay为0新增、0更新、2,803不变，checkpoint不移动。这些是独立POC库的统计，不能与后续三日接管基线重复相加。

样本明确显示`web.mr(date)`按出院日期返回：早期743/743条的出院日等于查询窗口日。其后2,803行的修改滞后最大39天，因此不能仅重取最近7个出院日就假定能捕获所有迟到修改。

已经形成的策略是：对新日期顺序抽取；首页按已观察的出院日语义考虑60日滚动replay，50日滞后预警、60日触发扩窗。这是风险缓解策略，不是已证明能捕获所有历史修改的保证，也不等于已启用定时任务。

必须保留的边界：

- 其他接口日期参数的含义不能从`web.mr`类推；第二批仍标unverified，只执行显式日期replay。
- 多余实参成功返回不能证明存在修改时间增量；目前没有已验证的修改时间取数能力。
- 两参数接口在指定三日样本中，区间与逐日并集曾逐行一致；不能据此无限外推所有接口、日期和边界。
- 窗口内修改滞后较短，不能证明窗口外没有再次修改；源端删除的识别与自动删除传播也未完成验证。
- 三日接口数据齐全不等于某病例全住院期间文书齐全；在院病例可取数仍缺确认在院的对照清单。

## 8. 已明确不继续纠缠的关联问题

检验申请、项目、结果的关联在指定窗口验证通过；检验结果42,391行全部找到申请父项，同一项目多条结果保留为独立行。

检查报告与住院非药品医嘱的编号关联不可靠。此前已做有限编号、名称/部位/时间候选验证，不能将候选当成临床真值。根据项目决定，**不将检查报告与医嘱的一一关联作为接入前置条件，不再继续编号或名称匹配研究。** HIS/PACS来源可能不同，检查报告先作为独立事实保存和消费。

是否存在对应医嘱与“检查报告本身是否可用于质控”是两个问题；不得因关联缺失就推断检查未执行或报告不可用。

| 凭据边界 | 运行身份与部署身份分开；既有passfile/口令文件保护；不把凭据、正文或真实病例键回传开发机 |

历史失败审计、identity序列空洞是可解释的运行记录，不应为了“全绿”删除。备份工具链与恢复已验证，不代表自动备份、异地容灾、PITR或长期无人值守已经上线。
